# 学习需求与掌握清单

> 本文整理自一次关于「AI 时代还要不要学技术细节」的对话，是「技术全景与架构选型」学习包的需求来源。
> 交互式版本见 [`content/01-goal.html`](content/01-goal.html)，每个模块的「掌握标志」见 [`index.html`](index.html)。

**一句话：** 不追求「会做」每个细节，但要**会问、会判、会验**：会问关键问题，能判断方案是否适合，能用最小成本验证。操作性细节交给 AI 和文档，概念性细节、边界和失败模式不能省。

---

## 表 1：需求说明

| 原话 / 问题 | 理解的需求 | 需要的结果 | 不需要的 |
|---|---|---|---|
| 「不想学技术细节了」 | 不想背 API、配置项、手写实现、逐行改报错 | 知道技术大概怎么用、为什么存在、代价是什么 | 死记语法、函数名、配置项 |
| 「想学不同的语言、产品都用什么架构」 | 建立「语言—框架—分层—架构」的全景地图 | 听到 Vue、React、FastAPI、微服务时知道它在地图哪一层 | 读源码、编译原理、底层实现 |
| 「不同架构有什么优缺点、有什么功能」 | 能比较单体 / 微服务 / 分层，前端 / 后端 / 数据层 | 能按场景做初步选择，不被名词吓住 | 亲手搭建完整的微服务集群 |
| 「Vue、React 都是什么」 | 分清语言、框架、架构不是一回事 | 知道它们是前端 UI 框架 / 库，不是后端架构 | 精通组件生命周期、状态管理源码 |
| 「FastAPI 之类都是什么」 | 知道后端框架的位置和性格 | 知道 FastAPI 是 Python 后端 API 框架，适合快速做接口和 AI 服务化 | 精通异步事件循环的底层 |
| 「AI 时代只懂优缺点和选择行不行」 | 想弄清学习深度的边界 | 掌握「概念级细节 + 选择判断 + 验证能力」 | 成为每项技术的实现专家 |

## 表 2：需要掌握的内容

| 模块 | 必须掌握的概念级内容 | 选择 / 判断时要问的问题 | 掌握标志 | 可以交给 AI / 不必掌握 | 对应页面 |
|---|---|---|---|---|---|

| 编程语言性格 | Python 开发快、AI / 数据强；Java 企业级稳；Go 高并发云原生；JS / TS 前后端通吃；Rust 安全性能极致但难 | 团队熟什么？招人容易吗？性能、开发速度、生态哪个优先？ | 能说出 3 种语言各自适合和不适合的场景 | 高级语法、编译器细节 | [03](content/03-lang.html) |

| 后端与 API 框架 | FastAPI：Python 现代 API 框架，自动文档、异步，适合 AI 服务；Django 全家桶；Flask 轻；Spring Boot 企业级；NestJS / Express 是 Node 生态 | 要不要自带后台？接口多不多？并发高吗？团队语言栈是什么？ | 听到 FastAPI 知道它是后端框架，能说出适合 API / AI 服务化 | 框架配置与源码 | [05](content/05-backend.html) |
| 数据层 | 关系型 PostgreSQL / MySQL：表结构、强一致、复杂查询；NoSQL Redis / MongoDB：缓存、文档、灵活扩展；向量库服务 AI 检索 | 要不要强一致？关系复杂吗？读写量多大？能否接受最终一致？ | 能判断订单 / 金融偏关系型，缓存 / 会话偏 Redis，文档型偏 MongoDB | 数据库调优、索引底层、分库分表实操 | [06](content/06-data.html) |

| 基础设施 / DevOps | Git 管版本；Docker 打包环境；CI/CD 自动测试部署；K8s 编排容器 | 部署频率多高？环境一致重要吗？谁运维？预算多少？ | 知道 Docker 解决「环境不一致」，CI/CD 解决「人工上线易错」 | 手写复杂流水线、K8s 运维 | [08](content/08-devops.html) |
| 安全与权限 | 认证 vs 授权；最小权限；输入验证；密钥管理；HTTPS | 谁能访问什么？密钥放哪？输入可信吗？ | 能问出「权限边界在哪、密钥怎么管」 | 渗透测试、加密算法实现 | [09](content/09-safety.html) |
| 失败模式 | 超时、重试、幂等、降级、备份恢复、日志监控 | 失败会怎样？重试会不会重复扣款？数据能恢复吗？ | 能列出 3 个失败场景和应对方向 | 具体告警规则配置 | [09](content/09-safety.html) |
| 成本与演进 | 开发 + 运维 + 学习 + 迁移成本；单体能否以后拆；数据库能否换 | 总成本谁承担？流量涨 10 倍怎么办？迁移代价大吗？ | 能比较「现在的简单方案」和「未来的演进路径」 | 云账单精细优化 | [10](content/10-decide.html) |
| AI 协作与验证 | AI 能给方案和代码，但不承担线上责任；你要能判断和验证 | AI 方案符合约束吗？怎么最小验证？日志和测试在哪？ | 能用最小原型、接口文档、测试、日志验证 AI 方案 | 让 AI 代写大部分操作代码 | [12](content/12-ai.html) |

## 表 3：必须懂 vs 可以不懂

| 类型 | 例子 | 要到什么程度 |
|---|---|---|
| **必须懂的概念细节** | 数据流、接口契约、强一致 / 最终一致、认证授权、超时重试幂等、单体 / 微服务的代价、缓存脏数据、部署环境 | 能用自己的话解释，能问出关键问题，能判断方案边界 |
| **可以交给 AI 的操作细节** | 某函数怎么写、某配置项叫什么、某报错逐行怎么改、某框架样板代码 | 知道让 AI 生成，再用文档和测试验证 |
| **不必深入的底层细节** | 编译器优化、JVM 调优、K8s 源码、数据库索引 B+ 树实现 | 知道它们存在、会影响什么即可，除非专门做这一行 |

> 边界会移动：选定某个方向后，那一层的「不必深入」会变成「必须懂」。例如做数据库方向，就去学 [SQL 学习包](../SQL/index.html) 的索引与执行计划。

## 表 4：技术选择判断框架（五问）

| 顺序 | 要问的问题 | 目的 |
|---|---|---|
| 1 | 场景约束：团队几人？上线多快？流量多大？一致性要求多高？ | 防止「技术很酷但不适合」 |
| 2 | 团队能力：现有成员熟什么？招人容易吗？文档社区成熟吗？ | 降低学习和维护成本 |
| 3 | 总成本：开发 + 运维 + 学习 + 迁移成本 | 不只看开发快，还要看长期养不养得起 |
| 4 | 失败代价：挂了影响多大？数据错了能恢复吗？ | 决定要不要强一致、备份、降级 |
| 5 | 演进路径：现在的简单方案未来能不能平滑升级？ | 避免早期过度设计，也避免锁死 |

## 终点状态

> 听到任何技术名词，能快速定位它在哪一层、解决什么问题、代价是什么、什么场景不该用；AI 给你方案时，能问出关键问题并用最小成本验证。这样就不需要死抠技术细节，也不会被 AI 或名词带着走。
