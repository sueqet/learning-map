MODULE 07 · 技术全景

架构模式：产品的组织形式

在「简单」与「灵活」之间做权衡。

✓本节学习目标

  • 用「小作坊」和「专业化集团」的比喻，说出单体和微服务的优点与代价。
  • 解释分层架构（接入层 / 业务层 / 数据层）的职责划分，以及它和单体 / 微服务是不同维度。
  • 说出模块化单体为什么是很多团队的务实选择。
  • 知道事件驱动和 Serverless 各自解决什么问题、代价是什么。
  • 能根据团队规模、业务复杂度、运维能力判断「现在该用哪种架构」，并说出小团队别盲目上微服务的理由。
Pre-requisites · 前置知识

学完 05 后端 和 06 数据层，知道后端通过 API 被调用、数据有一致性问题。

Part 1 · 两种极端

01从全能作坊到专业分工

知识点 1单体：一个「全能小作坊」monolith · 一个应用装下所有功能

单体架构把所有功能——用户、商品、订单、支付——打包在一个应用里：一个代码库、一次部署、通常连一个数据库。功能之间互相调用就是普通的函数调用，又快又简单。

优点缺点
起步极快：开发、测试、部署链路都很短功能膨胀后代码盘根错节，牵一发而动全身
调用是函数调用，没有网络延迟和失败一个严重 bug（如内存泄漏）可能拖垮整个站点
事务简单：一个数据库里就能保证一致只能整体扩容：订单忙，也得把整个应用一起复制
排查容易：日志和调用栈都在一个地方团队变大后互相踩脚，发布要排队
★

核心要点：单体不是贬义词。它非常适合初创产品验证想法。不少知名产品长期以单体为主体运行（例如 Stack Overflow 多年来用单体应用和少量服务器支撑巨大流量）。问题往往不在「单体」本身，而在「没有边界的单体」。

知识点 2微服务：一个「专业化集团」microservices · 拆成独立部署的服务

微服务架构把作坊拆成一个个独立的「专业部门」：商品服务、订单服务、支付服务、用户服务……各自开发、各自部署、各自运行，通常还有各自的数据库，彼此通过网络（API 或消息）协作。大型互联网公司（如淘宝、微信）的后台由成千上万个服务组成，并按入口层、业务层、数据层组织，来支撑海量并发。

优点代价需要的配套
故障隔离：支付挂了，浏览和聊天照常运维极其复杂：几十上百个服务要部署、监控、升级容器 + Kubernetes、CI/CD
独立扩展：大促只给商品和订单服务加机器网络调用：延迟、超时、重试、部分失败API 网关、服务发现、熔断限流
独立发布：各团队按自己的节奏上线数据一致性：跨服务没有一个数据库事务可用最终一致、补偿流程（Saga）
技术自由：不同服务可以用不同语言排查困难：一个请求穿过十几个服务集中日志、链路追踪、监控告警
!

最坏的结果：「分布式单体」。拆成了很多服务，但它们之间强耦合，改一个功能要几个服务一起发布——同时承担了单体的僵硬和微服务的复杂。拆分之前先问：边界清楚吗？能独立发布吗？

Part 2 · 内部分工与中间路线

02分层、模块化与其他形态

知识点 3分层架构：接入层 / 业务层 / 数据层layered · 内部分工

无论单体还是微服务，内部通常都按分层组织：接入层接待请求（路由、参数校验、鉴权），业务逻辑层执行规则，数据访问层负责存取。每层只和相邻的层打交道。

一个分层的后端项目目录（看懂即可）
app/
├── api/            ← 接入层：定义接口、校验参数、检查登录（FastAPI 的路由）
│   └── orders.py
├── services/       ← 业务逻辑层：下单规则、库存扣减、价格计算
│   └── order_service.py
└── repositories/   ← 数据访问层：只负责读写数据库
    └── order_repo.py
优点缺点
职责清晰，便于团队分工和单独测试请求要层层穿透，有一些性能开销
换数据库只需改数据访问层简单功能也要写好几层，可能有样板代码
业务规则集中在一处，不会散落各地分得过细会变成过度设计
★

核心要点：「单体 / 微服务」说的是拆成几个部署单元；「分层」说的是每个单元内部怎么分工。两者是不同维度，可以自由组合：分层的单体、分层的微服务都很常见。

知识点 4模块化单体：两者之间的中间路线modular monolith · 部署简单、边界清晰

模块化单体仍然只部署一个应用，但内部按业务领域划分出边界清晰的模块（订单模块、支付模块……），模块之间只通过明确的接口调用，不直接读对方的数据表。它保留了单体部署简单的优点，又拥有接近微服务的清晰边界；将来真要拆，就沿着模块边界拆。Shopify 就公开分享过把超大型单体改造为模块化单体的经验。

杂乱的单体模块化单体微服务
部署单元1 个1 个很多个
模块边界模糊，互相直接调用、直接读表清晰，只走模块接口清晰，靠网络强制隔离
模块间调用函数调用函数调用网络调用
运维复杂度低低高
适合团队规模很小几人到几十人几十人以上、多个独立团队
★

核心要点：对大多数中小团队，模块化单体是性价比最高的默认选项：今天简单，明天可拆。

知识点 5事件驱动与 Serverlessevent-driven · serverless · 另外两种常见形态

事件驱动：服务之间不直接互相调用，而是发布一条事件（「订单已支付」），发货、积分、短信等服务各自订阅并处理，中间通过消息队列（Kafka、RabbitMQ、RocketMQ）传递。Serverless：你只写函数，云平台在有请求时自动运行它、按调用次数计费，不用管服务器（AWS Lambda、阿里云函数计算、Cloudflare Workers）。

事件驱动Serverless
优点发布方不用知道谁在订阅，新增功能只需加一个订阅者；能削峰填谷免运维服务器、按量付费、自动扩缩容，低流量时几乎零成本
代价流程不直观、只能最终一致、要处理消息重复 / 丢失 / 乱序、排查更难冷启动延迟、单次执行时长有限制、厂商锁定、持续大流量时可能更贵、本地调试难
适合一件事触发多个后续动作、上下游处理速度不一致流量波动大或很低的接口、定时任务、事件处理、小工具
!

没有银弹：Amazon Prime Video 团队在 2023 年公开过一个案例：把一个音视频质量监控系统从分布式的 Serverless 组件合并成单个进程后，基础设施成本降低了约 90%。架构好不好，取决于它是否匹配这个具体的负载。

知识点 6架构演进：先单体，按需再拆evolution · 架构服务于当前阶段

架构没有绝对的好坏，只有是否适合当前阶段。常见的健康路径是：单体 → 模块化单体 → 把确实需要独立的模块拆成服务。拆的时候常用「绞杀者模式」：新功能放进新服务，旧功能逐步迁移，旧系统慢慢「被绞杀」，而不是一次性推倒重来。

阶段团队建议架构重点
验证想法1–5 人单体（内部分层）快速上线、快速改
产品成型5–30 人模块化单体划清模块边界，补测试、CI/CD、监控
规模扩张30 人以上、多个团队按业务边界逐步拆出服务先补齐运维配套，再拆；一次只拆一个
值得拆的信号不该拆的信号
多个团队频繁互相阻塞、发布要排队团队不到十个人
某个模块的扩容需求和其他模块差异巨大业务还在摸索，边界天天变
某个模块需要更高的可用性或独立的发布节奏还没有自动化部署、集中日志和监控
★

一句话总结：验证想法、小团队 → 从单体起步；业务复杂、大团队 → 用微服务解耦，用分层理清内部。拆分是为了解决真实存在的问题，而不是为了「看起来先进」。
