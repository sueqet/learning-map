MODULE 10 · 技术全景

选型判断：五问框架与成本演进

不要只问「它有什么优缺点」。

✓本节学习目标

  • 按顺序说出五问框架：场景约束、团队能力、总成本、失败代价、演进路径。
  • 把「总成本」拆成开发、运维、学习、迁移四部分，不只看「开发快不快」。
  • 区分可逆与不可逆的技术决策，知道哪些要快定、哪些要慎重。
  • 用五问框架给个人博客、电商订单系统、AI 问答服务各写出选型和理由。
Pre-requisites · 前置知识

学完 02–09 模块。本节把前面每一层的「性格」和「代价」组合起来，练习真正做决定。

Part 1 · 判断的工具

01五问、成本与演进

知识点 1五问框架：约束、团队、成本、失败代价、演进five questions · 选择不是查表

面对一个技术选择，不要只问「它有什么优缺点」，而是按顺序问五个问题。前面的问题会大幅缩小后面的选择范围。

顺序要问的问题目的
1场景约束：团队几个人？多快要上线？流量多大？一致性要求多高？有没有合规要求？防止「技术很酷但不适合」
2团队能力：成员现在熟悉什么？招人容易吗？文档和社区成熟吗？降低学习和维护成本
3总成本：开发 + 运维 + 学习 + 迁移，以及云资源费用不只看开发快，还要看长期养不养得起
4失败代价：挂了影响多大？数据错了能不能恢复？决定要不要强一致、备份、降级、多活
5演进路径：现在的简单方案，将来能不能平滑升级？既避免早期过度设计，也避免把自己锁死
★

核心要点：优缺点表告诉你「选项是什么」，五问告诉你「哪个适合我」。同一个技术，在不同答案下可能从最佳选择变成最差选择。

知识点 2总成本：开发 + 运维 + 学习 + 迁移total cost · 养不养得起

很多选型失败，是因为只算了「开发多快」，没算「之后每个月要花多少人和钱维持它」。一个技术的真实成本由四部分组成：

成本包含什么常被忽略的点
开发成本写功能、联调、测试分布式系统里，接口联调和一致性处理会让同样的功能多花不少时间
运维成本部署、监控、升级、值班、排障、云资源费用每月都在发生，持续整个产品生命周期
学习成本团队掌握新技术的时间、踩坑的时间新技术早期产出慢、事故多
迁移成本以后要换掉它时的代价数据迁移和契约变更最贵；越晚换越贵
!

注意：上面的计算器是示意模型，系数是为了展示「成本结构」而设定的假设，不是行业数据。真实项目里，你可以用同样的思路，把每一项换成自己团队的估算。

知识点 3演进路径：不过度设计，也不锁死evolution · 单向门与双向门

有两种相反的错误：过度设计（为了想象中的百万用户，第一天就上微服务）和锁死（选了一条以后很难回头的路）。一个实用的区分方法来自亚马逊：把决策分成「双向门」（走错了可以退回来，快速决定）和「单向门」（走过去就很难回头，慎重决定）。

决策可逆吗怎么对待
UI 组件库、某个工具库、CI 工具双向门：换掉代价小快速决定，不合适就换
前端框架中等：可以逐页迁移看团队熟悉度，别频繁换
核心数据模型、主数据库单向门：数据迁移最贵慎重，做原型验证
对外公开的 API 契约单向门：别人已经在用加版本号，设计时多想一步
深度绑定某云厂商的专有服务偏单向门评估收益是否值得被锁定

保持可演进的几个习惯：内部分层并定义清晰的接口；尽量使用标准协议（SQL、HTTP、OpenAPI、Docker 镜像）；把重要决定写成简短的架构决策记录（ADR）：背景、选项、选择、理由，以后回头看时知道当初为什么这么选。

★

核心要点：早期选简单但可演进的方案。双向门快速推进，单向门放慢脚步、做最小验证。

Part 2 · 三个虚拟产品

02用五问做一次完整选型

知识点 4案例一：个人博客 / 文档站case · 最好的后端可能是没有后端

五问：① 1 个人，周末开发，流量小，内容一周更新几次，需要被搜索引擎收录；② 会一点前端；③ 预算接近零，不想运维服务器；④ 挂了几小时损失很小，文章都在 Git 里；⑤ 以后可能加评论、搜索。

层选择理由
前端 / 渲染SSG：Astro、VitePress、Hugo 或 Next.js 静态导出内容不常变 + 要 SEO + 要快 → 静态生成
后端不需要没有需要保密的业务规则
数据Markdown 文件 + GitGit 就是版本记录和备份
部署GitHub Pages、Vercel、Cloudflare Pages 等静态托管 + CDN推送即发布，免费额度通常够用
演进评论用第三方服务；搜索用静态索引或托管搜索需要时再加，不提前建后端
★

结论：这个场景的最优解是「没有后端、没有数据库」。会判断「不需要什么」，和会选技术一样重要。

知识点 5案例二：电商订单系统case · 一致性与失败模式是重点

五问：① 10–20 人团队，有大促峰值，订单和支付绝不能错；② 团队熟 Java 或 Go；③ 能负担托管云服务，有 1–2 人懂运维；④ 超卖、重复扣款会造成真实损失和投诉；⑤ 预计两年内业务和团队翻倍。

层选择理由
前端商品页 SSR（Nuxt / Next.js），后台管理 SPA + 组件库商品页要 SEO 和实时价格；后台要开发快
后端Spring Boot 或 Go；模块化单体起步，订单、库存、支付边界清晰团队熟悉；边界清晰便于大促前把最热的模块拆出去
数据MySQL / PostgreSQL（事务）+ Redis（商品详情缓存、限流）+ 消息队列（支付成功后的发货、积分、通知）钱和库存强一致；热点读走缓存；后续动作异步解耦
关键设计库存扣减防超卖、支付幂等键、对账、限流与降级、定期备份和恢复演练这些是失败代价最高的地方（09 模块）
基础设施Docker + CI/CD + 托管容器服务；监控告警覆盖下单和支付链路频繁发布要安全；大促要能扩容
!

易错：为了扛大促，一开始就拆成几十个微服务。真正的风险点在一致性和失败模式，而不是服务数量。先把幂等、事务、限流、降级、备份做扎实。

知识点 6案例三：AI 问答服务case · 公司知识库客服

五问：① 3–5 人，两个月上线，内部几百人使用；回答要有出处；② 团队熟 Python；③ 大模型按 token 计费，要控制成本；④ 答错可能误导员工，部分文档涉及敏感信息；⑤ 以后可能对外开放给客户。

层选择理由
前端Vue / React 聊天界面，流式显示回答（SSE）内部工具不需要 SEO；流式输出体验更好
后端Python + FastAPI（异步）团队熟悉；AI 生态在 Python；大部分时间在等模型返回，异步划算
模型先调用大模型 API；敏感数据多或合规要求高时，评估私有化部署开源模型API 起步最快；私有化换来数据不出域，代价是 GPU 和运维
数据PostgreSQL + pgvector 存文档片段和向量；Redis 做会话和限流数据量不大，一个库搞定，少一份运维
关键设计回答附上引用来源；准备一套测试问题集做评估；按用户限流、缓存常见问题；接口超时与重试防幻觉、控成本、可验证
★

核心要点：AI 应用的特殊风险在于幻觉、成本、隐私和评估。选型时除了技术栈，还要问：答案怎么验证？一次问答花多少钱？哪些数据不能发给外部模型？
