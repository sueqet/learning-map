MODULE 01 · 技术全景

学习目标：会问、会判、会验

先把「要学什么、不学什么」说清楚。

✓本节学习目标

  • 用一句话说清自己的学习目标：建一张技术全景地图，并具备选择、判断、验证的能力。
  • 区分操作性细节和概念性细节，知道哪些可以交给 AI，哪些必须自己懂。
  • 说出「只背优缺点表」不够用的 4 个原因，各举一个例子。
  • 解释「会问、会判、会验」分别指什么，并各举一个例子。
  • 拿到任意一条知识，能把它归入「必须懂 / 交给 AI / 不必深入」三类之一。
Pre-requisites · 前置知识

无。用过电脑、网页和手机 App 就够了。听说过 Vue、React、FastAPI、微服务这些名词但分不清，正是本学习包要解决的问题。

Part 1 · 从一段对话到学习目标

01我到底要学什么

知识点 1我的需求：建一张技术全景地图need · 需求说明

这个学习包来自一次对话。起点是一句「不想学技术细节了」，接着问了不同语言和产品用什么架构、Vue 和 React 是什么、FastAPI 是什么，最后问到「AI 时代只懂优缺点和选择，行不行？」。把这些问题合起来，需求可以整理成下表。

原话 / 问题理解的需求需要的结果不需要的
「不想学技术细节了」不想背 API、配置项、手写实现、逐行改报错知道技术大概怎么用、为什么存在、代价是什么死记语法、函数名、配置项
「想学不同语言、产品都用什么架构」建立「语言—框架—分层—架构」的全景地图听到 Vue、React、FastAPI、微服务时，知道它在地图的哪一层读源码、学编译原理和底层实现
「不同架构有什么优缺点、有什么功能」能比较单体、微服务、分层，以及前端、后端、数据层能按场景做初步选择，不被名词吓住亲手搭一套完整的微服务集群
「Vue、React 都是什么」分清语言、框架、架构不是一回事知道它们是前端 UI 框架 / 库，不是后端架构精通组件生命周期、状态管理源码
「FastAPI 之类都是什么」知道后端框架的位置和性格知道 FastAPI 是 Python 的后端 API 框架，适合快速做接口和 AI 服务化精通异步事件循环的底层实现
「AI 时代只懂优缺点和选择行不行」想弄清学习深度的边界掌握「概念级细节 + 选择判断 + 验证能力」成为每项技术的实现专家
★

一句话目标：不追求「会做」每个细节，但要会问、会判、会验：会问关键问题，能判断方案适不适合，能用最小成本验证。

知识点 2操作性细节 vs 概念性细节two kinds of details · 学习深度的分界线

「细节」其实有两种。操作性细节是「怎么写、怎么配」，AI 和文档几秒钟就能补上；概念性细节是「为什么这样、边界在哪、出错会怎样」，没有它就判断不了 AI 说得对不对。AI 时代要放下的是前一种，后一种反而更重要。

知识类型例子AI 时代要不要
操作性细节某个函数怎么写、某个配置项叫什么、某行报错怎么改不必死记 AI 和文档能补
概念性细节为什么需要异步？强一致和最终一致差在哪？接口契约是什么？微服务为什么会让运维变复杂？必须有 否则无法判断 AI 说得对不对

可以把它叫作细节感：懂关键概念、边界、失败模式和验证方法，但不背操作步骤。打个比方，你不需要知道每颗螺丝怎么拧，但要知道承重墙在哪、哪里会漏水、出了问题该找哪一层。

!

注意：「不学操作细节」不等于「完全不碰代码」。能读懂一小段示例、能看出一条报错属于哪一层、能把最小示例跑起来，是「会验」的基础。本学习包里的代码都只要求「看得懂它在干什么」。

知识点 3为什么「只背优缺点表」不够labels vs judgment · 四个理由

优缺点表是一种标签，比如「FastAPI 快」「微服务好扩展」。标签能帮你入门，但真正做选择、看方案、排故障时，标签不够用，原因有四个：

  1. 选择是权衡，不是查表。要看团队熟不熟、要不要自带后台、数据关系复杂不复杂、并发多高、运维成本多少。
  2. AI 会自信地给出错误方案。AI 能生成代码，但不为线上故障负责。你要能追问：数据一致性怎么保证？重试会不会重复扣款？日志在哪？
  3. 架构的代价藏在细节里。微服务的好处是隔离和独立扩展，代价是网络调用、分布式事务、链路追踪、部署复杂度。不知道代价，小团队就会盲目上微服务。
  4. 排障需要理解数据流。出问题时要能判断：问题在前端状态、接口契约、后端逻辑、数据库查询，还是部署环境？
标签式认知有细节感的认知
FastAPI 很快「快」主要指开发快和异步 I/O 并发好；遇到 CPU 密集的计算照样慢，要放进后台任务或单独的服务。
微服务好扩展能只给热点服务加机器，代价是服务间网络调用、数据一致性、监控排障都变难，需要专人运维。
Redis 很快数据放在内存里所以快；但要考虑缓存和数据库不一致、内存成本、宕机后数据还在不在。
NoSQL 很灵活不强制表结构，所以改字段方便；代价是数据质量要靠应用自己保证，复杂关联查询不如 SQL。
!

易错：把「某技术很流行」当成「它适合我」。流行说明生态好、好招人，但不说明它符合你当前阶段的约束。

Part 2 · 学到什么程度

02能力目标与学习边界

知识点 4目标能力：会问、会判、会验ask · judge · verify

把学习目标从「会做」改成「会问、会判、会验」。三者是递进的：先会提问题，才能判断；判断之后，用证据去验证。

🗣 会问

这个方案的边界、代价、失败模式是什么？权限边界在哪？密钥放哪？挂了会怎样？

⚖ 会判

方案是否符合当前约束：团队几个人、上线多快、流量多大、一致性要求多高、预算多少？

🔬 会验

用最小原型、接口文档、测试、日志、压测验证，而不是凭感觉或凭 AI 的语气。
能力你在做什么例子对应模块
会问找出方案没说清的地方「支付失败自动重试，会不会扣两次钱？」09 安全与失败模式、12 AI 协作
会判拿方案对照约束「3 个人的团队，上来就 20 个微服务 + K8s，不合适」07 架构模式、10 选型判断
会验用最小成本拿到证据「用压测工具打 1000 并发，看错误率和响应时间」11 最小闭环、12 AI 协作
★

核心要点：AI 时代可以少学操作细节，但不能少学系统常识和判断力。

知识点 5必须懂 / 交给 AI / 不必深入learning boundary · 三类知识

遇到一条新知识，先给它分个类，再决定花多少时间。分类标准只有一个：它会不会影响你的判断？会影响判断的必须懂；只影响「怎么写出来」的交给 AI；离你的工作太远的，知道它存在就行。

类型例子要到什么程度
必须懂 概念细节数据流、接口契约、强一致 / 最终一致、认证与授权、超时 / 重试 / 幂等、单体与微服务的代价、缓存变脏、部署环境能用自己的话解释，能问出关键问题，能判断方案边界
交给 AI 操作细节某函数怎么写、某配置项叫什么、某报错逐行怎么改、某框架的样板代码知道让 AI 生成，再用文档和测试验证
不必深入 底层实现编译器优化、JVM 调优、K8s 源码、数据库索引 B+ 树的实现知道它存在、会影响什么即可，除非你专门做这一行
!

边界会移动：如果以后你选择做数据库方向，B+ 树就从「不必深入」变成「必须懂」（本仓库的 SQL 学习包第 09 模块专门讲）。分类是相对于你当前的目标的。
