Part 1 · 从代码到可运行的包

01版本控制与容器

知识点 1Git / GitHub：版本控制与协作Git · 谁在什么时候改了什么

Git 是版本控制工具：记录每一次改动（谁、什么时候、改了什么、为什么），可以随时回到任何历史版本，多个人可以在各自的分支上并行开发再合并。GitHub / GitLab / Gitee 是托管 Git 仓库的平台，在 Git 之上提供代码评审（Pull Request）、问题跟踪、自动化流水线等协作功能。

概念白话解决什么
提交 commit给当前代码拍一张带说明的快照出问题能精确找到「哪次改动引入的」
分支 branch平行宇宙，互不干扰多人同时开发不同功能
合并 / Pull Request把分支的改动合回主线，合之前让别人审一遍代码质量和知识共享
回滚 revert撤销某次改动线上出问题时快速恢复
!

高频事故：把数据库密码、API 密钥提交进 Git。即使后来删掉，它仍然留在历史记录里。密钥要放在环境变量或密钥管理服务中（09 模块细讲）。

知识点 2Docker：把应用装进标准集装箱Docker · 解决「在我电脑上能跑」

最经典的事故台词是：「在我电脑上明明能跑！」原因是开发电脑和服务器的环境不一样：Python 版本、依赖库版本、系统库、配置都可能不同。Docker 把应用连同它需要的运行环境一起打包成一个标准的「集装箱」，在任何装了 Docker 的机器上运行结果都一样。

Dockerfile：打包一个 FastAPI 应用的说明书（看懂即可）
# 从一个装好 Python 3.12 的基础环境开始
FROM python:3.12-slim
WORKDIR /app
# 先装好固定版本的依赖
COPY requirements.txt .
RUN pip install -r requirements.txt
# 再拷入代码，并指定容器启动时运行的命令
COPY . .
CMD ["fastapi", "run", "main.py", "--port", "8000"]
概念白话
镜像 image打包好的模板：代码 + 运行环境 + 依赖。像菜谱加上备好的食材
容器 container镜像运行起来的实例。同一个镜像可以同时跑很多个容器
Dockerfile告诉 Docker 怎么构建镜像的说明书
镜像仓库存放和分发镜像的地方，如 Docker Hub、云厂商的镜像仓库
Docker Compose一个文件描述多个容器（应用 + 数据库 + 缓存），一条命令全部启动
容器虚拟机
包含什么应用和依赖，共享宿主机的操作系统内核完整的操作系统
启动秒级甚至更快分钟级
体积与开销小，一台机器能跑很多大
隔离程度进程级隔离，够用但弱于虚拟机更强
★

核心要点：Docker 解决的是环境一致性和交付标准化：开发、测试、生产跑的是同一个镜像。它是后面 CI/CD 和 Kubernetes 的基础。

Part 2 · 自动上线与规模化运行

02流水线、编排与部署

知识点 3CI/CD：自动化流水线CI/CD · 解决「人工上线易错」

人工上线的典型事故：忘了跑测试、漏传了一个文件、在错误的服务器上执行了命令、只有某个同事知道怎么部署。CI（持续集成）让每次提交代码都自动跑检查和测试，尽早发现问题；CD（持续交付 / 持续部署）让测试通过的代码自动打包，并发布到测试或生产环境。整个过程叫流水线，常用工具有 GitHub Actions、GitLab CI、Jenkins。

.github/workflows/ci.yml：一条最小的 CI 流水线（看懂即可）
on: [push, pull_request]          # 每次推代码或提 PR 时触发
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest                 # 测试不通过，流水线变红，后面的部署不会执行
阶段做什么失败时
代码检查格式、静态分析、依赖漏洞扫描标红，提醒提交者修
自动测试单元测试、接口测试阻止后续步骤，不会带着 bug 上线
构建打包 Docker 镜像，推到镜像仓库停止
部署到测试环境自动发布，跑冒烟测试停止，生产不受影响
部署到生产滚动发布或灰度发布，必要时人工确认自动或一键回滚到上一个版本
★

核心要点：CI/CD 把上线从「靠人记住步骤」变成「靠机器执行规则」。它让小步快跑、频繁发布变得安全，出问题也能快速回滚。

知识点 4Kubernetes：成百上千个容器的调度员K8s · 容器编排

只有几个容器时，手动启动就行。当你有成百上千个容器分布在几十台机器上时，谁来决定每个容器放在哪台机器？挂了谁来重启？流量大了谁来加实例？Kubernetes（K8s）就是干这个的「容器操作系统」。你只需声明「我要 3 个订单服务的副本」，它会持续把实际状态维持成你声明的样子。

能力白话
调度自动把容器放到资源够用的机器上
自愈容器挂了自动重启，机器挂了把容器挪到别的机器
自动扩缩容CPU 或请求量高了自动加副本，闲了自动减
滚动更新与回滚新版本一个个替换旧版本，不停机；有问题一键回到旧版本
服务发现与负载均衡服务之间按名字互相找到，流量自动分摊到各副本
!

别急着上：K8s 很强大，但学习和运维成本也很高。一个小团队、几个服务的项目，用 PaaS 平台或「云服务器 + Docker Compose」往往就够了；确实需要时，优先用云厂商的托管 K8s，别自己从零搭集群。

知识点 5部署去哪：云服务器、PaaS、Serverlessdeployment · 你要管多少东西

部署方式的本质区别是：你自己要管多少东西。管得越多越灵活，但运维成本越高。

方式你要管什么例子适合代价
云服务器（虚拟机）操作系统、安全补丁、运行环境、部署、监控阿里云 ECS、AWS EC2需要完全控制、长期稳定负载运维工作量最大
PaaS / 应用托管平台只管代码或镜像Vercel、Render、Fly.io、各云的应用托管服务小团队、初创、前端站点灵活度有限，规模大后可能更贵
托管 K8s / 容器服务容器和编排配置阿里云 ACK、AWS EKS、Google GKE服务多、需要弹性的中大型系统需要懂 K8s
Serverless 函数只管函数代码AWS Lambda、阿里云函数计算流量波动大的接口、定时任务冷启动、时长限制、厂商锁定
托管数据库只管表结构和数据阿里云 RDS、AWS RDS几乎所有生产环境比自建贵一些，但省去备份、主从、升级
★

核心要点：运维时间也是成本。小团队应该把精力花在产品上，尽量用托管服务；前端静态资源放 CDN，数据库优先用托管版。

知识点 6日志、指标、链路：系统的仪表盘observability · 比用户先发现问题

系统上线后，你需要知道它「现在好不好」「哪里不好」。这叫可观测性，有三根支柱，外加告警：

支柱回答什么问题例子常见工具
指标 metrics整体好不好？什么时候开始变坏？每秒请求数、错误率、P99 延迟、CPUPrometheus + Grafana
日志 logs具体发生了什么？报了什么错？「订单 1001 支付回调失败：签名错误」ELK、Loki、云日志服务
链路追踪 traces一个请求经过了哪些服务？慢在哪一段？下单请求 800ms，其中库存服务占 650msOpenTelemetry、Jaeger
告警出问题时谁来处理？错误率 > 5% 持续 3 分钟 → 通知值班Alertmanager、云监控
★

核心要点：先看指标确定「什么时候、哪里」变坏，再看日志确认「发生了什么」，跨服务时用链路找「慢在哪段」。最值得监控的四个黄金信号：延迟、流量、错误、饱和度。没有监控，就只能等用户来告诉你系统挂了。
