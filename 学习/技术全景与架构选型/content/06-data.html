数据层：数据放在哪

数据的「仓库」。

  • 区分键值、文档、宽列、图等 NoSQL 类型，各举一个代表产品。
  • 解释缓存为什么快、为什么会「脏」，以及「先更新数据库，再删除缓存」的做法。

Pre-requisites · 前置知识

Part 1 · 两大阵营

01档案柜与收纳箱

知识点 1关系型数据库：结构严格的档案柜RDBMS / SQL · 强一致的主力

关系型数据库把数据存在一张张二维表里，必须提前定义好表结构（schema）：有哪些列、每列什么类型。表和表之间用主键、外键关联，用 SQL 查询。它最大的强项是事务：一组操作要么全部成功，要么全部失败。

转账：事务的经典例子（看懂即可）
BEGIN;                                                -- 开始事务
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- A 扣 100
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- B 加 100
COMMIT;                                               -- 两步都成功才提交
-- 如果第二步失败（比如断电），整个事务回滚：A 的钱不会凭空消失
ACID白话转账里的意思
原子性 Atomicity要么全做，要么全不做不会出现「A 扣了钱、B 没收到」
一致性 Consistency数据始终满足规则总金额不变，余额不能为负
隔离性 Isolation并发的事务互不干扰两笔转账同时发生也不会算错
持久性 Durability提交了就不会丢提交后立刻断电，重启后数据还在
代表一句话
PostgreSQL功能最全面的开源关系型数据库，扩展丰富（JSONB、全文检索、pgvector）
MySQL国内互联网使用最广之一，生态和运维经验极丰富
SQLite嵌入在程序里的单文件数据库，手机 App、小工具常用
TiDB、OceanBase 等分布式关系型数据库：兼容 SQL，又能水平扩展到很多台机器
★

核心要点：强项是强一致和复杂关联查询，适合订单、支付、库存、账户这类不容出错的核心业务。代价是表结构改动要走迁移流程，单机写入能力有上限。

知识点 2NoSQL：键值、文档、宽列、图NoSQL · 灵活的收纳箱

NoSQL（Not only SQL）是一大类「不用二维表」的数据库，像灵活的收纳箱：不要求固定表结构，强项是灵活性和水平扩展（加机器就能扛更多数据）。它们各自为特定的数据形状优化：

类型怎么存代表适合
键值一个 key 对应一个值，像超大的字典Redis缓存、登录会话、验证码、计数器、排行榜
文档一条记录是一个 JSON 风格的文档，字段可以各不相同MongoDB结构多变的内容、商品属性、快速迭代的产品
宽列按列族存储，为海量写入设计Cassandra、HBase海量日志、消息记录、物联网数据
图节点 + 关系Neo4j社交关系、推荐、风控关系网络
搜索引擎倒排索引Elasticsearch / OpenSearch全文搜索、日志检索
!

易混：「NoSQL 不需要 schema」不准确——schema 只是从数据库挪到了应用代码里，数据质量要靠你自己保证。另外，PostgreSQL 的 JSONB 也能存灵活字段，很多「需要灵活」的场景用一个 PostgreSQL 就够了。

Part 2 · 快与对的权衡

02缓存与一致性

知识点 3缓存与 Redis：快，但可能「脏」cache · 用一致性换速度

数据库在磁盘上，查一次几毫秒到几十毫秒；Redis 在内存里，通常不到一毫秒。所以常把读得多、改得少的数据（商品详情、首页配置）复制一份放进缓存。代价是：现在数据有了两份，两份可能不一致，用户就会读到旧数据，这叫缓存「脏」了。

操作最常见的做法（Cache-Aside 旁路缓存）
读先查缓存；命中就直接返回；没命中再查数据库，并把结果写进缓存（设置过期时间 TTL）
写先更新数据库，再删除缓存；下次读的时候自然会从数据库加载新值
兜底给每个缓存设置 TTL：就算忘了删，最多脏 TTL 那么久
常见缓存问题是什么应对方向
缓存穿透一直查一个不存在的数据，缓存永远不命中，压力全打到数据库缓存空结果、参数校验、布隆过滤器
缓存击穿一个超热的 key 刚好过期，瞬间大量请求涌向数据库热点 key 不过期或加互斥锁重建
缓存雪崩大量 key 同时过期或 Redis 整个挂了过期时间加随机值、Redis 高可用、降级
!

易错：加缓存前先问：这份数据读到几秒的旧值，会造成什么损失？商品描述旧几秒无所谓；库存和余额就不能只看缓存做决定。

知识点 4强一致 vs 最终一致consistency · 读到旧数据能不能接受

强一致：写入成功后，任何人立刻读到的都是新值。最终一致：写入后短时间内，有人可能还读到旧值，但过一会儿所有人都会看到新值。数据一旦分布在多台机器（主从复制、缓存、多个微服务），强一致就要付出性能和可用性的代价，所以要按业务区分对待。

业务需要为什么
账户余额、支付、扣库存强一致读到旧值会导致超卖、多扣钱，损失真金白银
订单状态强一致（核心链路）用户付完款必须看到「已支付」，否则会重复支付
点赞数、浏览量、粉丝数最终一致差几个、晚几秒，没人在意
搜索结果、推荐列表最终一致新商品晚一分钟能被搜到，可以接受
主从复制的从库读看情况刚写完立刻读从库可能读不到，「写后立即读」的场景应读主库
★

核心要点：判断一致性需求只问一句：读到旧数据几秒钟，会造成什么损失？损失是钱和信任 → 强一致；损失几乎为零 → 最终一致，换来更快、更便宜、更好扩展。分布式理论里的 CAP 说的也是这个取舍：网络出问题时，一致性和可用性只能优先保一个。

Part 3 · AI 与选择

03向量数据库与选型

知识点 5向量数据库与 AI 检索vector DB · 按「意思」找

传统搜索按关键词匹配：搜「退款」找不到写着「钱怎么退回来」的文档。AI 模型可以把一段文字变成一串数字（向量 / embedding），意思相近的文字，向量也相近。向量数据库专门存这些向量，并快速找出「意思最接近」的内容。

它是 RAG（检索增强生成）的核心：用户提问 → 把问题变成向量 → 在知识库里找最相关的几段 → 连同问题一起交给大模型 → 大模型基于这些资料回答，减少胡编。

关键词搜索语义（向量）搜索
匹配方式字面相同意思相近
「退款」能否找到「钱怎么退回来」不能能
精确查型号、订单号擅长不擅长
代表Elasticsearch、数据库全文检索Milvus、Qdrant、Weaviate、Pinecone；PostgreSQL 的 pgvector 扩展
★

核心要点：实际系统常把两者结合（混合检索）。数据量在百万条以内时，PostgreSQL + pgvector 往往就够了：少一个组件，就少一份运维和数据同步的麻烦。

知识点 6数据层怎么选choosing · 从一个库起步

选数据层时，按顺序问五个问题：

  1. 数据错了或丢了，损失多大？涉及钱 → 关系型 + 事务 + 备份。
  2. 结构经常变吗？每条记录字段都不一样 → 文档型或 JSONB。
  3. 读写量和延迟要求多高？热点数据反复读 → 加缓存。
  4. 怎么查？复杂关联 → SQL；按 key 取 → 键值；全文搜索 → 搜索引擎；按意思找 → 向量库。
  5. 团队能运维几个组件？每多一个数据库，就多一份备份、监控、同步和故障点。
场景常见选择
订单、支付、账户、库存PostgreSQL / MySQL + 事务
商品详情、首页这类热点读数据库 + Redis 缓存
登录会话、验证码、限流计数Redis
字段多变的内容、配置MongoDB，或 PostgreSQL JSONB
站内搜索起步用数据库全文检索，规模大了上 Elasticsearch
AI 知识库问答起步用 pgvector，规模大了上专门的向量数据库
★

核心要点：大多数项目的合理起点是一个 PostgreSQL（或 MySQL），遇到明确的瓶颈再加 Redis、搜索引擎、向量库。不要一开始就上五种数据库。
