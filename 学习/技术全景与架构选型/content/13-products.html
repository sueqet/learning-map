MODULE 13 · 技术全景

产品架构拆解：六类产品怎么搭

架构是从难点里长出来的。

✓本节学习目标

  • 掌握「先找核心难点，再倒推架构」的四步拆解法。
  • 说出聊天、秒杀、短视频、外卖、协同文档、AI 对话这六类产品各自最难的地方。
  • 对每类产品，能讲出 3–5 个关键组件，以及它们分别是为了解决哪个难点。
  • 对每类产品，能给出「只有 3 个人时」的简化版，而不是照搬大厂架构。
Pre-requisites · 前置知识

学完前 12 个模块，尤其是 06 数据层、07 架构模式、09 安全与失败模式。本节描述的是业界公开分享中常见做法的抽象，帮助你理解思路，并不代表任何一家公司的真实内部架构。

Part 1 · 方法

01从难点倒推架构

知识点 1拆解方法：从核心难点倒推架构method · 四步拆解法

你最初的问题是：「不同的产品都使用什么样的架构？」答案是：没有哪个产品是「先选好一堆技术再拼起来」的。架构总是从产品最难的那件事里长出来的。拆解任何产品，都可以用四步：

  1. 找核心难点：这个产品最不能出错、最难扛的是什么？（消息丢了？库存超卖？视频卡顿？）
  2. 估算规模：多少用户、每秒多少请求、多少数据、读多还是写多？
  3. 从难点倒推组件：每一个关键组件都应该能回答「我是为了解决哪个难点」。
  4. 给出 MVP 版：如果只有 3 个人、两个月，哪些组件可以先不要？
产品核心难点关键技术
即时通讯海量长连接；消息不丢、不乱、实时WebSocket、会话序号、ACK 重发、消息存储分片
秒杀大促瞬间流量是平时百倍；库存不能超卖CDN、网关限流、Redis 预扣、消息队列削峰
短视频信息流海量视频的存储分发；千人千面推荐对象存储、转码、CDN、推荐系统、计数服务
外卖打车实时位置；就近匹配；多方订单状态地理索引、调度算法、状态机、对账
协同文档多人同时编辑不打架、不丢字OT / CRDT、WebSocket、操作日志
AI 对话推理慢且贵；流式输出；内容安全SSE、推理集群、RAG、限流计费、内容审核
★

核心要点：看到一张复杂的架构图时，逐个问：这个组件是为了解决哪个难点？答不上来的组件，在你的场景里很可能不需要。

Part 2 · 六类产品

02逐个拆解

知识点 2即时通讯：消息不丢、不乱、实时到达IM · 类微信聊天

聊天看起来简单：A 发一句，B 收到。难点在于规模和可靠：上亿人同时在线，每个人都要和服务器保持一条长连接；网络随时抖动，但消息既不能丢，也不能乱序，还不能重复显示；手机离线时，消息要存起来等上线再补。

难点常见对策用到的技术
实时推送客户端和服务器保持长连接，有消息立刻推下去WebSocket 或自研 TCP 协议；长连接网关集群（Go / C++ / Java 等高并发语言）
不丢消息带唯一 id；服务端先落库再回执 ACK；客户端没收到 ACK 就重发超时重试 + 消息 id
不重复接收端按消息 id 去重幂等
不乱序每个会话分配递增序号 seq，客户端按 seq 排序，发现缺口就主动拉取会话内序号
离线与多端同步在线时推，离线后上线按 seq 拉（推拉结合）；手机后台走系统推送通道消息存储 + 推送服务
海量消息存储按会话分片，写多读少宽列数据库（HBase / Cassandra）或分库分表；Kafka 削峰
群聊小群「写扩散」（每人一份收件箱），大群「读扩散」（存一份，大家来读）按群规模选策略
!

3 人团队版：一个后端服务同时处理 WebSocket 和业务；消息存 PostgreSQL，按（会话 id, seq）建索引；Redis 记录谁在线；先不做多端同步和千人大群。这套足以支撑早期几千人同时在线。

知识点 3秒杀大促：瞬间流量与库存不超卖flash sale · 削峰与防超卖

秒杀的特点是：100 件库存，几十万人在同一秒点「购买」。如果所有请求都直接打到数据库，数据库瞬间被压垮，整个网站跟着瘫痪。核心思路是层层过滤：让绝大多数请求在越靠前的地方被挡住或消化，只有真正能买到的那一小部分走到数据库。

层做法挡住了什么
前端商品页静态化放 CDN；开始前按钮置灰；点击后防连点；排队页或验证码页面流量、机器刷单、重复点击
接入层网关按用户 / IP / 设备限流，黑名单防刷超出系统承受能力的请求
库存库存预先放进 Redis，用原子操作扣减，扣成功才放行绝大部分「其实买不到」的请求
下单扣库存成功后发消息，订单服务异步慢慢建单瞬时写入洪峰（削峰）
数据库条件更新 UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0；一人一单靠唯一约束最后一道防超卖、防重复下单的防线
隔离秒杀服务独立部署；准备降级开关；提前全链路压测秒杀出事拖垮正常购物
!

3 人团队版：如果「秒杀」只是几百人抢 50 张优惠券，不需要上面整套。数据库条件更新 + 唯一约束（一人一单）+ 简单限流就足够，再做一次压测确认。

知识点 4短视频信息流：存储分发与推荐feed · 类抖音

短视频有两个大难题：一是海量大文件——每天上传的视频要转成多种清晰度，再快速送到全国各地的手机上；二是千人千面——每个人刷到的内容都不一样，推荐决定了产品的生死。

难点常见对策用到的技术
上传客户端直传对象存储（服务端只发临时签名），分片上传、断点续传对象存储
转码上传完成后发消息，转码集群异步生成多种清晰度和封面消息队列 + 转码服务
播放分发视频走 CDN；播放器按网速自动切换清晰度、预加载下一条CDN、自适应码率
推荐离线训练模型；在线「召回 → 粗排 → 精排」层层筛选；用户行为实时更新特征推荐系统、特征存储、大数据平台
点赞播放计数Redis 计数，异步批量落库最终一致
内容安全机器审核 + 人工复审审核服务
!

3 人团队版：对象存储 + CDN + 云厂商的转码服务，几乎不用自己写视频处理；feed 先按「时间 + 热度」排序，不做个性化推荐。等有了足够的用户行为数据，推荐才有意义。

知识点 5外卖打车：位置、调度与订单状态机delivery · LBS 与实时调度

外卖和打车涉及三方（用户、商家或乘客、骑手或司机），难点是：位置每几秒就变一次；要在几秒内找到「附近最合适」的骑手；一个订单在多方之间流转，状态绝不能错乱；最后还要三方对账。

难点常见对策用到的技术
高频位置上报骑手端每隔几秒上报，写入内存型存储，只保留最新位置Redis 等内存存储
就近查询地理索引：把地图切成格子，快速找附近的人GeoHash、Redis GEO、PostgreSQL 的 PostGIS 扩展
派单调度算法综合距离、顺路程度、预计送达时间，批量匹配调度服务
订单状态状态机：已下单 → 已接单 → 配送中 → 已送达，只允许合法转换；所有状态变更幂等状态机 + 幂等 + 事件
实时通知状态变化推送给相关各方推送、长连接
结算对账事务记账 + 定期三方对账关系型数据库
!

3 人团队版：做一个校园跑腿小程序：PostgreSQL + PostGIS 查附近的人；派单先用「附近骑手抢单」规则；订单状态机写在一个服务里，每次状态变更都检查「当前状态是否允许」。

知识点 6协同文档：多人同时编辑不打架collaboration · OT / CRDT

两个人同时编辑同一段文字，如果简单地「谁最后保存就用谁的」，另一个人的修改就丢了。协同文档的核心是：同步「操作」而不是整篇文档，再用专门的算法把并发的操作合并，让所有人最终看到一模一样的结果。

难点常见对策用到的技术
并发冲突把每次编辑表示为「在第几个位置插入 / 删除什么」，用算法变换后合并OT（操作转换）或 CRDT（无冲突复制数据类型）
低延迟同步操作通过长连接实时广播；同一文档的连接路由到同一节点WebSocket、长连接网关
版本历史存操作日志，定期打快照，随时回到任意版本操作日志 + 快照
离线编辑本地先保存，重新联网后合并CRDT 尤其擅长
权限分享文档级权限、分享链接、只读 / 评论 / 编辑认证授权
!

3 人团队版：千万别自己从零实现 OT / CRDT 算法。用成熟的开源 CRDT 库（例如 Yjs）+ 一个 WebSocket 服务；或者先做「编辑锁」——同一时间只允许一个人编辑，简单可靠。

知识点 7AI 对话产品：流式、推理成本与安全AI chat · 类聊天机器人

AI 对话产品和传统 Web 应用最大的不同：一次请求可能要几秒到几十秒、成本按 token 计，而且输出内容不可完全预测。架构围绕四件事展开：体验（流式）、成本、质量、安全。

难点常见对策用到的技术
等待太久边生成边推送，前端逐字显示；支持中途停止SSE、流式渲染
推理贵、GPU 紧张调用模型 API；或自建推理集群并批处理请求提高吞吐大模型 API、vLLM 等推理引擎
多轮上下文保存会话历史，超长时截断或摘要，控制 token会话存储
私有知识、实时信息检索增强（RAG）；调用搜索、计算等工具向量检索、Agent / 工具调用
成本失控按用户配额与限流；缓存高频问题；简单问题路由到小模型网关、计费、模型路由
内容安全输入输出审核；防提示注入；敏感数据脱敏审核服务
质量评估问题集 + 线上点赞 / 点踩反馈评估流水线
!

3 人团队版：FastAPI + 大模型 API + SSE 流式 + PostgreSQL 存会话（需要知识库时加 pgvector）+ 按用户限流。这正是 10 模块的 AI 问答案例。
