MODULE 09 · 技术全景

安全与失败模式

权限边界在哪？挂了会怎样？

✓本节学习目标

  • 分清认证（你是谁）和授权（你能做什么），并识别最常见的越权漏洞。
  • 说出最小权限、输入验证、密钥管理三条安全底线，各举一个反例。
  • 解释为什么每个网络调用都要设超时，以及什么错误该重试、什么错误不该。
  • 用「重复扣款」的例子解释幂等，并说出幂等键的做法。
  • 区分限流、熔断、降级，知道它们如何保住核心链路。
  • 说清「主从复制 ≠ 备份」，以及「没恢复过的备份不算备份」。
Pre-requisites · 前置知识

Part 1 · 安全：权限边界在哪

01谁能做什么

知识点 1认证 vs 授权authentication vs authorization · 你是谁 / 你能做什么

认证（Authentication）回答「你是谁」：密码、短信验证码、扫码、第三方登录。认证通过后，服务端会发给你一个登录凭证（Session 或 Token，如 JWT），之后每次请求都带上它。授权（Authorization）回答「你能做什么」：普通用户只能看自己的订单，管理员才能下架商品。就像进公司：门禁卡证明你是员工（认证），但不代表你能进机房（授权）。

认证授权
回答的问题你是谁？你能做什么？
常见手段密码、验证码、OAuth 第三方登录、单点登录 SSO角色权限（RBAC）、资源归属检查（只能操作自己的数据）
失败时401 未认证403 无权限
!

最常见的漏洞——越权：接口只检查了「有没有登录」，没检查「这条数据是不是你的」。结果把网址里的 /orders/1001 改成 /orders/1002 就能看到别人的订单。「访问控制失效」长期位居 OWASP Web 安全风险榜首。看 AI 生成的接口时，第一件事就是问：它检查数据归属了吗？

知识点 2最小权限、输入验证、密钥管理security basics · 三条底线

安全细节很多，但有三条底线足以挡住大部分事故：

原则反例好的做法
最小权限应用用数据库 root 账号连接；所有员工都有生产服务器权限只给完成工作所需的最小权限；应用账号不能删表；权限定期回收
输入验证（永远不信任输入）把用户输入直接拼进 SQL；把用户评论原样插进网页参数化查询防 SQL 注入；输出时转义防 XSS；限制上传文件的类型和大小
密钥管理把数据库密码、API 密钥写在代码里并提交到 Git放在环境变量或密钥管理服务中；按环境区分；定期轮换；一旦泄露立即吊销
传输加密登录页用 HTTP 明文传密码全站 HTTPS
依赖安全几年不更新依赖；装来路不明的包定期升级、开启依赖漏洞扫描；确认包名是官方的
SQL 注入：拼接 vs 参数化（看懂即可）
# ✗ 危险：用户输入 name = "' OR '1'='1" 时，会查出所有用户
cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

# ✓ 安全：参数单独传给数据库，永远被当作「值」而不是「SQL 代码」
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
★

核心要点：审查任何方案（包括 AI 写的）都可以问三句：权限给大了吗？输入验证了吗？密钥放哪了？本仓库 SQL 学习包第 14 模块有可交互的 SQL 注入演示。

Part 2 · 失败模式：挂了会怎样

02网络调用一定会失败

知识点 3超时与重试timeout · retry · 失败的第三种结果

函数调用只有成功和失败两种结果，但网络调用有三种：成功、失败、以及「不知道」——请求发出去了，迟迟没有回音，对方可能根本没收到，也可能已经处理完、只是响应丢了。

  • 必须设超时。不设超时，一个变慢的下游会让所有请求都卡住等待，耗尽线程和连接，最后整个系统一起倒下（级联故障）。
  • 只对临时性失败重试：超时、503、429。参数错（400 / 422）、没权限（403）重试一万次也不会成功。
  • 重试要克制：限制次数，用指数退避 + 随机抖动（1 秒、2 秒、4 秒……再加点随机），否则所有客户端同时重试，会形成「重试风暴」把刚恢复的服务再次打垮。
错误该不该重试原因
超时、连接被重置可以（前提是操作幂等）可能是网络抖动
503 服务暂不可用、429 被限流可以，退避后再试对方暂时忙
400 / 422 参数错误不要请求本身有问题，重试结果不变
401 / 403不要先解决登录或权限
!

危险组合：「超时」+「自动重试」+「操作不幂等」= 重复扣款、重复下单、重复发短信。所以讨论重试之前，必须先讨论下一个知识点：幂等。

知识点 4幂等：重试也不重复扣款idempotency · 做一次和做多次结果一样

幂等指同一个操作执行一次和执行多次，最终结果一样。「查询余额」天然幂等；「把订单状态设为已取消」也幂等；但「扣 100 元」不幂等——执行两次就扣了 200。因为网络会超时、用户会连点、客户端会自动重试，所有涉及钱和状态变化的写操作都应该设计成幂等的。

做法怎么做例子
幂等键客户端为每一次「意图」生成唯一 id（如 Idempotency-Key 请求头），服务端记录处理过的 id，重复请求直接返回第一次的结果支付平台的扣款接口普遍采用
唯一约束数据库对业务单号加唯一索引，重复插入会被拒绝同一个订单号只能有一条支付记录
状态机只允许合法的状态转换只有「待支付」能变成「已支付」，已支付的再来一次直接忽略
前端兜底点击后禁用按钮减少重复点击，但不能替代后端幂等
★

核心要点：看到任何「失败自动重试」的设计，立刻追问：这个操作幂等吗？靠什么保证？这是 01 模块里「会问」的典型例子。

知识点 5限流、熔断、降级rate limit · circuit breaker · degradation · 保住核心链路

系统总有扛不住的时候。目标不是「永远不出问题」，而是出问题时保住最重要的功能（通常是下单和支付），让次要功能先「让路」。

手段类比做什么例子
限流景区限流超过承受能力的请求直接拒绝（429），保护系统不被打垮每个用户每秒最多 10 次请求；验证码每分钟 1 次
熔断家里的保险丝下游连续失败时，暂时不再调用它，直接走兜底；过一会儿放少量请求试探是否恢复推荐服务连续超时 → 30 秒内不再调用
降级停电时只保冰箱非核心功能关闭或返回简化结果，把资源留给核心链路个性化推荐 → 改为固定热门榜；评论区暂时只读
★

核心要点：这些手段都要提前设计：哪些是核心链路？每个依赖挂了用什么兜底？出事时再想就来不及了。

知识点 6备份与恢复：数据能不能找回backup · restore · 最后一道防线

机器坏了、有人误删、被勒索病毒加密……数据层的最后一道防线是备份。注意：主从复制不等于备份。主从复制防的是「机器挂了」，可一条误删的 DELETE 会被同步到所有从库。

概念白话
3-2-1 原则至少 3 份数据副本，存在 2 种不同介质上，其中 1 份在异地
RPO（恢复点目标）最多能接受丢失多长时间的数据？每天备份一次，最坏丢 24 小时
RTO（恢复时间目标）出事后多久必须恢复服务？
恢复演练定期真的拿备份恢复一次，确认它能用、知道要多久
!

真实教训：2017 年 GitLab.com 发生过生产数据库被误删的事故，事后发现好几种备份方式都没有按预期工作，最终丢失了数小时的数据。没恢复过的备份，不算备份。
