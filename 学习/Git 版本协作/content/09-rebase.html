变基与整理提交

rebase 把一段提交重放（replay）到新的基点上，换来一条干净的线性历史；但它会重写提交哈希，因此只适用于尚未分享的提交。本节带你掌握它该在什么时候用、又绝不能怎么用。

✓本节学习目标

  • 学完后，你能用自己的话说清 rebase 的本质——「把提交重放（replay）到新的基点上」，并用图解区分它与 merge。
  • 学完后，你能用 git rebase <branch> 把当前分支的提交搬到目标分支顶端，并在冲突时用 continue/abort 处置。
  • 学完后，你能用 git pull --rebase 拉取远程更新并保持线性历史（linear history）。
  • 学完后，你能用 git rebase -i 重写提交：reword / squash / fixup / drop 及调整顺序。
  • 学完后，你能判断何时该用 rebase、何时该用 merge，并解释为什么不要对已推送/共享的分支 rebase。
Prerequisites · 前置知识

会用命令行；已掌握 Git 基础（add / commit / branch / checkout）；理解 commit 是「快照链」、HEAD 与分支指针对齐；能看懂简单分支合并图。如果你还不太熟悉 merge 的语义，建议先回看上一节 08-tags.html。

Learning Content · 学习内容

01变基与整理提交

01rebase 的思想与可视化rebase-idea

rebase（变基 / rebase）的核心理念：把一个分支上的一段提交，重新接到另一个分支的「新基点（base）」顶端。它不像 merge 那样生成一个「把两条历史并起来」的合并提交，而是把原来的提交逐个重放（replay / reapply）到新基点上，最终得到一条干净的直线历史。

形象地记：merge 是「会师」——两条历史汇合，留下一个分叉与合并提交；rebase 是「挪根基」——把整个分支的起点替换掉，历史被拉直成一条线。正因为提交的父提交（parent）变了，重放后每个提交的哈希（SHA-1）都会改变，这是下面「禁忌」的根本原因。

图 1 · 变基前：feature 从小基点 base 分出，main 已先前进到 C
gitGraph commit id: "base" branch feature checkout feature commit id: "A" commit id: "B" checkout main commit id: "C"
图 2 · 变基后：feature 的 A、B 被「重放」到 C 顶端（哈希已改变，标为 A′、B′），历史拉直
gitGraph commit id: "base" commit id: "C" branch feature checkout feature commit id: "A'" commit id: "B'"
图 3 · 对照：merge 不重写，而是生成一个「合并提交」把两条历史汇合
gitGraph commit id: "base" branch feature checkout feature commit id: "A" commit id: "B" checkout main commit id: "C" merge feature
★

核心要点：rebase 的结果是线性历史——提交数量不变、内容不变，只是「换了爹」，所以哈希会变。这是它与 merge 最根本的区别，也是它「危险」的根源。

02基础 rebase 与 git pull --rebaserebase-basic

最基础的用法是把当前分支的提交「重放」到目标分支顶端。例如你在 feature 上做了两个提交，想让它们基于最新的 main：

shell
# 先切到 feature（或当前已在其上），把它重放到 main 顶端
git checkout feature
git rebase main

# 常见等价写法：把当前分支的提交接到远程分支顶端
git rebase origin/main

团队里更常见的场景是「拉取远程更新并保持线性历史」。默认的 git pull（等价于 fetch + merge）会在你本地落后时产生合并提交；而 git pull --rebase 等价于 fetch + rebase，把你本地的提交重放到远程顶端，历史保持一条直线。

shell
# 拉取远程更新并变基，而非合并
git pull --rebase origin main

# 拉取后若提交被重放，需重新推送（很可能需要强推，见下方禁忌）
git push --force-with-lease origin feature

重放过程中若某个提交碰到冲突，Git 会停下等你处理。处理完冲突后是逐个提交继续的（因为是逐提交重放），可用 --continue 继续，--skip 跳过当前提交，--abort 放弃整个 rebase 回到开始前。

shell
# 解决冲突后（先 add，再 continue / skip / abort 三选一）
git add <file>
git rebase --continue   # 解决完这个提交，继续重放下一个
git rebase --skip       # 丢弃当前这个提交（别乱用，会少一个提交）
git rebase --abort      # 放弃本次变基，回到开始之前的状态
⚠

易错点：rebase 冲突可能多次出现——因为它是逐提交重放，每个提交都可能撞车，和 merge「只冲突一次」很不一样。请耐心逐个解决；实在理顺不了就 git rebase --abort 全身而退。

03交互式 rebaseinteractive

交互式 rebase（interactive rebase）是重写历史的主力工具：git rebase -i HEAD~3 会打开编辑器，列出最近 3 个提交，每行开头是一个动作。你改动作、调顺序，保存退出后 Git 按你的指令重新生成提交。

shell
# 编辑最近 3 个提交（HEAD~3 表示从当前往前的最近 3 个）
git rebase -i HEAD~3

# 编辑器里的样子（把左列动作改成想要的）：
pick 3a2b6c1 修复：登录 token 过期
pick 7d1e9f2 小调整：修正一个边界
pick 9f0b8a4 功能：新增导出

常用动作一览。其中 squash 和 fixup 都是「合并进上一个提交」，区别在于：squash 会弹出编辑器让你合并提交信息，fixup 直接丢弃本提交的信息、只保留上面那个标题。

动作缩写作用
pickp保留这个提交不动
rewordr保留提交，但修改提交信息
squashs合并进上一个提交，并合并提交信息
fixupf合并进上一个提交，丢弃本提交信息
dropd从历史中删除这个提交
edite暂停在此提交，便于修改内容

经典组合：把好几个「反复小修改」压缩（squash/fixup）成一个有意义的提交，再用 reword 把标题写清楚；用 调整行顺序 来重排提交；用 drop 丢弃写错/临时的提交。

shell
# 把最后 3 个「小修小补」压成 1 个清晰提交，并给它改标题
pick 3a2b6c1 功能：新增导出
squash 7d1e9f2 小调整：修正边界
fixup 9f0b8a4 小调整：改个拼写

# 或丢弃一个不再需要的提交：
drop 9f0b8a4 临时：实验性改动（已废弃）
★

核心要点：rebase -i 是「把历史重写成理想模样」的工具——适合在合并进主干之前，把你的提交整理得更整洁、可读。它同样会改变提交哈希，因此也只能用于尚未分享的本地提交。

04rebase vs merge 对比与禁忌rebase-merge

两者没有绝对对错，只是目标不同：rebase 换来「干净的线性历史」，代价是重写提交、不适合共享；merge 换来「真实可信的历史」，代价是多出分叉与合并提交。如何选，取决于这条分支是否已被别人分享。

维度rebasemerge
是否重写历史是（提交哈希改变）否（新增一个合并提交）
历史形态线性、干净(lint 起来更像一条直线)有分叉，保留真实汇聚时间线
是否产生合并提交否是
冲突处理逐提交重放，可能多次冲突一次合并，通常只冲突一次
能否用在已推送分支❌ 不可（会破坏他人工作）✅ 安全
典型命令git rebase / git pull --rebasegit merge / git pull
适合场景整理尚未分享的本地提交合并到共享/长期分支，如合并 PR
⛔

强警告：不要对已推送/共享的分支 rebase！rebase 会重写提交哈希。一旦同事已经基于这些提交 pull 或 merge 了，你 rebase 后再 git push 会被拒绝（非快进引用）；强行 git push --force 会把分支历史覆盖成你重写后的样子，导致同事本地的提交「凭空消失」或在 pull 时产生分叉与重复提交，甚至丢失他们的工作。

✦

安全法则：只 rebase「你自己写的、还没有推到共享 remote、别人还没依赖」的提交。对已经分享的分支，老老实实用 merge；实在想整理，用 git pull --rebase 的前提是你是这条分支的唯一作者，否则改用 git fetch + git merge。
