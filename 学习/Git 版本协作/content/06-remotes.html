GIT · 协作

远程仓库与克隆/推送/拉取

克隆、推送、拉取——把你本地的 Git 仓库连接到 GitHub，让不同的机器与不同的人之间同步与协作，这是团队开发的第一步。

✓本节学习目标

  • 你能用 git clone 克隆一个仓库，并解释克隆后 origin 与远程跟踪分支 origin/HEAD 的含义。
  • 你能用 git remote -v 查看远程配置，并用 git remote add / rename / remove 管理多个远程（如 fork 场景下的 origin 与 upstream）。
  • 你能说清 git fetch、git pull、git push 三者的方向、作用与使用时机，并判断各自是否会改动本地工作区。
  • 你能用 git push -u 为本地分支关联上游（upstream），实现裸 git push。
  • 当推送被拒（non-fast-forward）时，你能读懂错误信息，并用「先 pull --rebase 再 push」的正确流程解决。
Prerequisites · 前置知识

会用命令行、能在终端运行命令；了解 Git 的 commit（提交）与 branch（分支）概念；本地已有一个 Git 仓库（通过 git init 或 git clone 建立）；如需练习推送，建议有一个 GitHub / GitLab 等远程托管平台的账号及其仓库地址。

01让代码在多人之间流动：远程仓库与协作

小节克隆仓库与远程跟踪分支git clone · remote-tracking branch

当你拿到一个远程仓库地址（如 GitHub 上的项目），最常用的方式就是 git clone。它会把整个仓库「复制」到本地：下载全部历史提交、所有分支与标签，并自动配置好远程连接，让你可以直接开始开发。

shell
# 克隆一个仓库到当前目录（会在当前目录下新建同名目录）
git clone https://github.com/user/zoom-repo.git

# 克隆到你自己指定的目录名
git clone https://github.com/user/zoom-repo.git my-copy

# 只拉取最近一条提交（浅克隆，速度快，适合大仓库或只需最新代码）
git clone --depth 1 https://github.com/user/zoom-repo.git

# 克隆后查看远程配置与所有分支
git remote -v
git branch -a          # -a 同时列出本地分支与远程跟踪分支

克隆一旦完成，Git 会替你做好三件事：一是建立一个名为 origin 的远程（remote），指向你填写的那个 URL；二是把远程的默认分支（比如 main）检出到本地，并自动给它设置「上游」（即 git push -u 的效果）；三是创建一系列只读的远程跟踪分支（remote-tracking branch），如 origin/main，用来记录你「上一次与远程同步时」远程分支的状态。

★

核心要点：origin 只是远程的默认名字，不是特殊命令；origin/main 是本地保存的、只读的远程跟踪分支，用来当作下一次 merge/rebase 的参照，不要直接在上面提交。

小节管理远程：git remote add / -v / removegit remote

远程（remote）本质上是「一个指向远程仓库的书签」，由名字 + 地址组成。默认克隆后只有一个 origin，但协作里经常需要同时连接多个远程——最典型的就是 fork（派生）别人的仓库：你自己的副本叫 origin，原作者的仓库叫 upstream，你用 upstream 拉取最新改动，用 origin 推送自己的提交。

shell
# 查看所有远程（-v 显示每个远程的 拉取/推送 地址）
git remote -v

# 添加一个远程：名字 + 地址
git remote add upstream https://github.com/original/zoom-repo.git

# 重命名远程
git remote rename origin my-fork

# 修改某个远程的地址（例如从 HTTPS 换成 SSH）
git remote set-url origin git@github.com:user/zoom-repo.git

# 删除一个远程
git remote remove upstream     # 也可用 git remote rm upstream
命令作用
git remote -v列出所有远程的名字与其 fetch/push 地址
git remote add <name> <url>添加一个新的远程连接
git remote rename <old> <new>重命名某个远程
git remote set-url <name> <url>修改某个远程的地址
git remote remove <name>断开并删除某个远程
!

易错点：记住「origin、upstream 只是名字」——它们长得像命令，但没有任何魔法。你完全可以把远程命名为 foo，只要名字唯一即可。推则送、拉则取，靠的是 remote = 名字 + 地址 这个映射。

小节push / fetch / pull 的区别与用法fetch vs pull vs push

这三个命令分别对应「数据往哪走」。快速记忆：push 是你往上是推送（本地 → 远程）；fetch/pull 是别人往下是拉取（远程 → 本地）。三者都做网络交互，但对本地工作区的修改程度完全不同。

命令方向是否改动本地工作区 / 当前分支是否改动远程典型用途
git fetch远程 → 本地（仅更新引用）否（只更新 origin/* 跟踪分支，不动工作区与 HEAD）否先「看」一下远程有什么新东西，再决定怎么合并
git pull远程 → 本地（fetch + merge）是（把远程改动合并进当前分支）否日常快速拉取并合并到本地分支
git push本地 → 远程否是（把你的本地提交发布到远程分支）把本地工作成果共享给团队
shell
# 只下载远程最新状态，不合并
git fetch origin

# 拉取并合并（= fetch + merge）
git pull origin main

# 推送本地 main 分支到远程 origin/main
git push origin main

!

易错点：git pull 默认用的是 merge，会多出一个「合并提交」Merge commit。如果你想让历史保持线性、更整洁，可用 git pull --rebase；但要记住 rebase 会改写本地提交历史，只适合还没分享出去的本地提交。

小节关联上游（-u）与常见推送失败处理--set-upstream · non-fast-forward

每次都要写 git push origin main 很啰嗦。用 -u（即 --set-upstream）把本地分支和某个远程分支绑定成上下游，之后直接 git push 就能自动推到正确的地方，git pull 也会自动从那里拉取。

shell
# 第一次推送并设置上游（绑定本地 main 与远程 origin/main）
git push -u origin main

# 设置好上游之后，下面两条命令就够了：
git push
git pull

推送被拒（rejected）是最常见的协作冲突。核心原因只有一个：远程有你没有的提交。Git 为了不丢别人代码，拒绝把你的历史「覆盖」上去。典型的报错如下：

shell
$ git push
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs
hint: Updates were rejected because the remote contains work that you do not have locally.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

这时不要用 git push -f 去强制覆盖。正确做法是：先和远程同步，把本地提交「垫」到远程最新提交之上，再重新推送。

场景 / 报错原因正确处理
non-fast-forward远程有你没有的提交先 git pull --rebase（或 git pull），解决冲突后再 git push
Permission denied / 认证失败未登录、无权限、或使用了错误的认证方式用 SSH 密钥或 HTTPS Personal Access Token 认证；git remote set-url 换成正确的地址
想彻底改写历史（仅限自己的分支）刻意重写 commit确认只影响自己的分支后，才考虑 git push -f
shell
# 标准自救流程：远程分叉时，先把本地提交垫到最新之上
git pull --rebase origin main

# 若与他人改了同一文件，会提示冲突，逐个文件解决后：
git add .
git rebase --continue

# 冲突解决了，再安全推送
git push
✕

红线：从不对共享的 main / master 分支使用 git push -f——它会丢弃别人的提交。强制改写历史只应发生在你自己、且未与他人共享的分支上。

★

核心要点：推送前那条铁律是「远程有我没」——只要远程出现了本地没有的提交，就先用 pull --rebase 把远程的最新改动拉下来，把本地提交接到它后面，再 push。先同步、再推送，永远成立。

⌕

▲ 进阶挑战

  • 在 GitHub 上 fork 一个任意开源仓库，克隆到本地；试着把原作者的仓库添加为 upstream，用 git fetch upstream 拉取最新改动，并说明为什么推送应该走 origin 而不走 upstream。
  • 用 git clone --depth 1 克隆一个大型仓库，再运行 git fetch --unshallow 补全历史；对比两次操作后 git log 与仓库体积的差异，体会「完整克隆 vs 浅克隆」的取舍。
  • 故意制造一次分叉：先在某分支连续提交两次，再与远程同步（用 git pull --rebase），观察提交顺序；最后把其中一次提交用 git rebase -i 压缩（squash），并解释为什么这种改写不能发生在共享分支上。
  • 查阅 git push 与 git fetch 的 --all、--tags、--force-with-lease 等选项，写出一段笔记：哪种场景下你会更倾向于 --force-with-lease 而不是裸 --force。
