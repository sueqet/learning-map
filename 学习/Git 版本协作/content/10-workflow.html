GIT · 协作

团队协作工作流

当代码不再是你一个人的，个人分支、Pull Request、Code Review 和同步策略就成为日常。这一节讲清楚几种主流协作工作流，以及怎么用一套约定让团队写得更稳、合得更顺。

✓本节学习目标

  • 学完后，你能用自己的话说出 feature branch / GitFlow / fork+PR / trunk-based 四种工作流的区别与各自适用的团队。
  • 你能完整走通一次 GitHub Pull Request 流程，并讲清 Code Review 在每个环节的作用。
  • 你能用 Conventional Commits 写出规范的提交信息，并解释 分支保护（protected branch） 为什么重要。
  • 你能在多人协作中识别常见的冲突类型，并用 fetch / merge / rebase 选对同步方式。
  • 你能为实际团队画出一张 feature branch 或 fork+PR 的流程图。
Prerequisites · 前置知识

会用命令行；掌握 git init / add / commit / push；理解分支（branch）与合并的概念；在 GitHub 上创建过仓库、会提交、能开 Pull Request。

01常见协作工作流对比feature branch / GitFlow / trunk-based

单人开发时"一条分支一直提交"很省事；可一旦多人同时改同一份代码，分支（branch）和合并（merge）就变成了隔离彼此改动、降低摩擦的手段。所谓"工作流（workflow）"，难点不在命令，而在约定：谁在什么时候建分支、往哪里合、怎么合、合之前要过哪些检查。下面是最常见的四种。

%%{init: {'theme':'neutral'}}%% gitGraph commit id: "c1" branch feature/login checkout feature/login commit id: "f1: feat(auth)" commit id: "f2: feat(oauth)" checkout main commit id: "other's commit" checkout feature/login checkout main merge feature/login commit id: "m2"

▲ 上图：feature branch / GitHub Flow 的骨架——每个功能一条短命分支，开发完经 PR 合并回 main。

工作流核心思想分支策略适合团队优点代价
feature branch
GitHub Flow		 一切改动都走短生命周期分支 + Pull Request 只有 main 长期存在 小到中型、持续交付（+ 有 CI） 轻量、易学、始终可发布 依赖团队自觉走 PR、规范严格
GitFlow 严格区分多条长期分支，像"版本公交" main / develop / feature / release / hotfix 版本化发布、有明显 release 周期的产品 规则清晰、release 与 hotfix 生命周期分明 分支多、流程重，不适合持续部署
fork + PR 先 fork 出自己仓库副本，再向上游提 PR 每人持有 fork 副本 + 向上游 PR 开源项目 / 不可信或外来贡献者 无需写权限也能贡献，天然隔离 同步双方 fork 较繁琐
trunk-based
主干开发		 所有人尽量每天小步直接合入主干 单一 main（改动通常用 feature flag 隔离） 成熟团队、CI/CD 与自动化测试极强 集成快、冲突少 需要高测试覆盖率与强纪律
★

核心要点：工作流的本质是"分支如何创建 + 如何合并"的团队约定。Git 命令本身不变，变的只是规范；选哪种，取决于团队的发布节奏与自动化程度，而非"哪个更高级"。

无论哪种，最基本的"单条 feature 分支"操作都是相同的——这是所有协作流程的地基：

shell
# 1) 确保从最新 main 出发，再切一条特性分支
git checkout main
git pull origin main
git checkout -b feature/email-login

# 2) 在分支上提交，并推送远端（-u 建立跟踪关系）
git add .
git commit -m "feat(auth): add email login"
git push -u origin feature/email-login

# 3) 之后在 GitHub 上针对它创建 Pull Request
!

易错点：建分支前务必先 git pull 到最新。基于过期 main 建的分支，很可能与你同事刚合的改动撞车，造成大量无谓冲突。

02GitHub Pull Request 与 Code Review 流程重点

把一条分支的改动"请求合并"进目标分支，就是 Pull Request（PR，拉取请求）。它不只是"合并按钮"——它把"谁在何时改了什么、为什么改、谁看过"全部记录了下来，是异步代码审查（Code Review）和自动化检查（CI）的载体，也是团队质量与协作透明度的核心。

%%{init: {'theme':'neutral'}}%% flowchart TD A[创建 feature 分支并推送] --> B[在 GitHub 上创建 Pull Request] B --> C[填描述 / 关联 issue / 选 reviewer] C --> D{CI 自动化检查通过?} D -- 否 --> E[查看失败原因并修复] E --> F[再次 push 更新分支] F --> D D -- 是 --> G[Code Review 评审] G --> H{Reviewer 通过?} H -- 否 --> I[回复评论 / 修改提交] I --> F H -- 是 --> J[合并·Merge / Squash / Rebase merge] J --> K[删除已合并分支]

▲ 上图：一次 PR 的完整生命周期。注意 D → E → F 的循环——CI 挂了或 review 有意见，都会让 PR 回到"再改再推"。

Review 后有意见，怎么更新分支？

shell
# 普通修正：直接追加提交并 push，PR 会自动更新
git add .
git commit -m "refactor(auth): extract email validator"
git push origin feature/email-login

# 想要"一次性提交"的干净历史（interactive rebase 后需强推到同一分支）
git rebase -i main        # 把多个提交 squash 成一个
git push --force-with-lease origin feature/email-login
!

危险：git push --force 会改写已推送的远端提交。在共享分支上强推可能覆盖别人已 pull 的历史。优先用 git push --force-with-lease（只在确认远端未变化时才强推），且先与团队沟通。feature 分支是自己的，强推没问题；main/develop 等共享分支永远不要强推。

★

核心要点：一个健康的 PR 应该小而聚焦（一次只解决一件事）、有清晰的描述与关联 issue、通过 CI、并至少得到一名 reviewer 的批准（approve）再合并。

03团队最佳实践conventional commits · 分支保护 · 同步策略

流程定了，还得靠一些"规则"把它固化下来。下面三件事是绝大多数团队都会做的：规范提交信息、保护关键分支、以及统一同步策略。

① Conventional Commits（规范提交）

一份被机器和人都能读懂的提交信息，会让 CHANGELOG 自动生成、回滚与定位问题轻松很多。格式为 类型(作用域): 描述：

shell
feat(auth): add email & Google OAuth login
^--^ ^--^  ^-----------------------^
|    |    └─ 主体：说明"做了什么"（祈使句、小写）
|    └────── 作用域(scope)：影响的模块，可选
└─────────── 类型：feat/fix/docs/style/refactor/perf/test/...
类型含义示例
feat新功能feat(auth): add email login
fix修复 bugfix(cart): correct total on coupon
docs文档docs: update README quick start
refactor重构（不改行为）refactor: extract email validator
perf性能优化perf(image): lazy load thumbnails
test测试test(auth): cover login failures
style格式（不改逻辑）style: run prettier

② Protected branch（保护分支）

在 GitHub 仓库设置里，把 main（及 develop 等核心分支）设为受保护，即可：

  • 禁止直接推送到 main——只能通过 PR 合并；
  • 要求至少 N 名 reviewer 批准后才允许合并；
  • 要求 CI 必须先通过（required status checks）；
  • PR 分支过期（落后于 main）时禁止合并，强制先同步。

这就把"走 PR、走 review、CI 必须绿"写进了制度，而非依赖自觉。

③ 同步策略：merge 还是 rebase？

做法历史形态优点缺点
merge多一个"合并提交"，保留真实分叉；历史呈网状不改写历史，安全、可回滚任意一节点历史杂乱，分支多时难读
rebase线性一条直线，像"串行"历史干净、好看改写提交，共享分支慎用
squash merge
(PR 合并方式)		整条分支压缩成一个提交主分支每个提交=c一个功能丢失分支中间过程
★

核心要点：自己的 feature 分支可以放心 rebase / force-push；共享主干（main/develop）只合并、不改写。规则一句话："自己的分支随便折腾，共享的分支只嫁不娶。"

04多人协作常见问题与对策冲突 · 同步 · 脏分支

人一多，最常见的不是"命令不会"，而是三个场景：合并冲突、分支落后于主干、忘记同步导致 PR 过期。掌握下面这套动作，就能从容应对。

场景一：本地分支落后于远端 main（别人已经合了东西）。先把最新 main 拉下来，再同步你的分支：

shell
git checkout feature/email-login   # 回到你的分支
git fetch origin                   # 只拉取远端元数据，不改工作区
git merge origin/main              # 方式 A：merge（多一个合并节点）

# 或想保持线性历史时用方式 B：
git rebase origin/main             # 若有冲突，逐个解决后用
git rebase --continue

场景二：真撞上冲突（conflict）。Git 会在相同文件相同位置被修改时停下来，把冲突标记写进文件：

shell
# 冲突片段形如：
# <<<<<<< HEAD
# const price = amount * rate;
# =======
# const price = amount * 1.1;   // 别人的计算方式
# >>>>>>> feature/email-login

# 手动保留正确的那一份，删掉 <<</===/>>> 三行后：
git add .
git commit                     # merge 冲突后，完成合并提交
# 或 rebase 冲突后：
git rebase --continue
常见问题根因对策
PR 被 CI / 保护规则挡下分支过期或测试失败先 git pull，再 merge/rebase 同步，修复后重新 push
合并冲突成堆相同文件长时间各自开发小步提交、经常同步、降低每个 PR 的改动面
改了别人代码没及时 pull 就动手任务开始前 git pull；改前先看主人是否私有
在共享分支强推同伴 pull 后其 git 历史被改写共享分支禁强推；feature 分支用 --force-with-lease
大 PR 难 review一次塞进太多改动拆小、每 PR 一件事；先合小步再发大计划
!

防患于未然：频繁冲突的根源往往不是"Git 不好"，而是改动太小、太少同步。习惯 小步提交 + 经常 git fetch + 及时合入，比学会一堆解冲突的魔法命令更有效。

★

最终心法：协作不靠"谁的手速快"，而靠透明（走 PR、留记录）+ 同步（及时 fetch/rebase）+ 规范（Conventional Commits、保护分支）。命令都是工具，稳定的是约定。
