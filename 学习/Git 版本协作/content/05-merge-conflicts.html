GIT · 协作

合并与冲突解决

学会辨析 快进合并（fast-forward merge）与三方合并（three-way merge），理解为什么只在「两边都改了同一处」时才产生冲突，并掌握编辑 → add → commit 的标准解决三步——以及回退的 --abort 与续跑的 --continue。

✓本节学习目标

  • 能说出快进合并与三方合并各自在什么条件下发生，并判断一条命令会走哪种。
  • 能一句话点破冲突成因：三方合并的两边都对同一文件的同一处做了修改。
  • 能读懂 <<<<<<< / ======= / >>>>>>> 三个标记，并分清哪边是 ours、哪边是 theirs。
  • 能按「编辑文件 → git add → git commit」三步解决一个真实冲突，并在需要时用 --abort 回退、用 --continue 继续。
  • 能选择合适策略（--no-commit、ours/theirs、mergetool），并避免把未解决的标记提交进版本库。
Prerequisites · 前置知识

会用命令行；会创建/切换/合并分支（见上一节 04-branches.html）；理解「提交 commit」与「工作区 / 暂存区 / 版本库」三层模型；知道什么是「共同祖先 merge base」。

Learning Content · 学习内容

01合并的两种形态，与冲突到底从哪来

小节快进合并 vs 三方合并先分清两种合并，才能理解冲突

当你对 feature 分支执行 git merge 时，Git 的走向只有两种：快进（fast-forward）或三方合并（three-way merge）。它们由「目标分支有没有比共同祖先前进一步」决定。

  • 快进合并 Fast-forward：目标分支 main 自共同祖先之后没有产生新提交，Git 只是把指针从 main 直接往前平移到 feature 的顶端。因为没有任何分叉，所以不可能产生冲突，也不生成新的合并提交。
  • 三方合并 Three-way merge（也叫 merge commit）：两个分支都从共同祖先各自前进了，历史出现分叉。Git 以「合并基础 merge base」为参照，同时对比两边变化，尝试自动合并，必要时生成一个新的合并提交（merge commit）。冲突只会出现在这种情况里。
gitGraph commit id: "A" commit id: "B" branch feature checkout feature commit id: "C" commit id: "D" checkout main merge feature id: "快进合并"

图 1 · 快进合并：main 没有新提交，指针从 A 直接平移到 D，不产生合并提交。

gitGraph commit id: "A" branch feature checkout feature commit id: "B" checkout main commit id: "C" merge feature id: "三方合并"

图 2 · 三方合并：main 与 feature 都从 A 各自前进，需要合并提交来衔接两组修改——冲突的温床。

shell
git checkout main
git merge feature        # 若无分叉 → fast-forward；若有分叉且可自动合并 → merge commit；否则 → 冲突

# 强制生成合并提交（即使可快进也走三方合并，保留分支历史）
git merge --no-ff feature
★

快速判断口诀：「只有两边都在共同祖先之后改过，Git 才需要动用三方合并；也只有三方合并这一种还可能遇到冲突。快进永远不会冲突。」

小节冲突的成因与冲突标记含义两边都改了同一处，Git 无法替你决定

三方合并时，Git 以合并基础（merge base，即共同祖先）为起点，把 ours（你现在所在的 HEAD 分支）与 theirs（被合并进来的分支）各自产生的差异叠加起来。只要两边改的是不同文件或同一文件的不同部分，Git 都能自动合并。

  • 冲突（conflict）只在一种情形发生：两个分支都修改了同一个文件里相同的行（或一方修改、另一方删除了该文件）。Git 不知道该保留哪份，只好把决定权交回给你。
  • 一旦冲突，Git 会暂停合并，修改工作区里的文件并写入冲突标记，等你手动处理后再次提交。
shell
# 合并产生冲突时的终端输出
$ git merge feature
Auto-merging src/app.js
CONFLICT (content): Merge conflict in src/app.js
Automatic merge failed; fix conflicts and then commit the result.

发生冲突后，打开那个文件会看到如下的冲突标记 conflict markers：

src/app.js
function greet(name) {
<<<<<<< HEAD
  console.log("你好，" + name);
=======
  console.log("Hello, " + name);
>>>>>>> feature
}

每个标记的含义：

标记含义说明
<<<<<<< HEADours · 当前分支这侧从该行到 ======= 之间，是你现在的分支（HEAD）保留的内容。
=======分界线把上方的 ours 与下方的 theirs 隔开。
>>>>>>> featuretheirs · 待合并分支这侧从 ======= 到该行之间，是被合并进来的分支（这里叫 feature）的内容。
!

不要直接提交：文件里残留 <<<<<<<、=======、>>>>>>> 就提交，等于把「未决定的冲突」当成最终代码写进了版本库。解决的第一步永远是把标记删掉、留下最终想要的代码。

i

更容易看清冲突：用 git status 会列出「both modified」的文件；用 git diff 可查看差异；也可以让编辑器或 git mergetool 高亮两边内容。

小节解决冲突的标准流程：编辑 → add → commit三步收尾，外加 abort / continue

解决冲突只有三步：① 编辑文件消除标记 → ② git add 暂存 → ③ git commit 提交。整个过程仍是普通的 Git 提交流程，只是多了一步「人类做决定」。

  1. 编辑（edit the file）：打开冲突文件，删掉三个标记，保留你真正想要的那一段代码（可以是 ours、theirs，或手动合成一份更好的）。对每个冲突文件都这么做。
  2. 暂存（git add）：把处理完的文件加入暂存区，告诉 Git「这个文件我已解决」。用 git add <file>。
  3. 提交（git commit）：所有冲突都解决并 add 后，执行 git commit。它会带上 Git 生成的合并提交信息。
shell
git status                       # 查看哪些文件冲突（both modified）
git add src/app.js               # 步骤②：把解决好的文件标记为已解决
git commit                       # 步骤③：完成合并，生成合并提交

# 或者用 --continue 直接继续（等价于跳过手动 commit 的第二问）
git commit --no-edit             # 若想直接用默认的合并提交信息
shell
# ===== 后悔药：放弃这次合并 =====
git merge --abort                # 回到合并开始前的状态，丢弃所有冲突改动

# ===== 解决后，用 --continue 继续 =====
git add src/app.js
git merge --continue             # 打开编辑器让你确认合并提交信息，然后提交

两条「终止/续跑」命令的对照：

命令作用什么时候用
git merge --abort彻底放弃本次合并，把工作区、暂存区还原到合并前想反悔、冲突太多、先退回再说。
git merge --continue确认所有冲突已解决且已 add，继续完成合并并提交全部加完 git add 后，用它代替手打 git commit。
★

一条铁律：git add 是「我已解决这个文件」的确认，git commit 是「这次合并完成」的收尾。只要还有任何文件没 add，git commit 就不会以合并提交终结。

!

小心：合并进行中（包括冲突中）不要乱切换分支、不要 git reset --hard，否则可能丢掉尚未合并的工作区改动。拿不准就先 git merge --abort。

小节合并策略与常用工具--no-commit、ours/theirs、mergetool

合并并不是只有「冲突就手动改」一种玩法。根据场景，可以调整合并如何执行（策略）与要不要立刻提交，还能借用冲突标记里的 ours/theirs 直接选取一侧，或调用可视化工具。

shell
git merge --no-commit feature      # 合并但不自动提交，便于先检查再 commit
git merge --no-ff feature          # 强制走三方合并、生成合并提交（即使能快进）
git merge -s ours feature          # 合并策略：无脑保留当前分支内容，丢弃对方改动
git merge -s recursive -X ours feature    # -X 偏好：遇冲突时直接选 ours 這侧
git mergetool                       # 打开可视化工具逐文件解决冲突

常用策略与偏好速查：

语法作用典型场景
--no-commit只把合并结果放到工作区/暂存区，不生成提交想 review 完改动再提交。
--no-ff禁止快进，强制产生一个合并提交想保留特性分支的完整历史形状。
-s ours整个合并结果直接采用当前分支，丢弃对方确定以本分支为准（如已先合过对方）。
-X ours / -X theirs仅对发生冲突的部分自动选择某一侧，其余仍自动合并小冲突想省事，「选我 / 选它」。
mergetool调用图形化/三方对比工具逐文件解决冲突复杂、想看左右并排对比。

注意 -s ours 与 -X ours 的区别：前者是整份合并结果都取自己，后者是只在冲突点选自己、其余照常自动合并。--ours/--theirs 作为 git checkout 的修饰符则是「在工作区直接取某一侧的版本」——例如想整个文件都要对方的版本：

shell
git checkout --ours src/app.js     # 整个文件用当前分支（HEAD）版本
git checkout --theirs src/app.js   # 整个文件用被合并分支版本
git add src/app.js                 # 选完仍要 add + commit 才完成合并
i

界外提示：合并策略与 ours/theirs 是「偷懒选项」，适合确信该取哪侧时用；一旦两边都写了关键代码，粗暴选一边会默默丢弃别人的工作。复杂冲突仍建议打开文件逐段人工合成。

!

切勿把冲突带上线：项目很常见的一道 CI 红线就是「禁止提交带 <<<<<<< 标记的文件」。解决到 0 个冲突、删干净所有标记，再 git add、git commit。

▲ 进阶挑战

  • 故意制造一次冲突：新建两个分支，分别改动 README.md 的同一行，然后合并。观察冲突标记，练习用「编辑 → add → commit」解决，并用 git log --graph 确认产生了合并提交。
  • 重现一次 git merge --abort：制造冲突后先 abort，确认工作区回到合并前状态，再重新合并解决一次。
  • 对比 -s ours 与 -X ours：用同一个冲突场景各试一次，说明「整份取自己」与「只在冲突点取自己」的结果差异。
  • 用 git merge --no-commit 合并一个不会冲突的分支，先查看暂存区改动，再手动 git commit，体会它与默认自动提交的不同。
