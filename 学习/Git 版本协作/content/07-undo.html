GIT · 协作

撤销、回退与恢复

代码改错了、提交错了、甚至误删了提交，别慌。这一节讲清楚 reset / revert / restore / checkout / reflog 五把「后悔药」分别作用在哪一层、什么场景该用哪个，让你既不丢内容，也不把团队的共享历史搞乱。

✓本节学习目标

  • 学完后，你能说清 git reset 的 --soft / --mixed / --hard 三档各自动了哪一层（HEAD 指针、暂存区、工作区）。
  • 学完后，你能区分「撤销已推送提交」和「改写本地未推送提交」，并正确选择 revert 或 reset。
  • 学完后，你能用 git restore 恢复文件、用 git checkout 切换分支，并说清二者与 reset/revert 的区别。
  • 学完后，你能用 git reflog 找回被 reset --hard 或删分支后「看似丢失」的提交。
Prerequisites · 前置知识

会用命令行、熟悉 add / commit / push；理解工作区（working tree）、暂存区（index/stage）、仓库（HEAD 提交）三层结构；知道分支与 HEAD 指向的含义。

小节git reset 的三档（--soft/--mixed/--hard）与 HEAD~ 引用

一句话：git reset 的本质是把当前分支的 HEAD 指针移回某个目标提交（通常用 HEAD~ 表示「上一个提交」），移动完之后「还要不要重置暂存区、要不要重置工作区」由后面这个 --<mode> 决定。整个它只在你本地生效，几乎总要改写（rewrite）历史，所以只适合还没推送出去的提交。

先记住 Git 的三个「区」：工作区（你看到的实际文件）、暂存区（index，git add 放进去的快照）、仓库（HEAD 指向的最新提交）。reset 的每一档就是「把魔爪伸到哪一层」。

shell
# 常见的 HEAD 引用
git reset HEAD~1            # 回到上一个提交（默认 --mixed）
git reset HEAD~2            # 回到再往前一个
git reset HEAD^             # HEAD 的父提交（合并提交时 ^ 指第一父）
git reset --soft HEAD~1     # 只移动 HEAD 指针
git reset --mixed HEAD~1    # 移动 HEAD + 清空暂存区（改动保留在工作区）
git reset --hard HEAD~1     # 移动 HEAD + 清空暂存区 + 丢弃所有工作区改动！
命令档位移动 HEAD清空暂存区（index）改动工作区那次提交的改动去哪了
--soft ✔✘✘ 仍留在暂存区，等你重新 commit（改动已暂存，最「轻」）
--mixed（默认） ✔✔✘ 回到工作区、变成未暂存，需要重新 add 再提交
--hard ✔✔✔ 彻底丢光（连同工作区里未提交的改动一起），工作区回到目标提交的样子
引用写法含义（HEAD 引用 & reflog）
HEAD当前分支指向的最新提交
HEAD~ / HEAD~1当前提交的父提交（第一父提交），即「上一个提交」
HEAD~2往前数第 2 个提交（祖父提交）
HEAD^当前提交的第一父提交；合并提交时可写 HEAD^2 指第二父提交
HEAD@{1}reflog 中「上一次」HEAD 的位置，常用来找回被 reset --hard 甩掉的提交
★

这样记：没写档位时默认 --mixed；--soft 只「拔指针」，--mixed 再「吐回暂存区」，--hard 最后「连工作区一起清」。越往右破坏力越强——如果你只是想把几个提交「并成一个再提交」，用 --soft 最安全；想彻底抹掉一个错误的本地提交且不保留改动，才考虑 --hard。

!

易错警告：--hard 会丢弃未提交的工作区改动。它把工作区直接重置为目标提交的状态，你「改了还没 add/commit」的内容会被永久清掉。如果工作区里有还没保存的改动，先 git stash 暂存起来，或用 --soft/--mixed 保留改动，再决定要不要丢。并且——reset --hard 之后提交看似「没了」，但 reflog 往往还能救回来（见最后一小节）。

小节用 git revert 撤销已推送的提交生成新提交

一句话：git revert 不是「把历史删掉」，而是「用一个新的提交，把某个提交所做的工作反向抵消掉」。它会计算目标提交的「反向补丁」（inverse patch），把改动反过来，然后生成一个全新的提交。原来的提交仍然躺在历史里，只是被这次新提交「抵消」了。

这正是它与 reset --hard 最大的区别，也决定了它的适用场景：revert 不重写历史，而是向历史里「追加」内容，所以对已经推送、别人可能已经拉取的分支是安全的。

shell
# 撤销最近一个提交，生成一个新提交（会弹出提交信息编辑器）
git revert HEAD

# 撤销指定哈希的提交
git revert abc1234

# 撤销一个范围（多个提交）
git revert HEAD~2..HEAD

# 只把"撤销改动"放到工作区/暂存区，并自动生成提交，但不弹出编辑器
git revert --no-commit HEAD
git revert --no-edit HEAD
★

记住：revert 生成的是「新的提交」，历史没有消失，只是多了一个反向提交。这对共享分支（已经 push 的 main 或队友在用的分支）是唯一的正确选择——因为改写共享历史会让所有同事的推送和拉取产生冲突。

!

易错警告：不要用 reset --hard 去撤销已经推送、别人已拉取的提交。一旦你本地 reset --hard 把历史改了再强推（push --force），队友好不容易拉下来的提交会丢，团队可能各自为政、产生一堆合并冲突。已推送的「错误提交」请一律用 git revert 生个新提交来抵消；只有你自己还没推送的提交，才适合用 reset 改写本地历史。

补充：revert 也不是「删除历史」——它只是人为制造一个反方向的提交。如果目标提交后来又被别的提交基于它修改过，revert 可能遇到冲突，需要你手动解决后再提交。这也是「已推送的历史尽量不要乱动」的一个体现。

小节git restore 与 git checkout 恢复文件/分支恢复 vs 回退

一句话：git restore 是恢复「文件内容」，git checkout 主要是「切换分支」。当你改乱了某个文件、想让它回到上次提交的样子，用的是 restore；当你想到另一个分支去干活，用的是 checkout。老版本 Git 里这两件事都用 git checkout -- / git checkout <branch> 来表达，很容易混淆，所以新版拆出了更清晰的 restore。

shell
# 丢弃工作区中对 file.txt 的未提交改动（用暂存区的版本覆盖）
git restore file.txt

# 把文件从暂存区"撤销回工作区"（取消 git add，但改动不丢）
git restore --staged file.txt

# 从指定提交恢复文件内容
git restore --source=HEAD~1 src/app.js

# 旧写法：等价于 git restore file.txt
git checkout -- file.txt

# 切换分支（不是恢复文件！）
git checkout other-branch
git switch other-branch

注意 restore 的两种行为：不带 --staged 时它从暂存区恢复文件（丢弃你对工作区文件的未提交修改）；带 --staged 时它把文件从暂存区退回到工作区（把它变成「已修改未暂存」，好让你重新审视再提交）。两者都不生成新提交、都不改写历史。

命令典型语义生成新提交改写历史最常用场景
git reset --hard <c> 把当前分支 HEAD 强行移回目标提交 否✔ 是 撤销本地未推送的错误提交，整段抹掉
git restore <file> 丢弃某文件的工作区改动（回到暂存区/上次提交） 否否 改乱了单个文件，想把它「恢复如初」
git checkout <branch> 切换分支（git checkout -- file 才是恢复文件） 否否 换分支干活；-- 后的文件是旧式恢复文件
git revert <c> 用新提交反向抵消某个提交 是否（追加） 撤销已推送的提交，不破坏共享历史
⚠

别搞混：git restore 只管「文件」，git checkout 既可切分支也可恢复文件。若你只想撤销工作区改动而不想动历史，restore 是首选；若目标是要把整个分支/HEAD 移回去，才用 reset。它们虽都叫「撤销」，但作用对象和破坏力完全不同。

小节用 git reflog 找回误删的提交最后一道保险

一句话：git reflog（reference log）记录了你本地所有引用（HEAD、各分支、tag）每次移动的「日志」，哪怕你 reset --hard 把某个提交「删」了，它的哈希仍会留在 reflog 里。它是你本地的「操作流水账」，专门用来在误操作之后把历史找回来。

shell
# 查看本地 HEAD / 分支引用的移动日志（默认 90 天内）
git reflog

# 输出示例（每行：哈希  HEAD@{序号}  操作描述）
# abc1234 HEAD@{0}: reset: moving to HEAD~2
# 9f8e7d6 HEAD@{1}: commit: fix: 修正登录接口超时
# 3c2b1a0 HEAD@{2}: commit: feat: 新增导出功能

# 找回被 reset 掉的提交：按上次的 HEAD 位置恢复
git reset --hard HEAD@{1}

# 直接按 reflog 里看到的哈希恢复
git reset --hard 9f8e7d6

看懂几行即可：HEAD@{0} 是最新的状态，HEAD@{1} 是上一次。若你刚 reset --hard HEAD~2，被甩掉的提交通常就在 HEAD@{1} 或更早。用 git reset --hard <该哈希> 就能把头指针重新指回去，那个「丢失」的提交连同它后面的历史就都回来了。

★

核心结论：reflog 是「本地」的保险，只在你这台机器的这个仓库里有效，不会推到远程，别人看不到。它默认保留 90 天（gc.reflogExpire 可调）。所以：commit 随手记、reflog 常看看；一旦发现 reset 错了，第一时间用 reflog 找回，别急着放弃。

!

易错点：reflog 对「未提交的工作区改动」无能为力。reflog 只记录已提交的历史移动。你用 reset --hard 丢掉的未 git add / git commit 的改动，reflog 救不回来——那部分内容只能靠 git stash 或编辑器/文件系统里的恢复。所以把「关键改动随手提交 + 临时的先 stash」当成习惯，才能最大化保住你的内容。

顺带一提：git fsck --lost-found 也能列出悬空对象（dangling commits），是 reflog 之外的另一条找回路子，但 reflog 是最快最直观的入口。
