GIT · 协作

工作区、暂存区与版本库

Git 所有的秘密都藏在三个区域里：工作区、暂存区、版本库。搞懂它们之间 add → commit 的流转，就抓住了 Git 的核心模型，也能顺手看懂 git status 的每一行。

✓本节学习目标

  • 学完后，你能准确说出 Git 的三大区域（工作区 / 暂存区 / 版本库）各自存放什么，并画出它们的数据流向。
  • 学完后，你能区分 blob / tree / commit 三种对象，以及 HEAD 与分支引用分别指向谁。
  • 学完后，你能正确使用 git add 与 git commit 让文件从工作区流入版本库，并说清 -m 与 -am 的区别与陷阱。
  • 学完后，你能通过 git status 判断文件处于 untracked / staged / modified 哪种状态。
  • 学完后，你能解释为什么 Git 要把「暂存」和「提交」分成两步，并举出只 add 不 commit 的实用场景。
Prerequisites · 前置知识

会用命令行（能进目录、建文件）；知道什么是文件与目录；学完本系列第一节 git-basics，理解 git init 会在项目里生成隐藏的 .git 版本库存放。

Learning Content · 学习内容

01三大区域模型
（工作区 / 暂存区 / 版本库）

核心三大区域模型Working Directory / Staging Area / Repository

回想一下，你在项目里写代码、改文件，这些改动一开始并不属于 Git。Git 把你的整个项目划分成三个区域，文件会沿着一条固定的路径在它们之间移动：

  • 工作区（Working Directory）：你在编辑器里看到的、能直接编辑的真实文件目录。这里的改动 Git 「暂时不知道」。
  • 暂存区（Staging Area，也叫 Index）：一个临时的「待提交清单」。这里登记的是你即将要提交进去的内容，本质是 .git/index 这个文件。
  • 版本库（Repository）：即仓库对象数据库，藏在 .git 目录里。只有回到这里的文件才会被 Git 真正存档、可追溯。

下面的流程图把三条「管道」一次看清：

flowchart LR
  F["你编辑文件
File on disk"] --> W["工作区
Working Directory"]
  W -->|"git add"| S["暂存区
Staging / Index"]
  S -->|"git commit"| R["版本库
Repository (.git)"]
  R -->|"git checkout / reset"| W
  R -.->|"git log"| H["历史记录
可回退、可协作"]
★

核心要点：文件想进入 Git 的历史，必须走完 工作区 → add → 暂存区 → commit → 版本库 这条完整链路。跳跃中间任何一步，都到不了版本库。

进阶Git 对象与引用blob / tree / commit，HEAD 与分支

版本库里的历史不是一堆「文件快照文件夹」，而是由对象（objects）与引用（references）组成的有向图。理解它们，才能看懂 commit 到底存了什么、HEAD 又是怎么「知道当前在哪」。Git 用 SHA-1 哈希（一串 40 位十六进制数）为每个对象编号，作为它的唯一地址。

对象存什么作用
blob某一个文件的内容快照（二进制数据）记录「这个时刻这份文件长什么样」，不含文件名
tree一个目录的清单（文件名 → blob/tree 的映射）把 blob 组织成目录树，代表某一刻的整个文件结构
commit顶层 tree 的哈希 + 父提交 + 作者 + 时间 + 提交消息一次「版本」，指向一个完整快照，并串起历史链条

再来看引用：

  • 分支（branch）：一个指向某次 commit 的可移动指针（如 main、develop）。新提交会让它自动前移。
  • HEAD：一个「当前所在位置」的指针，通常指向当前分支（HEAD → main → 某 commit）。HEAD 决定了 commit 会加到哪条分支上。
!

易错点：很多人以为「分支就是一串 commit」。其实分支只是一个指针，真正装历史的是 commit 及其链式引用；分支只是帮你「记住」某个 commit，方便来回切换。HEAD 也有「分离」（detached）状态，进阶后你会遇到。

实操git add 与 git commit 的正确流程含 -am / -m 的坑

把「暂存」与「提交」拆成两步，是 Git 最重要的设计。你先用 git add 把想提交的改动挑出来放进暂存区，再用 git commit 把它们一次性定格成版本。这样你可以在一次提交里只挑某几个文件，或者先攒一批再统一提交。

shell
# 1) 把某个文件放进暂存区（staging）
git add README.md

# 2) 把当前目录（含子目录）里“新增/修改/删除”的文件改动都暂存
git add .

# 3) 提交暂存区内容，形成一次版本（commit）
git commit -m "docs: 添加项目说明"

# 4) 一步到位：只对“已被 Git 追踪过、这次只改了内容/删除了”的文件，
#    自动暂存并提交（注意：不会加入“全新的未跟踪文件”！）
git commit -am "fix: 修复登录校验逻辑"
命令会暂存不会暂存
git add <file>指定的一个文件其它未指定的改动
git add .当前目录（含子目录）里所有新增/修改/删除的改动仓库其它顶层路径的改动（跨目录请用 git add -A 或 git add -u）
git commit -am "…"已被追踪、且有修改/删除的旧文件全新的未跟踪文件（untracked）——最容易踩的坑
✕

高频错误：新建了一个文件后嫌麻烦，直接 git commit -am "xx"，结果提交里根本没有这个新文件——因为 -a 只处理「已被追踪」的文件。新文件必须先 git add 一次。凡是用 -am 提交前，先跑 git status 看一眼有没有遗漏的 untracked 文件。

观察用 git status 观察文件状态untracked / staged / modified

学会 git status，你就有了「透视三个区域」的眼睛。它会告诉你每个文件当前落在哪个状态，先确认再动作，是避免误操作的好习惯。

shell
git status            # 详细状态（推荐新手看这个）
git status -s         # 精简版：一行一个文件，左侧“暂存区”列、右侧“工作区”列

# 常用结果速记：左列 = 暂存区状态，右列 = 工作区状态
#   ??  = 未跟踪（untracked，还没 add 过）
#   A   = 已暂存新增（staged，待提交）
#   M   = 已修改（M 在左列=已暂存；M 在右列=改后未暂存）
状态英文叫法含义（文件在哪）下一步
全新文件untracked在工作区，Git 尚未追踪，不属于任何版本git add 纳入追踪
已暂存staged改动已进暂存区，等待提交git commit 定格
改后未暂存modified文件已追踪，但改后又没 addgit add 再提交
★

核心要点：一个文件可能同时「既有已暂存的新内容、又有改后未暂存的内容」——此时它横跨暂存区与工作区两侧。git status -s 左右两列就是捕捉这种「夹层」状态的利器。
