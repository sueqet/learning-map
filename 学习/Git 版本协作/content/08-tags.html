GIT · 协作

标签与版本发布

学会用 tag 把一个 commit 固定成可追溯的版本节点：打、看、删、推送标签，并按 v1.0.0 这样的版本号规范对外发布。

✓本节学习目标

  • 学完后你能说清 tag 是绑定到某个 commit 的固定引用，不会随着分支提交而移动。
  • 学完后你能区分轻量标签与附注标签，并指出附注标签额外保存了 tagger、日期和消息。
  • 学完后你能用 git tag 创建、查看、删除标签，并用 git push --tags 一次性推送。
  • 学完后你能按版本号规范（如 v1.0.0）给发布节点打标签，并简要说明 semver 的含义。
  • 学完后你能正确删除并同步远端标签，而不会误删分支或提交。
Prerequisites · 前置知识

会用命令行终端；理解 commit 与 branch 的概念；能完成一次常规的「改 → commit → push」流程。如果你还不熟悉分支，建议先学「分支与合并」。

Learning Content · 学习内容

08标签与版本发布

小节标签是什么、为什么用于版本发布tag 是固定引用

在 Git 里，tag（标签）是绑定到某一个具体 commit 的引用。它与 branch 最大的不同在于：branch 会随着新提交自动向前移动，而 tag 一经创建就固定不动，始终指向你打标签那一刻的提交。正因为这种「钉死」的特性，tag 天然适合用来标记版本发布——当你对外发布 v1.0.0 时，希望别人能精确地拉取到「发布时的这一版代码」，而不是模糊的「最新代码」。

  • 可追溯（traceable）：每个 tag 指向一个准确的 commit，用 git checkout v1.0.0 就能还原当时的代码。
  • 不可变基线（immutable milestone）：发布后不应再随意改动这个 tag，否则「v1.0.0」的含义就变了。
  • 语义化：配合版本号（如 v1.0.0），人类一眼就能读懂这是主版本、次版本还是补丁版本。

★

核心要点：tag 是指向单个 commit 的固定引用，是「版本发布」的锚点；branch 会移动，tag 不会。

!

易混点：tag 和 branch 放在同一张大图上，一个在动、一个不动。把「分支」理解成不断前进的指针，把「标签」理解成钉在墙上的一枚图钉。

小节轻量标签 vs 附注标签-a / -m，含 tagger/日期

Git 支持两种标签：轻量标签（lightweight tag）和附注标签（annotated tag）。轻量标签只是一个指向 commit 的简单指针（本质就是一个引用了 commit 的引用文件），除了名字外不携带任何额外信息，也没有独立对象；而附注标签则会在对象库里新建一个完整的 tag 对象，记录打标签的人（tagger）、时间戳和一条可选的消息（message）。

对比项轻量标签（lightweight）附注标签（annotated）
创建命令git tag v1.0.0git tag -a v1.0.0 -m "发布 v1.0.0"
存储对象仅一个指向 commit 的引用独立 tag 对象（含 tagger/date/message）
是否带签名否可用 -s 加 GPG 签名
适用场景临时标记、个人快速标注正式版本发布、需要作者与日期信息
查看详细信息仅地址git show v1.0.0 能看到作者与消息
shell
# 附注标签：推荐用于正式发布（含作者、时间、消息）
git tag -a v1.0.0 -m "发布 v1.0.0：首个稳定版"

# 查看某个附注标签的详细信息（能看到 tagger / 日期 / 消息）
git show v1.0.0
★

核心要点：正式版本发布请使用附注标签（-a -m），因为它记录了「是谁、在什么时候、为什么打这个标签」；这些信息对你追溯发布历史至关重要。

✖

易错点：轻量标签没有独立的 tag 对象，因此 git show v1.0.0 只会展示它所指向的那个 commit 的改动，而看不到任何「标签作者 / 标签消息」。别把它当附注标签用。

小节打标签、查看、删除与推送git push --tags

掌握了概念后，实际只用到几条命令。最值得记住的一点是：默认 git push 不会推送标签，需要用 git push --tags 一次性把本地所有标签推上去（或用 git push origin v1.0.0 推送单个）。

shell
# 1) 打标签（默认打在当前 HEAD 指向的 commit 上）
git tag v1.0.0                    # 轻量
git tag -a v1.0.0 -m "发布 v1.0.0"  # 附注（推荐）

# 2) 查看标签
git tag                            # 列出所有标签
git tag -n                         # 带一行消息列出
git show v1.0.0                    # 看单个标签详情

# 3) 推送标签到远端
git push origin v1.0.0             # 推送单个标签
git push --tags                    # 推送所有标签

# 4) 删除标签（本地 + 远端）
git tag -d v1.0.0                         # 删除本地标签
git push origin :refs/tags/v1.0.0         # 删除远端标签
git push origin --delete v1.0.0           # 等价写法
操作命令说明
创建标签git tag v1.0.0打在当前 commit 上
创建附注标签git tag -a v1.0.0 -m "消息"推荐
查看所有标签git tag按字典序列出
查看标签详情git show v1.0.0附注标签显示作者/日期/消息
推送全部标签git push --tags必须显式，默认不推
推送单个标签git push origin v1.0.0精确推送
删除标签git tag -d v1.0.0只删本地
删除远端标签git push origin --delete v1.0.0同步远端
!

易错点：git tag -d 只删除本地标签；若不执行远端的删除命令，远端仍会保留该标签，别人还能拉到。发布过的标签应避免删改。

★

核心要点：标签不会随 git push 自动上传。想共享标签，必须用 git push --tags（全推）或 git push origin <tagname>（单个推）。

小节版本号规范与最佳实践v1.0.0 / semver

给版本打标签时，人们习惯遵循语义化版本（Semantic Versioning，semver）：版本号形如 主版本.次版本.修订号（MAJOR.MINOR.PATCH）。每条规则都有明确含义，改动它的场景对应不同的升级级别。

段位示例何时递增
MAJOR（主版本）从 v1.0.0 到 v2.0.0存在不向下兼容的接口/行为变更
MINOR（次版本）从 v1.2.0 到 v1.3.0新增功能且向后兼容
PATCH（修订号）从 v1.2.0 到 v1.2.1仅修复 Bug、不新增功能
  • 前缀约定：Git 标签常写作 v1.0.0（带 v 前缀），而语义化版本号本身是 1.0.0。团队里保持一致即可，v 前缀是社区最常见的习惯。
  • 发布锚点：在「发布候选」那一刻，把 tag 打到要发布的那个 commit 上，之后就不会再动。
  • 为发布打附注标签：用 -a 记录作者与发布说明，方便回溯「这个版本是谁、何时、为何发布」。
  • 命名清晰：避免自定义花哨标签（如 great-release），以语义化版本号为准，机器才好解析。
★

核心要点：语义化版本让升级级别「一看就懂」——主版本破坏性变更、次版本新增功能、修订号只修 Bug。打完标签再发布，别人才能精确复现你的版本。

✖

易错点：不要在已发布的 tag 上继续 commit 或改标签——那会让「v1.0.0」这个稳定版本指向不同代码。需要修复就开新版本（如 v1.0.1）。

▲ 进阶挑战

  • 在本地一个已有提交历史的仓库里，为「最近一次提交」打一个附注标签 -a v1.0.0 -m "..."，再用 git show 验证能看到 tagger、日期与消息；也打一个轻量标签，对比 git show 的差异。
  • 把本地所有标签推送到远端（git push --tags），然后在另一台机器上用 git fetch --tags 拉全，再 git checkout v1.0.0 回到发布时的代码，验证可复现。
  • 模拟一次「误打标签后删除」：先创建一个标签，再本地删除它并同步删除远端，确认分支与提交都毫发无损。
