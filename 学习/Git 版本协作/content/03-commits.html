GIT · 协作

提交与历史查看

提交历史就是一条由一串 commit 对象用 parent 指针串起来的时间线（timeline）。这一节你将学会用 log、diff、show、blame 把它读出来、看清每次改动是什么、由谁什么时间做的，并读懂/写出可回溯的提交信息。

✓本节学习目标

  • 用 git log --oneline 一眼看出一条紧凑的历史列表，说出每条提交的短哈希与主题。
  • 用 git log --graph 读懂分支与合并形成的提交族谱（commit graph）。
  • 在工作区 / 暂存区 / 上次提交三者之间，用对应的 git diff 变体做对比。
  • 用 git show 查看单个提交，用 git blame 逐行定位某行代码是谁、哪个提交引入的。
  • 用 %h/%an/%s 等占位符自定义 git log 输出，并说出规范提交信息（commit message）的结构。
Prerequisites · 前置知识

会用命令行（cd、ls、会看帮助）；理解 Git 三个区域：工作区（working tree）、暂存区（staging/index）、HEAD 提交（对应上一节）；会用 git add / git commit 创建提交。

01提交与历史查看
把一条 commit 时间线变成能读懂的故事

1git log 与历史先理解：历史是一串 commit 对象

先牢牢记住这个核心概念：提交历史（history）不是一堆文件副本，而是一条由 commit 对象组成的链表。每一个 commit（提交对象）本身几乎不装文件内容，它只保存：一次完整快照对应的 tree（树对象）引用、author/committer（作者/提交人）、时间戳、一段 message（提交信息），以及指向上一个提交的 parent（父提交）引用。正是这些 parent 引用把一个个 commit 串成了历史。

所以看历史，本质是在沿 parent 链从新到旧遍历这些 commit 对象。git log 就是干这个的——默认把当前分支上的提交按时间倒序列出来。

  • git log：完整列出每条提交的哈希、作者、日期、信息，条目多时很冗长。
  • git log --oneline：每条压缩成一行——短哈希 + 主题，日常最常用。
  • git log -3：只看最近 3 条。
  • git log --author="xiao"、--since：按人、按时间过滤。
shell
# 最常用——一条一目了然的历史
git log --oneline

# 带上分支/标签装饰，看清 refs 指向谁
git log --oneline --decorate -5

# 看最近 3 条完整信息
git log -3

# 只看某个作者、某段时间之后的提交
git log --author="xiao" --since="2 weeks ago"

当分支出现合并（merge）时，历史会真的"分叉再汇合"。用 --graph 可以把它画成 ASCII 族谱；配合 --oneline --decorate --all 则能同时看到所有分支。下面这张 gitGraph 图，就是你运行 git log --graph --oneline --decorate --all 后看到的东西的"放大版"。

```mermaid gitGraph commit commit branch feature/login commit commit checkout main commit merge feature/login commit ```
★

核心要点：每一个 commit 用一个约 40 位的 SHA-1 哈希唯一标识；--oneline 只显示前 7 位，足够在项目里定位。看历史时记住"history = 一串 commit 对象"，后面 show/blame 就都顺理成章了。

2git diff 对比改动工作区 / 暂存区 / 提交之间

Git 里"改动"存在三种状态，所以 git diff 的默认行为只对比其中相邻的两个，选错就是白比。搞清它对比的双方，是本节重点。

命令对比的双方典型用途
git diff工作区 ↔ 暂存区想看我还没 add 的改动
git diff --staged
（= --cached）		暂存区 ↔ HEAD 提交想看我已 add、但还没 commit 的改动
git diff HEAD工作区 ↔ HEAD 提交综合看所有未提交改动（暂存 + 未暂存）
git diff A..B提交 A ↔ 提交 B两个提交/分支之间的完整差异
shell
# 1. 正在改文件，还没 add——看未暂存的改动
git diff

# 2. 已经 git add 了，还没 commit——看暂存区与上次提交的差异
git diff --staged

# 3. 想一次性看所有未提交改动
git diff HEAD

# 4. 简洁版：只列出文件名 / 只统计增删行数
git diff --name-only
git diff --stat

# 5. 对比两个分支（提交）之间的差异
git diff main..feature/login
!

易错点：git diff 与 git diff --staged 是两个不同的比较。--cached 与 --staged 等价；提交前建议务必用 git diff --staged 先确认"将要提交的内容"正是你想要的，避免把临时文件也带进去。

3git show 与 git blame看单个提交 + 逐行找作者

历史是一串 commit 对象，那么"某个 commit 到底改了什么"就要看它的快照差异。git show 就是"打开一个 commit"的命令：它同时展示这个提交的元信息（作者、时间、信息）和它对 parent 的 diff。

  • git show：默认展示 HEAD（最近一次提交）。
  • git show <hash>：展示指定提交；哈希只要前几位能区分即可（多用 --oneline 拿到的短哈希）。
  • git show --stat：只看它改了哪些文件、增删行数。

而 git blame 是"逆向"的：给定一个文件，它逐行标注每一行最后被哪个 commit 修改、由谁在什么时候写的。这是回答"这行谁写的 / 上个版本为什么长这样"的利器。

shell
# 看最近一次提交（含 diff）
git show

# 看某条提交改了什么、谁提交的
git show 1a2b3c4

# 只统计改动的文件与行数
git show --stat a1b2c3d

# 逐行追溯某个文件的每一行来自哪个提交/作者
git blame src/login.ts

# 只看第 40 到 60 行
git blame -L 40,60 src/login.ts
★

用途区分：git show 回答"这个 commit 改了什么"（以提交为中心），git blame 回答"这行代码是谁改的"（以文件/行为中心）。两者搭配，定位"哪个提交引入了 bug"非常高效。

4格式化提交信息 & commit 规范%h/%an/%s — 让输出可读、可机器处理

默认的 git log 输出字段多、堆在一起。用 --pretty / --format 配合占位符（placeholders）可以定制每一行。这些占位符就是《Git 版本协作》里最常出现的一组英文缩写，务必记住几个核心的。

占位符含义例
%h短哈希（short hash）1a2b3c4
%H完整哈希1a2b3c4...(40位)
%an作者名（author name）xiao
%ae作者邮箱（author email）xiao@dev.me
%ad作者日期（author date）2024-05-01
%cn提交人（committer name）xiao
%s主题（subject）feat: 支持邮箱登录
%d引用装饰（refs/decorations）(HEAD -> main)
shell
# 输出：短哈希 | 作者 | 日期 | 主题
git log --pretty=format:"%h | %an | %ad | %s" --date=short

# 一条简洁的自定义一行 log
git log --pretty="%h %an %s"

# 预设样式：oneline / short / medium / full
git log --pretty=oneline
git log --pretty=short

历史可读性的另一半在于提交信息本身。团队里常约定 Conventional Commits 风格，格式为 type(scope): subject，其中 type 是动作类型，scope 是影响范围，subject 用一句话说清"做了什么"。

shell
# 规范的提交信息：类型(范围): 一句话主题
feat(auth): 支持邮箱登录

# 正文（可选）：解释为什么这么改
- 新增 OAuth 回调
- 复用现有用户体系

# 关联工单
Closes #123

常见 type：feat 新功能、fix 修 bug、docs 文档、style 格式、refactor 重构、test 测试、chore 杂项。

!

为什么规范重要：历史是一串 commit 对象，而 git log --format 能按 %s 过滤/统计。若大家只写 update、asdf、fix 这类 meaningless 信息，历史就失去检索价值。规范让历史和 git log --grep、changelog 生成都成为可能。

✕

危险操作：提交信息是"写给未来的自己和其他协作的人看"的。已经推到远程并共享的提交，不要随意用 git commit --amend 或 git rebase 去改写——它会改变 commit 的哈希（rewrite history），导致别人基于旧哈希的本地历史失配、产生冲突。改写只应发生在尚未共享的提交上。

⌕

  • 在一个真实项目里跑 git log --graph --oneline --decorate --all，用一张截图或文字描述你最复杂的一条合并（merge）族谱长什么样。
