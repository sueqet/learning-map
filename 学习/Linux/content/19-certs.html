LINUX · 证书

证书与信任自签

当 HTTPS 站点用的是自签证书时，默认不被系统信任、会报证书告警。这一节教你读懂系统根证书存储、用 openssl s_client 抓取证书，并按 update-ca-trust 的标准流程把自签证书正确地加入信任库——而不是去改会被重建的 ca-bundle。

✓本节学习目标

  • 学完后，你能说出系统根证书存储的默认路径，并分清 Debian/Ubuntu 系与 RHEL 系的集中信任目录与配套命令。
  • 学完后，你能用 openssl s_client 从任意 HTTPS 端点导出其自签证书，并保存为 PEM 文件。
  • 学完后，你能把自签证书放入 /etc/pki/ca-trust/source/anchors/，用 update-ca-trust 让它被系统信任。
  • 学完后，你能解释为什么直接向 tls-ca-bundle.pem 追加内容是不规范的，并说出正确的替代方案。
  • 学完后，你能用 curl -v / openssl verify 验证自签站点是否已被系统信任，并按标准方法移除不再信任的证书。
Prerequisites · 前置知识

会用终端、会执行需要 sudo 的命令，并大致了解文件权限；对 HTTPS/TLS「证书是公钥凭证」要有常识，初步接触过第 18 节 SSH 会更顺利（非必须）。

Learning Content · 学习内容

01信任从哪来：
系统根证书存储

1为什么需要「信任」？信任库 + 证书链

TLS 握手时，客户端（浏览器、curl、git…）会拿服务器出示的证书，去自己的信任库（trust store）里找它的签发者（CA）。只有证书链的根能被信任库认可，连接才被信任、才不会有「证书无效」告警。系统会内置一份常见权威 CA 的公钥证书清单，例如 Let's Encrypt、DigiCert 等。

flowchart LR C[客户端 浏览器/curl] -->|TLS 握手：出示服务器证书| S[服务器] S -->|证书链：叶证书 + 中间CA + 根CA| C C --> T{系统信任库能找到其签发者吗} T -->|是| OK[信任 ✓ 建立加密连接] T -->|否| NO[不信任 ✗ 证书告警 / 校验失败]
发行系默认证书存储路径集中信任目录（放自定义证书）重建信任库的命令
Debian / Ubuntu/etc/ssl/certs//usr/local/share/ca-certificates/update-ca-certificates
RHEL 系（RHEL/CentOS/Fedora/Rocky）/etc/pki/tls/certs//etc/pki/ca-trust/source/anchors/update-ca-trust
!

易混淆：「默认证书存储」只是编译进程序的一个公共路径；真正追加信任要进「集中信任目录」再重建，两者是不同的目录。本节以 RHEL 系（源码笔记所在环境）为主线讲解。

2抓取自签证书：openssl s_client

要信任某个自签站点，第一步是把它在 443 端口出示的证书导出为 PEM 文件。openssl s_client 会主动连上目标、完成一次只读的 TLS 握手并打印证书链；-showcerts 把链上每一张证书都打印出来，再交给 openssl x509 -outform PEM 只保留叶子证书并转成 PEM 格式落盘。

shell · 导出 Harbor 自签证书
# 1) 抓取 core.harbor.domain 在 443 出示的证书，转成 PEM 保存
openssl s_client -connect core.harbor.domain:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -outform PEM > harbor-selfsigned.crt

# 2) 看一眼内容，确认是 -----BEGIN CERTIFICATE----- 开头
cat harbor-selfsigned.crt

# 3) 把变量清理掉（对应源码里的做法，避免污染当前 shell）
com=core.harbor.domain; file_name=harbor-selfsigned.crt; unset com file_name
  • 为什么有 </dev/null：防止 s_client 把手动输入当作 TLS 交互而挂起，直接关掉 stdin。
  • 为什么有 2>/dev/null：丢弃 s_client 写到 stderr 的握手调试信息，只保留证书。
  • GitLab 同理：把域名换成 gitlab.example.com 即可套用同一条命令。

3标准流程信任自签：update-ca-trust

拿到 PEM 后，不要手动改 bundle。规范做法是把证书放进 /etc/pki/ca-trust/source/anchors/，再执行 update-ca-trust，让系统把「自定义信任锚」和系统默认 CA 一起合并进各种 bundle 与哈希链接。

shell · 标准做法（RHEL 系）
# 1) 把证书放入自定义信任锚目录（需要 root）
sudo cp harbor-selfsigned.crt /etc/pki/ca-trust/source/anchors/

# 2) 重建信任库：合并 anchors 与系统默认 CA，生成/刷新各 bundle
sudo update-ca-trust

# 3) 验证：此时 curl 不再对这对自签报证书告警
curl -v https://core.harbor.domain
flowchart LR A[/etc/pki/ca-trust/source/anchors/ （你放的 .crt）] --> U[update-ca-trust] U --> B[/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem] U --> C[extracted / 下其它 bundle 与 ca-bundle 哈希链接]
★

核心法则：自定义信任锚只放到 source/anchors/，剩下的交给 update-ca-trust。你管「输入」，永远不要替它管「输出」。

4为什么原方法不推荐？不要手工改 bundle

原笔记把自签证书用 echo …>> /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem 直接追加进去。这看着「一次成功」，实则埋雷：/etc/pki/ca-trust/extracted/ 是 update-ca-trust 的输出区，每次执行都会按当前 anchors + 系统默认 CA 重新生成，你追加的内容会被整体覆盖丢失；一旦别人顺手执行一次 update-ca-trust，信任就悄悄失效，且问题极其难排查。

对比项❌ 原笔记做法✅ 标准做法
改动位置/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem/etc/pki/ca-trust/source/anchors/*.crt
性质工具输出区，会被重建「自定义信任锚」输入区
是否会被 update-ca-trust 覆盖会，直接丢失不会，会被合并进输出
重现性 / 可维护性差，且修改「生成物」好，只声明「信任源」
推广不推荐推荐
✖

务必避免：用 echo >> tls-ca-bundle.pem、或直接编辑 /etc/ssl/certs/ 下的 ca-bundle。这些都属于「改输出、绕过工具」的手法，重建即失效，还会让机器间配置不一致。

!

顺手记住对应关系：Debian/Ubuntu 系的「输入区」是 /usr/local/share/ca-certificates/（文件需 .crt 后缀），重建命令是 update-ca-certificates；RHEL 系才是 source/anchors/ + update-ca-trust。

5验证、临时信任与移除curl -v / openssl verify / 撤销

信任生效后，最直观的验证是用 curl -v（-v 会打印 SSL certificate verify result），或用 openssl verify 显式校验。

shell · 验证 / 临时信任 / 移除
# 1) 确认系统已信任（成功时不再出现 certificate verify failed）
curl -v https://core.harbor.domain

# 2) 用 openssl 显式校验某个证书文件是否被系统信任
openssl verify -CAfile /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem harbor-selfsigned.crt

# 3) 仅对【本次】临时信任，不污染系统信任库（适合一次性的请求）
curl --cacert harbor-selfsigned.crt https://core.harbor.domain

# 4) 移除不再信任的自签证书：删掉锚点文件再重建
sudo rm /etc/pki/ca-trust/source/anchors/harbor-selfsigned.crt
sudo update-ca-trust
★

小结：信任的「来源」永远在 source/anchors/；加信任＝放证书 + update-ca-trust，移除信任＝删该文件 + update-ca-trust。全程不碰 bundle 本体。

▲ 进阶挑战

  • 动手：为一个自签的 Harbor 或 GitLab 域名走完整流程——导出证书、放入 source/anchors/、执行 update-ca-trust、再用 curl -v 确认不再报证书告警，并把每一步记录成笔记。
  • 思考：用表格对照 RHEL 系（update-ca-trust + source/anchors/）与 Debian/Ubuntu 系（update-ca-certificates + /usr/local/share/ca-certificates/）两套机制的「输入区 / 输出区 / 重建命令」，找出规律。
  • 动手：用 openssl s_client -connect 域名:443 -showcerts 检查某个站点的证书链，判断它是否缺少中间证书（missing intermediate）——想一想这会不会导致信任失败。
  • 实践：把信任从「系统级」改为「用户级/一次性」，例如用 curl --cacert 或 git config http.sslCAInfo，体会「不污染全局信任库」的好处与局限。
