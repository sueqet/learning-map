LINUX · 文件系统

软链接与硬链接

一种数据、两种「名字」。理解 inode 与目录项，就能看懂 ln -s（软链接）与 ln（硬链接）的本质、差异和易踩的坑。

✓本节学习目标

  • 学完后，你能说清「一个文件 = 一个 inode + 若干目录项（名字）」，并用 ls -i 验证。
  • 学完后，你能用 ln 创建硬链接、用 ln -s 创建软链接，并讲出两者的核心区别。
  • 学完后，你能读懂 ls -l 的首字符（是否 l）与链接数，并用 stat 查看 inode、链接数与文件类型。
  • 学完后，你能解释：删掉目标文件后，为什么软链接会失效而硬链接仍能读取，以及数据到底何时才真正释放。
  • 学完后，你能避开软链接相对路径、跨文件系统限制、以及 -f 覆盖目标等常见误区。
Prerequisites · 前置知识

会用终端并熟悉 cd / ls / rm，了解 Linux 目录体系（见 08 节），知道「文件系统用 inode 描述文件」这一基本概念。

09软链接与硬链接：一个文件的多种身份

01 概念先懂 inode：文件到底「藏」在哪理解本质，后面就顺了

在 Linux 里，一个「文件」并不是一个名字那么简单。真正的数据存放在 inode（索引节点）里——它记录了权限、属主、大小、时间戳和指向数据块的指针；而目录项（dentry）只是把「一个名字」映射到「某个 inode」的一行记录。同一个 inode 可以被多个名字指向，这就是链接。

  • 名字 ≠ 文件本体：名字只是索引，真正的宿主是 inode。
  • 用 ls -i 看 inode 编号，用 stat 看 inode 详情、链接数与文件类型。
  • 理解这点后：硬链接 = 多个名字指向同一个 inode；软链接 = 一个独立的 inode（类型 l）里存着一条路径字符串。

shell
ls -i /etc/hostname        # 查看 inode 编号
stat /etc/hostname         # 查看更多：inode、链接数、类型、权限
★

核心要点：链接的本质是「让多个名字指向一个 inode（硬），或用一条路径指向另一个名字（软）」。先把这段关系画进脑子，再学命令。

02 硬链接硬链接：同一个 inode 的另一个名字ln target hardlink

ln 目标 硬链接名（不带 -s）创建的是硬链接——它不复制任何数据，只是往目录里新增一条「名字 → 同一个 inode」的记录。于是多个名字共享同一份数据、同一权限、同一时间戳。

  • 所有硬链接的 inode 编号相同（用 ls -li 看最左列）。
  • ls -l 第 2 列的数字是「链接数」，即有多少个名字指向这个 inode；每创建一个硬链接就 +1。
  • 删除其中一个名字（rm / unlink）只是让链接数 −1；只有链接数减到 0，数据块才真正释放。
  • 限制：硬链接不能跨文件系统，也不能指向目录（避免目录环）。
shell
cd /tmp && touch a            # 先造一个文件 a
ln a h1                       # 硬链接 h1 指向同一 inode
ls -li a h1                   # 最左列 inode 相同；第 2 列为 2

rm a                          # 删掉原名，a 的数据仍在
cat h1                        # h1 仍能读到完整内容
stat h1                       # 链接数已减为 1，数据未释放
★

核心要点：硬链接不加 -s；它不占新数据空间，只是多一个名字。硬链接之间没有「主从」关系，删哪个都一样，数据等到链接数归零才释放。

!

易错点：不能对目录创建硬链接、也不能跨文件系统。如果你对目录用了 ln，或者目标在不同分区，都会报错（如 Operation not permitted / Invalid cross-device link）。

03 软链接软链接（符号链接）：一个存「路径」的独立文件ln -s target link

ln -s 目标 软链接名创建的是软链接 / 符号链接。它其实是一个独立的小文件（有自己的 inode，文件类型是 l），内容只是「指向目标的路径字符串」。你访问软链接时，系统会按那条路径去「跳到」真正的目标。

  • ls -l 里以 l 开头，结尾会显示 → 目标；用 readlink 直接读出它存的路径。
  • 软链接可以跨文件系统，也可以指向目录——这正是它被广泛使用的原因（如版本切换、/bin → /usr/bin、项目里的 current → v1.2）。
  • 缺点：目标一旦被删除或改名，软链接就变成失效链接（broken / dangling）——它还在，但指向空。
  • 软链接不参与原文件的链接数：它有自己的 inode，所以不会让目标的链接数变化。
shell
ln -s /etc/hostname mylink     # 软链接指向 /etc/hostname
ls -l mylink                   # lrwxrwxrwx ... mylink -> /etc/hostname
readlink mylink                # 输出 /etc/hostname

rm /etc/hostname               # 删除目标
cat mylink                     # 报错：No such file（失效链接）
ls -l mylink                   # 仍是 l，只是变成 mylink -> /etc/hostname（已失效）
⚠

相对/绝对路径的坑：软链接存的是你输入的原样路径。若写成相对路径（如 ln -s conf/app.conf l），系统是以软链接所在目录为基准去找目标的，而不是你的当前目录。跨目录移动软链接后极易失效。稳妥做法是给绝对路径，或用 $(pwd)/目标。

怎么选：你不想复制数据、且目标不会变、在同一分区、又不是目录——用硬链接；绝大多数场景（跨分区、指向目录、想随时切换目标、想一眼看出指向谁）都用软链接。日常生产环境几乎全是软链接。

05 命令常用命令与易错点清单背下来就能用

把这一节当成「速查卡」：创建、查看、定位、删除链接，以及最常见的三个坑。

shell
ln 目标 链接            # 创建硬链接（同分区、非目录）
ln -s 目标 链接          # 创建软链接
ln -sf 目标 链接         # 若链接已存在则强制覆盖（-s 表示软链接，-f 强制）
ln -i 目标 链接          # 覆盖前交互式询问

ls -li                 # 最左列 inode，同 inode = 硬链接
ls -l                  # 首字符 l = 软链接；第 2 列数字 = 硬链接的链接数
readlink 链接           # 显示软链接存的路径
stat 链接               # 查看 inode / 链接数 / 类型 / 大小
find /path -type l      # 找出一棵目录树里所有的软链接
!

坑 1 · -s 别写反：不带 -s 是硬链接，带才是软链接。想创建软链接却漏了 -s，会莫名多出「另一个名字」，还改不动目标内容时很迷惑。

⚠

坑 2 · 删除软链接 ≠ 删除目标：rm 软链接只删掉软链接这个「入口」，不影响目标文件。只有当你确实想删目标时才去动它。同理，cp 默认会跟随软链接复制到它的内容，想保留软链接本体要用 cp -d / cp -a。

⚠

坑 3 · 相对路径 + 移动 = 失效：软链接存的是原样路径，若用相对路径且又把软链接搬到别的目录，它找不回目标。构造跨目录链接时，优先写绝对路径，或先 cd 到软链接所在地再决定目标写法。

▲ 进阶挑战

  • 动手·观察链接数：在 /tmp 里 touch a，然后 ln a h1、ln -s a s1，用 ls -li 与 stat 分别看 inode 和链接数；再 rm a，分别 cat h1 与 cat s1，把两种结果和原因写下来。
  • 思考·目录为什么禁硬链接：普通用户无法对目录创建硬链接。想一想：如果允许会造成什么后果？（提示：目录本身的「链接数」语义、递归遍历会不会绕圈、rm -r 会不会清不干净。）
  • 实践·跨文件系统：若 /tmp 与 /home 是两个分区，分别执行 ln /etc/hostname /tmp/x 与 ln -s /etc/hostname /tmp/y，看哪一个报 Invalid cross-device link，并说明原因。
  • 思考·备份与软链接：分别用默认 cp、cp -a、tar 备份一个含软链接的目录，进去对比软链接是被「保留」还是被「跟成复制文件」。哪条命令最安全？
