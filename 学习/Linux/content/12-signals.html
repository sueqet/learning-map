LINUX · PROCESS

信号与 kill

信号是内核向进程发出的异步通知。学完本节，你会分清常见的 1/2/3/15/9 号信号，会用 kill / killall / pkill 优雅或强制地控制进程，并且知道为什么先发 SIGTERM、再发 SIGKILL。

✓本节学习目标

  • 学完后，你能说出「信号」的定义，以及它是如何异步通知进程的。
  • 学完后，你能背出 SIGHUP / SIGINT / SIGQUIT / SIGTERM / SIGKILL 的编号与默认行为。
  • 学完后，你能用 kill / killall / pkill 按 PID 或进程名发送任意信号。
  • 学完后，你能解释 SIGTERM 与 SIGKILL 的差异，并写出「先优雅、后强制」的终止流程。
  • 学完后，你能区分 SIGINT（Ctrl+C）与 SIGQUIT（Ctrl+\）的来源和用途差别。
  • 学完后，你能用 SIGHUP 重载守护进程配置（如 nginx / sshd）。
Prerequisites · 前置知识

建议先学 11 节「进程状态与优先级」：会用 ps / top 找出进程的 PID，并理解进程本身（R/S/D/Z 等状态）的概念。本节聚焦「如何主动通知一个正在运行的进程」。

Learning Content · 学习内容

01信号（Signal）
内核向进程发出的异步通知

01信号是什么异步 · 事件通知 · 内核 → 进程

进程平时总在自顾自地执行。但主机上经常发生一些外部事件——你按了 Ctrl+C、防火墙上有个连接断开、系统要关机、某个守护进程的配置文件被改动了。内核需要一种方式打断正在运行的进程，让它知道「有件事发生了」。这一机制就是信号（signal）。

信号是内核向进程发送的异步通知：

  • 异步：进程不需要主动轮询，信号可以随时到达并打断当前执行流。
  • 内核发起：多数信号由内核产生（如异常、Ctrl+C 对应的按键）；也可由另一个进程通过 kill 发送给目标进程。
  • 编号 + 名称：每个信号有一个数字编号和一个 SIGxxx 名称（编号因平台有细微差异，但常用的一批一致）。

进程收到信号后，按该信号的默认行为去处理（多数是「终止」）；关键的是——部分信号允许进程捕获并自定义处理，另一些则无法捕获或忽略。

★

核心要点：信号是「内核 / 其它进程 → 目标进程」的单向异步通知。它不携带业务数据，只表达「发生了某类事件」。 “进程收到信号”时，绝大多数情况该进程会退出。

02五个常用信号速查编号 · 默认行为 · 能否捕获

先记住这一张表——它是本节的核心。第 4 部分会逐个展开。

信号编号默认行为能否被捕获/忽略典型用途
SIGHUP1终止能重新加载配置（守护进程约定）
SIGINT2终止能Ctrl+C，请求用户中断
SIGQUIT3终止 + core dump能Ctrl+\，退出并生成 core dump
SIGTERM15终止能请求程序优雅退出，可做清理
SIGKILL9强制终止不能强制立即杀死进程，内核直接终止

查看当前系统全部支持哪些信号，用 kill -l（小写 L，列出信号列表）：

shell
kill -l              # 列出所有信号名
# 输出示例（每行若干）：
#  1) SIGHUP      2) SIGINT      3) SIGQUIT     4) SIGILL     5) SIGTRAP
#  6) SIGABRT     7) SIGBUS      8) SIGFPE      9) SIGKILL   10) SIGUSR1
# 15) SIGTERM   ...

kill -l 9          # 用编号查名称
# SIGKILL

kill -l SIGTERM    # 用名称查编号
# 15
⚠

易错点：kill -l 里的 -l 是「列表（list）」；而 kill <PID> 里不带选项才是发送 SIGTERM。别把「列出信号」和「默认发 15 号信号」搞混。

03如何发出信号kill · killall · pkill

要给某个进程发信号，最常用的是 kill。kill 的语法是 kill [-信号] <PID>：不带信号默认发 SIGTERM(15)。也可以用 -s 指定名称，或直接写编号。

shell
# 先找到进程的 PID
ps aux | grep nginx
pgrep nginx            # 输出若干 PID

# 按 PID 发信号（默认 SIGTERM）
kill -15 <PID>          # 发送 SIGTERM（默认，优雅退出）
kill -9 <PID>           # 发送 SIGKILL（强制杀死）
kill -1 <PID>           # 发送 SIGHUP（重载配置）
kill -s SIGTERM <PID>   # 等价写法：用 -s + 信号名

# 按进程名发信号
killall nginx          # 按进程名发送 SIGTERM
pkill -9 nginx         # 按进程名发送 SIGKILL

三者都用于「向进程发信号」，区别主要在如何定位目标：

工具定位方式默认信号典型场景
kill按 PIDSIGTERM精确指挥某一个已知进程
killall按进程名（精确匹配完整名字）SIGTERM一次结束所有同名进程
pkill按进程名 / 正则匹配SIGTERM更灵活地按模式批量匹配

最佳实践：先发 SIGTERM 给进程清理机会，等几秒无响应再发 SIGKILL：

shell
kill -15 <PID> && sleep 5 && kill -9 <PID>
flowchart TD A([找到 PID / 进程名]) --> B[发送 SIGTERM 15] B --> C{进程在 5 秒内退出?} C -->|是| D([优雅结束 ✓
已释放连接/刷写缓冲]) C -->|否 / 假死| E[发送 SIGKILL 9
由内核直接终止]

04逐个讲：五个常用信号TERM / KILL / INT / QUIT / HUP

SIGTERM（15）—— 优雅退出

  • 最常用的关闭信号，给程序机会做清理：关闭网络连接、刷写缓冲区、保存状态等。
  • kill <PID> 不带参数默认就是发 SIGTERM。

SIGKILL（9）—— 强制终止

  • 由内核直接终止，程序没有任何机会执行清理代码。
  • 无法被捕获、阻塞或忽略——哪怕进程想「赖着不走」也没用。
  • 适用于程序假死、无法响应 SIGTERM 的情况。

SIGINT（2）—— 中断

  • 来源于键盘 Ctrl+C，表示用户要打断当前任务。
  • 与 SIGTERM 语义相近，区别在来源：SIGINT 是用户交互触发，SIGTERM 是程序 / 系统管理触发。

SIGQUIT（3）—— 退出并 core dump

  • 来源于键盘 Ctrl+\（注意不是 Ctrl+C）。
  • 终止进程并生成 core dump 文件（进程崩溃现场），用于事后调试。
  • 程序假死时可用此信号拿到崩溃现场（下一节「core dump 调试」展开）。

SIGHUP（1）—— 重载配置

  • 原始含义：终端断开 / 挂断（hanging up）。当控制终端关闭时，内核会给进程发 SIGHUP。
  • 守护进程把它约定为「重新加载配置」的信号——这是社区约定，非系统强制。
  • 常见支持程序：nginx、sshd、rsyslog 等。
★

一句话区分：想优雅关进程发 SIGTERM；进程死了不响应才用 SIGKILL；用户在终端按 Ctrl+C 是 SIGINT；想拿崩溃现场用 SIGQUIT；想让守护进程重载配置发 SIGHUP。

!

易错点：永远不要一上来就 kill -9。SIGKILL 不给程序保存现场、关闭连接、刷缓冲的机会，可能导致数据丢失或文件损坏；况且它无法被捕获，所以没有任何「安全下车的通道」。多数运维规范顺序是：kill → 等几秒 → kill -9。

05实战：用 SIGHUP 重载配置nginx / sshd 守护进程

很多服务（nginx、sshd）改完配置后不需要重启整只进程，而是「重载」。直接 kill -1 给守护进程发 SIGHUP，它就会重新读取配置文件，而不中断现有连接。

shell
# 改动 nginx.conf 后（不必停机）：
kill -1 $(cat /var/run/nginx.pid)   # 重载 nginx 配置（SIGHUP）

# 更稳妥：先检查配置语法再重载
nginx -t                            # 语法检查
kill -HUP $(cat /var/run/nginx.pid) # -HUP 等价于 -1

# sshd 也可用 signal 重载（保留现有连接）
kill -1 $(cat /var/run/sshd.pid)   # 或 systemctl reload sshd

对服务而言，systemctl reload 本质上也是发 SIGHUP（或由单元文件指定的信号）。用信号重载比「停掉再启动」更平滑——连接不断、无停机时间。

★

要点：SIGHUP 的「重载配置」是程序的约定，不是内核硬性规定。一个进程是否响应 SIGHUP 做重载，取决于它自己有没有写这个处理逻辑。
