Linux 目录体系

先建立 Linux 目录体系的整体地图，再深入两个最容易混淆的特殊目录：/proc（内核与进程的实时信息）与 /run（用户空间的运行时数据）。搞清楚它们各自管什么、何时消失，你就成功了一半。

✓本节学习目标

  • 学完后，你能画出 FHS 顶层目录树，说出 /etc、/var、/usr、/tmp、/dev 各自该放什么。
  • 学完后，你能从 /proc 中读取内核与进程的实时信息（如 /proc/meminfo、/proc/[PID]/cmdline）。
  • 学完后，你能说清 /run 存储什么（PID 文件、套接字、锁文件），以及为何重启后会清空。
  • 学完后，你能用一张表对比 /proc 与 /run 的用途、类型、生命周期差异，不再混用。
  • 学完后，你能正确指出 /var/run 与 /run 的符号链接方向（/var/run → /run），并解释为何容易写反。
Prerequisites · 前置知识

会用终端（ls、cat、cd、ln），了解「文件」「进程」「硬链接/符号链接」的基础概念；这一节不讲命令细节，重点是目录该放什么、何时消失。

Learning Content · 学习内容

01Linux 目录体系总览：先分清「谁放在哪儿」

FHSFilesystem Hierarchy Standard：顶层目录Linux 的「房间布局」

Linux 遵循 FHS（文件系统层次标准），把整个系统安排在根目录 / 下的一棵目录树里。知道每个目录的职责比死记路径更重要：持久配置放 /etc，可执行程序放 /usr，会变化的日志放 /var，运行时临时状态放 /run，内核与进程的实时信息放 /proc。

flowchart TD R["/"] --> bin["/bin → usr/bin"] R --> boot["/boot"] R --> dev["/dev"] R --> etc["/etc"] R --> home["/home"] R --> lib["/lib → usr/lib"] R --> proc["/proc"] R --> root["/root"] R --> run["/run"] R --> sbin["/sbin → usr/sbin"] R --> tmp["/tmp"] R --> usr["/usr"] R --> var["/var"] proc -. 内核动态生成 .-> p1["CPU/内存/进程实时信息"] run -. tmpfs 内存 .-> r1["PID/套接字/锁，重启清空"]
目录放什么要不要持久化
/bin →/usr/bin基本用户命令（ls、cat）持久
/boot内核、initramfs、引导加载器持久
/dev设备文件（由 udev 管理）启动时创建
/etc系统配置文件（持久化配置）持久（关键）
/home普通用户家目录持久
/lib →/usr/lib共享库持久
/proc内核与进程的实时信息（虚拟）非持久
/rootroot 用户家目录持久
/run运行时数据（PID、套接字、锁）非持久（重启清空）
/sbin →/usr/sbin系统管理命令持久
/tmp临时文件重启清空
/usr用户程序与数据（大多数内容）持久
/var可变数据：日志、缓存、/var/run、/var/log持久
★

核心要点：把「持久 vs 运行时」作为分界线：配置文件、程序、日志 → 持久化目录；当前状态的临时信息（PID、套接字、锁、内核状态）→ 放 /proc 与 /run，重启即变。

/proc/proc：内核与进程的「实时观察窗口」procfs · 虚拟文件系统

/proc 是一个虚拟文件系统（procfs）：它不占磁盘，里面的文件由内核在读取的瞬间动态生成。它既是内核与用户空间的接口，也用「每一个正在运行的进程对应一个数字目录」的方式，把进程信息暴露成文件，供 cat、ps、top 等工具读取。

proc · 内核信息
cat /proc/cpuinfo   # CPU 硬件详情
cat /proc/meminfo   # 内存使用情况
cat /proc/devices   # 已注册的设备列表
cat /proc/modules   # 已加载的内核模块
proc · 进程信息（按 PID 编号的子目录）
cat /proc/1234/status     # 进程状态：内存、线程、PPID 等
cat /proc/1234/cmdline    # 启动该进程的命令行参数
ls -l /proc/1234/fd/      # 该进程已打开的文件描述符
cat /proc/1234/maps       # 该进程的内存映射
  • 读取即实时：文件内容随内核/进程状态变化，没有固定大小，也没法「写回」去改内核。
  • 随进程消失：进程结束，它的 /proc/[PID]/ 子目录立即被内核清理。
  • 常用工具：ps、top、lsof 背后往往就是在读 /proc。
★

核心要点：/proc 是内核生成、用户只读的运行观察窗口——它用来「看」，不用来「存」。

/run/run：用户空间的「运行时数据区」tmpfs · 内存中

/run 基于 tmpfs（内存中的临时文件系统），是用户空间程序（服务、守护进程）存放运行时状态的地方：它们被写入，而非由内核生成。系统开机时创建，重启后自动清空，因此非常适合放「只活在本次开机期间」的临时状态。

run · 运行时数据
cat /run/sshd.pid          # 服务 PID 文件（记录 sshd 进程号）
ls -l /run/docker.sock     # 进程间通信用套接字文件
find /run/lock -maxdepth 1 # 锁文件（防止服务重复启动）
ls /run/systemd/           # systemd 的运行时信息
  • PID 文件：记录服务进程 PID，可用于判断是否已有实例、检查存活。
  • 套接字文件：供进程间通信，如 Docker 守护进程的 /run/docker.sock。
  • 锁文件：防止同一服务被重复启动（如 /run/lock/lvm）。
  • 生命周期：随开机创建、随重启清空，服务需在启动时自己重新创建。
!

易错点：别把运行时状态放进 /etc 这类持久化配置目录。PID、套接字、锁都是「过一天就失效」的瞬态数据，放 /run；配置文件（持久）才放 /etc。

Key Contrast · 核心对照

02/proc 与 /run：一张表看懂它们

对比/proc vs /run：用途、类型、生命周期的区别两者的核心差异

两者都存放运行时信息、都非持久化，这是最常被混淆的根源。但它们由谁生成、给谁用、何时消失很不一样：/proc 是内核写、用户看；/run 是用户程序写、用户程序看。

特性/proc/run
类型虚拟文件系统（procfs）临时文件系统（tmpfs，内存中）
用途提供内核和进程的实时信息存储运行时临时数据（PID 文件、套接字）
数据来源由内核动态生成由用户空间程序（服务、守护进程）写入
生命周期进程结束，其目录自动清理系统重启后清空
持久性非持久化（随内核/进程状态变化）非持久化（仅运行时存在）
典型内容CPU、内存、进程信息、已加载模块PID 文件、锁文件、套接字文件、systemd 状态
★

一句话记忆：/proc 是「内核自己报的状态」，/run 是「程序给自己留的便签」。前者管「系统现在怎样」，后者管「服务现在在跑什么」。

易错/var/run 与 /run：被写反的符号链接常见混淆点 · 已修正

在很多 systemd 发行版上，/var/run 并不是一个独立的真实目录，而是指向 /run 的符号链接。也就是说，/var/run 和 /run 指向的是同一个临时目录。

!

方向容易写反——务必记住：
　错误的说法：「/run 是 /var/run 的符号链接」（反了）。
　正确的方向：/var/run → /run，即 /var/run 是 /run 的符号链接，两者指向同一位置。

验证符号链接方向
ls -ld /run /var/run   # 看类型与链接指向
# 典型输出（注意 var/run 是 lrwxrwxrwx，箭头指向 ../run）
# drwxr-xr-x  ... /run
# lrwxrwxrwx  ... /var/run -> ../run

由于现代 systemd 普及，/var/run 都指向 /run。因此历史代码里写的 /var/run/sshd.pid 与今天的 /run/sshd.pid 其实是同一文件——这既是为了向后兼容，也避免「运行时状态」和「可变数据」在 /var 里混放。

i

记忆技巧：顺着「/var/run 是 /run 的别名」来记。读链接时箭头 → 从旧路径指向新路径：/var/run → /run。

Practical · 实际场景

03它用来解决问题

场景两个典型用例：查进程资源 & 管服务上手练习

场景 1：想知道进程 1234 的内存映射，用 /proc；场景 2：想确认 Nginx 是否在运行、它的 PID 是多少，用 /run。

场景 · let's practice
# 场景 1：查看进程 1234 的内存映射（来自 /proc）
cat /proc/1234/maps

# 场景 2：查找 Nginx 服务的 PID（来自 /run）
cat /run/nginx.pid     # 或等价的 /var/run/nginx.pid

# 顺手：看本机 pidof，再核对 /proc 里的真实情况
pidof nginx            # 返回 PID 列表
ps -p $(cat /run/nginx.pid)   # 用 PID 确认该进程状态
i

提醒：如果 /run/nginx.pid 不存在，通常意味着服务没在运行，或该服务尚未创建 PID 文件——这是排查「服务没起来」的第一步。
