LINUX · SYSTEMD

systemd 服务单元

systemd 是现代 Linux 的初始化与系统服务管理器，而 .service 服务单元文件是它描述「怎么启动、依赖谁、如何重启」的剧本。看懂 [Unit] / [Service] / [Install] 三段，你也能写出一份能开机自启、崩溃自愈的服务。

✓本节学习目标

  • 学完后，你能说出 .service 服务单元文件的三段基本结构 [Unit] / [Service] / [Install] 各自的作用。
  • 学完后，你能分清 /etc/systemd/system/ 与 /usr/lib/systemd/system/ 两个存放路径，并说出哪个优先级更高。
  • 学完后，你能在 [Unit] 中使用 After/Before 控制启动顺序，用 Wants/Requires 表示弱/强依赖。
  • 学完后，你能在 [Service] 中写出 ExecStart/ExecStop/ExecReload，并配置 User/Group/WorkingDirectory/EnvironmentFile 等运行参数。
  • 学完后，你能对比 Type（simple/exec/forking/oneshot/notify）与 Restart（no/always/on-failure/on-abnormal）各取值的差异，并针对不同服务合理选择。
  • 学完后，你能编写一份完整可用的服务单元文件，并记住修改后必须执行 systemctl daemon-reload 才能生效。
Prerequisites · 前置知识

会用 systemctl 常见子命令（start/stop/status/restart/enable）管理服务，理解绝对路径与进程/守护进程概念。有一点点文件系统与权限概念即可，本页不涉及复杂编程。

01认识 systemd：一切皆「单元」

01什么是 systemd 与服务单元

systemd 是绝大多数现代 Linux 发行版（RHEL/CentOS/Rocky、Debian/Ubuntu、Fedora 等）采用的初始化系统（PID 1）与系统/服务管理器。它取代了旧的 SysVinit，负责在开机时拉起服务、管理运行状态、维护依赖与并行启动。

systemd 把每一项可管理的东西抽象成一个个单元（unit）。最常用的是服务单元，配置文件后缀为 .service。systemd 依靠这份文本文件知道：这个服务是什么、怎么启动、依赖谁、要不要随开机启动。

  • 单元类型很多：.service（服务）、.target（启动目标，如 multi-user.target）、.socket（套接字）、.timer（定时器）等。
  • 管理命令：systemctl 是「控制面板」，systemd-analyze 用于诊断，journalctl 看日志。
  • 核心关系：你写一份 .service → 放到 unit 目录 → daemon-reload → systemctl enable/start。systemd 就会替你拉起并守护它。
flowchart LR A[编写 .service 单元文件] --> B["放入 unit 目录 (etc/ 或 usr/lib/)"] B --> C["systemctl daemon-reload"] C --> D["systemctl enable 开自启"] C --> E["systemctl start 立即启动"] E --> F["systemd 守护并管理进程"] D --> F
★

核心要点：systemd「一切皆单元」，服务对应 .service 文件。写服务 = 写一份声明式的配置文件，交给 systemd 去执行，而不是自己在脚本里手维护进程。

02存放路径与三段基本结构

系统里有两类存放 .service 的位置，它们的来源与优先级不同：

路径来源优先级 / 用途
/etc/systemd/system/用户 / 管理员自定义的服务优先级最高，会覆盖系统自带同名单元（也用于放 enable 时生成的软链接）
/usr/lib/systemd/system/软件包安装时带来的服务系统默认单元；用户通常只读，不做修改

一份 .service 文件由三个段组成，每个段各司其职：

ini · 服务单元基本骨架
[Unit]
# 服务元数据和依赖关系

[Service]
# 服务运行参数和执行命令

[Install]
# 服务安装配置（enable/disable 时使用）
  • [Unit]：描述「这是什么服务、依赖谁」（元数据 + 依赖）。
  • [Service]：描述「怎么启动、由谁运行」（运行参数 + 命令）。
  • [Install]：描述「开机自启装到哪个 target」（enable/disable 用）。
⚠

易错：不要手动去改 /usr/lib/systemd/system/ 里的文件——软件升级会覆盖你的修改。想覆盖行为，请在 /etc/systemd/system/ 放同名单元，或使用 .d/ 覆盖片段（如 xxx.service.d/override.conf）。

02[Unit] 段：身份与依赖

03[Unit] 段：元数据与依赖关系

[Unit] 段描述服务的身份与依赖。它不定义命令，只定义「这个服务是什么、应该排在谁前面/后面、缺了谁会不会起不来」。

ini · [Unit]
[Unit]
Description=服务描述信息
Documentation=https://example.com/docs
After=network.target docker.service    # 在这些服务启动之后再启动
Before=some.service                    # 在这些服务启动之前启动
Wants=syslog.target                    # 弱依赖（缺失不影响主服务）
Requires=network.target                # 强依赖（缺失则主服务无法启动）

这里最容易混的两组关系：

键含义作用
After=本服务之后才启动这些单元只约束启动顺序，不构成依赖关系
Before=本服务之前启动这些单元同上，只约束顺序
Wants=弱依赖尽量拉起这些单元；缺失/失败不影响主服务启动
Requires=强依赖这些单元必须成功；缺失则主服务无法启动
!

别搞混「顺序」与「依赖」：After/Before 只决定谁先谁后，不代表「谁依赖谁」；Wants/Requires 才表达依赖强弱。你既需要顺序又需要依赖时，常常同时写：After=network.target + Requires=network.target。

03[Service] 段：让进程真正跑起来

04[Service] 段：运行参数与命令

[Service] 段是服务单元的核心，定义实际的启动命令、运行身份、工作目录、环境变量与资源限制等。

ini · [Service]
[Service]
Type=simple                     # 服务类型
ExecStart=/usr/bin/myapp        # 启动命令（必须绝对路径）
ExecStop=/usr/bin/myapp stop    # 停止命令（可选）
ExecReload=/bin/kill -HUP $MAINPID  # 重载命令（可选）
Restart=on-failure              # 重启策略
RestartSec=5                    # 重启前等待秒数
User=www-data                   # 运行用户
Group=www-data                  # 运行用户组
WorkingDirectory=/opt/myapp     # 工作目录
Environment=ENV=production      # 环境变量
EnvironmentFile=/etc/myapp.env  # 从文件加载环境变量
LimitNOFILE=65536               # 最大文件描述符数
TimeoutStartSec=30              # 启动超时秒数
  • Exec* 命令必须用绝对路径：systemd 不依赖 shell 的 PATH，写相对路径会找不到。
  • ExecStart 是启动主命令；ExecStop、ExecReload 可选，缺省时 systemd 用默认方式停止/忽略重载。
  • 运行身份：User/Group 决定服务以哪个用户权限运行，高权限进程建议降到低权限账户，降低安全风险。
  • 环境变量：Environment= 直接给单个变量；EnvironmentFile= 从文件加载，更适合管理配置（见最佳实践）。
  • 资源限制：LimitNOFILE 提高文件描述符上限、TimeoutStartSec 控制启动超时。
★

核心要点：[Service] 段负责「真正把进程跑起来」。ExecStart 用绝对路径、用 User 降权运行、用 EnvironmentFile 管理配置——这三点在实战里几乎是必备的。

05Type 与 Restart：启动判定与崩溃自愈

Type 告诉 systemd 应该怎样判断服务已经成功启动；Restart 则决定服务停止后是否自动拉起。它们回答的是两个完全不同的问题，常被放在一起考核。

Type 的常用取值：

值说明典型场景
simple默认值，ExecStart 直接是主进程，启动即算完成大多数前台进程
exec类似 simple，但等到 exec 成功后才认为启动完成（较新 systemd 推荐）同 simple，更严谨
forking传统守护进程；主进程 fork 后父进程退出httpd、nginx 等
oneshot一次性任务，配合 RemainAfterExit=yes 使用脚本、初始化、一次性命令
notify服务启动后主动通知 systemdDocker、BuildKit 等

Restart 的常用取值：

值说明使用建议
no默认值，不自动重启调试 / 一次性任务
always无论何种原因停止都重启希望始终存活的常驻服务
on-failure仅在异常退出（非零退出码）时重启生产环境最常用，正常停止不重启
on-abnormal信号终止、超时等异常时重启（不含正常退出）对信号异常更敏感的场景
ini · 常见组合
# 前台常驻进程（默认）
Type=simple
ExecStart=/usr/bin/myapp

# 传统守护进程（会 fork），崩溃自愈
Type=forking
ExecStart=/usr/sbin/nginx -c /etc/nginx/nginx.conf
Restart=on-failure
RestartSec=5

# 一次性任务 + 结束后仍显示为 active
Type=oneshot
ExecStart=/usr/bin/setup-tasks
RemainAfterExit=yes
⚠

易错：给一个会 fork 的守护进程乱用 Type=notify 却不发通知，systemd 会一直等你通知，误判启动超时。选 Type 前先想清楚：这个服务是前台常驻、会 fork、一次性还是主动通知。

★

核心要点：生产环境一般用 Restart=on-failure 或 Restart=always，搭配 RestartSec=5 之类的等待秒数，既保证服务崩溃后自愈，又避免「秒崩秒重启」打爆系统资源。

04[Install] 段与完整示例

06[Install] 段、完整示例与最佳实践

[Install] 段只在执行 systemctl enable / disable 时被读取，它告诉 systemd：把这个服务「挂」到哪个 target 下，从而实现开机自启。

ini · [Install]
[Install]
WantedBy=multi-user.target   # 多用户模式下启用（绝大多数服务用这个）
WantedBy=graphical.target    # 图形界面模式下启用
Alias=myapp.service          # 服务别名
键说明
WantedBy=multi-user.target最常用。多用户命令行模式开机自启，绝大多数服务器服务用这个。
WantedBy=graphical.target图形界面（有 GUI）模式下自启。
Alias=给服务起别名，可通过别名启动/管理。

把三段串起来，就是一份真实可用的服务单元（以 Nginx 为例，Type=forking、on-failure、开机自启）：

ini · nginx.service
[Unit]
Description=The NGINX HTTP Server
Documentation=https://nginx.org/en/docs/
After=network.target

[Service]
Type=forking
ExecStart=/usr/sbin/nginx -c /etc/nginx/nginx.conf
ExecReload=/usr/sbin/nginx -s reload
ExecStop=/usr/sbin/nginx -s stop
Restart=on-failure
User=nginx
Group=nginx
WorkingDirectory=/var/www/html
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target
shell · 应用与排查
systemctl daemon-reload          # 每次改完 unit 必须先重载
systemctl enable --now nginx     # 开机自启 + 立即启动
systemctl status nginx           # 查看运行状态
systemctl reload nginx           # 触发 ExecReload（热重载配置）
journalctl -u nginx -f           # 实时看该服务日志

最佳实践小结：

原则 / 坑正确做法
路径必须绝对ExecStart 等命令一律写绝对路径，不依赖 shell 的 PATH。
配置不要硬编码环境变量用 EnvironmentFile 单独管理，不要把密钥/配置写死在 unit 文件里。
生产环境重启策略建议 Restart=on-failure 或 Restart=always，并配 RestartSec 防重启风暴。
改完必重载修改后必须 systemctl daemon-reload 才能生效；restart 不负责解析新配置。
降权运行用 User/Group 把高权限进程降到低权限账户，减小安全面。
!

最隐蔽的一个坑：很多人以为 systemctl restart 服务 就能让刚写入的新配置生效。事实上 restart 只是把进程停了再启，systemd 仍在用旧的 unit 缓存。真正让「配置改动生效」的是先 systemctl daemon-reload，再 restart/reload。忘了这步，你改的命令怎么都不起作用。

★

核心要点：写完 .service 后的标准动作是「daemon-reload → enable → start/status」。daemon-reload 让 systemd 重新读取你刚改的单元文件，restart/reload 只是操控进程、并不会重新解析新配置。
