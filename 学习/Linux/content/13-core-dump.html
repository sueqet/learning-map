LINUX · 进程

core dump 调试

程序崩溃时别只看到一个「Segmentation fault」——让它把它崩溃瞬间的内存快照写进文件，事后用 gdb 还原调用栈与变量值。这就是程序的黑匣子。

✓本节学习目标

  • 学完后，你能说出 core dump 是什么、它相当于程序的「黑匣子」，以及它解决哪类「程序崩了但没现场」的难题。
  • 学完后，你能用 ulimit -c 查看当前限制，用 ulimit -c unlimited 启用、ulimit -c 0 禁用 core 文件。
  • 学完后，你能在 /etc/security/limits.conf 里配置永久生效的 core 大小上限，并知道它何时才被应用。
  • 学完后，你能区分哪些信号会触发 core dump（如 SIGSEGV / SIGABRT / SIGQUIT）与哪些不会（如 SIGKILL / SIGTERM）。
  • 学完后，你能用 gdb ./程序 core 配合 bt、frame N、info locals 查看崩溃现场。
  • 学完后，你能系统地排查「程序崩了却没有生成 core 文件」的各种可能原因。
Prerequisites · 前置知识

会编译并运行一个最小的 C 程序（gcc），并已经了解信号与进程（上一节 12-signals）——因为 core dump 正是进程收到「致命信号」并终止时由内核生成。一点 C 指针知识有助于理解示例里的段错误。

Learning Content · 学习内容

01程序的「黑匣子」：core dump

01什么是 core dump

被调试的程序崩了，最难受的是现场没了——函数栈、局部变量、指针的值都随风而逝。core dump 就是为解决这件事：程序崩溃时，内核把该进程当前的内存状态（寄存器、栈、堆、打开的文件等）转储到一个文件里，供事后用调试器分析。就像飞机失事后的黑匣子，记录了坠落瞬间的一切。

  • 触发条件：进程收到一个「默认行为为终止并产生 core」的信号，且系统允许生成 core（见第三、四节）。
  • 产出物：一个 core 文件（通常放在进程的工作目录），里面是进程地址空间的镜像。
  • 不是每次崩溃都有：只有「终止 + core」类信号（如段错误）才生成；被优雅终止（SIGTERM）或被强制杀死（SIGKILL）的程序不会留下 core。
  • 不能凭空还原：core 只是「内存快照」，要看到函数名、源码行号，还需要程序本身及符号信息（编译时加 -g）。
★

核心要点：core dump = 崩溃瞬间的内存快照，用于事后调试。它还原的是「死的时候」的现场，前提是系统开了生成开关、程序带着调试符号。

02哪些信号会触发 core dump

信号是否生成 core，取决于它的默认动作。凡是默认动作是「终止 + core」的信号，进程收到后会在终止前由内核写一份 core 文件。表里结合上一节「信号与 kill」对照记忆：

信号编号默认动作典型来源产生 core？
SIGQUIT3终止 + core键盘 Ctrl+\✅ 会
SIGSEGV11终止 + core非法内存访问（段错误）✅ 会
SIGABRT6终止 + coreabort()✅ 会
SIGFPE8终止 + core算术错误（如除以 0）✅ 会
SIGILL4终止 + core非法指令✅ 会
SIGTERM15终止kill <pid>❌ 不会
SIGINT2终止键盘 Ctrl+C❌ 不会
SIGKILL9强制终止kill -9❌ 不会
!

易错点：不是所有「崩溃/退出」都有 core。能被捕获/忽略并优雅退出的信号（SIGTERM、SIGINT）和无法捕获的 SIGKILL，都不会留下 core。只有默认动作为「终止 + core」的信号才生成。

03启用 core dump：ulimit 与 limits.conf

很多系统默认禁用 core 文件（ulimit -c 显示 0）。要得到 core，先得打开这个开关。注意 ulimit 是 shell 内建命令，只对当前 shell 及其随后启动的进程生效，换个终端/重新登录就恢复默认。

shell
ulimit -c              # 查看当前 core 大小限制（0 表示禁用；单位为 KB）
ulimit -c unlimited    # 当前会话启用，不限大小
ulimit -c 0            # 禁用（某些安全 / 防磁盘占满场景）
ulimit -c              # 再次查看，确认已是 unlimited

永久启用：写入 /etc/security/limits.conf。该文件由 PAM 读取，在新会话（重新登录 / 新开终端）时应用，不会立刻影响已打开的 shell。

limits.conf
# /etc/security/limits.conf —— 永久生效
* soft core unlimited   # soft：当前会话可临时放宽的上限
* hard core unlimited   # hard：只有 root 能进一步放宽的硬上限

还有一个影响「core 文件叫什么、放哪」的内核参数 core_pattern（/proc/sys/kernel/core_pattern），默认常是 core，可带 %e（程序名）%p（PID）等占位符。某些发行版把它交给 systemd-coredump 处理（如 Fedora/RHEL），此时文件不落在当前目录，而由 journald/服务存储——这常常就是「明明崩了却找不到 core」的原因之一。

shell
cat /proc/sys/kernel/core_pattern   # 查看内核 core 命名/去向规则
# 例如：core             → 就叫 core，落在进程当前目录
# 例如：|/usr/lib/systemd/systemd-coredump ...  → 交给 systemd 处理
⚠

区分作用域：ulimit -c 控制「是否生成、多大」；core_pattern 控制「生成到哪、怎么命名」。两者都影响你能否顺利拿到 core，排障时两个都要查。

04动手：写一个会崩的程序

为了后续练 gdb，先造一个「自找段错误」的小程序并带调试符号编译。下面代码通过空指针解引用引发 SIGSEGV。

c
// crash.c
#include <stdio.h>
void boom(void){
    int *p = 0;        // p 指向地址 0（空指针）
    *p = 42;           // 写地址 0 → 非法内存访问 → SIGSEGV
}
int main(void){
    printf("start\n");
    boom();            // 在这里崩掉
    printf("end\n");   // 这行不会执行
    return 0;
}
shell
gcc -g -o crash crash.c   # -g 保留调试符号，gdb 才能显示行号/变量名
ulimit -c unlimited       # 确保这个会话允许生成 core
./crash                   # 运行 → "start" 后崩溃，留下 core 文件
ls -lh core*              # 确认 core 文件已生成（名字取决于 core_pattern）
★

核心要点：编译时一定加 -g。没有符号信息，gdb 只能看到一堆地址而看不到函数名与行号，也就退化成「读天书」。

05用 gdb 分析崩溃现场

拿到 core 后，把它和同一份程序一起交给 gdb。常见流程：

shell
gdb ./crash core        # 加载程序与 core 文件
# ---------- 常用命令 ----------
bt                      # backtrace：查看崩溃时的调用栈（从 main 到崩溃点）
frame 2                 # 切换到第 2 号栈帧
info locals             # 查看当前帧的局部变量值
print p                 # 打印某个变量（等价 print 也可用 p）
info registers          # 查看寄存器（崩溃时 PC/SP 等）
quit                    # 退出 gdb

展开来看，一次典型会话会这样输出：

gdb
(gdb) bt
#0  boom () at crash.c:5
#1  main () at crash.c:10

(gdb) frame 1            # 切到 main 这一帧
#1  main () at crash.c:10
10	    boom();

(gdb) info locals        # 看上一层/当前帧的局部变量

看到的信息：崩溃时所在源码行、完整调用栈（谁调用了谁、一层层回溯到 main）、各栈帧的变量值。有了这三样，多数崩溃原因就一目了然——上例中 *p = 42 在 crash.c:5 写入空指针就是元凶。

!

关键前提：core 文件必须与生成它的那个程序（同版本、同编译器、同 -g 构建）匹配。用不匹配的程序去读 core，会得到错误/缺失的函数名与行号，甚至完全读不出来。

★

一句话记忆：core 给出「死前的现场」——bt 看调用栈、frame 切栈帧、info locals 看变量。把这三招连起来，就能定位崩溃发生在哪一行、为什么。

06整体工作流与「没有 core」的排障

把上面几节串起来，核心流程如下——它回答了「程序崩了该怎么查」：

flowchart LR A[程序运行] --> B[收到致命信号
SIGSEGV / SIGABRT / SIGQUIT 等] B --> C{允许生成 core 吗?
ulimit -c > 0 且 core_pattern 有效} C -->|是| D[内核写入 core 文件] D --> E[gdb ./程序 core] E --> F[bt 看调用栈
frame 切栈帧
info locals 看变量] C -->|否| G[仅终止，无 core] G --> H[无法事后分析]

「程序崩了却没有 core 文件」——从这几点逐个排查：

检查项命令 / 依据说明
core 大小被禁用ulimit -c为 0 则不生成，改为 unlimited。
被 core_pattern 重定向cat /proc/sys/kernel/core_pattern若交给 systemd-coredump，文件不在当前目录，要去看 journald。
崩的信号不产生 corekill / 崩溃原因SIGTERM / SIGKILL / 优雅退出 没有 core。
当前目录不可写ls -ld .core 落在进程工作目录，写不进去就没文件。
触发了 core 大限ulimit -c软/硬上限过小会被截断或丢弃。
⚠

会占磁盘：core 文件与进程地址空间大小相当，可能很大。生产环境通常要么禁用、要么限制大小、要么统一收走；排查完及时删除，别让一大堆 core 塞满磁盘。
