Shell 基础与脚本执行

这一节让你搞懂 Shell 到底是什么——它只是内核与你之间的一名「翻译官」；学会三种执行脚本的方式、用 shebang 声明解释器，并分清 bash 与 sh 的取舍。这是把重复劳动写成脚本的第一步。

✓本节学习目标

  • 学完后，你能说出 Shell 的核心作用，并准确区分「Shell 解释器 / 内核 / 硬件」三者分工。
  • 学完后，你能用 echo $SHELL、echo $0、cat /etc/shells 查看当前与系统支持的 Shell。
  • 学完后，你能说明 bash script.sh、./script.sh、source script.sh 三种执行方式的区别，以及各自对「可执行权限」的要求。
  • 学完后，你能用 shebang（#!/bin/bash / #!/bin/sh）声明脚本解释器，并解释它必须写在首行的原因。
  • 学完后，你能对比 bash 与 sh 在语法特性与可移植性上的差异，并根据需求为脚本选择合适的解释器。
Prerequisites · 前置知识

01认识 Shell，并让脚本跑起来

小节Shell 是什么？——命令解释器内核与用户之间的翻译官

Shell（外壳）是命令行解释器：它接收你在终端输入的命令，把命令解析、翻译后交给操作系统内核去执行，再把内核的执行结果返回给你。它「站在内核之外」，所以叫外壳。

要记住的分工是：Shell ≠ 内核。Shell 不做实际的工作，它只负责「传话」；真正动手调度 CPU、读文件、管内存的是内核。

flowchart LR A[你在终端输入命令] --> B[Shell 解释器 翻译/解析] B -->|系统调用| C[内核 Kernel] C -->|驱动| D[硬件 磁盘/CPU/内存] D --> C C -->|返回结果| B B -->|回显到屏幕| A
★

核心要点：Shell 是「用户 ↔ 内核」之间的解释器，它自己并不直接操作硬件。你在 bash、zsh、sh 里敲的命令，最终都通过内核才真正落到系统上。

小节查一查：现在用的是哪个 Shellecho $SHELL / echo $0 / /etc/shells

动手确认「当前正用哪一个解释器」。这三条命令最常用，含义各不相同：

shell
echo $SHELL        # 查看当前登录用户使用的 shell（环境变量，多为 /bin/bash 或 /bin/zsh）
echo $0            # 查看"当前正在运行的 shell/脚本"的名字
cat /etc/shells    # 查看系统里注册支持的所有 shell
命令含义适用场景
echo $SHELL当前登录 shell 的路径日常查看默认交互 shell
echo $0当前正在运行的 shell / 脚本名在脚本内打印脚本自身名字；交互时一般显示 shell 名
cat /etc/shells系统注册的所有合法 shell判断某个 shell 是否可用
!

易混淆：原始笔记写「echo $0＝查看当前执行的脚本名称」。这句话只在脚本里成立；在交互终端中 $0 通常返回当前 shell 名（如 bash），并不是某个「脚本」。所以判断脚本名要用 $0，判断登录 shell 用 $SHELL。

02如何执行脚本

小节三种执行脚本的方式bash 不要权限 · ./ 要权限 · source 不开子进程

同样一个脚本，执行方式不同，走的路和权限要求也完全不同。这是本节最容易考、最容易踩坑的地方。

shell
bash script.sh     # ① 把脚本当作参数，显式交给 bash 解释器 —— 不需要可执行权限
sh   script.sh     #    （同前，用 sh 解释器）

./script.sh        # ② 直接执行 —— 需要可执行权限: chmod +x script.sh
                   #    内核会先读脚本首行的 shebang 来决定用哪个解释器

source script.sh   # ③ 在"当前 shell"里执行（等价于 . script.sh）—— 不需要可执行权限
方式是否要 chmod +x是否起子进程说明
bash script.sh否是（新 bash 进程）显式指定解释器，忽略 shebang
./script.sh是是按 shebang 找解释器，需要 x 权限
source script.sh否否（在当前 shell）在现行 shell 里逐行执行，变量会留到当前 shell
⚠

易错点：用 ./script.sh 却报 Permission denied，几乎都是忘了 chmod +x。此时换成 bash script.sh 往往就能跑——因为它绕过了「文件可执行」这一关。脚本里要设置某条路径时，别忘了先给文件加执行权限，再补 chmod +x script.sh。

★

核心区别：bash 是把脚本当参数喂给解释器；./ 是把脚本当可执行程序去启动，由内核按 shebang 找到解释器；source 则不新建子进程，直接在当前 shell 里跑，因此脚本里定义的变量会「污染」并保留在当前的 shell 环境里。

小节shebang：脚本首行声明解释器#!/bin/bash 与 #!/bin/sh

脚本的第一行可以写一行以 #! 开头的注释——这叫 shebang。当你在终端执行 ./script.sh 时，内核会读取它来决定用哪个解释器来运行脚本。它是「给内核看的声明」，而不是给 Shell 看的普通注释。

shell
#!/bin/bash      # 用 bash 执行：支持 [[]]、(())、数组等 bash 特有语法
#!/bin/sh        # 用系统默认 sh 执行：更接近 POSIX 标准，兼容性更好但功能较少
  • 必须写在第一行：shebang 只在文件最开头生效，前面不能有其它内容（哪怕是空行后的注释）。
  • 必须用绝对路径：#!/bin/bash 指向固定位置；这是内核读取约定，不能用 PATH 查找。
  • 有没有 shebang 都行：用 bash script.sh 显式指定时，内核不看 shebang；只有 ./ 方式才依赖它。
  • 没有 shebang 时 ./ 会怎样？内核会尝试用「当前 shell」来执行（发行版不同行为略有差异），因此结果可能不可靠。
★

一句话记牢：shebang 只在 ./ 直接执行时起作用；它指定解释器，且必须处于脚本第一行。若用「bash script.sh」方式运行，shebang 会被忽略，实际用的是你在命令行写的那个解释器。

小节bash 与 sh：选哪个？功能 vs 可移植性

同一个脚本，解释器不同，能用的语法也不同。核心取舍是：bash 功能强、sh 更通用。

对比项#!/bin/bash#!/bin/sh
定位Bourne Again SHell，增强版系统默认 sh（兼容 POSIX）
专属语法支持 [[ ]]、(())、数组、=~ 正则等主要支持 POSIX 标准，语法更保守
可移植性较少，依赖系统装有 bash更好，跨发行版更稳
功能上限更高，适合写脚本相对有限
典型用法日常脚本、要写复杂判断/数组需要尽量通用、跨平台运行的脚本

补充：/bin/sh 在不少发行版上其实是一个「指向 bash 的软链接」，这一细节会让「sh 更保守」的直觉不完全准确；但作为脚本作者，写成 #!/bin/sh 就等于承诺「我只用 POSIX 要求的语法」，这样换到任何系统都稳。

!

书写建议：想要可移植就写 #!/bin/sh、只用 POSIX 语法；想要功能全就写 #!/bin/bash 并享受 [[ ]]、数组等便利。别在 #!/bin/sh 里用 [[ ]]——有的系统上是 sh 并不认，会直接报语法错误。
