01从「崩掉」到「接得住」

认识异常错误、异常与内置异常先分清三类「错」

写程序时总共有三类「错」：语法错误、运行时异常、逻辑错误。语法错误在解析阶段就让程序无法运行；逻辑错误是程序跑得通但结果不对；而异常（Exception）是语法正确、但执行到某一步时触发的错误——它恰恰是我们能「接住」、能「处理」的错误。

  • 语法错误：如 if True print("hi") 缺少冒号，解析期就报 SyntaxError，无法靠 try 捕获。
  • 运行时异常：代码能编译，执行时才抛出，可被 try/except 捕获。
  • 逻辑错误：不报错但结果错误，try 无能为力，要靠测试与调试。
python
# 语法错误：解析期就失败，try 救不了
# if True print("hi")        # SyntaxError: expected ':'

# 运行时异常：语法没问题，执行到这才崩 — 这才是我们要处理的
print(10 / 0)                # ZeroDivisionError: division by zero
print(int("abc"))            # ValueError: invalid literal for int()
print([1, 2][5])             # IndexError: list index out of range
print({"a": 1}["b"])         # KeyError: 'b'
print("x" + 1)               # TypeError: can only concatenate str

Python 内置了几十种异常，全部继承自 Exception。下面是最高频的几种：

异常触发场景典型例子
ZeroDivisionError除以零10 / 0
ValueError类型对，但值不合法int("abc")
TypeError类型不匹配"x" + 1
IndexError下标越界[1,2][5]
KeyError字典缺键{"a":1}["b"]
AttributeError属性/方法不存在(1).foo
FileNotFoundError打开不存在的文件open("nope.txt")
ImportError导入模块/名字失败import not_a_module
★

核心要点：异常是执行期抛出的、可被捕获的错误；语法错误在解析期就结束，try 是救不回来的。

try/except完整的异常处理结构

try 块里放「可能出错的代码」；一旦抛异常，控制流立刻跳到匹配的 except 块；只有没抛异常才走 else；而 finally 无论是否异常都一定执行（哪怕之前 return）。

python
def safe_div(a, b):
    try:
        r = a / b                       # 可能抛 ZeroDivisionError
    except ZeroDivisionError:           # 捕获并处理：程序不崩溃
        print("除数不能为 0")
        return None
    else:                               # 只有 try 没抛异常才会执行
        print("计算结果：", r)
        return r
    finally:                            # 无论是否异常，都一定会执行
        print("（这里的清理代码一定会跑）")

safe_div(10, 2)   # 计算结果：5.0 / 清理
safe_div(10, 0)   # 除数不能为 0 / 清理

控制流可以用一张图看得很清楚：

flowchart TD A[执行 try 块] --> B{发生了异常?} B -- 否 --> C[执行 else 块] B -- 是 --> D[从上往下匹配 except] D --> E[执行对应 except 块处理] C --> F[执行 finally 块] E --> F F --> G[程序继续 / 若无处理则向上传播]
块执行时机典型用途
try总是先执行放可能出错的代码
except抛异常且类型匹配时处理错误、降级、记日志
else仅当 try 无异常时把「成功后的逻辑」与 try 分开
finally无论是否异常都执行释放资源、关闭文件/连接
★

核心要点：finally 负责「必定要做的收尾」，else 负责「只有成功才做的后续」，两者都用好了才算真正理解异常处理。

except 进阶捕获多个异常与错误分级

需要处理不同类型的错误时，可以写多个 except，按从上到下匹配；范围大的（Exception）要放在最后兜底。一次想捕获好几类，把它们包成一个元组；想拿到异常对象，用 as。

python
try:
    n = int(input("输入一个数字："))
    print(100 / n)
except ValueError:
    print("你输入的不是整数")            # 先匹配具体的
except ZeroDivisionError:
    print("不能输入 0")
except (TypeError, OverflowError) as e:  # 元组一次性捕获多类
    print("其它数值异常：", e)
except Exception as e:                   # 兜底，务必放最后
    print("未知异常：", e)
写法作用建议
except:捕获一切（含 KeyboardInterrupt / SystemExit）❌ 易吞掉 Bug，尽量别用
except ValueError:只捕获指定异常✅ 推荐，明确、可预期
except (A, B):一次捕获多类（元组）✅ 处理方式相同时用
except ValueError as e:捕获并拿到异常对象✅ 需要看错误详情/记日志时用
!

易错点：except:（不带类型）会捕获包括KeyboardInterrupt（Ctrl+C）、SystemExit 在内的所有异常，把真正的问题掩盖成「什么都没发生」。请始终指明异常类型，哪怕最后用一个 except Exception 兜底并记录日志。

raise主动抛错与自定义异常

很多时候错误不是第三方抛的，而是你自己在业务里发现「这个状态不合法」——此时用 raise 主动抛异常，强制调用方处理。assert 用于开发期的断言检查，失败抛 AssertionError。

python
def set_age(age):
    if not isinstance(age, int):
        raise TypeError("年龄必须是整数")     # 主动抛：类型不对
    if age < 0 or age > 150:
        raise ValueError(f"年龄不合法：{age}")  # 主动抛：值不对
    print("设置年龄为", age)

# assert：开发期断言，失败抛 AssertionError；python -O 运行会被跳过
assert 100 / 10 == 10, "计算结果应等于 10"

当系统自带异常不够表达业务语义时，可定义自定义异常——继承 Exception，并可在 __init__ 里携带更多上下文信息：

python
class InsufficientBalanceError(Exception):
    """余额不足异常，携带 need / have 上下文便于上层定位。"""
    def __init__(self, need, have):
        self.need = need
        self.have = have
        super().__init__(f"余额不足：需要 {need}，仅 {have}")

class BankAccount:
    def __init__(self, balance=0):
        self.balance = balance
    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientBalanceError(amount, self.balance)
        self.balance -= amount

try:
    BankAccount(100).withdraw(200)
except InsufficientBalanceError as e:
    print("交易失败：", e)   # 交易失败： 余额不足：需要 200，仅 100
★

核心要点：用 raise 把「异常状态」显式化，比返回一个幽灵般的 None 更保险；自定义异常继承 Exception（不要继承 BaseException），这样能被通用的 except Exception 捕获。

传播与最佳实践异常链、EAFP 与「不吞异常」

异常被抛出后，会沿调用栈逐层向上传播，直到遇到能匹配它的except；若一直没人接，程序就崩溃并打印完整回溯（traceback）。如果想在「处理一层」的同时保留原始错误，用 raise ... from 把它串成一条异常链。

python
def inner():
    return 10 / 0

def outer():
    return inner()          # 异常从 inner 一路传到调用方

try:
    outer()
except ZeroDivisionError as e:
    print("在上层捕获：", e)   # 在上层捕获：  division by zero

# 抛新异常时用 from 保留原始链，方便追根溯源
try:
    n = int("abc")
except ValueError as ve:
    raise RuntimeError("转换失败") from ve   # __cause__ 指回 ValueError

处理「可能失败」的常见做法有两派，Python 社区更推崇EAFP（Easier to Ask Forgiveness than Permission）：

风格写法特点
LBYL
Look Before You Leap		if "k" in d: print(d["k"])先检查再操作；需额外判断、有竞态风险，代码更啰嗦。
EAFP
Ask Forgiveness		try: print(d["k"])
except KeyError: ...		直接做、出错再处理；更简洁、更符合 Python 习惯。
python
d = {"name": "Ada"}

# EAFP：直接取，出错再兜底（推荐）
try:
    print(d["name"])
except KeyError:
    print("键不存在")

# with 语句清理资源：文件、连接、锁等用完自动关闭，等价于 finally
with open("notes.txt", "w", encoding="utf-8") as f:
    f.write("hello")
!

千万别这样做：try: ... except: pass 是「吞异常」的典型坏味道——程序看似不崩，Bug 却被藏进暗处。
正确姿势：指明异常类型；要么记日志/降级，要么确实处理不了就用 raise 再抛，让调用方知晓。
