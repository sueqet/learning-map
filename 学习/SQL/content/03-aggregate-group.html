01先把「多行变一行」的五个聚合函数讲透
COUNT 的三种写法是后面一切分组的基石

知识点聚合函数 COUNT / SUM / AVG / MAX / MINaggregate function · 把多行压缩成一个值

聚合函数（aggregate function）的作用是把一组行压缩成单个值：COUNT 数个数、SUM 求和、AVG 求平均、MIN/MAX 取极值。它们是「统计」这件事的原子操作——只要需求里出现「总共多少」「平均多少」「最大/最小」，就一定会用到它们。理解聚合的关键不是记函数名，而是记住一条铁律：除 COUNT(*) 外，所有聚合都会忽略 NULL。

当查询里没有 GROUP BY 时，整张表会被当成一个组，查询结果永远只有一行（哪怕表是空的：COUNT 返回 0，SUM/AVG/MIN/MAX 返回 NULL）。加上 GROUP BY 之后，同样的聚合函数就会对「每个组」分别计算一次，输出多行。

COUNT 有三个容易混淆的形态：COUNT(*) 数的是行数；COUNT(col) 只数 col 非 NULL 的行；COUNT(DISTINCT col) 先对非 NULL 值去重再计数。三者可以差很多，在 customers 上分别是 8、7、5——这正是面试与排错里最常被追问的点。

  • 没有 GROUP BY 的聚合查询：整表一组，固定返回一行。
  • 聚合忽略 NULL：AVG(col) = SUM(col) / COUNT(col)，分母不是 COUNT(*)。
  • 空集上 SUM / AVG / MIN / MAX 返回 NULL，只有 COUNT 返回 0。
aggregate.sql
-- 五个聚合函数一起看：没有 GROUP BY，整张 orders（12 行）就是一组
SELECT COUNT(*)                    AS 行数,       -- 12：数行，NULL 行也算
       COUNT(customer_id)          AS 非空客户数, -- 12：该列没有 NULL
       COUNT(DISTINCT customer_id) AS 下单客户数, -- 7：去重后只有 7 个客户
       SUM(amount)                 AS 金额合计,   -- 8658.00
       ROUND(AVG(amount), 2)       AS 平均金额,   -- 721.50 = 8658 / 12
       MIN(amount)                 AS 最小金额,   -- 59.00
       MAX(amount)                 AS 最大金额    -- 2297.00
FROM orders;

预期结果（1 行 7 列）：

行数非空客户数下单客户数金额合计平均金额最小金额最大金额
121278658.00721.5059.002297.00

NULL 与空集的处理规则：这是聚合最容易翻车的地方，务必逐行对照。

函数是否忽略 NULL无行 / 全为 NULL 时说明
COUNT(*)不忽略0统计行数，整行都是 NULL 也算一行
COUNT(col)忽略0只数 col 非 NULL 的行
COUNT(DISTINCT col)忽略0非 NULL 值的去重计数
SUM(col)忽略NULL空集返回 NULL 而不是 0，需要 0 请写 IFNULL(SUM(col), 0)
AVG(col)忽略NULL等于 SUM(col) / COUNT(col)，分母不含 NULL 行

★

核心要点：COUNT(*) 数「行」，COUNT(col) 数「非空」，COUNT(DISTINCT col) 数「非空且不重复」；SUM / AVG / MIN / MAX 一律忽略 NULL，所以 AVG 的分母是 COUNT(col)，不是 COUNT(*)。

!

易错：用 SUM(amount) / COUNT(*) 手算平均值是错的。本页 orders 恰好没有 NULL，两种写法都得 721.50；一旦出现 NULL，分母变大而分子不变，平均值会被算低——正确写法永远是 AVG(amount)。

知识点GROUP BY 分组语义group by · 把行切成桶，每个桶输出一行

GROUP BY 的语义是「按分组键的值把行分到不同的桶里，每个桶最终只输出一行」。分组键取值相同的行进同一个桶；SQL 里 NULL 被视为「相同值」，所以所有分组键为 NULL 的行会合成独立的一组，不会与 0 或空字符串混在一起。

它在逻辑执行顺序中位于 WHERE 之后、HAVING 之前：FROM → WHERE → GROUP BY → 聚合 → HAVING → SELECT → ORDER BY → LIMIT。因此「分组之后，查询处理的对象就不再是行，而是组」，这也是为什么 SELECT 里只能出现分组键和聚合函数。

分组键可以是一列、多列（组合键），也可以是表达式。多列分组的组数等于各列取值组合的个数，所以 GROUP BY city, gender 在 customers 上会得到 6 组（含一组 NULL, NULL），而不是 5 或 8。性能上，如果分组键上有索引（或索引前缀有序），MySQL 可以顺着索引边读边聚合，避免建临时表和排序；否则就要把数据全部读进来再 Using temporary; Using filesort。

  • 分组键相同（含 NULL）的行合并成一个桶，每个桶只输出一行。
  • 组数 ≠ 行数；组数由分组键的取值组合数决定。
  • MySQL 8.0 不再为 GROUP BY 隐式排序，要顺序必须显式写 ORDER BY。
group_by.sql
-- 单列分组：8 行客户 → 6 个城市桶
SELECT city,
       COUNT(*)      AS 客户数,
       COUNT(gender) AS 有性别记录数   -- NULL 桶里 gender 也是 NULL，所以是 0
FROM customers
GROUP BY city;

-- 想看稳定顺序，必须显式排序（MySQL 8.0 已移除 GROUP BY 的隐式排序）
SELECT city, COUNT(*) AS 客户数
FROM customers
GROUP BY city
ORDER BY 客户数 DESC, city ASC;

核心要点：GROUP BY 之后，一行代表一个「组」而不是一条记录。SELECT 列表里只能出现分组键、聚合函数，以及依赖分组键的表达式——记住这一条，80% 的分组报错都能提前避开。

!

易错：把 GROUP BY 当 ORDER BY 用。MySQL 5.7 时代 GROUP BY 会顺带排序，8.0 已去掉该行为，结果顺序完全不可依赖；另外别以为 NULL 会被自动过滤，它自成一组，只有 WHERE city IS NOT NULL 才能把它排除。

02过滤行还是过滤组？
WHERE 与 HAVING 的分工，以及分组时最容易踩的三个坑

知识点HAVING 与 WHERE 的区别having · 分组前过滤行，分组后过滤组

WHERE 和 HAVING 都在做过滤，但作用对象完全不同：WHERE 作用在单行上，在分组之前执行；HAVING 作用在组上，在分组和聚合之后执行。因为 WHERE 执行时「组」还不存在，所以它不能引用聚合函数——写 WHERE COUNT(*) > 1 会直接报「Invalid use of group function」。

既然两条路都能达到「只保留客户数大于 1 的城市」这类效果，判断标准就是条件里有没有聚合：行级条件（状态、日期、金额阈值）一律写 WHERE，让 MySQL 尽早把无用行丢掉；只有涉及 COUNT / SUM / AVG 的组级条件才写 HAVING。

性能差异在数据量大时非常明显：把 o.status = 'paid' 写进 HAVING，意味着退款与取消的订单也参与了一次分组和聚合，算完才被丢弃；写进 WHERE 则这些行在分组前就出局了。此外 HAVING 也可以过滤分组键（如 HAVING city = '北京'），但那是 WHERE 的活，放到 HAVING 只会更慢。

  • WHERE 过滤行、HAVING 过滤组；执行顺序不能颠倒。
  • 聚合函数只能出现在 HAVING（或 SELECT / ORDER BY）里，不能进 WHERE。
  • 能写 WHERE 就别写 HAVING；HAVING 是「别无选择时」的过滤器。
where_vs_having.sql
-- 一条 SQL 里同时出现 WHERE 与 HAVING：注意它们各管一段
SELECT c.city,
       COUNT(*)        AS 订单数,
       SUM(o.amount)   AS 金额合计
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'paid'                        -- ① 分组前：丢掉退款/取消的订单（行级）
GROUP BY c.city                                -- ② 按城市分桶
HAVING COUNT(*) >= 2 AND SUM(o.amount) > 1000  -- ③ 分组后：只保留活跃城市（组级）
ORDER BY 金额合计 DESC;

-- ✗ 错误示范：聚合条件写进 WHERE
-- SELECT c.city, COUNT(*) FROM customers c JOIN orders o ON c.id = o.customer_id
-- WHERE COUNT(*) >= 2 GROUP BY c.city;   -- ERROR 1111: Invalid use of group function

预期结果（3 行，口径：先 WHERE o.status = 'paid' 再分组；深圳订单 1 条、广州金额 2297 但订单数 1，都被 HAVING 挡掉）：

WHERE 与 HAVING 对照：

核心要点：一句话判断法——条件里出现聚合函数就必须 HAVING，否则一律 WHERE。写 SQL 时先问自己「这个条件是在挑行，还是在挑组」。

!

易错：HAVING status = 'paid' 能跑通，但它会在分组后过滤，把退款、取消订单也算了一遍；另外 HAVING 里引用 SELECT 别名是 MySQL 扩展，迁到 PostgreSQL 可能报错。

知识点分组常见陷阱（非聚合列）only_full_group_by · 结果不确定比报错更危险

最常见的分组错误，是在 SELECT 里放了一个既不在 GROUP BY 中、又没有被聚合函数包住的列。此时「这一列该取组内哪一行的值」在语义上没有答案：MySQL 8.0 默认开启 ONLY_FULL_GROUP_BY，直接报 ERROR 1055 拦住你；而如果关掉它（或使用旧版本），MySQL 会「随便取一行」，结果随执行计划变化，比报错危险得多。

正确做法有三条：把该列补进 GROUP BY（它就成了分组键的一部分，组数可能变多）；用聚合函数把这一列收拢成一个确定值（MIN / MAX / SUM 等）；如果确实只需要「任意一个」，用 MySQL 提供的 ANY_VALUE(col) 显式表态，而不是依赖隐式行为。

除此之外还有几个高频坑：NULL 自成一组导致「未知」数据被单独统计；AVG 用 COUNT(*) 当分母；把行级条件写进 HAVING；以及分组键上套了函数（如 GROUP BY DATE_FORMAT(order_date,'%Y-%m')）导致索引失效，只能扫全表再建临时表。

  • 非聚合列 = 语义不确定：要么进 GROUP BY，要么被聚合，要么显式 ANY_VALUE。
  • NULL 自成一组，必要时用 GROUP BY IFNULL(col,'未知') 主动合并。
  • 分组键上用函数会破坏索引的有序性，代价通常变成全表扫描 + 临时表。
pitfall.sql
-- ✗ 错误写法：name 既不在 GROUP BY，也没有被聚合
SELECT city, name, COUNT(*) FROM customers GROUP BY city;
-- ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause
--   and contains nonaggregated column 'test.customers.name' ...

-- ✓ 写法 1：把 name 也作为分组键（组数会变多）
SELECT city, name, COUNT(*) AS n FROM customers GROUP BY city, name;

-- ✓ 写法 2：用聚合把非分组列收拢成确定值
SELECT city,
       COUNT(*)            AS 客户数,
       MIN(signup_date)    AS 最早注册,
       MAX(signup_date)    AS 最近注册
FROM customers
GROUP BY city;

-- ✓ 写法 3：确实只需要任意一行时，显式声明（MySQL 专有函数）
SELECT city, ANY_VALUE(name) AS 任意姓名, COUNT(*) AS n
FROM customers
GROUP BY city;

03去重计数、多列分组与超聚合
从「数几个人」到「各层小计 + 总计」

知识点去重计数与多列分组count distinct · 数「不同的值」而不是「行」

业务里「有多少客户下单了」问的从来不是订单行数，而是不同客户的数量，这就要用 COUNT(DISTINCT col)。它先剔除 NULL、再去重、最后计数，因此在 orders 上得到 7（7 个不同客户），而不是 12（订单行数）。MySQL 也支持多列去重 COUNT(DISTINCT a, b)，统计的是「组合」的不重复个数，任何一列为 NULL 的行都不计入。

多列分组则用 GROUP BY a, b，语义是「先按 a 分桶，再在每个桶里按 b 细分」，最终每个取值组合一行。GROUP BY city, gender 在 customers 上是 6 行，其中一行是 NULL, NULL（id=8 的客户城市和性别都为空）——这类「双 NULL 组」在报表里常被当成脏数据，处理前先确认业务含义。

代价方面：COUNT(DISTINCT col) 必须去重，通常要借助临时表或排序，比 COUNT(*) 贵；如果 col 上有索引且能走覆盖索引，代价会明显下降。多列分组的组数可能爆炸式增长（列的组合数），在宽表上要留意结果集大小与 Using temporary 的出现。

  • 三种计数的语义互不相同，写报表前先想清楚要数的是「行」「非空值」还是「不同值」。
  • COUNT(DISTINCT a, b) 统计组合去重数，含 NULL 的组合会被跳过。
  • 多列分组的组数是各列取值组合数，可能远大于单列分组。
count_distinct.sql
-- ① 三种计数放一起：8 / 7 / 5
SELECT COUNT(*)               AS 总行数,      -- 8
       COUNT(city)            AS 有城市的人数, -- 7：id=8 的 city 为 NULL
       COUNT(DISTINCT city)   AS 不同城市数    -- 5
FROM customers;

-- ② 多列分组：城市 × 性别，每个组合一行（共 6 行，含一组 NULL, NULL）
SELECT city, gender, COUNT(*) AS 人数
FROM customers
GROUP BY city, gender;

-- ③ 只保留人数 ≥ 2 的组合：多列分组 + HAVING
SELECT city, gender, COUNT(*) AS 人数
FROM customers
GROUP BY city, gender
HAVING COUNT(*) >= 2;

核心要点：注意最后一行的对照——COUNT(DISTINCT city, gender) 得 5，而 GROUP BY city, gender 得 6。差异来自 NULL：去重计数会跳过含 NULL 的组合，分组则把 NULL 当成一个正常取值。

!

易错：用 COUNT(DISTINCT col) 时要意识到它比 COUNT(*) 贵得多（需要去重结构），大表上频繁调用会拖慢查询；如果只要「有没有」而不在乎精确值，可以先想想业务上是否能用 EXISTS 之类的半连接替代。

知识点GROUP BY 扩展（ROLLUP / 过滤分组）with rollup · 小计与总计一次查出

报表里除了明细分组，往往还要「小计」和「总计」。MySQL 8.0 支持在 GROUP BY 后加 WITH ROLLUP，在结果集末尾追加逐层汇总行：单列 ROLLUP 追加一行总计，多列 ROLLUP 会按层级从细到粗逐级追加。代价是这些汇总行会把被汇总的列置为 NULL，与数据本身真的为 NULL 的行混在一起，肉眼无法区分。

MySQL 8.0 提供了 GROUPING(col) 函数来消除歧义：返回 1 表示这一行的该列是「汇总产生的 NULL」，返回 0 表示是真实数据。配合 IF(GROUPING(status) = 1, '合计', status) 就能输出可读的报表。它也解决了 ROLLUP 与 HAVING 冲突的问题：HAVING 会把汇总行一起过滤掉，需要时用 OR GROUPING(status) = 1 放行。

需要注意的是，MySQL 只支持 ROLLUP，不支持 CUBE 与 GROUPING SETS——那两种是 PostgreSQL / Oracle / SQL Server 的语法。在 MySQL 里要等价效果，只能把多个分组的查询用 UNION ALL 拼起来。

  • WITH ROLLUP 追加汇总行，被汇总的列显示为 NULL。
  • GROUPING(col) = 1 才能可靠地区分「汇总行」与「真 NULL」。
  • MySQL 不支持 CUBE / GROUPING SETS，只能用 UNION ALL 模拟。
rollup.sql
-- ① 明细 + 总计：WITH ROLLUP
SELECT status,
       COUNT(*)    AS 订单数,
       SUM(amount) AS 金额合计
FROM orders
GROUP BY status WITH ROLLUP;

-- ② 用 GROUPING() 区分「真 NULL」与「汇总行」（MySQL 8.0）
SELECT IF(GROUPING(status) = 1, '合计', status) AS 状态,
       COUNT(*)    AS 订单数,
       SUM(amount) AS 金额合计
FROM orders
GROUP BY status WITH ROLLUP;

-- ③ ROLLUP 与 HAVING 冲突时，用 GROUPING() 放行汇总行
SELECT IF(GROUPING(status) = 1, '合计', status) AS 状态, COUNT(*) AS 订单数
FROM orders
GROUP BY status WITH ROLLUP
HAVING COUNT(*) >= 2 OR GROUPING(status) = 1;

-- ④ 多列 ROLLUP：先出每个「状态 × 客户」的明细，再出状态小计，最后总计
SELECT o.status, o.customer_id, COUNT(*) AS 订单数, SUM(o.amount) AS 金额合计
FROM orders o
GROUP BY o.status, o.customer_id WITH ROLLUP;

WITH ROLLUP✓ 支持逐层小计 + 总计，汇总列显示为 NULL

CUBE✗ 不支持PostgreSQL / Oracle / SQL Server 支持，MySQL 用 UNION ALL 模拟
GROUPING SETS✗ 不支持同上，需要多条查询 UNION ALL 拼装

★

核心要点：ROLLUP 的价值是「一条 SQL 同时拿到明细与总计」；代价是汇总行的 NULL 与真实 NULL 混淆，所以生产报表里请务必用 GROUPING() 或 IF(GROUPING(col)=1,'合计',col) 明确标注。

!

易错：本页的练习台不支持 WITH ROLLUP / GROUPING()，请到真实数据库（MySQL 8.0）验证；另外 ROLLUP 配合 HAVING 时会连汇总行一起过滤掉，这是最常见的「总计行消失」原因。
