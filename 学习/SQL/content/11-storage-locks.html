知识点InnoDB vs MyISAM 与引擎选择storage-engine · 引擎决定「事务、锁、恢复」三件事

存储引擎（storage engine）是 MySQL 里真正负责「数据怎么存、怎么读、怎么加锁、能不能回滚」的插件层。Server 层负责解析 SQL、优化与执行，但事务、锁、崩溃恢复这些能力全部由引擎提供。所以同一句 SQL 在不同引擎上，并发行为和安全性完全不同。MySQL 8.0 的默认引擎是 InnoDB。

InnoDB 的核心优势有三点：行级锁 + MVCC 让读写并发不互相阻塞；redo / undo 日志保证崩溃后已提交数据不丢、未提交数据能回滚；聚簇索引按主键组织数据，主键查询一次 B+ 树即可拿到整行。它还支持外键、事务、8.0 的全文索引。

MyISAM 只有表级锁，不支持事务、不支持崩溃恢复、不支持外键；它的索引和数据文件分离（非聚簇），一次写会锁整张表。历史上它以「count(*) 快、结构简单」著称，但 8.0 里这些优势已不明显，只适合日志归档、只读字典这类极低并发场景。

  • 结论：新项目一律 InnoDB；遇到 MyISAM 老表，用 ALTER TABLE … ENGINE=InnoDB 迁移。
  • 注意：迁移会重建表、长时间持有锁，需在低峰期做，并预留与原表相当的空间。

核心要点：选引擎只看三件事——要不要事务、要不要行级并发、要不要崩溃恢复。只要有一个「要」，答案就是 InnoDB。

知识点redo / undo / binlog 三种日志redo-undo-binlog · 不丢、能回滚、能归档

MySQL 里同时存在三种日志，它们各管一段，不要混为一谈：redo log 保证「已提交的改动不丢」；undo log 保证「未提交的改动能回滚，且能读到旧版本」；binlog 保证「数据能归档、能复制到从库、能按时间点恢复」。

redo log 属于 InnoDB 层，是物理逻辑日志，采用 WAL（Write-Ahead Logging，预写日志）：修改数据页时先写 redo，脏页可以延迟刷盘，只要事务提交时 redo 已落盘（innodb_flush_log_at_trx_commit=1）就不算丢。它的空间是循环复用的，所以一旦写满就必须推进 checkpoint 把脏页刷下去。

undo log 也属于 InnoDB 层，是逻辑日志，记录的是「反向操作」：INSERT 对应 DELETE，UPDATE 记录旧值。它承担两件事——事务回滚，以及 MVCC 一致性读时沿版本链回溯旧数据。所以长事务会让 undo 无法被清理，形成历史版本堆积。

binlog 属于 Server 层，所有引擎共用，是追加写的逻辑日志，用于归档、主从复制、基于时间点恢复（PITR）。格式有 STATEMENT / ROW / MIXED，8.0 默认 ROW。为保证 redo 与 binlog 内容一致，InnoDB 提交时用两阶段提交（2PC）：先写 redo 并置 prepare，再写 binlog，最后 redo 置 commit。

知识点MVCC 与 Read Viewmvcc-read-view · 读不加锁，也能读到一致快照

MVCC（Multi-Version Concurrency Control，多版本并发控制）让读操作不加锁也能看到一致的数据：每一行在 undo log 里串成一条版本链，读的时候用一份 Read View（读视图）决定「这条版本我该不该看见」。这样读和写互不阻塞，是 InnoDB 高并发的基石。

每行记录都有隐藏列：DB_TRX_ID 是最后修改它的事务 id，DB_ROLL_PTR 指向 undo log 里的旧版本，DB_ROW_ID 在无主键时充当行标识。更新一行不会原地覆盖，而是写入新版本、把 roll_ptr 指向上一个版本，于是形成「最新版本 → 旧版本 → 更旧版本」的链。

Read View 有四个关键字段：m_ids（创建时仍活跃的事务 id 列表）、min_trx_id、max_trx_id、creator_trx_id。判断某版本是否可见：若 DB_TRX_ID == creator_trx_id 则自己改的可见；若 DB_TRX_ID < min_trx_id 说明它早已提交，可见；若 DB_TRX_ID >= max_trx_id 说明是「未来事务」，不可见；若落在 m_ids 里说明创建时它还没提交，不可见。不可见就沿 DB_ROLL_PTR 往下一个版本走，直到找到可见版本或链尾。

RC 与 RR 的差别只在「什么时候生成 Read View」：RC 每条 SELECT 都新建一个，所以能看到别人新提交的数据；RR 只在事务第一次快照读时建一次，之后一直复用，所以整事务看到同一份快照。

mvcc.sql
-- 查看 / 设置隔离级别
SELECT @@transaction_isolation;                       -- 8.0 变量名，旧版是 tx_isolation
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 快照读（不加锁，走 MVCC）：读的是 Read View 对应的历史版本
START TRANSACTION;
SELECT level FROM customers WHERE id = 3;             -- 第一次快照读，建立 Read View

-- 当前读（加锁，读最新已提交版本）：不受 Read View 影响
SELECT level FROM customers WHERE id = 3 FOR UPDATE;

-- 事务开启时就固定快照（RR 下等价于第一次 SELECT 的效果）
START TRANSACTION WITH CONSISTENT SNAPSHOT;
SELECT COUNT(*) FROM orders;
COMMIT;

-- 长事务排查：跑得越久，undo 越不能清理
SELECT trx_id, trx_started, TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs, trx_state
FROM information_schema.innodb_trx
ORDER BY secs DESC;
对比项READ COMMITTED（RC）REPEATABLE READ（RR，默认）
Read View 生成时机每条 SELECT 都新建事务内第一次快照读时建一次
同一事务两次查询可能看到不同结果（不可重复读）结果一致
幻读可能出现快照读不出现；当前读靠间隙锁/临键锁防住
间隙锁基本不用（唯一键冲突、外键检查除外）范围条件会加间隙锁
并发度更高，锁更少略低，但语义更稳
典型使用互联网高并发读多写少对一致性要求强的账务类逻辑
★

核心要点：「快照读」看 Read View + undo 版本链，「当前读」（FOR UPDATE / FOR SHARE / UPDATE / DELETE）永远读最新已提交版本并加锁。RR 之所以「可重复读」，靠的就是复用第一次的 Read View。

!

易错：RR 下「事务 A 读到旧值」并不代表 B 的提交丢了——只是 A 的 Read View 把它判定为不可见。另外 DB_TRX_ID 不是自增主键，别拿它当业务 id。

知识点行锁 / 表锁 / 意向锁 / 间隙锁lock-types · 锁什么、锁多宽，取决于索引

InnoDB 的锁可以按粒度分成两层：表级锁（表锁、意向锁、元数据锁 MDL、AUTO-INC 锁）和行级锁（记录锁、间隙锁、临键锁、插入意向锁）。加行锁之前，InnoDB 会先在表上加一把意向锁，它的作用是「声明这张表里有行正被锁着」，这样别人想加表锁时不用逐行检查就能快速判断该不该等。

行级锁有三种形态：记录锁（Record Lock）锁住一条索引记录；间隙锁（Gap Lock）锁住两个索引值之间的开区间，防止别人插入；临键锁（Next-Key Lock）= 间隙锁 + 记录锁，锁定左开右闭区间，是 RR 下范围查询的默认加锁方式。此外还有插入意向锁，表示「我要往这个间隙插一条记录」，它只在插入时短暂出现。

到底加哪种锁，取决于三件事：是否走索引、是否唯一命中、隔离级别。走唯一索引且等值命中存在的记录时，临键锁退化为记录锁；没走索引就会退化成「锁住扫描到的所有行」，等价于全表加锁。RR 下范围条件会加间隙锁，RC 下基本只用记录锁（唯一键冲突检查、外键检查例外）。

locks.sql
-- 排他行锁 / 共享行锁
START TRANSACTION;
SELECT * FROM customers WHERE id = 3 FOR UPDATE;     -- X 锁，别人不能改也不能加锁读
SELECT * FROM customers WHERE id = 3 FOR SHARE;      -- S 锁，别人可读，改则要等

-- 唯一索引等值命中 -> 记录锁；范围条件 -> 临键锁（锁住区间，防插入）
SELECT * FROM orders WHERE customer_id = 3 FOR UPDATE;        -- 非唯一索引，多个记录 + 间隙
SELECT * FROM orders WHERE id > 5 AND id < 10 FOR UPDATE;    -- 范围，加临键锁

-- 没走索引的更新：会锁住扫描到的每一行（危险）
UPDATE customers SET level = '黄金' WHERE city = '北京';       -- city 无索引 -> 全表行锁

-- 显式表锁（一般不用，交给意向锁自动处理）
LOCK TABLES orders WRITE;
UNLOCK TABLES;

-- 查看当前锁与等待关系（8.0）
SELECT ENGINE, OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

知识点死锁成因与排查deadlock · 循环等待是怎么形成的

死锁（deadlock）是两个及以上事务各自持有别人需要的锁、又都在等对方释放，形成循环等待。它需要同时满足四个条件：互斥、持有并等待、不可抢占、循环等待——打破其中任意一个，死锁就不会发生。实践中最容易打破的是「循环等待」，也就是让所有事务按同一顺序加锁。

InnoDB 默认开启死锁检测（innodb_deadlock_detect=ON）：一旦发现循环等待，会立刻回滚「undo 量较小」的那个事务，向客户端返回 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction，另一个事务继续执行。这跟锁等待超时不是一回事：innodb_lock_wait_timeout 默认 50 秒，是「等了太久」主动放弃，不涉及循环。

排查手段：SHOW ENGINE INNODB STATUS\G 里的 LATEST DETECTED DEADLOCK 段落会打印两个事务的 SQL、持有/等待的锁、被回滚者；performance_schema.data_lock_waits 给出实时的等待关系；打开 innodb_print_all_deadlocks=ON 可以把每次死锁写进错误日志，便于事后统计。

处理原则：应用层必须捕获 1213 并重试（带退避），而不是把错误抛给用户；同时从 SQL 侧消除成因——固定加锁顺序、缩短事务、避免无索引更新、避免在事务里做远程调用。

deadlock.sql
-- 查看最近一次死锁的完整信息（重点看 LATEST DETECTED DEADLOCK 段落）
SHOW ENGINE INNODB STATUS\G

-- 实时看谁在等谁（8.0）
SELECT w.REQUESTING_ENGINE_TRANSACTION_ID AS waiter,
       w.BLOCKING_ENGINE_TRANSACTION_ID  AS blocker,
       l.OBJECT_NAME, l.INDEX_NAME, l.LOCK_MODE, l.LOCK_DATA
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks l
  ON l.ENGINE_LOCK_ID = w.REQUESTING_ENGINE_LOCK_ID;

-- 把每次死锁都记进错误日志，便于事后统计高频成因
SET GLOBAL innodb_print_all_deadlocks = ON;

-- 调小等待时间，让「锁等待」更快暴露（死锁检测与之无关）
SET SESSION innodb_lock_wait_timeout = 5;

-- 易造成死锁的写法：两个事务按不同顺序更新同一批行
-- 事务 A: UPDATE customers SET level='黄金' WHERE id=1; 然后 WHERE id=2;
-- 事务 B: UPDATE customers SET level='白银' WHERE id=2; 然后 WHERE id=1;
-- 修复：两个事务都改成先 id=1 再 id=2（固定顺序）

知识点加锁实践与避免锁等待locking-practice · 短事务、有序、走索引

减少锁等待的底层原则只有一句：让事务尽可能短、加锁尽可能窄、加锁顺序尽可能一致。具体落地就是三条：把 SQL 写成能精确命中主键或唯一索引的形式；把事务边界缩到「只包住必须原子的一组 SQL」，绝不在事务里发 RPC、调第三方、跑大查询；对同一批资源，所有代码路径都按同一个顺序加锁。

锁策略上分两类：悲观锁用 SELECT … FOR UPDATE 先占住行再改，适合冲突概率高的场景（如库存扣减）；乐观锁用版本号或状态条件在 UPDATE 时校验，冲突才失败重试，适合冲突概率低的场景（如内容编辑）。8.0 还提供 FOR UPDATE NOWAIT（拿不到锁立即报错，不排队）和 SKIP LOCKED（跳过被别人锁住的行），非常适合抢任务队列这类「谁抢到算谁的」场景。

批量更新要分批提交，避免一个事务锁住几万行并长时间持有 undo；删除/更新历史数据时按主键区间切片，每批 sleep 一小会儿让别的会话有机会插入。上线前用压测和 data_lock_waits 观察真实锁冲突，比事后救火有效得多。

practice.sql
-- ① 悲观锁：库存扣减，主键精确命中，事务里只有必要的两条 SQL
START TRANSACTION;
SELECT stock FROM products WHERE id = 5 FOR UPDATE;        -- 只锁 id=5 这一行
UPDATE products SET stock = stock - 1 WHERE id = 5 AND stock >= 1;
COMMIT;

-- ② 乐观锁：不带 FOR UPDATE，用版本号/条件判断，冲突就重试
UPDATE products
   SET stock = stock - 1, version = version + 1
 WHERE id = 5 AND stock >= 1 AND version = 12;
-- 受影响行数 = 0 表示被别人抢先改过，应用层重试

-- ③ 拿不到锁就立刻返回，不要排队
SELECT * FROM order_items WHERE order_id = 100 FOR UPDATE NOWAIT;

-- ④ 抢任务队列：跳过已被别人锁住的行
SELECT id FROM order_items
 WHERE status = 'pending'
 ORDER BY id
 LIMIT 10
 FOR UPDATE SKIP LOCKED;

-- ⑤ 大表清理：按主键切片分批，每批一个小事务
DELETE FROM order_log WHERE id <= 100000 LIMIT 1000;   -- 循环执行，每批 COMMIT

-- ⑥ 观测：谁在等锁、等了多久
SELECT * FROM performance_schema.data_lock_waits;
SELECT trx_id, trx_state, trx_started, trx_rows_locked
FROM information_schema.innodb_trx
WHERE trx_rows_locked > 0;

★

核心要点：锁等待几乎总能追到三个原因——没走索引、事务太长、加锁顺序不一致。按这个顺序排查，命中率最高。

!

易错：SKIP LOCKED 会跳过被锁的行，拿到的结果不是完整结果集，只能用于「任务分发」这类允许跳过的场景，绝不能用在需要精确统计的查询上。另外 NOWAIT / SKIP LOCKED 需要 MySQL 8.0 及以上。
