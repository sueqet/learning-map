Learning Points · 知识点

01先建立地图：数据库是什么，SQL 又分成哪几类

知识点数据库、DBMS 与关系模型database · 数据放在哪里、以什么形状存放

数据库（database）是按照一定结构组织起来、能被高效读写的数据集合；数据库管理系统（DBMS, Database Management System）则是管理这些数据的软件，例如 MySQL、PostgreSQL、Oracle、SQL Server、SQLite。你平时说的「装了个数据库」，其实装的是 DBMS，数据文件由它替你保管。两者是「内容」与「管家」的关系，不是同义词。

目前应用最广的一类是关系型数据库（RDBMS），它基于 1970 年 E. F. Codd 提出的关系模型（relational model）：数据以二维表的形式存放，表与表之间通过「值相等」建立联系。关系模型把「数据长什么样」和「数据怎么存」分开了——你只需用声明式语言 SQL 描述想要什么，不必关心磁盘上怎么找，这正是它统治企业数据几十年的原因。

关系模型有一套严格术语，日常叫法和学术叫法要对得上号，否则读文档和面试时会卡住。下面这张表是必备对照：

日常叫法关系模型术语含义本站示例
数据库database / schema一组相关表的集合库名 shop
表关系 relation同结构记录的集合，二维表customers、orders
行元组 tuple / 记录 record一条完整记录一位客户、一笔订单
列属性 attribute / 字段 field同一种数据项，有固定类型name、amount
取值域 domain列允许的取值范围status ∈ {paid, refunded, cancelled}
行数基数 cardinality表中有多少条记录orders 有 12 行

★

核心要点：数据库是「数据集合」，DBMS 是「管理它的软件」；关系模型的四大要素是表（关系）、行（元组）、列（属性）、域（取值范围）。SQL 查询的输入和输出都是表——这是后面学 JOIN、子查询的思维基础。

!

易错：关系模型里的「关系」不是「表之间有关联」的意思，它就是「表」本身；「主键」也不是「主要的那个键」，而是唯一标识一行的约束。把日常语义套到术语上，是初学者最容易翻车的地方。

知识点SQL 语言分类（DDL/DML/DQL/DCL/TCL）sql-family · 一条语句属于哪一类，决定了它能不能回滚

SQL（Structured Query Language，结构化查询语言）是关系型数据库的标准语言。按「操作对象」和「是否受事务控制」的不同，习惯上分成五类：DDL（数据定义）、DML（数据操纵）、DQL（数据查询）、DCL（数据控制）、TCL（事务控制）。分类不是学术游戏——它直接决定了这条语句能不能被 ROLLBACK 撤销、会不会隐式提交。

最容易记混的是 DQL 与 DML。严格说 SELECT 只读不写，所以单列一类叫 DQL；但在很多资料和面试语境里，DQL 会被并入 DML，两种说法都算对，你答的时候说明清楚即可。另一个高频点是 TRUNCATE：它长得像 DML，实际是 DDL。

下面这张表把五类的代表语句、作用对象和事务特性一次说清：

分类全称作用对象代表语句能否 ROLLBACK
DDLData Definition Language库、表、索引等结构CREATE、ALTER、DROP、TRUNCATE、RENAME不能（隐式提交）
DMLData Manipulation Language表中的行INSERT、UPDATE、DELETE、REPLACE能（事务内）
DQLData Query Language表中的行（只读）SELECT不需要
DCLData Control Language用户权限GRANT、REVOKE不能（隐式提交）
TCLTransaction Control Language事务边界BEGIN、COMMIT、ROLLBACK、SAVEPOINT本身就是事务控制
five-families.sql
-- DDL：定义结构（隐式提交，执行后无法 ROLLBACK）
CREATE TABLE customers (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(50) NOT NULL,
  city        VARCHAR(30),
  gender      CHAR(1),
  signup_date DATE,
  level       VARCHAR(10)
);

-- DML：操纵数据（事务内可回滚）
INSERT INTO customers (name, city, gender, signup_date, level)
VALUES ('赵敏', '北京', 'F', '2024-03-01', '金卡');

UPDATE customers SET level = '银卡' WHERE id = 9;
DELETE FROM customers WHERE id = 9;

-- DQL：只读查询
SELECT level, COUNT(*) AS 人数 FROM customers GROUP BY level;

-- DCL：控制权限
GRANT SELECT ON shop.* TO 'report'@'%';

-- TCL：控制事务边界
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 1;
ROLLBACK;   -- 上面的 UPDATE 被撤销
★

核心要点：记两条分界线就够了：①「动结构 = DDL，动数据 = DML，只读 = DQL」；② DDL/DCL 会隐式提交当前事务，所以 TRUNCATE、DROP 一旦执行，前面的未提交修改也会一起落地。

!

易错：别以为「能写 WHERE 的就是 DML」——TRUNCATE TABLE 属于 DDL，它不能带 WHERE，只能整表清空，而且 MySQL 的 InnoDB 里它按数据页删除，速度快但不可回滚。想删部分行，只能用 DELETE ... WHERE。

提示：注意 TRUNCATE 虽然「清数据」，但它归在 DDL，不能带 WHERE、不能回滚。

02把环境跑起来：连接数据库，理解表的结构

知识点环境搭建：MySQL 安装、连接与客户端env-setup · 从零到能跑第一条语句

学 SQL 的第一道门槛不是语法，而是「把数据库跑起来并能连上」。完整链路是：安装 MySQL 8.0 → 启动服务（Windows 上是 MySQL80 服务，macOS/Linux 常用 brew services start mysql 或 systemctl start mysqld）→ 用客户端连接 → 验证版本与字符集。

连接需要五个要素：主机（host）、端口（port）、用户名（user）、密码（password）、库名（database）。MySQL 默认监听 3306 端口，本地地址写作 127.0.0.1 或 localhost。命令行客户端 mysql 是最轻量的验证工具；日常开发更常用图形客户端，见下表。

搭环境时最容易忽略的是字符集。MySQL 8.0 默认字符集已是 utf8mb4（能存 4 字节的 emoji），但老版本或手工建的库可能是 utf8（实际只有 3 字节），一旦存 emoji 就会报 Incorrect string value（因为 utf8 这个别名只支持 3 字节的 utf8mb3）。建库时显式写清楚最省事。

客户端形态适合场景备注
mysql 命令行终端快速验证、脚本化、服务器上运维MySQL 自带，最稳
MySQL Workbench图形官方全套工具、ER 图、建表向导Oracle 官方免费
DBeaver图形多数据库通用、免费开源支持 MySQL/PG/Oracle 等
DataGrip / Navicat图形商业开发，SQL 补全与调试强付费
Python + PyMySQL代码程序里连库做分析或 ETL需安装驱动

# 1) 命令行连接：-h 主机  -P 端口  -u 用户  -p 表示「回车后再输密码」
mysql -h 127.0.0.1 -P 3306 -u root -p

# 2) 连上后先做三件体检

SHOW VARIABLES LIKE 'character_set_server';              -- 期望 utf8mb4
SELECT user, host FROM mysql.user;                       -- 看有哪些账号

  COLLATE utf8mb4_0900_ai_ci;

# 4) 一次性执行脚本文件（不进入交互界面）

★

核心要点：连接五要素「主机 + 端口 + 用户 + 密码 + 库名」；MySQL 默认端口 3306，8.0 默认字符集 utf8mb4。装完先跑 SELECT VERSION()，能返回版本号就说明环境通了。

!

易错：① 不要把 root 账号和空密码暴露到公网——root@'%' 是常见入侵入口，生产应建最小权限账号；② 命令行里 -p 后面不要空格再加密码（会明文进 shell 历史），正确写法是只写 -p 然后回车输入；③ 报 Can't connect to MySQL server on '127.0.0.1' 多半是服务没启动或端口被占用，先查服务状态再改配置。

知识点表、行、列：主键与外键table-model · 约束是数据正确性的第一道闸门

一张表由列定义和行数据组成，但光有列和行还不够——必须加约束（constraint），数据库才能替你把住数据质量。主键（primary key）是唯一标识一行的列或列组合，它必须非空且唯一，一张表最多只能有一个主键（可以是多列组成的复合主键）。有了主键，你才能可靠地「定位某一行」。

外键（foreign key）是另一张表的主键在本表中的引用，用来维护引用完整性（referential integrity）。例如 orders.customer_id 指向 customers.id，数据库就会拒绝插入一个不存在的客户编号，避免出现「孤儿订单」。外键还可以声明 ON DELETE CASCADE（父行删除时子行跟着删）或 ON DELETE RESTRICT（有子行时禁止删除父行）。

设计上还有一个常考取舍：用自增整数做代理键（surrogate key），还是用身份证号、订单号这类自然键（natural key）？主流做法是用代理键做技术主键，把自然键加上唯一索引——因为自然键可能变长、可能变更，改起来代价很高。

对比项主键 primary key外键 foreign key
作用唯一标识本表的一行引用另一张表的主键，维护引用完整性
数量限制一张表最多 1 个（可复合）一张表可以有多个
能否为 NULL不能可以（表示「暂无关联」）
自动索引会创建主键索引（聚簇索引）InnoDB 要求有索引，没有就自动建一个
跨表影响无插入/删除子表行时会被父表校验
constraints.sql
CREATE TABLE customers (
  id   INT PRIMARY KEY AUTO_INCREMENT,   -- 代理主键：自增整数
  name VARCHAR(50) NOT NULL,
  city VARCHAR(30),
  UNIQUE KEY uk_name (name)              -- 自然键上的唯一约束
) ENGINE=InnoDB;

CREATE TABLE orders (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,
  order_date  DATETIME NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  status      VARCHAR(12) NOT NULL DEFAULT 'paid',
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id)
    ON DELETE RESTRICT ON UPDATE CASCADE,   -- 有订单的客户不允许被删
  KEY idx_customer (customer_id),
  CONSTRAINT ck_amount CHECK (amount >= 0)  -- 金额不允许为负
) ENGINE=InnoDB;

-- 外键生效的验证：customer_id = 999 不存在，这条 INSERT 会直接报错
INSERT INTO orders (customer_id, order_date, amount, status)
VALUES (999, '2024-05-01 10:00:00', 199.00, 'paid');
★

核心要点：主键 = 唯一 + 非空 + 一张表最多一个；外键 = 指向别的表的主键 + 可以为 NULL + 可以有多个。外键是「数据库帮你兜底」的引用完整性，而不是性能优化手段。

!

易错：① 主键为 NULL 是不允许的，但唯一索引（UNIQUE）允许多个 NULL；② 复合主键 PRIMARY KEY(order_id, product_id) 保证的是「组合唯一」，单独一列仍可重复；③ 外键会带来写入开销，很多互联网公司选择在应用层保证一致性而不用物理外键——这是权衡，不是「外键没用」。

03把字段类型选对，再写下第一条 SQL

知识点常用数据类型与选型data-types · 类型选错，后面再改要付代价

数据类型（data type）决定了三件事：能存什么值、占多少空间、能做什么运算。它属于 DDL 的一部分，建表时定下来，之后再改（ALTER TABLE ... MODIFY）往往要重建表，大表上代价很高，所以一开始就要选对。

选型的基本原则是：够用就好、语义清晰、避免隐式转换。数值分整数（TINYINT/INT/BIGINT）与精确/近似小数（DECIMAL vs FLOAT/DOUBLE）；字符串分定长 CHAR 与变长 VARCHAR，超长文本用 TEXT；时间分 DATE、DATETIME、TIMESTAMP。用字符串存数字，会让索引失效、排序变成字典序（'10' < '9'），是最常见的性能与正确性双杀。

一个真实的高频坑：用 FLOAT 存金额。FLOAT/DOUBLE 是二进制浮点，0.1 + 0.2 不等于 0.3，对账时会出现 0.01 元的偏差。金额一律用 DECIMAL(M,D) 精确小数。

场景推荐类型原因不要用
订单金额、单价DECIMAL(10,2)精确十进制，不会出现浮点误差FLOAT / DOUBLE
自增主键INT / BIGINT有序、占位小，适合做聚簇索引VARCHAR(32) 的 UUID
姓名、城市VARCHAR(n)变长，按实际长度存储CHAR(255) 定长浪费
性别、状态码CHAR(1) / TINYINT长度固定，读取快TEXT
下单时间DATETIME原样存储，不随时区变化，范围到 9999 年存字符串 '2024-05-01'
创建/更新时间戳TIMESTAMP按 UTC 存储、自动随会话时区换算用来存 2038 年后的时间
布尔标记TINYINT(1)MySQL 里 BOOLEAN 就是它的别名CHAR(1) 存 'Y'/'N'
types.sql
CREATE TABLE products (
  id       INT PRIMARY KEY AUTO_INCREMENT,
  name     VARCHAR(60)   NOT NULL,          -- 变长字符串，按需分配
  category VARCHAR(20)   NOT NULL,          -- 分类名，短且固定取值
  price    DECIMAL(10,2) NOT NULL,          -- 金额：精确小数，共 10 位、2 位小数
  stock    INT UNSIGNED  NOT NULL DEFAULT 0,-- 库存不能为负
  is_active TINYINT(1)   NOT NULL DEFAULT 1,-- 布尔标记
  created_at TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP
                         ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 浮点误差演示：结果不是 0.3
SELECT 0.1 + 0.2 AS float_result;          -- 0.30000000000000004
SELECT CAST(0.1 AS DECIMAL(5,2)) + CAST(0.2 AS DECIMAL(5,2)) AS decimal_result; -- 0.30

-- 查看某列的真实类型与字节数
SELECT COLUMN_NAME, DATA_TYPE, COLUMN_TYPE, NUMERIC_PRECISION, NUMERIC_SCALE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'products';
★

核心要点：三条选型铁律：金额用 DECIMAL、时间用 DATETIME/TIMESTAMP（别存字符串）、短定长用 CHAR、其他用 VARCHAR。类型一致才能用上索引，也才不会出现「数字按字典序排」这类诡异结果。

!

易错：① TIMESTAMP 在 MySQL 中范围只到 2038-01-19，且会随服务器时区换算，跨时区业务容易「时间漂移」，长期存储建议用 DATETIME；② VARCHAR(255) 不是越大越好，过长的定义会影响索引长度和内存临时表；③ MySQL 8.0 的 utf8mb4 下 VARCHAR(n) 的 n 是字符数而非字节数。

知识点第一条 SQL：建库建表与插入数据first-sql · 打通「定义 → 写入 → 读出」的闭环

现在把前面几块拼起来，走完一条完整链路：CREATE DATABASE（建库）→ USE（切换库）→ CREATE TABLE（建表）→ INSERT（写数据）→ SELECT（读数据）。这五步是每个 SQL 项目的起点，也是你验证环境是否正常的标准动作。

写 INSERT 时强烈建议显式列出列名：INSERT INTO customers (name, city) VALUES (...)。省略列名依赖表的列顺序，一旦表结构变化（加列、调序）就会静默写错数据。同理，SELECT 也建议写清需要的列而不是 SELECT *。

最后要养成的习惯是：每写一条查询，都能预判它返回几行、关键值是什么。本站的交互练习台内置了统一示例数据（customers 8 行、orders 12 行、products 6 行、order_items 15 行、employees 9 行），你可以直接改查询、立刻看结果对照。

步骤语句预期结果
1 建库CREATE DATABASE shop ...库创建成功，字符集 utf8mb4
2 选库USE shop;提示 Database changed
3 建表CREATE TABLE customers (...)Query OK，可用 DESC customers 验证
4 插入INSERT INTO customers ...Query OK, 1 row affected
5 查询SELECT ... FROM customers返回对应行数的结果集
first-sql.sql
-- 1) 建库（显式字符集，避免中文与 emoji 乱码）
CREATE DATABASE IF NOT EXISTS shop
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE shop;

-- 2) 建表
CREATE TABLE IF NOT EXISTS customers (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(50) NOT NULL,
  city        VARCHAR(30),
  gender      CHAR(1),
  signup_date DATE,
  level       VARCHAR(10) DEFAULT '普通'
) ENGINE=InnoDB;

-- 3) 插入：显式列出列名，city/gender 允许为 NULL
INSERT INTO customers (name, city, gender, signup_date, level) VALUES
  ('张伟', '北京', 'M', '2024-01-05', 'gold'),
  ('李娜', '上海', 'F', '2024-02-11', 'silver'),
  ('王强', '广州', 'M', '2024-03-20', 'normal');

-- 4) 查询：先看全部，再按条件过滤
SELECT id, name, city, level FROM customers ORDER BY id;
SELECT name, city FROM customers WHERE level = 'gold';
SELECT COUNT(*) AS 客户数 FROM customers;
SELECT level, COUNT(*) AS 人数 FROM customers GROUP BY level ORDER BY 人数 DESC;
★

核心要点：第一条 SQL 的闭环是「建库 → 选库 → 建表 → 插入 → 查询」。INSERT 与 SELECT 都显式写列名，是专业习惯；CREATE 语句加 IF NOT EXISTS，脚本可以反复执行不报错。

!

易错：① 忘了 USE shop; 或建表时没写库名，会把表建到别的库里；② 中文字符串必须用单引号（双引号在 MySQL 默认模式下是标识符，不是字符串）；③ 下面的练习台只支持查询（SELECT），CREATE/INSERT/UPDATE/DELETE 等写操作请到真实数据库执行。
