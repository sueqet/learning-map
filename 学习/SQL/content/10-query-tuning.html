01先定位，再改写
把「哪条 SQL 慢、慢在哪」说清楚

知识点慢查询日志与问题定位slow query log · 找到真正贵的 SQL

慢查询日志（slow query log）是 MySQL 记录「执行时间超过 long_query_time 的语句」的机制，是优化工作的入口。没有它，你只能靠用户投诉去猜哪条 SQL 有问题；有了它，慢 SQL 会自己浮出水面，还附带 Query_time、Lock_time、rows_examined、rows_sent 四个关键数字。

光看日志文件不够：日志是「逐条流水」，同一个语句模板可能每天执行几百万次，单次只有 200 ms 但累计吃掉一半 CPU。因此定位要分两层——先用聚合统计找出「总耗时最贵」的语句模板（performance_schema.events_statements_summary_by_digest），再用单条样本 + EXPLAIN 看它具体贵在哪一步。

  • 「慢」的定义由 long_query_time 决定，生产上常设 0.5–1 秒；它只影响记录，不改变执行。
  • rows_examined / rows_sent 的比值是判断「扫了太多行」最直接的信号，比值远大于 1 通常意味着索引没用好。
  • 慢日志只记录已经执行完的语句；正在锁等待、卡住的语句要靠 SHOW FULL PROCESSLIST 或 performance_schema 抓。
slowlog.sql
-- 1) 打开慢查询日志（MySQL 8.0，动态生效，无需重启）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;              -- 单位：秒，可写小数如 0.5
SET GLOBAL log_output = 'TABLE';             -- FILE / TABLE，双写用 'FILE,TABLE'
SET GLOBAL log_queries_not_using_indexes = ON;

-- 2) 用 performance_schema 按「总耗时」找 TOP 10 语句模板
SELECT DIGEST_TEXT                     AS 语句模板,
       COUNT_STAR                      AS 执行次数,
       ROUND(SUM_TIMER_WAIT / 1e12, 2) AS 总耗时秒,
       ROUND(AVG_TIMER_WAIT / 1e9, 2)  AS 平均毫秒,
       SUM_ROWS_EXAMINED               AS 总扫描行,
       SUM_ROWS_SENT                   AS 总返回行
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 3) 命令行快速聚合慢日志（-s c 按出现次数排序，-t 10 取前 10 条）
-- mysqldumpslow -s c -t 10 /var/lib/mysql/slow.log

-- 4) 抓「正在跑 / 正在等锁」的语句（慢日志看不到这些）
SHOW FULL PROCESSLIST;
定位手段能看到什么局限
慢查询日志 slow query log执行时间 ≥ 阈值的完整语句，含 Query_time / Lock_time / rows_examined / rows_sent只记录执行完的语句；量大需轮转，文本参数被原样写出
performance_schema digest 表语句模板级聚合：执行次数、总耗时、平均耗时、总扫描行需开启对应 consumer；语句被归一化成模板，看不到具体参数
SHOW FULL PROCESSLIST当前正在执行或等待锁的语句与状态只是瞬时快照，执行完就消失
EXPLAIN / EXPLAIN ANALYZE访问方式、预估行数（ANALYZE 还能给实际耗时与实际行数）得先把慢 SQL 捞出来，无法自动发现问题
SHOW ENGINE INNODB STATUS最近一次死锁详情、当前事务与锁等待只保留最近一次，历史需靠监控
★

核心要点：定位慢 SQL 看三层数字——「总耗时」（谁最贵）、「平均耗时 × 次数」（值不值得优化）、「rows_examined / rows_sent」（贵在哪一步）。一个平均 5 ms 但每秒 20 万次的语句，比一条 3 秒的报表 SQL 更值得先动手。

!

易错：慢日志不是万能的。被锁阻塞的语句、还没执行完的长事务都不会进慢日志；只看慢日志容易漏掉「锁等待导致的雪崩」。另外 log_queries_not_using_indexes = ON 在小表上会产生大量噪音日志，生产环境务必配合 log_throttle_queries_not_using_indexes 限流。

知识点SQL 重写技巧query rewrite · 不改索引也能变快

SQL 重写（query rewrite）是指在不改变业务语义的前提下，把语句换成优化器更容易用上索引、扫描更少行的等价形式。它是最便宜、见效最快的优化手段：不需要加索引、不需要改表结构，很多慢 SQL 只是被写成了「索引无法使用」的形状。

重写的核心原则只有一句话：让索引列保持「裸露」——不要在 WHERE 的条件列上套函数、做算术、做隐式类型转换，也不要让列被 OR、NOT IN、前导 % 破坏掉可定位性。其次才是减少搬运：SELECT * 会让「覆盖索引」这条捷径失效。

  • WHERE YEAR(order_date) = 2024 中的 YEAR() 让 order_date 索引失效，改成范围条件即可命中。
  • NOT IN (子查询) 遇到内表 NULL 时结果恒为空，性能与语义都有坑，优先用 NOT EXISTS 或 LEFT JOIN ... IS NULL。
  • 相关子查询（correlated subquery）会对驱动表每一行执行一次内层查询，绝大多数场景可改写成 JOIN + GROUP BY 一次扫描完成。
rewrite.sql
-- ❌ 反模式 1：函数包裹索引列 → 索引失效，全表扫描
SELECT id, amount FROM orders WHERE YEAR(order_date) = 2024;
-- ✅ 改写：换成范围条件，order_date 索引可用
SELECT id, amount FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';

-- ❌ 反模式 2：SELECT * → 无法用覆盖索引，必定回表
SELECT * FROM orders WHERE customer_id = 3;
-- ✅ 改写：只取需要的列
SELECT id, order_date, amount FROM orders WHERE customer_id = 3;

-- ❌ 反模式 3：NOT IN 子查询（内表含 NULL 时结果恒空）
SELECT * FROM customers c
WHERE c.id NOT IN (SELECT o.customer_id FROM orders o);
-- ✅ 改写：NOT EXISTS（或 LEFT JOIN ... WHERE o.customer_id IS NULL）
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- ❌ 反模式 4：相关子查询，外层每行执行一次内层查询
SELECT c.name,
       (SELECT SUM(o.amount) FROM orders o WHERE o.customer_id = c.id) AS 总额
FROM customers c;
-- ✅ 改写：JOIN + GROUP BY，一次扫描完成
SELECT c.name, SUM(o.amount) AS 总额
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

-- ❌ 反模式 5：OR 跨列，单索引无法同时命中
SELECT id, customer_id, status FROM orders
WHERE customer_id = 3 OR status = 'paid';
-- ✅ 改写：UNION ALL 拆成两条各自可走索引的查询（用 <> 避免重复行）
SELECT id, customer_id, status FROM orders WHERE customer_id = 3
UNION ALL
SELECT id, customer_id, status FROM orders WHERE status = 'paid' AND customer_id <> 3;

-- ❌ 反模式 6：前导通配符，B+ 树无法定位
SELECT id, name FROM products WHERE name LIKE '%手机%';
-- ✅ 改写：前缀匹配可用索引；全文检索需求请用 FULLTEXT 索引
SELECT id, name FROM products WHERE name LIKE '手机%';

注意：最后两条（UNION ALL 与前导通配符）在下方练习台里跑不了，练习台只支持 SELECT 的常规语法，请到真实数据库里用 EXPLAIN 验证改写效果。

反模式为什么慢改写方向
WHERE YEAR(col) = 2024条件列被函数包裹，索引无法定位 → 全表扫描改成 col >= A AND col < B 的范围条件
SELECT *传输多、必定回表、覆盖索引失效只列需要的字段，必要时把过滤列也放进索引
NOT IN (子查询)内表有 NULL 时结果恒空；半连接优化易被破坏NOT EXISTS / LEFT JOIN ... IS NULL
相关子查询驱动表每行执行一次内层查询，复杂度 O(n×m)JOIN + GROUP BY 或窗口函数一次扫描
OR 跨不同列单一索引无法同时满足两侧条件，易退化为全扫UNION ALL 拆成多条可走索引的查询
LIKE '%xx%'前导通配符无法用 B+ 树做范围定位改前缀匹配 'xx%'，或使用 FULLTEXT 索引
WHERE varchar_col = 123隐式类型转换等价于对列做函数运算，索引失效补上引号，保持类型一致
★

核心要点：重写的第一优先级是「让索引可用」：索引列不参与运算、不做隐式转换、不被 OR 拆散。第二优先级是「少搬数据」：只取需要的列，让覆盖索引真正生效。语义等价是底线，改完必须比对结果集行数与关键值。

!

易错：NOT IN 与 NOT EXISTS 在内表有 NULL 时结果不同：前者返回空集，后者正常返回。改写前先确认连接列是否 NOT NULL，否则你改的是 bug 不是性能。另外 OR 改 UNION ALL 时记得用 <> 排除重叠条件，否则行数会翻倍。

提示：估算基于 orders 约 100 万行的生产规模——内置示例表只有 12 行订单，数据量太小看不出差距，这里用行数量级说明代价差异。

02连接与分页
代价最大的两块

知识点JOIN 算法（NLJ / BNL / Hash Join）join algorithms · 决定多表查询的量级

MySQL 8.0 的 EXPLAIN FORMAT=JSON 会把整棵连接计划包在一个 nested_loop 里，但「嵌套循环」只是骨架，真正决定代价的是每一步用哪种算法：被驱动表的连接列有索引时用索引嵌套循环（Index Nested-Loop Join，INLJ）；没索引时 8.0.18 之前用块嵌套循环（Block Nested-Loop Join，BNL），8.0.18 引入、8.0.20 起全面替代 BNL 的是哈希连接（Hash Join）。

理解它们只需要抓住「谁被扫、扫几次」：INLJ 里驱动表的每一行都去被驱动表做一次索引查找，代价是 驱动行数 × log(被驱动行数)；BNL 把驱动表按 join_buffer_size 分块，每块全扫一遍被驱动表，代价是 被驱动行数 × 块数；Hash Join 用较小的表在内存建哈希表，大表只探测一次，代价约 两表行数之和。

  • 等值连接 + 被驱动表连接列有索引 → 优化器首选 INLJ，这是最理想的情况。
  • 被驱动表无索引的等值连接 → 8.0.20 之后用 Hash Join；老版本用 BNL，靠调大 join_buffer_size 减少块数来缓解。
  • Hash Join 只适用于等值连接（=）；范围连接、非等值连接仍走嵌套循环。
  • 优化顺序永远是：先给被驱动表的连接列建索引，再考虑驱动表选择与连接顺序。
join-algo.sql
-- 1) 看清连接算法与顺序：8.0 用 nested_loop 包裹整棵计划
EXPLAIN FORMAT=JSON
SELECT c.name, o.amount
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid';
-- 关注：blockNestedLoop / usingJoinBuffer / hashJoin 等字段，
-- 以及 customers 的 type 是否为 eq_ref（INLJ 的理想形态）

-- 2) 8.0.18+ 的优化器提示：强制或禁用 Hash Join
SELECT /*+ HASH_JOIN(c, o) */ c.name, o.amount
FROM orders o JOIN customers c ON c.id = o.customer_id;

SELECT /*+ NO_HASH_JOIN(c, o) NO_BNL(c) */ c.name, o.amount
FROM orders o JOIN customers c ON c.id = o.customer_id;

-- 3) 老版本 BNL 的关键参数：缓冲区越大，被驱动表全扫的块数越少
SHOW VARIABLES LIKE 'join_buffer_size';

-- 4) 最根本的优化：给被驱动表的连接列建索引，让它从 BNL/Hash 变成 INLJ
CREATE INDEX idx_orders_customer ON orders (customer_id);
算法触发条件代价量级EXPLAIN 特征
INLJ（Index Nested-Loop Join）被驱动表连接列有索引驱动表行数 × 一次索引查找被驱动表 type=ref/eq_ref，Extra 无 join buffer 提示
BNL（Block Nested-Loop Join）被驱动表无索引，8.0.18 之前被驱动表全扫 × 分块数Extra: Using join buffer (Block Nested Loop)
Hash Join等值连接且无可用索引，8.0.18+约「两表行数之和」，各扫一次Extra: Using join buffer (hash join)
Simple NLJ无索引且无法使用 join buffer笛卡尔积级别，MySQL 实际极少使用计划中直接嵌套全扫
★

核心要点：多表查询的优化口诀——「小表驱动大表 + 被驱动表连接列必须有索引」。有了索引就是 INLJ，量级从「乘积」降为「和」；没有索引才会掉进 BNL 或 Hash Join。看到 Using join buffer 就该先想「这里是不是缺一个索引」。

!

易错：8.0.20 起 BNL 已逐步被 Hash Join 取代，网上大量「调大 join_buffer_size 优化 BNL」的老经验需要重新验证；在 8.0.20+ 上调这个参数通常不再有效。另外 Hash Join 在内存不足时会落盘（Grace Hash Join），反而变慢，别盲目用 hint 强制它。

知识点深分页优化deep pagination · 把 O(offset) 降到 O(n)

深分页（deep pagination）指的是 LIMIT offset, n 中 offset 很大的场景，比如第 50000 页。很多人以为 LIMIT 会让 MySQL「只取 20 行」，其实恰恰相反：MySQL 必须先按 ORDER BY 定位并读取前 offset + n 行，然后丢弃前 offset 行。offset 越大，扫描行数线性增长，而且如果查询用到非索引列，还要回表 offset + n 次。

优化思路有三条，代价从高到低：延迟关联（deferred join）先在索引上翻页拿到主键，再回表只取 n 行，把回表次数从 offset+n 降到 n，但仍要扫 offset+n 行索引；游标分页（keyset pagination）用「上一页最后一条的排序键」作为起点，扫描行数恒定为 n，代价与页深无关；覆盖索引让整个翻页过程不回表。

  • LIMIT offset, n 的代价与 offset 成正比，是深分页的根因，不是索引「没建好」。
  • 延迟关联适合必须支持「跳到任意页」的旧接口；游标分页适合「下一页 / 下拉加载」的产品形态。
  • 游标分页的排序键必须唯一且稳定，否则可能出现漏行或重复行（常见做法是 (created_at, id) 复合游标）。
paging.sql
-- ① 朴素深分页：扫描 offset + n 行，回表 offset + n 次
SELECT id, customer_id, order_date, amount
FROM orders
ORDER BY id
LIMIT 1000000, 20;

-- ② 延迟关联：先在索引上翻页拿到主键，再回表只取 20 行
SELECT o.id, o.customer_id, o.order_date, o.amount
FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON t.id = o.id;

-- ③ 游标分页：记住上一页最后一条的主键，直接定位，代价恒定
SELECT id, customer_id, order_date, amount
FROM orders
WHERE id > 1000020          -- 上一页最后一条的 id
ORDER BY id
LIMIT 20;

-- ④ 复合游标：排序键不唯一时用 (order_date, id) 保证不漏行
SELECT id, order_date, amount
FROM orders
WHERE (order_date, id) > ('2024-06-01', 1000020)
ORDER BY order_date, id
LIMIT 20;
方案扫描行数优点限制
LIMIT offset, noffset + n，回表 offset + n 次写法最简单，支持任意跳页页越深越慢，代价线性增长
延迟关联offset + n 索引行 + n 次回表回表次数从 offset+n 降到 n仍要扫 offset + n 行索引
游标分页n代价恒定，与页深无关只能「下一页」，不能随机跳页
覆盖索引 + 主键区间n（不回表）最快，可直接定位需要单调递增主键或时间戳
★

核心要点：深分页的本质是「MySQL 要数到 offset 才能开始取」，任何在 LIMIT 前加 ORDER BY 的写法都逃不掉这一步。真正的解法是不要用 offset 定位——改用「上一页最后一条的排序键」做游标；确实要支持跳页时，用延迟关联把回表次数压到 n。

!

易错：游标分页在并发插入场景下是「稳定但不重复」的：新插入的行不会出现在后续页里，这通常是可接受的；但如果业务要求「绝对快照」，就得改用时间范围 + 快照读。另外 ORDER BY 的列必须与游标条件列一致，否则索引失效、退化成全表排序。

🖥 演示：深分页优化器拖动滑块调 offset，看扫描行数与回表次数
场景：orders 约 200 万行，每页 20 条。曲线为「朴素 LIMIT offset,n」的扫描行数随 offset 增长；游标分页是一条贴近横轴的水平线。

03统计与写入
优化器怎么看表，我们怎么写

知识点COUNT 与统计信息count & statistics · 语义差别与优化器决策

COUNT 家族的写法看着差不多，语义和代价却不同：COUNT(*) 与 COUNT(1) 统计行数、不忽略 NULL；COUNT(col) 只统计该列非空的行；COUNT(DISTINCT col) 统计去重后的非空个数，代价明显更高。在 InnoDB 里，COUNT(*) 并不读取每一行的全部数据，而是选择一棵较小的二级索引扫描计数——所以「COUNT(*) 比 COUNT(1) 慢」是过时的说法，MySQL 8.0 中二者等价。

统计信息（statistics）是优化器决策的依据：它靠 table_rows（表行数估算）、索引 Cardinality（列基数估算）和数据分布来估算「走索引还是全表扫」「选哪张表做驱动表」。统计信息一旦过期或采样偏差大，优化器就可能选错索引——这类「昨天还快、今天突然慢」的问题，第一步就是 ANALYZE TABLE 再重看 EXPLAIN。

  • InnoDB 不保存精确行数，information_schema.tables.table_rows 只是估算值，不能当 COUNT(*) 用。
  • COUNT(DISTINCT col) 需要去重，代价高；海量数据上的「大致有多少」可以接受估算值或汇总表。
  • ANALYZE TABLE 重新采样统计信息；8.0 默认 innodb_stats_auto_recalc = ON，但大表仍会有采样误差。
count-stats.sql
-- 1) COUNT 家族的语义差别（customers 共 8 行，id=8 的 city 为 NULL）
SELECT COUNT(*)             AS 全表行数,      -- 8：不忽略任何行
       COUNT(city)          AS 非空城市数,    -- 7：忽略 NULL
       COUNT(DISTINCT city) AS 去重城市数,    -- 5：北京 / 上海 / 广州 / 深圳 / 杭州
       COUNT(1)             AS 等价写法      -- 8：与 COUNT(*) 等价
FROM customers;

-- 2) 统计信息：优化器靠它估行数、选索引
SELECT table_name, table_rows, avg_row_length
FROM information_schema.tables
WHERE table_schema = 'shop' AND table_name = 'orders';   -- table_rows 是估算值

SHOW INDEX FROM orders;      -- 关注 Cardinality（索引基数估算）
ANALYZE TABLE orders;        -- 重新采样，解决「选错索引」

-- 3) 验证估算准不准：EXPLAIN 的 rows 是估算，EXPLAIN ANALYZE 给实际行数
EXPLAIN SELECT id FROM orders WHERE status = 'paid' AND customer_id = 3;

★

核心要点：两句话记住——① COUNT(*) 与 COUNT(1) 在 InnoDB 中完全等价，别再背「COUNT(1) 更快」；② table_rows 是估算值，优化器用它做决策，但业务上要精确数字只能老老实实 COUNT(*) 或维护汇总表。

!

易错：用 COUNT(col) 去统计「有多少条记录」会漏掉 NULL 行（比如 COUNT(city) 得到 7 而不是 8）。另一个坑是分页总数：每次请求都 SELECT COUNT(*) 大表，代价可能比查询本身还高，常见做法是「最多数到 1000 条」或维护计数汇总表。

知识点批量操作与大事务拆分batch & transaction splitting · 控制影响面

一次影响几百万行的 DELETE / UPDATE / INSERT 会形成一个大事务（long transaction）：undo 日志持续膨胀、行锁/间隙锁长时间持有、binlog 里出现一个巨大的事务，从库要等它全部执行完才能推进——主从延迟就是这么来的。批量操作优化的核心不是「让语句更快」，而是把一个大动作切成许多小动作，让每个事务都短小可控。

标准做法是「分批 + 按主键推进 + 逐批提交 + 批间留间隔」：每批处理 500–2000 行，用主键区间或 ORDER BY id LIMIT n 推进，批间 SLEEP 一小段时间让从库追上；同时必须保证操作幂等，因为中途失败后你只会重跑某一批，而不是从头再来。批量插入则相反，要把多条 VALUES 合并成一条 INSERT，减少网络往返与解析开销。

  • 大事务的风险：undo 膨胀、锁等待、主从延迟、失败回滚成本高、binlog 暴涨。
  • 分批的关键参数：批大小（500–2000 行）、批间 sleep、每批独立的提交边界、进度可续跑。
  • 在线 DDL 用 pt-online-schema-change / gh-ost，不要直接 ALTER 千万行大表。
batch.sql
-- ❌ 大事务：一次删除 500 万行，undo 膨胀 + 锁持有久 + 主从延迟
DELETE FROM orders WHERE status = 'cancelled';

-- ✅ 分批删除：按主键区间推进，每批 1000 行，逐批提交
DELETE FROM orders
WHERE status = 'cancelled' AND id BETWEEN 1 AND 1000;

-- ✅ 循环推进（伪代码）：每批提交后把上界 +1000，批间 sleep 观察复制延迟
-- WHILE 上批受影响行数 > 0:
--   DELETE FROM orders WHERE status = 'cancelled' AND id > :last_id
--   ORDER BY id LIMIT 1000;
--   SELECT SLEEP(0.1);

-- ✅ 批量插入：一条 INSERT 多组值，比逐条插入快一个数量级
INSERT INTO order_items (order_id, product_id, qty, unit_price) VALUES
  (1, 1, 2, 9.90), (1, 2, 1, 19.90), (2, 3, 3, 5.50);

-- ✅ 批量更新：用派生表 JOIN 一次更新多行，避免逐行往返
UPDATE products p
JOIN (SELECT 1 AS id, 8.80 AS price UNION ALL SELECT 2, 18.80) t ON t.id = p.id
SET p.price = t.price;
维度一个大事务（500 万行）分批（每批 1000 行）
undo / redo 日志持续膨胀，可能撑爆 undo 表空间每批结束后可回收
锁持有时间全程持有，阻塞其他写入每批短暂持有，冲突面小
主从复制延迟单个大 binlog 事务，从库长时间追不上批间间隔可控，延迟可观察
失败重试成本整体回滚，前面的工作全部白做只需重跑当前批（要求幂等）
原子性天然原子需靠幂等 + 进度记录来保证最终一致
★

核心要点：批量操作的黄金公式——「小批次 + 主键推进 + 逐批提交 + 批间间隔 + 幂等可重跑」。批大小不是越小越好：太小会让事务数量暴涨、开销占比升高，500–2000 行是常用区间，最终要用实测的主从延迟与 IO 使用率来定。

!

易错：分批删除时若 WHERE 只有非索引条件，每批仍会全表扫描，必须配合主键或索引条件推进。批间不 sleep、不监控复制延迟，会把从库拖垮；另外别忘了 DELETE ... LIMIT 在某些隔离级别下可能扩大锁范围，建议先 EXPLAIN 确认走的索引。

从「感觉快了」到「证明快了」

知识点优化流程与效果验证optimization workflow · 可复现、可回滚、可度量

优化不是「改完试试看」，而是一个闭环：发现 → 采集基线 → 定位瓶颈 → 提出假设并验证 → 灰度上线 → 记录结论并回归监控。其中最容易跳过、也最关键的一步是「采集基线」：没有优化前的 rows_examined、平均耗时、P99 和 EXPLAIN 计划，你根本无法判断改动到底有没有用，也无法在出问题时回滚。

验证要落到可对比的数字上：同一份数据量、同一条 SQL、同一套参数，优化前后各跑一次，对比「扫描行数、返回行数、平均耗时、P99、回表次数、复制延迟」。特别要注意 EXPLAIN 的 rows 是估算值，EXPLAIN ANALYZE（8.0.18+）才会给出实际执行行数与耗时，两者结合才能判断优化器是否「估准了」。

  • 基线三件套：EXPLAIN ANALYZE 输出、同一语句的耗时统计、慢日志/监控里的 P99 曲线。
  • 每次只改一个变量（要么改 SQL、要么加索引），否则无法归因。
  • 上线要灰度：先在从库或小流量验证，观察复制延迟与错误率，准备好回滚脚本。
verify.sql
-- ① 采集基线：优化前后用同一语句模板对比（清空后再采集更干净）
TRUNCATE TABLE performance_schema.events_statements_summary_by_digest;

SELECT DIGEST_TEXT,
       COUNT_STAR,
       ROUND(AVG_TIMER_WAIT / 1e9, 2) AS 平均毫秒,
       SUM_ROWS_EXAMINED              AS 总扫描行,
       SUM_ROWS_SENT                  AS 总返回行
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 5;

-- ② 看清计划：EXPLAIN 给估算，EXPLAIN ANALYZE 给实际行数与耗时
EXPLAIN ANALYZE
SELECT c.name, SUM(o.amount) AS 总额
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE o.order_date >= '2024-01-01'
GROUP BY c.id, c.name
ORDER BY 总额 DESC
LIMIT 10;

-- ③ 上线后回归：确认统计信息与新索引被正确使用
SHOW INDEX FROM orders;
ANALYZE TABLE orders;

易错：只在开发库小数据上验证——示例表 12 行订单走全表扫描也很快，优化器的选择与百万行时完全不同；用「感觉快多了」当结论；以及忘记 EXPLAIN 的 rows 只是估算值，误把估算当实际。
