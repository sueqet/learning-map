知识点字符串函数string functions · 清洗、拼接与截取

字符串函数（string functions）是 SQL 里最常用的「数据清洗工具箱」：把大小写统一、把两列拼成展示用的字符串、把一段文本截成需要的部分、把多余空格去掉。它们出现在 SELECT 里做展示与导出，也出现在 WHERE 与 GROUP BY 里做归一化比较。

最关键的一点是「字符」和「字节」不是一回事。MySQL 的 LENGTH() 返回字节数，CHAR_LENGTH() 返回字符数；在 utf8mb4 下一个汉字占 3 字节，一个 emoji 占 4 字节。用 LENGTH() 去做「名字不超过 10 个字」这类校验，几乎必然出错。

  • 拼接优先用 CONCAT，但 CONCAT 一旦遇到 NULL，整个结果就是 NULL——要跳过 NULL 用 CONCAT_WS，或先 COALESCE。
  • SUBSTR(str, pos, len) 的位置从 1 开始（不是 0），越界不会报错，只返回能取到的部分。
  • 函数写在列上会让索引失效（非 sargable），能改写成范围条件或前缀 LIKE 就不要用函数。
string-fn.sql
-- 客户姓名与等级字段的清洗（内置 customers 表，8 行）
SELECT id,
       UPPER(name)                AS 姓名大写,
       LENGTH(name)               AS 字节数,
       CHAR_LENGTH(name)          AS 字符数,
       CONCAT(city, '-', level)   AS 城市等级,
       CONCAT_WS('/', city, level, name) AS 拼接跳过NULL,
       LEFT(name, 1)              AS 姓氏,
       RIGHT(level, 1)            AS 等级末字,
       TRIM('  北京  ')            AS 去首尾空格,
       REPLACE(level, '卡', '')   AS 等级数字,
       INSTR('abc-def', '-')      AS 分隔符位置
FROM customers
WHERE city IS NOT NULL
ORDER BY id;

预期结果：7 行（id=8 的 city 为 NULL 被过滤）。其中 LENGTH('张伟') 得 6、CHAR_LENGTH('张伟') 得 2；REPLACE('金卡','卡','') 得 金；INSTR('abc-def','-') 得 4。

知识点日期时间函数date & time functions · 截断、求差与格式化

日期时间函数解决三类问题：把时间粒度降下来（按天 / 月 / 季度分组）、求两个时间点的间隔（账期、留存、工龄）、按指定格式输出（报表与导出）。它们几乎总与 GROUP BY 一起出现。

选类型时先想清楚语义：DATETIME 存「墙上时间」，不随时区变化；TIMESTAMP 按 UTC 存储、按会话时区展示，范围只到 2038 年；DATE 只存日期。跨时区的系统用 TIMESTAMP 更省心，但要知道它的范围限制。

  • DATEDIFF(a, b) 算的是 a - b 的天数，单位固定为天，不按「整月」算；要按月用 TIMESTAMPDIFF(MONTH, a, b)。
  • DATE_FORMAT() 适合展示，不适合过滤——过滤请用范围条件保留索引可用性。
  • 做「补零」的连续日期序列要靠递归 CTE 或日历表，而不是靠日期函数。
date-fn.sql
-- 按月统计订单数与金额（内置 orders 表，2024-01 ~ 2024-04）
SELECT DATE_FORMAT(order_date, '%Y-%m') AS 月份,
       COUNT(*)                         AS 订单数,
       SUM(amount)                      AS 金额
FROM orders
WHERE order_date >= '2024-01-01'
  AND order_date <  '2024-05-01'
GROUP BY DATE_FORMAT(order_date, '%Y-%m')
ORDER BY 月份;

预期结果（4 行）：2024-01 / 3 单 / 1635、2024-02 / 3 单 / 2674、2024-03 / 3 单 / 1216、2024-04 / 3 单 / 3133。注意 WHERE 用的是对常量的范围比较，order_date 上的索引仍然可用。

知识点数值函数与类型转换numeric functions & casting · 取整、取余与精度

数值函数负责取整、取余、绝对值与四舍五入，常出现在金额分摊、分页、分桶与奇偶判断里。比函数更重要的，是类型选择：金额、税率、汇率这类「必须精确」的数值一律用 DECIMAL(p,s)，不要用 FLOAT / DOUBLE——后者是二进制浮点，0.1 + 0.2 不等于 0.3，累加多次后误差会显形。

类型转换分显式与隐式。显式用 CAST(x AS type) 或 CONVERT(x, type)；隐式转换发生在比较、拼接、函数参数里，看着方便，实则危险：字符串转数字时非法内容会变成 0，数字与字符串比较时可能整列转类型从而放弃索引。

  • ROUND(x, d) 保留 d 位小数；TRUNCATE(x, d) 直接截断不进位，两者语义不同。
  • FLOOR 向 −∞ 取整、CEIL 向 +∞ 取整，负数上表现与「去掉小数」不同：FLOOR(-2.5) = -3。
  • MOD(a,b) 的符号跟随被除数；整除用 DIV（7 DIV 2 = 3）。
numeric.sql
-- 订单明细的取整、分摊与奇偶判断（内置 order_items / products）
SELECT oi.id,
       oi.qty * oi.unit_price                       AS 小计,
       ROUND(oi.qty * oi.unit_price, 1)             AS 保留一位,
       FLOOR(oi.qty * oi.unit_price)                AS 向下取整,
       CEIL(oi.qty * oi.unit_price / 3)             AS 三等分向上,
       MOD(oi.order_id, 2)                          AS 订单号奇偶,
       CAST(oi.qty AS DECIMAL(10,2)) / 3            AS 精确三等分
FROM order_items oi
WHERE oi.order_id = 1001
ORDER BY oi.id;

预期结果（2 行）：id=1 小计 129、三等分向上 43；id=2 小计 118、三等分向上 40。MOD(1001,2)=1 表示订单号为奇数。CAST(... AS DECIMAL) 后再除，得到精确小数而不是浮点近似值。

!

易错：ROUND 的进位行为与数据类型有关，FLOAT / DOUBLE 上的结果可能与 DECIMAL 不同；CAST('abc' AS SIGNED) 得到 0 而不报错，脏数据会被静默当成 0 参与统计。其它数据库提示：PostgreSQL 用 x::numeric 转换，SQL Server 用 CONVERT(numeric, x)。

CASE WHEN · 行列转换

知识点CASE WHEN 与条件表达式case expression · SQL 里的 if-else

CASE 是 SQL 的条件表达式，相当于 if-else 链，有两种写法：搜索式 CASE WHEN 条件 THEN 值 … END 逐条判断布尔条件；简单式 CASE 表达式 WHEN 值 THEN 值 … END 等价于对表达式做等值比较。它不仅能放在 SELECT 里做标签，还能放进 WHERE、GROUP BY、ORDER BY 做动态分组与自定义排序。

与 CASE 配套的还有四个常用函数：IF(cond,a,b) 三元表达式、IFNULL(x,y) 处理单层 NULL、COALESCE(a,b,c) 取第一个非 NULL、NULLIF(a,b) 在相等时返回 NULL（常用于避免除零）。

  • CASE 只会命中第一个为真的分支，条件顺序决定结果；没有 ELSE 时返回 NULL。
  • 判断 NULL 只能用 IS NULL；WHEN NULL 与 WHEN city = NULL 永远不成立，因为结果是 UNKNOWN。
  • 条件聚合是 CASE 最有价值的用法：SUM(CASE WHEN … THEN x ELSE 0 END) 能把「行」折叠成「列」，这正是下一节行列转换的基础。
case-when.sql
-- 客户城市补全 + 订单金额分档 + 状态中文化（customers JOIN orders）
SELECT c.id,
       c.name,
       COALESCE(c.city, '未知城市')                       AS 城市,
       CASE
         WHEN o.amount >= 1000 THEN '大额'
         WHEN o.amount >= 100  THEN '中额'
         ELSE '小额'
       END                                                AS 金额档,
       CASE o.status
         WHEN 'paid'      THEN '已支付'
         WHEN 'refunded'  THEN '已退款'
         WHEN 'cancelled' THEN '已取消'
         ELSE '其它'
       END                                                AS 状态中文
FROM customers c
JOIN orders o ON c.id = o.customer_id
ORDER BY o.amount DESC;

预期结果：12 行（orders 全部 12 条都能匹配到客户；id=8 的客户没有订单，内连接后不出现）。最大一笔是 2297 的「大额 / 已支付」，最小一笔 59 是「小额 / 已支付」。

核心要点：CASE 顺序敏感、无 ELSE 返回 NULL；条件聚合里用 ELSE 0 还是省略 ELSE 会影响 COUNT（NULL 不被计数），但 SUM 通常不受影响。

!

易错：CASE city WHEN NULL THEN '未知' ELSE city END 永远走 ELSE，因为 city = NULL 是 UNKNOWN 而不是 TRUE。SQL Server 的 ISNULL(x,y) 只接两个参数、Oracle 的 NVL 同理，跨库时优先用标准的 COALESCE。

知识点行列转换（PIVOT）pivot / unpivot · 窄表与宽表互转

数据库里存的是窄表（long format）：一行一个「月份 + 品类 + 金额」，方便写入与聚合；而报表和看板要的是宽表（wide format）：一行一个月，品类各占一列。把窄变宽就叫行列转换，也就是 PIVOT；反向的宽变窄叫 UNPIVOT。

MySQL 没有 PIVOT 关键字（SQL Server、Oracle 有，PostgreSQL 用 crosstab）。MySQL 的标准做法是条件聚合：用 CASE WHEN 把不属于当前列的值变成 0，再 SUM 起来，配合 GROUP BY 得到一行一个维度。

  • 列数固定时手写 CASE WHEN 最直接；列数不固定（品类会新增）需要动态 SQL：先用 GROUP_CONCAT 查出列清单，再 PREPARE + EXECUTE 拼语句。
  • ELSE 0 让「该月没有这个品类」显示 0 而不是 NULL；如果业务上「没有」和「为 0」含义不同，就省略 ELSE 保留 NULL。
  • 宽表列数一旦随数据变化，就不是稳定的表结构——大多数情况下更该在应用层或 BI 工具里做透视。
pivot.sql
-- 窄表 → 宽表：月份 × 品类 × 金额（orders + order_items + products）
SELECT DATE_FORMAT(o.order_date, '%m')                                     AS 月份,
       SUM(CASE WHEN p.category = '数码' THEN oi.qty * oi.unit_price ELSE 0 END) AS 数码,
       SUM(CASE WHEN p.category = '图书' THEN oi.qty * oi.unit_price ELSE 0 END) AS 图书,
       SUM(CASE WHEN p.category = '家居' THEN oi.qty * oi.unit_price ELSE 0 END) AS 家居,
       SUM(oi.qty * oi.unit_price)                                         AS 合计
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
GROUP BY DATE_FORMAT(o.order_date, '%m')
ORDER BY 月份;

预期结果（4 行 × 5 列）：01 / 1428 / 118 / 89 / 1635、02 / 2297 / 59 / 318 / 2674、03 / 1127 / 0 / 89 / 1216、04 / 2796 / 0 / 337 / 3133。3 月和 4 月没有卖出「图书」，靠 ELSE 0 显示为 0。

★

核心要点：MySQL 的行列转换 = 条件聚合：GROUP BY 定行、CASE WHEN 定列、SUM 定值。别去搜索 MySQL 的 PIVOT 语法，它不存在。

!

易错：漏掉 GROUP BY 会只出一行；品类值写错（比如数据里是 '数码 ' 带空格）会让整列变成 0——排查时先 GROUP BY p.category 看真实取值。另外聚合列越多，SQL 越难维护，品类超过十来个就该考虑动态 SQL 或 BI 层透视。

03递归 CTE 与 JSON
树形结构 · 半结构化数据

知识点递归 CTE（树形结构 / 生成序列）recursive CTE · 自己引用自己的查询

递归 CTE（recursive common table expression）用 WITH RECURSIVE 定义，由两部分拼成：锚点成员（anchor，产生第一批行，不引用自己）和递归成员（recursive member，引用 CTE 自身，不断用上一轮的结果算出下一轮），两者用 UNION ALL 连接。执行时先算锚点，再反复执行递归成员，直到某一轮不再产生新行。

它主要解决两类问题：树形 / 图结构——组织架构、商品类目、评论回复、物料 BOM；生成序列——连续日期、数字区间、补零用的日历表。这些用普通 JOIN 写不出来，因为层级深度事先不知道。

  • 递归必须有终止条件（WHERE n < 10）或数据本身无环，否则会一直迭代。
  • MySQL 默认 cte_max_recursion_depth = 1000，超过会报错 Recursive query aborted after 1001 iterations；需要更深可 SET SESSION cte_max_recursion_depth = 100000。
  • 维护一个 path 字符串列既方便展示层级，也是断环的常用手段。
recursive-cte.sql
-- ① 生成 1..10 的连续序列
WITH RECURSIVE seq(n) AS (
  SELECT 1                                  -- 锚点成员
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 10         -- 递归成员 + 终止条件
)
SELECT n FROM seq ORDER BY n;

-- ② 员工上下级树（employees.manager_id 为 NULL 表示顶层）
WITH RECURSIVE tree AS (
  SELECT id, name, manager_id, 1 AS lvl,
         CAST(name AS CHAR(200)) AS path
  FROM employees
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, t.lvl + 1,
         CONCAT(t.path, ' > ', e.name)
  FROM employees e
  JOIN tree t ON e.manager_id = t.id
)
SELECT lvl, name, path FROM tree ORDER BY lvl, id;

预期结果：① 10 行，1 … 10；② 9 行，按层级排列——第 1 层 3 人（张伟、刘敏、赵磊），第 2 层 5 人（李娜、王强、陈晨、周涛、吴迪），第 3 层 1 人（孙悦，路径 张伟 > 李娜 > 孙悦）。

核心要点：锚点只执行一次，递归成员反复执行到「没有新行」为止。写的时候先问两句：起点是谁？下一轮怎么来？——再加上终止条件，递归 CTE 就成型了。

!

易错：数据里有环（A 的上级是 B、B 的上级又是 A）会导致无限递归直到触发深度上限报错。MySQL 8.0 没有 SQL 标准的 CYCLE 子句（PostgreSQL 14+ 才有），要在递归成员里用路径列 + LOCATE / FIND_IN_SET 排除已访问节点。练习台不支持 WITH，请到真实数据库验证。

知识点JSON 类型与函数JSON type · 半结构化数据的存取

MySQL 5.7 起提供原生 JSON 类型：写入时校验合法性，内部用二进制格式存储（读取比字符串解析快），并提供一整套函数与 -> / ->> 运算符。8.0 又补上了 JSON_TABLE（把 JSON 数组展开成行）与多值索引（8.0.17+，可给数组元素建索引）。

它适合稀疏、易变、整块读写的属性：第三方回调原文、埋点事件参数、商品的可变规格。它不适合替代规范化列：高频过滤、连接、聚合的字段如果塞进 JSON，每次查询都要解析，而且普通索引用不上——只有「生成列 + 索引」或「多值索引」才能救回来。

  • -> 等价于 JSON_EXTRACT，返回 JSON 类型，字符串值带双引号；->> 再套一层 JSON_UNQUOTE，返回纯字符串。
  • 路径语法：$ 根、$.key 取字段、$.arr[0] 取数组元素、$[*] 匹配全部元素。
  • 需要按 JSON 里的字段过滤时，加一个 GENERATED ALWAYS AS (... STORED 生成列再建索引，查询才能走索引。
json.sql
-- 客户扩展属性放在 JSON 列里，用生成列 + 索引支撑按城市过滤
CREATE TABLE customer_profile (
  customer_id BIGINT PRIMARY KEY,
  info JSON NOT NULL,
  city VARCHAR(32) GENERATED ALWAYS AS (info->>'$.city') STORED,
  KEY idx_city (city)
);

INSERT INTO customer_profile (customer_id, info) VALUES
  (1, '{"city":"北京","tags":["高价值","活跃"],"vip":true}');

-- 取值：-> 返回带引号的 JSON，->> 返回纯字符串
SELECT info->'$.city'                          AS 带引号,
       info->>'$.city'                         AS 纯字符串,
       JSON_EXTRACT(info, '$.tags[0]')         AS 首个标签,
       JSON_UNQUOTE(JSON_EXTRACT(info, '$.vip')) AS 是否VIP,
       JSON_LENGTH(info, '$.tags')             AS 标签个数
FROM customer_profile;

-- 把 JSON 数组展开成多行，再和普通表连接
SELECT cp.customer_id, jt.tag
FROM customer_profile cp
JOIN JSON_TABLE(cp.info, '$.tags[*]' COLUMNS (tag VARCHAR(32) PATH '$')) jt
WHERE cp.customer_id = 1;

预期结果：第一段查询 1 行，带引号 = "北京"、纯字符串 = 北京、首个标签 = "高价值"、是否VIP = true、标签个数 = 2；第二段查询 2 行：高价值、活跃。

★

核心要点：JSON 列本身不能直接建普通索引；要按内部字段过滤，用 生成列（STORED）+ 索引，或 8.0.17+ 的多值索引。判断标准很简单：这个字段会被频繁过滤 / 连接 / 聚合吗？会，就拆成普通列。

!

易错：-> 和 ->> 差一个字符，返回的东西不同——拿 -> 的结果去和普通字符串比较会因带引号而匹配失败。另外 JSON 列存大文档会让行变宽、缓冲池利用率下降。练习台不支持 JSON 函数，请到真实数据库验证。

存储过程 · 函数 · 触发器

知识点存储过程 / 函数 / 触发器（选学）stored program · 把逻辑放进数据库

存储程序（stored program）是把一段逻辑保存在数据库里并由数据库执行的对象：存储过程用 CALL 调用、可以带流程控制与事务、能返回多个结果集；函数返回一个标量值，可以直接出现在 SELECT 里；触发器没有调用入口，在 INSERT / UPDATE / DELETE 前后自动执行，通过 NEW / OLD 访问行数据。

它们的价值在于把一次网络往返变成一次数据库内调用：批量数据迁移、复杂校验、审计留痕、定时任务都合适。代价同样明显——难单元测试、难版本管理、调试手段弱、跨数据库迁移成本高。所以业界更常见的做法是：业务逻辑放应用层，数据库层只保留数据完整性（约束、触发器做审计）与必要的批处理。

  • 能用一条集合 SQL 解决的，不要写逐行循环；游标逐行处理是性能与可维护性的双重负担。
  • 存储过程里的显式事务要自己 START TRANSACTION / COMMIT / ROLLBACK，异常路径必须回滚。
  • 触发器里出错会连带回滚触发它的那条语句，排查困难；审计类触发器要尽量简单、不要做重活。
procedure.sql
-- 存储过程：按部门整体调薪，无匹配则回滚
DELIMITER //
CREATE PROCEDURE raise_salary(IN p_dept VARCHAR(32), IN p_pct DECIMAL(5,2))
BEGIN
  DECLARE v_rows INT DEFAULT 0;
  START TRANSACTION;
  UPDATE employees
     SET salary = ROUND(salary * (1 + p_pct / 100), 2)
   WHERE dept = p_dept;
  SET v_rows = ROW_COUNT();
  IF v_rows = 0 THEN
    ROLLBACK;
    SELECT '未匹配到员工，已回滚' AS msg;
  ELSE
    COMMIT;
    SELECT CONCAT('已调整 ', v_rows, ' 人') AS msg;
  END IF;
END //
DELIMITER ;

CALL raise_salary('技术', 5);

-- 函数：只返回标量，可放进 SELECT 列表
DELIMITER //
CREATE FUNCTION order_level(p_amount DECIMAL(10,2)) RETURNS VARCHAR(8)
  DETERMINISTIC
BEGIN
  RETURN CASE WHEN p_amount >= 1000 THEN '大额'
              WHEN p_amount >= 100  THEN '中额'
              ELSE '小额' END;
END //
DELIMITER ;

SELECT id, amount, order_level(amount) AS 金额档 FROM orders ORDER BY amount DESC;

-- 触发器：审计订单金额变更
CREATE TABLE orders_audit (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_id BIGINT, old_amount DECIMAL(10,2),
  new_amount DECIMAL(10,2), changed_at DATETIME
);

CREATE TRIGGER trg_orders_audit
AFTER UPDATE ON orders
FOR EACH ROW
INSERT INTO orders_audit (order_id, old_amount, new_amount, changed_at)
VALUES (OLD.id, OLD.amount, NEW.amount, NOW());

预期结果：CALL raise_salary('技术', 5) 调整 4 名技术员工（张伟、李娜、王强、孙悦）并提交；order_level 把 12 条订单分成 4 个大额、5 个中额与 3 个小额；触发器在每次 UPDATE orders 后写入一行审计记录。

★

核心要点：存储程序是「把计算搬到数据旁边」的优化手段，不是架构必需。用它的三条理由：批处理省往返、需要数据库内事务、要强制审计；除此之外优先放在应用层。

!

易错：MySQL 的函数只能返回标量，不能像 PostgreSQL 那样 SELECT * FROM fn() 返回一张表；函数若参与复制或严格模式，应声明 DETERMINISTIC 或 READS SQL DATA，否则开启 log_bin_trust_function_creators 才允许创建。练习台不支持 DDL 与存储程序，请到真实数据库验证。
