数据修改、事务与并发

✓本节学习目标

  • 会写单行 / 多行 INSERT 与 INSERT ... SELECT，并说清为什么批量插入更快。
  • 能按「先 SELECT 验证 → 再 UPDATE → 核对 ROW_COUNT()」的安全流程改数据，识别会误伤全表的写法。

知识点INSERT 与批量插入 / INSERT ... SELECTdml-insert · 把新行写进表

INSERT 是 DML（Data Manipulation Language，数据操纵语言）里把新行写入表的方式，基本形式是 INSERT INTO 表 (列, …) VALUES (值, …)。显式列出列名是最值得养成的习惯：表新增列或调整列顺序时，只写 VALUES 的语句会把数据写进错误的列，而且往往悄无声息。

性能上，一次插入多行（VALUES (...), (...), (...)）比循环执行多条单行 INSERT 快得多：只走一次网络往返、只解析一次 SQL、只提交一次事务。批量大小受 max_allowed_packet 限制，通常几百到几千行一批最稳妥。

INSERT ... SELECT 把查询结果直接写入目标表，数据不经过客户端，是归档、ETL（Extract-Transform-Load，抽取-转换-加载）和建汇总表的常用手段。要注意它在大表上会形成一个长事务，日志与锁的代价都集中在一条语句里。

insert.sql
-- ① 单行插入：显式列出列名，表结构变化时不会错位
INSERT INTO customers (name, city, gender, signup_date, level)
VALUES ('郑凯', '成都', 'M', '2024-05-01', '普通');
-- 结果：customers 8 → 9 行，新行 id = 9

-- ② 批量插入：一条语句写多行，只走一次网络往返
INSERT INTO products (name, category, price, stock) VALUES
  ('耳机',       '数码', 299.00, 150),
  ('显示器支架', '家居', 129.00,  60),
  ('漫画书',     '图书',  45.00, 300);
-- 结果：products 6 → 9 行

-- ③ INSERT ... SELECT：把查询结果直接写入另一张表（归档 / ETL）
CREATE TABLE orders_2024 LIKE orders;          -- 复制表结构
INSERT INTO orders_2024 (id, customer_id, order_date, amount, status)
SELECT id, customer_id, order_date, amount, status
FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';
-- 结果：orders_2024 得到 orders 中 2024 年的全部 12 行

-- ④ 冲突处理：主键 / 唯一键重复时跳过该行
INSERT IGNORE INTO customers (id, name, city, signup_date, level)
VALUES (1, '张伟', '北京', '2023-01-05', '金卡');   -- id = 1 已存在 → 跳过，不报错
写法典型场景代价与注意
INSERT ... VALUES（单行）零星写入、逐条循环每行一次往返与解析，慢
INSERT ... VALUES（多行）批量导入几百~几千行一次往返，快；受 max_allowed_packet 限制
INSERT ... SELECT表间复制、归档、汇总数据不经客户端；大表上是长事务，建议分批
INSERT ... SETMySQL 专有简写可读性差，跨数据库不通用
INSERT IGNORE重复数据直接跳过会把非冲突错误（如截断）一起吞掉
LOAD DATA INFILE超大文件（百万行级）导入最快；需要 FILE 权限与 secure_file_priv 配置
★

核心要点：批量插入的收益来自「减少往返 + 减少提交次数」。写一万行时，一条多行 INSERT 和一万条单行 INSERT 的差别可能是几十倍。

◆

动手提示：本页的 SQL 练习台只支持 SELECT，INSERT / UPDATE / DELETE / 事务请在真实 MySQL 8.0 实例上验证（可以用 Docker 起一个临时库，或在本地测试库上练习）。

!

易错：① 省略列名导致「插入位置错乱」；② INSERT IGNORE 顺手吞掉数据截断、类型转换等真实错误；③ 一次性 INSERT ... SELECT 几百万行，产生巨大事务、undo 膨胀并拖慢主从复制——应分批执行。

知识点UPDATE 与安全更新dml-update · 最危险的一条 DML

UPDATE 修改已有行的列值，语法是 UPDATE 表 SET 列 = 表达式 [, …] [WHERE 条件] [ORDER BY …] [LIMIT n]。SET 右侧可以引用当前值（price = price * 0.9），这是它比「先查出来再写回去」更可靠的地方。

UPDATE 之所以最危险，是因为漏写 WHERE 不会报错：整表会被改掉，而且只要不在事务里，改完就已提交。安全流程固定三步：① 用同样的 WHERE 先跑一次 SELECT 看清命中哪些行 → ② 执行 UPDATE → ③ 立即用 ROW_COUNT() 核对影响行数，与预期不符就 ROLLBACK。

并发方面，InnoDB 会对 UPDATE 扫描到的行加排他锁（X 锁）。如果 WHERE 用不到索引，扫描过的行都会被锁住，别人写同一批行就会等待——所以「更新慢」经常不是 UPDATE 本身慢，而是它锁得太多。

update-safe.sql
-- ① 先看清楚会命中哪些行
SELECT id, name, city, level FROM customers WHERE city = '北京';
-- 命中 2 行：张伟(id=1)、赵磊(id=6)

-- ② 再执行更新
UPDATE customers
SET level = '银卡'
WHERE city = '北京';

-- ③ 立刻核对影响行数
SELECT ROW_COUNT();          -- 2，与 SELECT 结果一致，放心提交

-- 用当前值参与计算：数码品类统一 9 折（3 行）
UPDATE products
SET price = ROUND(price * 0.9, 2)
WHERE category = '数码';

-- 多表更新：按已付款消费额刷新客户等级
UPDATE customers c
JOIN (SELECT customer_id, SUM(amount) AS total
      FROM orders WHERE status = 'paid'
      GROUP BY customer_id) t ON t.customer_id = c.id
SET c.level = CASE WHEN t.total >= 3000 THEN '金卡'
                   WHEN t.total >= 1000 THEN '银卡'
                   ELSE '普通' END;

-- 危险写法（只作对比，切勿在生产执行）
-- UPDATE customers SET level = '金卡';            -- 没有 WHERE → 8 行全部被改
-- UPDATE customers SET city = '北京' WHERE 1 = 1; -- 条件恒真 → 等价于全表更新
-- UPDATE customers SET city = '北京' WHERE name LIKE '%张%';  -- 模糊匹配容易误伤
WHERE 写法命中行数（本例）风险等级说明
WHERE id = 10051低主键精确定位，锁 1 行
WHERE city = '北京'2中非唯一列，先 SELECT 确认
WHERE category = '数码' AND stock > 1002中复合条件，注意索引是否覆盖
WHERE 1 = 18（全表）高条件恒真，等价于没有条件
不写 WHERE8（全表）极高不报错、直接改全表
ORDER BY id LIMIT 55中行数可控，但结果依赖排序稳定性
★

核心要点：「先 SELECT、再 UPDATE、后核对 ROW_COUNT()」是 DML 的两次确认原则。开启 MySQL 的 sql_safe_updates = 1 后，没有 WHERE（或 WHERE 不含索引列）的 UPDATE/DELETE 会被直接拒绝。

!

易错：① SET col = NULL 撞上 NOT NULL 约束会报错并整条失败；② SET count = count + 1 在并发下要靠行锁保证原子性，读出来再写回去会丢失更新；③ 在 UPDATE 里对索引列做函数运算（如 WHERE YEAR(order_date) = 2024）会让索引失效，扫描并锁住更多行。

知识点DELETE / TRUNCATE / DROP 的区别dml-delete · 删行、清表还是删表

三个语句删的对象根本不同：DELETE 删的是「行」，表还在；TRUNCATE 删的是「表里的全部数据」并把表当成新表；DROP 删的是「表本身」——结构、数据、索引、约束一起消失。

DELETE 属于 DML：逐行删除，每一行都写 undo / redo，可以带 WHERE、可以触发触发器，在事务里能被 ROLLBACK 撤销，代价随行数线性增长。TRUNCATE 和 DROP 属于 DDL（Data Definition Language，数据定义语言）：执行时隐式提交当前事务，因此无法回滚；TRUNCATE 直接释放数据页，速度快、日志量小，但会重置 AUTO_INCREMENT 且不触发触发器。

面试高频的一句话总结：「DELETE 能回滚但慢，TRUNCATE 快但不可回滚且重置自增，DROP 连表都没了」。生产上删数据前先备份或先改逻辑删除标记，是比记语法更重要的习惯。

delete-truncate-drop.sql
-- DELETE：按条件删行，可回滚
START TRANSACTION;
DELETE FROM orders WHERE status = 'cancelled';   -- 删 1 行（订单 1009）
SELECT ROW_COUNT();                              -- 1
ROLLBACK;                                        -- 数据回来了

-- DELETE 全部行：表结构保留，自增值不重置
DELETE FROM orders;              -- 12 行 → 0 行，下一个 id 仍从 1013 开始

-- TRUNCATE：清空整表，重置 AUTO_INCREMENT，隐式提交
TRUNCATE TABLE orders;           -- 12 行 → 0 行，下一个 id 回到 1

-- DROP：连表结构一起删除
DROP TABLE orders;

-- 只保留近期数据？用「新建表 + 改名」更快，但同样不可回滚
CREATE TABLE orders_new LIKE orders;
INSERT INTO orders_new SELECT * FROM orders WHERE order_date >= '2024-03-01';
RENAME TABLE orders TO orders_old, orders_new TO orders;   -- 原子换名

-- 大表分批删，避免长事务与主从延迟
DELETE FROM orders WHERE status = 'cancelled' ORDER BY id LIMIT 1000;

易错：① DELETE 不带 WHERE 删全表后想回滚，必须还在同一个事务里；一旦提交就只能靠备份或解析 binlog（binlog_format = ROW 时可用工具生成反向 SQL）。② TRUNCATE 重置自增，会让外部系统里缓存的旧 id 与新数据冲突。③ 以为 TRUNCATE 是「更快的 DELETE」，其实它的语义是「重建空表」。

◆

性能提醒：删 90% 的行时，DELETE ... LIMIT 分批删或「建新表 + RENAME」通常比一次性 DELETE 快得多，也不会长时间占着 undo 与主从带宽。

知识点幂等写入（ON DUPLICATE KEY / REPLACE）upsert · 重复执行也不出错

幂等（idempotent）写入指：同一个请求执行一次和执行多次，结果相同。接口重试、消息重复投递、定时任务重跑都会遇到这个问题。实现幂等的核心不是某条语法，而是先有业务唯一标识，再加唯一键，最后用 upsert（update or insert）落地。

INSERT ... ON DUPLICATE KEY UPDATE 是 MySQL 的做法：不存在就插入，唯一键/主键冲突就执行 UPDATE 分支（PostgreSQL 用 ON CONFLICT，SQL Server 用 MERGE）。它最大的好处是没被 SET 提到的列保持不变，因此不会丢数据。

REPLACE INTO 看起来像 upsert，实际语义是先删除冲突行、再插入新行：未列出的列被重置为默认值或 NULL，DELETE 与 INSERT 触发器都会触发，主键可能变化，外键上的 ON DELETE CASCADE 还可能连带删掉别的表的数据。除非你确实想要「整行替换」，否则优先用 ON DUPLICATE KEY UPDATE。

upsert.sql
-- 以唯一键 (order_id, product_id) 保证「一个订单里一个商品只有一行」
CREATE TABLE order_items_u (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  qty        INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  UNIQUE KEY uk_order_product (order_id, product_id)
);

-- 幂等写入：不存在则插入，存在则累加数量并刷新单价
-- MySQL 8.0.20+ 用别名 new 取代已废弃的 VALUES(col) 写法
INSERT INTO order_items_u (order_id, product_id, qty, unit_price)
VALUES (1001, 2, 1, 129.00) AS new
ON DUPLICATE KEY UPDATE
  qty        = order_items_u.qty + new.qty,
  unit_price = new.unit_price;
-- 第一次执行：插入 1 行（qty = 1）
-- 再执行一次：更新同一行（qty = 2），结果仍然只有 1 行 → 幂等

-- 只增不减：用 GREATEST 防止重复投递把库存改回去
INSERT INTO products (id, name, category, price, stock)
VALUES (1, '机械键盘', '数码', 499.00, 120) AS new
ON DUPLICATE KEY UPDATE stock = GREATEST(products.stock, new.stock);

-- REPLACE：先删后插，未列出的列会被重置（危险）
REPLACE INTO order_items_u (order_id, product_id, qty, unit_price)
VALUES (1001, 2, 5, 119.00);
-- 结果：id 变了，若表里还有 created_at / 备注等列，它们会被清空

-- 只忽略重复、什么都不改
INSERT IGNORE INTO order_items_u (order_id, product_id, qty, unit_price)
VALUES (1001, 2, 1, 129.00);

★

核心要点：幂等 = 唯一键 + 可重复执行。设计时先问「业务上的唯一标识是什么」（订单号、幂等键、业务主键），再决定用哪种 upsert，而不是先选语法。

!

易错：① 用 REPLACE INTO 做「局部更新」，导致没写的列被清空；② 依赖 VALUES(col) 的旧写法（MySQL 8.0.20 起已废弃，改用 AS new 别名）；③ 以为 ON DUPLICATE KEY UPDATE 不消耗自增值——高并发下它仍可能让自增 id 出现空洞。

知识点事务与 ACIDtxn-acid · 全做或全不做

事务（transaction）是一组要么全部成功、要么全部失败的 SQL。InnoDB 支持事务，MyISAM 不支持——这也是 MyISAM 早已不推荐的核心原因。手动事务的写法是 START TRANSACTION（或 BEGIN）开始，COMMIT 提交，ROLLBACK 回滚。

MySQL 默认 autocommit = 1：每条 SQL 自成一个事务并立即提交。要让多条语句同生共死，必须显式开事务。反过来，很多「回滚没生效」的事故都源于隐式提交：DDL（CREATE / ALTER / TRUNCATE / DROP）、LOCK TABLES、SET autocommit = 1 等都会在不知不觉中结束当前事务。

transaction.sql
-- 转账：A 扣 100、B 加 100，必须同生共死
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                      -- 两条同时生效

-- 中途发现问题就整体撤销
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 发现目标账户不存在
ROLLBACK;                    -- 第一条也撤销，余额回到原值

-- 查看与修改自动提交
SELECT @@autocommit;         -- 1
SET autocommit = 0;          -- 之后的语句需要显式 COMMIT
COMMIT;
SET autocommit = 1;          -- 恢复默认

-- 隐式提交陷阱：DDL 会悄悄结束当前事务
START TRANSACTION;
INSERT INTO customers (name, city, signup_date, level)
VALUES ('测试用户', '北京', '2024-05-01', '普通');
CREATE TABLE tmp_t (id INT);  -- ← DDL 隐式提交，上面的 INSERT 已经落盘
ROLLBACK;                     -- 什么也回滚不了
ACID 特性含义InnoDB 靠什么实现
原子性 Atomicity事务内的操作全做或全不做undo log：回滚时按记录反向撤销
一致性 Consistency数据始终满足约束与业务规则主键 / 唯一 / 外键 / CHECK 约束 + 正确的应用逻辑
隔离性 Isolation并发事务之间互不干扰MVCC（Read View）+ 行锁 / 间隙锁
持久性 Durability提交后即使断电也不丢redo log（WAL：先写日志再刷数据页）+ 双写缓冲
★

核心要点：ACID 不是四个口号，而是四套机制：undo 管回滚、redo 管持久、MVCC + 锁管隔离、约束 + 业务逻辑管一致。模块 11 会把 redo / undo / binlog 三者关系展开讲。

!

易错：把 DDL 写进事务里——它会让事务在你没察觉的地方提交；另外 autocommit = 0 后忘记 COMMIT，连接断开时数据会回滚，看起来像「插入丢失」。

知识点隔离级别与并发异常（脏读/不可重复读/幻读）txn-isolation · 快照与锁的取舍

隔离性（isolation）要解决三类并发异常：脏读（dirty read）——读到了别的事务还没提交的数据；不可重复读（non-repeatable read）——同一事务内两次读同一行，值变了；幻读（phantom read）——同一事务内两次执行同样的范围查询，行数变了。

SQL 标准定义了四个隔离级别，级别越高异常越少、并发度越低。MySQL 8.0 InnoDB 的默认级别是 REPEATABLE READ，它用 MVCC（Multi-Version Concurrency Control，多版本并发控制）让事务内看到固定的快照，再配合间隙锁（gap lock）在范围读上加锁，因此标准里允许的幻读在 InnoDB 中基本不会出现。

选择级别时问两个问题：业务能容忍哪种异常？并发压力有多大？账务类场景宁可保守（RR 或串行化）；以报表读为主的库可以降到 READ COMMITTED 换取更少的锁等待。

isolation.sql
-- 查看当前会话的隔离级别（MySQL 8.0 的变量名是 transaction_isolation）
SELECT @@transaction_isolation;          -- REPEATABLE-READ

-- 修改当前会话（只影响这个连接）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 只对下一个事务生效
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
SELECT stock FROM products WHERE id = 1;
COMMIT;

-- 全局修改（需权限，重启失效，建议写进 my.cnf）
SET GLOBAL transaction_isolation = 'READ-COMMITTED';

-- SERIALIZABLE 下读也会加共享锁；8.0 推荐写法是 FOR SHARE
SELECT stock FROM products WHERE id = 1 FOR SHARE;   -- 旧写法 LOCK IN SHARE MODE

-- 明确要写锁时用 FOR UPDATE（排他锁，别人改同一行要等）
SELECT stock FROM products WHERE id = 1 FOR UPDATE;

SERIALIZABLE不可能不可能不可能读也加共享锁，等价于串行执行，并发度最低
◆

面试点：MySQL 的 RR 与「标准 RR」不完全一样——InnoDB 通过 next-key lock（记录锁 + 间隙锁）在很大程度上消除了幻读。同时，长事务会让 RR 的 Read View 一直存活，undo 版本无法清理，这是「RR 更贵」的常见原因。

!

易错：① 把「事务里自己刚 UPDATE 再读到自己改的值」当成脏读——那是自己的修改，本来就可见；② 改隔离级别时用了 SET GLOBAL 却没意识到会影响所有新连接；③ 以为 RC 一定更快，忽略了 RC 下每条语句都要重建快照、且需要更多间隙锁的情况。

Practice · 事务实践

03回滚、保存点与长事务
把事务写短、写小、不依赖外部服务

知识点事务实践：回滚、保存点、长事务危害txn-practice · 生产环境的铁律

保存点（SAVEPOINT）让事务内部可以有「部分回滚」：SAVEPOINT sp1 打点，ROLLBACK TO SAVEPOINT sp1 回到该点（之前的操作仍然保留），RELEASE SAVEPOINT sp1 释放。典型场景是「主记录 + 多条明细」，某条明细失败时只撤销这一条，而不是整单重做。

长事务是生产事故的常客，危害至少三类：① 长时间持有行锁，阻塞其它写入甚至引发死锁；② undo log 无法清理（最老的 Read View 一直有效），回滚段膨胀、磁盘涨、查询变慢；③ 一个巨大事务的 binlog 要等提交后一次性传给从库，造成主从延迟。

实践规范可以浓缩成八个字：短、小、无外部依赖。把查询放在事务外；批量操作分批提交；绝不在事务里调用 HTTP / RPC；必要时用 innodb_lock_wait_timeout 与 max_execution_time 兜底，并通过 information_schema.INNODB_TRX 找到跑得最久的那个事务。

txn-practice.sql
-- 保存点：整单下单，某条明细失败只回滚该条
START TRANSACTION;
INSERT INTO orders (id, customer_id, order_date, amount, status)
VALUES (1013, 1, '2024-05-06', 0.00, 'paid');
SAVEPOINT after_order;

INSERT INTO order_items (order_id, product_id, qty, unit_price)
VALUES (1013, 1, 2, 499.00);
SAVEPOINT after_item1;

INSERT INTO order_items (order_id, product_id, qty, unit_price)
VALUES (1013, 999, 1, 0.00);            -- 商品不存在，业务校验失败
ROLLBACK TO SAVEPOINT after_item1;      -- 只撤销第二条明细

UPDATE orders SET amount = 998.00 WHERE id = 1013;
COMMIT;                                 -- 订单 + 第一条明细一起提交

-- 分批提交：把大批量更新拆成多批，避免长事务
-- （在应用层或存储过程里循环执行）
UPDATE orders SET status = 'archived' WHERE status = 'cancelled' ORDER BY id LIMIT 1000;
SELECT ROW_COUNT();                     -- 每批核对行数，为 0 时结束

-- 排查长事务：跑了多久、锁了多少行、正在执行什么
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs,
       trx_rows_locked, trx_query
FROM information_schema.INNODB_TRX
ORDER BY secs DESC;

-- 兜底：锁等待与单语句超时（会话级）
SET SESSION innodb_lock_wait_timeout = 5;
SET SESSION max_execution_time = 2000;  -- 单位毫秒，且只作用于 SELECT 语句
场景不推荐推荐做法
批量更新 10 万行一个事务全做完按主键分批提交，每批 500~1000 行
事务里调用第三方接口锁持有到接口返回先落库业务状态，接口用异步任务补偿
事务里做长查询SELECT 与写混在一个事务查询放事务外，事务只包住写操作
部分失败整单重做用 SAVEPOINT 只回滚出错的那一步
异常处理抛异常后不管连接状态捕获异常 → ROLLBACK → 记录日志
事务里执行 DDL以为能一起回滚DDL 单独执行，先提交再改结构
!

易错：① 事务开着却去做耗时操作（发消息、调接口、等用户输入），锁一直不放；② 只 ROLLBACK 却忘了 RELEASE SAVEPOINT，保存点越积越多；③ 用 KILL 杀掉长事务前没确认它是否在跑重要业务。

★

核心要点：事务只包住「必须原子」的写操作。把长事务拆短，比事后排查锁等待、主从延迟和 undo 膨胀划算得多。
