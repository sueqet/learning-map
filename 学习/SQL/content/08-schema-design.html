知识点CREATE / ALTER / DROP / TRUNCATEddl-basic

DDL（Data Definition Language，数据定义语言）管的是「结构」而不是「数据」：CREATE 建、ALTER 改、DROP 删、TRUNCATE 清空。它们是建表阶段最常用的四条语句，也是后面所有约束、索引、范式的载体——表结构一旦定下来，改起来远比一开始设计好要贵。

写 CREATE TABLE 时要一次性想清五件事：字段类型与长度、是否允许 NULL、默认值、主键与约束、索引与存储引擎（默认 InnoDB、字符集建议 utf8mb4）。线上大表做 ALTER 可能锁表数分钟甚至数小时，所以「先设计、后建表」比「先建表、再改」便宜得多。

  • CREATE TABLE 建表；CREATE TABLE ... LIKE 只复制结构；CREATE TABLE ... AS SELECT 复制结构并灌入数据。
  • ALTER TABLE 可加/删/改列、加索引、加外键。MySQL 8.0 支持 ALGORITHM=INSTANT 秒级加列，但列只能追加到末尾。
  • DROP TABLE 把结构与数据一起删掉，不可恢复；TRUNCATE TABLE 只清数据、保留结构，并重置自增计数器。
  • MySQL 中 DDL 会隐式提交（implicit commit），执行完无法用 ROLLBACK 撤销。
ddl-basic.sql
-- 建表：类型 + 非空 + 默认值 + 主键 + 唯一键 + 普通索引

知识点主键 / 外键 / 唯一 / 非空 / 默认 / CHECKconstraint

约束（constraint）是数据库层的「最后一道防线」：把业务规则直接写进表结构，让不合法的数据根本插不进来。相比只在应用层做校验，约束对所有写入路径都生效——包括运维手工 SQL、批量导入和别的服务。

MySQL 8.0 里最常用的六类约束：主键（primary key）唯一且非空，一张表只能有一个，InnoDB 用它当聚簇索引；外键（foreign key）引用另一张表的主键或唯一键，保证引用完整性；唯一键（unique）保证值不重复但允许 NULL；非空（not null）禁止缺值；默认值（default）在没写该列时填一个值；CHECK 用布尔表达式限制取值范围。

  • UNIQUE 允许多个 NULL：在 MySQL 里多个 NULL 不算重复，所以「邮箱唯一」并不能阻止多条空邮箱记录。
  • NOT NULL 不等于「不能是空字符串」：'' 是合法值，需要额外用 CHECK 拦住。
  • 外键的删除策略：ON DELETE CASCADE 级联删、SET NULL 置空、RESTRICT 禁止删（默认）。
  • CHECK 从 MySQL 8.0.16 起才真正强制生效，更早的版本会解析但忽略它。
constraint.sql
-- 六类约束一起用
CREATE TABLE orders (
  id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,          -- 主键
  customer_id INT UNSIGNED NOT NULL,                            -- 非空
  order_date  DATE         NOT NULL,
  amount      DECIMAL(10,2) NOT NULL DEFAULT 0.00,              -- 默认值
  status      ENUM('paid','refunded','cancelled') NOT NULL DEFAULT 'paid',
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id)          -- 外键
    ON DELETE RESTRICT ON UPDATE CASCADE,
  CONSTRAINT chk_amount CHECK (amount >= 0)                    -- CHECK
) ENGINE=InnoDB;

-- 后加约束：先确认历史数据已经干净，否则 ALTER 会失败
ALTER TABLE orders ADD CONSTRAINT chk_status
  CHECK (status IN ('paid','refunded','cancelled'));

易错：外键不是免费的——每次写入子表都要去父表检查并加锁，高并发下容易产生锁竞争。不少互联网业务因此「不建物理外键，改由应用层保证」，面试时要能说出这个权衡，而不是一口断言「外键必须建」或「外键没用」。

知识点自增主键 vs 业务主键 vs UUIDkey-choice

主键（primary key）是每一行的唯一身份证。常见方案有三种：自增整数（AUTO_INCREMENT）、业务主键（natural key）比如身份证号或订单号、UUID（通用唯一标识符）。选型的判断维度是三件事：唯一性由谁保证、写入性能如何、对外可读性与扩展性够不够。

在 InnoDB 里主键就是聚簇索引，而且每个二级索引的叶子节点都要存一份主键值。这意味着主键越宽，所有索引越大——用 36 字节的 UUID 字符串做主键，等于把每一条二级索引都撑大几十字节，这个代价比表面看到的更重。

  • 自增整数：最紧凑、插入顺序递增、B+ 树几乎不分裂，是 OLTP 的默认选择；缺点是暴露业务量、分库分表后要另找全局唯一方案。
  • 业务主键：语义清晰、便于外部对接；但业务键会变（手机号换绑、订单号规则调整），且往往很长，一改就要级联更新所有引用它的表。
  • UUID：全局唯一、适合分布式与多端生成；但随机值会导致页分裂与写放大。MySQL 8.0 建议存成 BINARY(16)，并用 UUID_TO_BIN(uuid, 1) 把时间高位提前，缓解随机插入。
key-choice.sql
-- 方案 A：内部用自增主键，对外单号加唯一索引（最常用）
CREATE TABLE orders (
  id       BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  order_no CHAR(20) NOT NULL,
  amount   DECIMAL(10,2) NOT NULL,
  UNIQUE KEY uk_order_no (order_no)
);

-- 方案 B：UUID 主键，存成 BINARY(16) 省空间（MySQL 8.0）
CREATE TABLE events (
  id   BINARY(16) PRIMARY KEY DEFAULT (UUID_TO_BIN(UUID(), 1)),
  name VARCHAR(50) NOT NULL
);
INSERT INTO events (name) VALUES ('signup');
SELECT BIN_TO_UUID(id, 1) AS id, name FROM events;   -- 展示时再转回字符串

-- 量化一下存储差异：36 字节 vs 16 字节
SELECT LENGTH(UUID()) AS str_len,
       LENGTH(UUID_TO_BIN(UUID(), 1)) AS bin_len;

★

核心要点：默认答案——内部用 BIGINT AUTO_INCREMENT 做主键，业务单号单独加 UNIQUE 索引。既拿到聚簇索引顺序写的性能，又满足对外可读、可校验的需求。

!

易错：别用 AUTO_INCREMENT 的值当业务含义（比如直接当订单号给用户看）：删除记录后它不会回收，批量插入还可能跳号（8.0 之前的版本重启会重置计数器，8.0 起会把计数器持久化）。它只保证唯一，不保证连续。

知识点索引初识：什么时候该加索引index-intro

索引（index）是数据库为加速查找额外维护的数据结构，InnoDB 默认用 B+ 树。它把「全表扫描」的 O(n) 变成树查找的 O(log n)，代价是占用磁盘、并拖慢每一次写入。这一节只讲「该不该加」的判断标准，原理与执行计划留给模块 09。

判断的核心指标是选择性（selectivity）：COUNT(DISTINCT 列) / COUNT(*)，越接近 1 表示值越分散、索引越有效。性别只有 M/F 两种取值，选择性约 0.25，走索引反而不如直接全表扫描；而手机号几乎唯一，选择性接近 1，索引效果非常显著。

  • 该加：WHERE / JOIN ON / ORDER BY / GROUP BY 中高频出现的列；外键列（InnoDB 需要它避免父表被过度加锁）；高选择性的列。
  • 慎重：更新极其频繁的列（每次写入都要维护索引）；选择性极低的列；已经能被联合索引最左前缀覆盖的列（避免重复索引）。
  • 代价：每多一个索引，INSERT / UPDATE / DELETE 就多一次 B+ 树维护；联合索引 (a,b) 已经存在时，单独再建 (a) 通常是冗余的。
index-intro.sql
-- 为高频过滤列加索引
CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE INDEX idx_orders_date_status ON orders (order_date, status);

-- 看查询走没走索引：type=ALL 是全表扫描，ref / range 才用上索引
EXPLAIN SELECT * FROM orders WHERE customer_id = 3;

-- 评估选择性：越接近 1 越适合建索引
SELECT COUNT(DISTINCT name)   / COUNT(*) AS name_sel,     -- 1.00
       COUNT(DISTINCT city)   / COUNT(*) AS city_sel,     -- 0.63（5 个城市 / 8 行，NULL 不计入 DISTINCT）
       COUNT(DISTINCT level)  / COUNT(*) AS level_sel,    -- 0.38
       COUNT(DISTINCT gender) / COUNT(*) AS gender_sel    -- 0.25
FROM customers;

-- 按城市过滤能立刻受益
SELECT id, name FROM customers WHERE city = '北京';
列不同值个数选择性结论
customers.name81.00很适合建索引（本例唯一，实际业务中一般也建）
customers.city50.63可以建，按城市过滤很常见（NULL 不计入 COUNT(DISTINCT)）
customers.level30.38一般，建议放进联合索引而不是单独建
customers.gender20.25不建议单列索引，优化器多半会放弃
orders.customer_id70.58必须建：既是外键列，又是高频连接键
!

易错：「加了索引就一定快」是误区。对索引列做函数运算或隐式类型转换（例如 WHERE YEAR(order_date) = 2024、字符串列与数字比较）会让索引失效；在低选择性列上单独建索引，优化器也可能干脆不用它。

知识点视图与物化视图view

视图（view）是一条被命名并保存下来的 SELECT 语句。查询视图时，数据库会把它展开成底层 SQL 去执行——视图本身不存数据，只存定义。它主要解决三个问题：把复杂查询封装成简单接口、隔离底层表结构变化、做列级或行级的权限控制。

物化视图（materialized view）则相反：把查询结果真正存下来，查询时直接读结果，代价是需要刷新策略（全量重建或增量刷新），数据有延迟。MySQL 8.0 没有内置物化视图，工程上的常见替代是「汇总表 + 定时任务/触发器刷新」，或者干脆在应用层缓存。

  • 普通视图：零存储、永远读到最新数据；但每次查询都要重新执行底层 SQL，逻辑复杂时会很慢。
  • 可更新视图：不含聚合、DISTINCT、GROUP BY、UNION、窗口函数等时，可以通过视图做 INSERT / UPDATE / DELETE。
  • WITH CHECK OPTION：限制通过视图写入的数据必须满足视图的 WHERE 条件，防止「写完就看不见」。
  • 物化视图：查询快、有存储成本与新鲜度延迟，必须明确「谁在什么时候刷新」。
view.sql
-- 视图：把「客户 + 订单数 + 消费总额」封装成一张虚拟表
CREATE OR REPLACE VIEW v_customer_orders AS
SELECT c.id AS customer_id, c.name, c.city,
       COUNT(o.id)                AS order_cnt,
       COALESCE(SUM(o.amount), 0) AS total_amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name, c.city;

SELECT * FROM v_customer_orders WHERE city = '北京';

-- 可更新视图 + WITH CHECK OPTION：只能写入北京客户
CREATE OR REPLACE VIEW v_bj_customers AS
SELECT id, name, city, level FROM customers WHERE city = '北京'
WITH CHECK OPTION;

UPDATE v_bj_customers SET level = '金卡' WHERE id = 1;   -- 允许
UPDATE v_bj_customers SET city = '上海' WHERE id = 1;     -- 拒绝：违反 WITH CHECK OPTION

-- MySQL 没有物化视图：用汇总表 + 定时任务代替
CREATE TABLE dw_customer_amount (
  customer_id INT UNSIGNED PRIMARY KEY,
  total_amount DECIMAL(12,2) NOT NULL
);
INSERT INTO dw_customer_amount
SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;
-- 之后由定时任务（如每天凌晨）重建这张表

核心要点：视图的价值是「封装 + 权限」，不是「加速」。想加速，要么给底层表加索引，要么建汇总表/物化结果并接受刷新延迟。

!

易错：视图嵌套视图会让执行计划变得极难排查；底层表被改列名或删列后，视图会直接失效并报 1356 错误。生产上建议视图层数不超过两层，并在表结构变更时同步检查依赖的视图。

知识点ER 建模与表关系（1:1 / 1:N / M:N）er-model

ER 建模（Entity-Relationship modeling，实体-关系建模）用「实体 + 属性 + 关系」描述业务：实体落到表，属性落到列，关系落到外键或中间表。先把关系想清楚再写 DDL，能避免「表建完才发现少了一张中间表」这类返工。

三种基数关系的落地方式各不相同：1:1 把外键放在任一侧并加 UNIQUE，或者干脆让两侧共享主键；1:N 把外键放在「多」的一侧，这是最自然、最常见的形式；M:N 必须引入中间表（junction table），把两个外键放进去，再用联合主键或联合唯一索引防止重复。

erDiagram CUSTOMERS ||--|| CUSTOMER_PROFILES : "1:1 档案" CUSTOMERS ||--o{ ORDERS : "1:N 下单" ORDERS ||--|{ ORDER_ITEMS : "1:N 包含" PRODUCTS ||--o{ ORDER_ITEMS : "1:N 被购买" EMPLOYEES ||--o{ EMPLOYEES : "1:N 管理" CUSTOMERS { int id PK varchar name varchar city } CUSTOMER_PROFILES { int customer_id PK "FK customers.id" varchar bio } ORDERS { int id PK int customer_id FK date order_date decimal amount } ORDER_ITEMS { int order_id PK "FK orders.id" int product_id PK "FK products.id" int qty decimal unit_price } PRODUCTS { int id PK varchar name decimal price } EMPLOYEES { int id PK int manager_id FK varchar name }
  • 1:1：如「客户 ↔ 客户档案」。字段很少时通常直接并进主表，拆开反而多一次 JOIN。
  • 1:N：如「客户 → 订单」。外键加在「多」的一侧（orders.customer_id），并给它建索引。
  • M:N：如「订单 ↔ 商品」。中间表 order_items 用联合主键，还可以携带自己的属性（数量、成交单价）。
  • 自引用 1:N：如「员工 → 直属经理」，同一张表的外键指向自身，manager_id 允许 NULL 表示顶层。
er-model.sql
-- M:N 落地：中间表 + 联合主键 + 两个外键
CREATE TABLE order_items (
  order_id   INT UNSIGNED NOT NULL,
  product_id INT UNSIGNED NOT NULL,
  qty        INT NOT NULL DEFAULT 1,
  unit_price DECIMAL(10,2) NOT NULL,                 -- 成交价（快照）
  PRIMARY KEY (order_id, product_id),                -- 同一订单不能重复同一商品
  CONSTRAINT fk_items_order
    FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
  CONSTRAINT fk_items_product
    FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT,
  KEY idx_product (product_id)                       -- 支持「该商品被哪些订单买了」
);

-- 1:1 落地：外键 + UNIQUE（或直接共享主键）
CREATE TABLE customer_profiles (
  customer_id INT UNSIGNED PRIMARY KEY,
  bio         VARCHAR(200),
  CONSTRAINT fk_profile_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE CASCADE
);

-- 1:N 落地：外键放在「多」的一侧
ALTER TABLE orders
  ADD CONSTRAINT fk_orders_customer
  FOREIGN KEY (customer_id) REFERENCES customers(id);

-- 自引用：员工表的 manager_id 指向自己
SELECT e.name AS 员工, m.name AS 经理
FROM employees e LEFT JOIN employees m ON e.manager_id = m.id
ORDER BY e.id;
关系例子落地方式注意点
1:1客户 ↔ 客户档案外键 + UNIQUE，或共享主键字段少就别硬拆，并进主表更省事
1:N客户 → 订单外键放在「多」的一侧外键列要建索引，否则删父行会锁很多行
M:N订单 ↔ 商品中间表 + 联合主键中间表可带自己的属性（qty、unit_price）
自引用员工 → 经理同表外键指向自身允许 NULL 表示顶层，查询要用 LEFT JOIN
★

核心要点：判断 M:N 只需问一句：「一条 A 能对应多条 B，同时一条 B 也能对应多条 A 吗？」两个都「是」，就必须有中间表。

!

易错：不要用逗号分隔字符串存多值（例如 product_ids = '1,3,5'）来逃避中间表。那样既违反 1NF，又无法建索引、无法做外键约束，后续任何统计都要靠字符串函数硬拆。

知识点范式：1NF / 2NF / 3NFnorm-123

范式（normal form）是一组消除数据冗余与更新异常的设计规则。它的语言是函数依赖（functional dependency）：写成 X → Y，读作「X 确定了 Y」。范式不是越高越好，而是「先规范化，再按性能需要有限反范式」。

  • 1NF：每一列都是原子值——不能在一格里塞多个值，也不能有重复组。
  • 2NF：在 1NF 基础上，非主键列必须完全依赖整个主键，不能只依赖其中一部分（消除部分依赖）。注意它只对复合主键才有意义。
  • 3NF：在 2NF 基础上，非主键列不能依赖另一个非主键列（消除传递依赖）。

把这三步走完，结果通常是「一张事实表 + 若干维度表」：客户信息只存一份、商品信息只存一份，订单明细用中间表连接两者。代价也很明确——查询时要多写几个 JOIN，这也是后面「反范式」存在的理由。

norm-123.sql
-- 3NF 的结果：一条事实只存一处
-- customers(客户信息) / products(商品信息) / orders(订单头) / order_items(订单明细)
CREATE TABLE order_items (
  order_id   INT UNSIGNED NOT NULL,
  product_id INT UNSIGNED NOT NULL,
  qty        INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,   -- 成交价，依赖 (order_id, product_id)
  PRIMARY KEY (order_id, product_id)
);

-- 查询时把「拆开的表」拼回来，这正是规范化的代价
SELECT o.id AS 订单号, c.name AS 客户, p.name AS 商品,
       oi.qty, oi.unit_price, oi.qty * oi.unit_price AS 小计
FROM orders o
JOIN customers   c  ON o.customer_id = c.id
JOIN order_items oi ON oi.order_id   = o.id
JOIN products    p  ON oi.product_id = p.id
WHERE o.id = 1001;
订单号客户商品qtyunit_price小计
1001张伟无线鼠标1129.00129.00
1001张伟笔记本259.00118.00
共 2 行；两行小计之和 247.00，正好等于 orders.amount（订单 1001），可以拿来交叉验证
范式要消除什么违反的样子修法
1NF非原子值、重复组一格里写「无线鼠标×1, 笔记本×2」拆成一行一个值
2NF部分依赖主键是 (订单号, 商品)，而订单日期只依赖订单号把只依赖部分主键的列拆到单独的表
3NF传递依赖订单表里同时存客户名和客户城市（订单号 → 客户 → 城市）客户信息单独建表，订单表只留 customer_id
★

核心要点：记忆法——1NF 管「一个格子放几个值」，2NF 管「依赖整个主键」，3NF 管「不要依赖非主键列」。三步依次递进，前一步不满足，后一步就无从谈起。

!

易错：2NF 只对复合主键才可能被违反。如果主键是单列（比如自增 id），「部分依赖」根本不存在，这张表天然满足 2NF——这是笔试里最常见的送分/送命点。

知识点BCNF 与反范式权衡norm-bcnf

BCNF（Boyce-Codd Normal Form，巴斯科德范式）是 3NF 的加强版：要求每一个非平凡函数依赖 X → Y 的左边 X 都必须是超键（superkey）。3NF 比它宽松的地方是：允许「决定因素 X 不是超键、但被决定的 Y 是主属性（属于某个候选键）」这种依赖；BCNF 连这种情况都不允许，因此更严格；代价是分解时不一定能保持所有函数依赖。

经典反例：表 course_teacher(学生, 课程, 教师)，规则是「每位教师只教一门课」（教师 → 课程）且「每个学生每门课只跟一位教师」（(学生, 课程) → 教师）。候选键是 (学生, 课程) 和 (学生, 教师)，但 教师 → 课程 的左边不是超键，所以它满足 3NF 却违反 BCNF。分解成 teacher_course(教师, 课程) 与 student_teacher(学生, 教师) 即可。

反范式（denormalization）是反向操作：刻意把冗余加回来，用空间和一致性维护成本换取查询性能。数仓里的宽表、订单表里冗余的客户名、报表里的预聚合汇总表都是反范式。关键不是「能不能冗余」，而是「冗余字段由谁、在什么时候维护」。

norm-bcnf.sql
-- 违反 BCNF 的写法：教师与课程混在一张表里
CREATE TABLE course_teacher (
  student VARCHAR(20),
  course  VARCHAR(30),
  teacher VARCHAR(20),
  PRIMARY KEY (student, course),
  UNIQUE KEY uk_student_teacher (student, teacher)
);
-- 教师 → 课程，但「教师」不是超键 ⇒ 违反 BCNF

-- BCNF 分解：教师→课程 单独成表，选课只留 (学生, 教师)
CREATE TABLE teacher_course (
  teacher VARCHAR(20) PRIMARY KEY,     -- 一位教师只教一门课
  course  VARCHAR(30) NOT NULL
);
CREATE TABLE student_teacher (
  student VARCHAR(20),
  teacher VARCHAR(20),
  PRIMARY KEY (student, teacher),
  CONSTRAINT fk_st FOREIGN KEY (teacher) REFERENCES teacher_course(teacher)
);

-- 反范式示例：订单表冗余客户名与城市，省掉一次 JOIN
ALTER TABLE orders
  ADD COLUMN customer_name VARCHAR(50) NULL,
  ADD COLUMN customer_city VARCHAR(30) NULL;
-- 代价：客户改名或搬家时，必须同步更新所有历史订单
-- （或者接受「历史快照」语义，明确它记录的是下单当时的客户信息）
层次核心要求能否保持依赖典型场景
3NF非主键列不传递依赖于主键可以保持绝大多数 OLTP 业务表
BCNF每个决定因素（依赖左边）都是超键不一定能保持依赖关系复杂、主属性互相决定
反范式刻意冗余以换取查询速度不适用报表、数仓宽表、读多写少的场景
★

面试标准答法：「先按 3NF（必要时到 BCNF）设计，保证一处存储、便于维护；再针对读多写少、JOIN 成本高的场景做有限反范式，并且保证每个冗余字段只有一个维护入口（定时重算、触发器或应用双写）。」

!

易错：反范式最大的风险不是占空间，而是数据不一致。同一份事实存两处，只要有一条写入路径漏了同步，报表和业务库就会对不上。做反范式前先问自己：「这个字段能不能靠定时任务从源表重算出来？」
