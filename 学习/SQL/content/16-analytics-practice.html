01增长分析：漏斗 · 留存 · 实验

知识点漏斗分析funnel analysis · 定位每一步的流失

漏斗分析（funnel analysis）把用户完成一个目标的全过程拆成有序的若干环节，统计每个环节的到达人数与转化率，从而把「转化率低」这种模糊结论，变成「加购到下单掉了 33%，主要流失在这一步」这种可执行的结论。电商最典型的漏斗是：浏览商品 → 加入购物车 → 提交订单 → 支付成功。

写好漏斗 SQL 的前提是把口径定死，一共三件事：窗口期（同一次会话内、7 天内还是 30 天内完成算一次漏斗）、去重粒度（按 user_id 去重，而不是数事件条数）、顺序（必须按时间先后完成，不能只看「各环节各自有多少人」）。口径一变，漏斗数字会完全不同，所以报表里必须写明窗口与去重方式。

  • 环节转化率 = 本环节人数 ÷ 上一环节人数；整体转化率 = 末环节人数 ÷ 首环节人数，两者含义不同，不要混用。
  • 用 COUNT(*) 统计环节人数会把同一用户重复触发的事件算多次，导致人数虚高；漏斗里应当用 COUNT(DISTINCT user_id)。
  • 严格漏斗必须先取每个用户每个环节的最早时间，再判断时间是否单调递增；「各环节独立去重人数」只是它的上界。

下面的 events 表是本页补充的事件表，字段含义：user_id 用户 id（对应 customers.id）、step 环节（view 浏览 / cart 加购 / order 提交订单 / pay 支付成功）、day 相对天数（1 表示第 1 天，用于判断顺序）。表中 10 个用户产生 24 条事件，其中用户 1 重复浏览了两次，正好用来对比去重与否的差别。

funnel.sql
-- ① 各环节去重人数（漏斗的第一步）
SELECT step,
       COUNT(*)                AS 事件数,      -- 会被重复事件放大
       COUNT(DISTINCT user_id) AS 去重人数     -- 漏斗应该看这个
FROM events
GROUP BY step;

-- ② 严格「有序漏斗」：先取每个用户每个环节的最早时间，再判断时间单调递增
--    练习台不支持窗口函数与 WITH，请到真实 MySQL 8.0 验证
WITH f AS (
  SELECT user_id,
         MIN(CASE WHEN step = 'view'  THEN day END) AS t_view,
         MIN(CASE WHEN step = 'cart'  THEN day END) AS t_cart,
         MIN(CASE WHEN step = 'order' THEN day END) AS t_order,
         MIN(CASE WHEN step = 'pay'   THEN day END) AS t_pay
  FROM events
  GROUP BY user_id
)
SELECT COUNT(*)                                          AS 浏览人数,
       SUM(t_cart  IS NOT NULL AND t_cart  >= t_view)   AS 加购人数,
       SUM(t_order IS NOT NULL AND t_order >= t_cart)   AS 下单人数,
       SUM(t_pay   IS NOT NULL AND t_pay   >= t_order)  AS 支付人数
FROM f;

cart 加入购物车660.0%60.0%4
order 提交订单466.7%40.0%2

★

核心要点：漏斗 = 口径（窗口 + 去重 + 顺序）+ 两个转化率（环节转化率看单步健康度，整体转化率看全链路效率）。报数字时必须连口径一起报，否则数字没有意义。

!

易错：用「各环节独立人数」当漏斗（如 10 → 6 → 4 → 3）会忽略顺序，真实数据里会有用户先加购、后浏览甚至只支付不浏览，导致人数被高估；正确做法是先按用户取各环节最早时间再校验单调。另外 COUNT(*) 会把重复事件算进去，本页数据里浏览环节会从 10 虚高到 11。

性能提示：events 表建议在 (step, user_id) 或 (user_id, day) 上建索引，并按时间做分区；漏斗查询通常只需扫最近 7–30 天的分区，避免全表扫描。

提示：环节转化率 = 本环节人数 ÷ 上一环节人数；累计转化率 = 本环节人数 ÷ 首环节人数。改一个数字，两个转化率会同时变化。

知识点留存与同期群分析retention & cohort · 看长期价值

留存（retention）衡量的是「某批用户在之后的时间里还有多少比例继续使用产品」；同期群分析（cohort analysis）则是把用户按首次行为的时间分组，分别追踪每一组的留存曲线。它的价值在于：整体留存率会被「新用户占比」这种结构变化污染，而同期群把不同批次的用户分开看，趋势才是干净的。

算留存之前必须先回答三个口径问题：新增怎么定义（注册、首次下单还是首次活跃）、活跃怎么定义（登录、下单还是打开 App）、时间粒度（日 / 周 / 月）。最常用的两个数字是 D1 次留（首日后第 1 天仍活跃人数 ÷ 首日新增人数）和 D7 七留，它们反映的是新用户第一次体验的质量。

  • 留存矩阵的行是同期群、列是第 N 天，右上角天然是空的（还没观测到），比较时只能比同一列。
  • 累计留存（截至第 N 天有过活跃）只增不减；同期群留存（恰好第 N 天活跃）可升可降，两者别混。
  • 把老用户混进「新增」、或拿「当日活跃 ÷ 当日新增」当留存，都是最常见的数据事故。
retention.sql
-- ① 以「首单月」为同期群，统计同期群规模与「首单后再次购买」的人数
SELECT DATE_FORMAT(f.first_day, '%Y-%m')       AS 同期群,
       COUNT(DISTINCT f.customer_id)           AS 同期群人数,
       COUNT(*)                                AS 累计订单数,
       COUNT(DISTINCT CASE WHEN o.order_date > f.first_day
                           THEN o.customer_id END) AS 复购人数
FROM (SELECT customer_id, MIN(order_date) AS first_day
      FROM orders
      WHERE status = 'paid'
      GROUP BY customer_id) f
JOIN orders o
  ON o.customer_id = f.customer_id
 AND o.status = 'paid'
GROUP BY DATE_FORMAT(f.first_day, '%Y-%m');

-- ② 日粒度留存矩阵（首日新增 → D1 / D7）
--    练习台不支持窗口函数，请到真实 MySQL 8.0 验证
SELECT DATE(login_time)                                        AS 首日,
       COUNT(DISTINCT user_id)                                 AS 新增人数,
       COUNT(DISTINCT CASE WHEN DATEDIFF(login_time, first_day) = 1 THEN user_id END) AS D1,
       COUNT(DISTINCT CASE WHEN DATEDIFF(login_time, first_day) = 7 THEN user_id END) AS D7
FROM (SELECT user_id, login_time,
             MIN(DATE(login_time)) OVER (PARTITION BY user_id) AS first_day
      FROM user_login) t
GROUP BY DATE(first_day)
ORDER BY 首日;

核心要点：留存三问——新增是谁、活跃是什么、粒度多细。答不上来这三个问题，留存率一定算错。同期群分析的作用是让不同批次的用户可比，而不是让留存率变高。

!

易错：上面的同期群 SQL 里 o.order_date > f.first_day 必须用严格大于，否则首单当天会被算成复购（用户 1 的首单 2024-01-05 与第二单 2024-01-20 都在 1 月，属于同月复购而非次日留存）。另外 2024-02 同期群复购为 0，是因为客户 3 的第二单 2024-02-15 状态是 refunded，被 status = 'paid' 过滤掉了——过滤条件必须与口径一致。

知识点AB 实验与指标统计A/B test · 用数据做决策

AB 实验（A/B test）把用户随机分成对照组与实验组，只改变一个变量（比如按钮颜色、推荐算法），然后比较两组的核心指标差异。它解决的是「改了之后到底有没有用」这个问题——没有对照组，任何涨幅都可能只是大盘波动或季节性造成的。

指标口径上有两个必须区分：核心指标（转化率、人均金额，用来判断成功与否）和护栏指标（退款率、崩溃率、客诉量，用来防止「赢了指标、输了体验」）。分子分母必须来自同一批用户、同一时间窗口，否则比较没有意义。

  • 绝对差（百分点）= 实验组转化率 − 对照组转化率；相对提升（lift）= 绝对差 ÷ 对照组转化率。
  • 判断显著性常用两比例 z 检验：z = (p₁ − p₀) ÷ √(p̄(1 − p̄)(1/n₀ + 1/n₁))，p̄ 为合并转化率。
  • 上线前先看分组比例（SRM）是否接近设计值，再看显著性，最后看业务收益是否值得。
abtest.sql
-- 用 customers.id 的奇偶模拟随机分桶（真实实验应使用实验平台的随机分组结果表）
SELECT CASE WHEN c.id % 2 = 0 THEN 'A 实验组' ELSE 'B 对照组' END AS 分组,
       COUNT(DISTINCT c.id)                                        AS 用户数,
       COUNT(DISTINCT o.customer_id)                               AS 下单用户数,
       ROUND(COUNT(DISTINCT o.customer_id)
             / COUNT(DISTINCT c.id), 4)                            AS 转化率,
       ROUND(SUM(o.amount) / COUNT(DISTINCT c.id), 2)              AS 人均金额,
       ROUND(STDDEV_SAMP(o.amount), 2)                             AS 金额标准差
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.status = 'paid'
GROUP BY CASE WHEN c.id % 2 = 0 THEN 'A 实验组' ELSE 'B 对照组' END;

-- 护栏指标：两组退款率（用全部订单做分母，退款做分子）
SELECT CASE WHEN c.id % 2 = 0 THEN 'A 实验组' ELSE 'B 对照组' END AS 分组,
       COUNT(*)                                                    AS 订单数,
       SUM(o.status = 'refunded')                                  AS 退款单数,
       ROUND(SUM(o.status = 'refunded') / COUNT(*), 4)             AS 退款率
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY CASE WHEN c.id % 2 = 0 THEN 'A 实验组' ELSE 'B 对照组' END;

核心要点：先看分组比例，再看显著性，最后看业务价值。上表 A 组比 B 组低 50 个百分点，但每组只有 4 人——这种量级的差异完全是随机噪声，不能得出「实验组更差」的结论，这正是 AB 实验必须做显著性检验的原因。

!

易错：①只看相对提升不看绝对差：转化率 1%→1.2% 是「相对提升 20%」，但绝对只涨 0.2 个百分点，业务上可能毫无意义；②中途偷看结果就停止实验（peeking），会让假阳性大幅上升；③同一个用户被分到两组（分桶键不稳定）；④护栏指标恶化仍坚持上线。

02时间维度与用户分层

知识点同比环比与累计指标YoY / MoM / YTD · 把趋势说清楚

同比（YoY, year over year）是与去年同一期比，能剔除季节性；环比（MoM / QoQ）是与上一个相邻期比，反映短期波动。累计指标（YTD, year to date）是年初至今的累计值，用来看年度目标进度。三者回答的是不同问题，报表里通常要同时给出。

实现思路很统一：先用 GROUP BY 把数据按期间汇总成一张「期间汇总表」，再让它与「上一期」或「去年同期」的汇总表做自关联。这样每个月只有一行，避免把明细行直接关联导致金额被重复累加。

  • 增长率 = (本期 − 基期) ÷ 基期；基期为 0 时必须用 NULLIF(基期, 0) 保护，否则会得到 NULL 或报错。
  • 基期没有数据时用 COALESCE(基期, 0) 保留行，但增长率应显示为「—」而不是 0%，因为 0% 和「无基期」含义完全不同。
  • 对比不完整的月份（比如本月只过了 15 天）必须做天数对齐，否则同比环比都会被低估。
yoy_mom.sql
-- ① 月度汇总 + 同比增长率（自关联去年同期）
SELECT m.ym                                      AS 月份,
       m.amount                                  AS 本月金额,
       COALESCE(y.amount, 0)                     AS 去年同期,
       ROUND((m.amount - COALESCE(y.amount, 0))
             / NULLIF(y.amount, 0) * 100, 1)     AS 同比增长率
FROM (SELECT DATE_FORMAT(order_date, '%Y-%m') AS ym, SUM(amount) AS amount
      FROM orders WHERE status = 'paid'
      GROUP BY DATE_FORMAT(order_date, '%Y-%m')) m
LEFT JOIN (SELECT DATE_FORMAT(order_date, '%Y-%m') AS ym, SUM(amount) AS amount
           FROM orders WHERE status = 'paid'
           GROUP BY DATE_FORMAT(order_date, '%Y-%m')) y
       ON y.ym = DATE_FORMAT(DATE_SUB(CONCAT(m.ym, '-01'), INTERVAL 1 YEAR), '%Y-%m')
ORDER BY m.ym;

-- ② 环比：与上一期自关联（把上面的 INTERVAL 1 YEAR 换成 1 MONTH 即可）
-- ③ 年初至今累计：练习台不支持窗口函数，用相关子查询代替
SELECT a.ym AS 月份, a.amount AS 本月金额,
       (SELECT SUM(b.amount)
        FROM (SELECT DATE_FORMAT(order_date, '%Y-%m') AS ym, SUM(amount) AS amount
              FROM orders WHERE status = 'paid'
              GROUP BY DATE_FORMAT(order_date, '%Y-%m')) b
        WHERE b.ym <= a.ym) AS 年初至今累计
FROM (SELECT DATE_FORMAT(order_date, '%Y-%m') AS ym, SUM(amount) AS amount
      FROM orders WHERE status = 'paid'
      GROUP BY DATE_FORMAT(order_date, '%Y-%m')) a
ORDER BY a.ym;

知识点用户分层（RFM）RFM segmentation · 把用户分对群

RFM 模型用三个维度刻画客户价值：R（Recency，最近一次消费距今天数，越小越好）、F（Frequency，统计窗口内的消费频次，越大越好）、M（Monetary，统计窗口内的消费金额，越大越好）。每个维度按业务阈值分成高 / 低两档，组合起来正好是 2×2×2 = 8 类人群，每一类对应一套运营动作。

分档方式有两种：按业务阈值（如「30 天内买过算高 R」）或按分位数（如 NTILE(5) 五等分）。阈值法可解释性强、跨月可比；分位数法自动适应数据分布，但每期边界会漂移，做趋势对比时要小心。无论用哪种，都要固定一个统计窗口（例如近 90 天）并写进口径文档。

  • R 的方向容易记反：天数越小越「高」，所以判断条件写 r_days <= 30。
  • 从未购买的用户 F = 0、M = 0，应单独归入「一般挽留客户」或新建「未转化」群，不要塞进活跃客户里。
  • RFM 是「当前状态快照」，不是永久标签；建议按月重算并保留历史，才能看用户在不同层级间的迁移。
rfm.sql
-- RFM 打标：先算 R / F / M，再用 CASE WHEN 分 8 类
-- 统计日取 2024-05-01，阈值：R <= 30 天、F >= 2 次、M >= 1500 元
SELECT t.name                                        AS 客户,
       t.r_days                                      AS R天数,
       t.f_cnt                                       AS F频次,
       t.m_amt                                       AS M金额,
       CASE
         WHEN t.r_days <= 30 AND t.f_cnt >= 2 AND t.m_amt >= 1500 THEN '重要价值客户'
         WHEN t.r_days >  30 AND t.f_cnt >= 2 AND t.m_amt >= 1500 THEN '重要保持客户'
         WHEN t.r_days <= 30 AND t.f_cnt <  2 AND t.m_amt >= 1500 THEN '重要发展客户'
         WHEN t.r_days >  30 AND t.f_cnt <  2 AND t.m_amt >= 1500 THEN '重要挽留客户'
         WHEN t.r_days <= 30 AND t.f_cnt >= 2 AND t.m_amt <  1500 THEN '一般价值客户'
         WHEN t.r_days >  30 AND t.f_cnt >= 2 AND t.m_amt <  1500 THEN '一般保持客户'
         WHEN t.r_days <= 30 AND t.f_cnt <  2 AND t.m_amt <  1500 THEN '一般发展客户'
         ELSE '一般挽留客户'
       END                                           AS 分层
FROM (
  SELECT c.id, c.name,
         COALESCE(DATEDIFF('2024-05-01', MAX(o.order_date)), 999) AS r_days,
         COUNT(o.id)                                              AS f_cnt,
         COALESCE(SUM(o.amount), 0)                               AS m_amt
  FROM customers c
  LEFT JOIN orders o
         ON o.customer_id = c.id
        AND o.status = 'paid'
  GROUP BY c.id, c.name
) t
ORDER BY t.m_amt DESC;

核心要点：RFM 的判断条件是「R 小、F 大、M 大 = 重要价值客户」。分层的意义在于差异化运营：重要价值客户做忠诚度维护，重要挽留客户做召回券，一般发展客户做频次激励，未购买用户做首单转化。

!

易错：①把 R 判成「越大越好」，导致流失客户被误判为高价值；②用 INNER JOIN 算 RFM，会把从未下单的客户（周涛）整行丢掉；这里必须用 LEFT JOIN + COALESCE，让 R 变成 999 天、F / M 变成 0；③忘记过滤 status = 'paid'，退款和取消的订单会虚增 F 与 M。

03工程化落地

知识点报表 SQL 与自动化reporting & scheduling · 让数字每天准时出现

分析 SQL 写对只是第一步，真正交付的是稳定可复用的报表。报表 SQL 的三条原则：口径固定（过滤条件、时间窗口、去重方式写进视图或注释，任何人跑出来都一样）、可复用（明细层 → 汇总层 → 报表层分层建模，避免每次从明细重算）、可验证（有对账 SQL，明细总额 = 报表总额）。

自动化指的是让报表按计划自己跑：MySQL 自带事件调度器（EVENT）可以做轻量定时任务，生产环境通常用 Airflow / DolphinScheduler 等外部调度器编排依赖。无论哪种，都要保证幂等——同一天重跑多次，结果必须一致，不能重复插入。

  • 幂等的两种常见做法：按日期分区「先删后插」，或给汇总表加日期唯一键并配合 ON DUPLICATE KEY UPDATE。
  • 重算窗口要留缓冲：结算延迟、退款、跨时区都可能让昨天的数据在今天就变了，建议每次回刷最近 3–7 天。
  • 报表必须带对账与监控：行数、金额、空值率异常就告警，而不是等业务方发现数字不对。
report.sql
-- ① 汇总表：按日期存每日销售
CREATE TABLE daily_sales (
  stat_date  DATE          NOT NULL PRIMARY KEY,
  order_cnt  INT           NOT NULL,
  amount     DECIMAL(12,2) NOT NULL
);

-- ② 幂等重跑：先删掉当天分区，再插入（同一天跑多少次结果都一样）
START TRANSACTION;
DELETE FROM daily_sales WHERE stat_date = '2024-04-30';
INSERT INTO daily_sales (stat_date, order_cnt, amount)
SELECT DATE(order_date), COUNT(*), SUM(amount)
FROM orders
WHERE status = 'paid'
  AND order_date >= '2024-04-30'
  AND order_date <  '2024-05-01'
GROUP BY DATE(order_date);
COMMIT;

-- ③ 另一种幂等方式：唯一键 + ON DUPLICATE KEY UPDATE
--    MySQL 8.0.20+ 起 VALUES() 已弃用，推荐行别名写法
INSERT INTO daily_sales (stat_date, order_cnt, amount)
SELECT DATE(order_date), COUNT(*), SUM(amount)
FROM orders WHERE status = 'paid'
GROUP BY DATE(order_date)
ON DUPLICATE KEY UPDATE
  order_cnt = VALUES(order_cnt),
  amount    = VALUES(amount);

-- ④ 对账：明细总额必须等于报表总额，否则报表不可信
SELECT (SELECT SUM(amount) FROM orders WHERE status = 'paid') AS 明细总额,
       (SELECT SUM(amount) FROM daily_sales)                  AS 报表总额;

-- ⑤ 定时调度：每天 02:00 重算（需开启 event_scheduler）
CREATE EVENT ev_daily_sales
ON SCHEDULE EVERY 1 DAY
STARTS '2024-05-01 02:00:00'
DO CALL sp_build_daily_sales();

★

核心要点：报表的可靠性来自三件事：口径写死、重跑幂等、结果对账。只要有一条缺失，数字迟早会「莫名其妙对不上」，而且没人能立刻定位原因。

!

易错：①用 TRUNCATE + 全量重跑代替分区重算，一旦中途失败报表就空了；②忘了 ON DUPLICATE KEY UPDATE 或唯一键，重跑会插入重复行，金额翻倍；③BETWEEN '2024-04-30' AND '2024-05-01' 这类写法对带时间的字段会多算一天，日期范围请用 >= 起点 AND < 终点。
