数据建模与数仓

✓本节学习目标

  • 能用事实表（fact table）+ 维度表（dimension table）拆解一个业务过程，并说清粒度（grain）决定什么。
  • 能画出星型模型与雪花模型的 ER 图，并说明二者在 JOIN 数量、冗余、查询代价上的取舍。
  • 能解释 ODS / DWD / DWS / ADS 各层的职责、粒度与典型产出表，说清为什么要分层。
  • 能实现 SCD Type 1 / 2 / 3（缓慢变化维），并知道哪种类型必须用时间区间关联事实表。
  • 能写清一个指标的完整口径（原子指标 + 修饰词 + 时间周期），并判断某维度该不该冗余进宽表。
  • 能从需求出发走完一次建模：选业务过程 → 定粒度 → 选维度 → 定事实。

知识点维度建模：事实表与维度表model-dim · 建模的地基

维度建模（dimensional modeling）是 Kimball 提出的一套数据仓库建模方法：先识别业务过程（business process），再把每个过程拆成一张事实表（fact table）加若干维度表（dimension table）。事实表回答「发生了什么、发生了多少」，维度表回答「谁、什么、何时、何地」，两者通过代理键（surrogate key）关联。

动手前必须先定粒度（grain）：事实表的一行到底代表什么。粒度是建模的第一决策，事后改粒度几乎等于重建模型——「一行 = 一个订单商品」和「一行 = 一个订单」会得出完全不同的表结构与指标结果。

  • 事实表：行数极大、列数很少，主要由外键 + 度量（measure）组成，一般只追加不修改。
  • 维度表：行数较小、列数多（宽而扁平），存放描述性属性与层级（品类 → 子品类）。
  • 代理键：数仓自增的整数主键，与业务主键（natural key）解耦，便于处理缓慢变化维与历史版本。
dim-fact.sql
-- 维度表：客户（代理键 customer_sk + 业务键 customer_id）
-- 数据来源：内置表 customers（8 行）
CREATE TABLE dim_customer (
  customer_sk BIGINT      NOT NULL AUTO_INCREMENT,
  customer_id INT         NOT NULL COMMENT '业务主键，对应 customers.id',
  name        VARCHAR(50) NOT NULL,
  city        VARCHAR(50),
  gender      CHAR(1),
  level       VARCHAR(20) NOT NULL COMMENT '金卡 / 银卡 / 普通',
  PRIMARY KEY (customer_sk),
  KEY idx_nk (customer_id)
) ENGINE=InnoDB;

-- 事实表：订单商品明细（粒度 = 一行一个订单商品）
-- 数据来源：内置表 order_items（15 行）关联 orders（12 行）
CREATE TABLE fact_order_item (
  order_item_id BIGINT        NOT NULL AUTO_INCREMENT,
  order_id      INT           NOT NULL,
  customer_sk   BIGINT        NOT NULL COMMENT '指向 dim_customer',
  product_sk    BIGINT        NOT NULL COMMENT '指向 dim_product',
  date_sk       INT           NOT NULL COMMENT '指向 dim_date，形如 20240105',
  qty           INT           NOT NULL,
  amount        DECIMAL(12,2) NOT NULL COMMENT '度量：qty * unit_price',
  status        VARCHAR(20)   NOT NULL COMMENT '退化维度：paid / refunded / cancelled',
  PRIMARY KEY (order_item_id),
  KEY idx_cust (customer_sk),
  KEY idx_prod (product_sk),
  KEY idx_date (date_sk)
) ENGINE=InnoDB;

存什么度量（可加和的数值）+ 外键描述性属性、层级、编码
行数规模极大，随业务持续增长小，千级到百万级
列数形态窄（列少）宽（列多，可冗余）
是否可变只追加，历史不改写属性会随时间变化（见 SCD）
主键代理键或复合键代理键 + 业务键

erDiagram dim_customer ||--o{ fact_order_item : "customer_sk" dim_product ||--o{ fact_order_item : "product_sk" dim_date ||--o{ fact_order_item : "date_sk" dim_customer { bigint customer_sk PK int customer_id string level } fact_order_item { bigint order_item_id PK bigint customer_sk FK decimal amount }
★

核心要点：度量放事实表、属性放维度表；先定粒度再建表。粒度一旦确定，维度与指标都只是它的上卷（roll-up）结果。

!

易错：把可加和的度量塞进维度表（例如把「订单金额」冗余进 dim_customer），客户属性一变历史金额就被改写；反过来，在一张事实表里混两种粒度（订单级 + 商品级），COUNT 与 SUM 会成倍放大。

知识点星型模型与雪花模型model-star · 维度的两种摆法

星型模型（star schema）是维度建模的默认形态：一张事实表居中，周围一圈维度表，维度表只做一层、不再继续规范化。因为形状像星星，所以叫星型。

雪花模型（snowflake schema）是把星型里的维度表继续做规范化（3NF）：例如把 dim_product 里的品类信息拆成独立的 dim_category，把城市信息拆成 dim_city。好处是减少冗余、属性一致性更强；代价是查询要多连几层表。

  • 数仓实践普遍推荐星型：存储便宜、JOIN 是主要代价，减少 JOIN 比省几列更划算。
  • 雪花适合「维度层级很深、属性变更频繁、必须严格消除冗余」的场景，常见于规范化要求高的企业模型。
  • 两种模型的事实表结构完全相同，差异只在维度表的拆分层数，所以可以随时由星型演进成雪花（或反向冗余回来）。
star-vs-snow.sql
-- 星型：事实表 + 2 个扁平维度表，共 2 次 JOIN
SELECT d.year_no AS 年份,
       p.category AS 品类,
       SUM(f.amount) AS 销售额
FROM fact_order_item f
JOIN dim_product p ON f.product_sk = p.product_sk
JOIN dim_date    d ON f.date_sk    = d.date_sk
GROUP BY d.year_no, p.category;

-- 雪花：品类被拆到 dim_category，多一层 JOIN（共 3 次）
SELECT d.year_no AS 年份,
       cat.category AS 品类,
       SUM(f.amount) AS 销售额
FROM fact_order_item f
JOIN dim_product  p   ON f.product_sk  = p.product_sk
JOIN dim_category cat ON p.category_sk = cat.category_sk
JOIN dim_date     d   ON f.date_sk     = d.date_sk
GROUP BY d.year_no, cat.category;
对比项星型模型 star schema雪花模型 snowflake schema
维度表层数一层，扁平多层，逐层规范化
典型查询 JOIN 次数少（维度数 = JOIN 次数）多（每拆一层多一次 JOIN）
数据冗余有冗余（品类名重复存放）冗余小，属性只存一处
查询性能更好（JOIN 少、易做列存裁剪）较差（JOIN 多，优化器压力大）
维护成本维度变更要同步刷新冗余列改一处即可，一致性更好
适用场景BI 报表、指标平台（主流）维度层级深、规范化要求高
★

核心要点：星型 = 少 JOIN、多一点冗余；雪花 = 少冗余、多几层 JOIN。选型的实际判据是「查询端能不能接受多几次 JOIN」。

!

易错：雪花模型连表多，一旦漏写某个 JOIN 或把一对多维度接错，结果行数会成倍膨胀；星型里的冗余列（如 dim_product.category）在源系统改名后必须重刷，否则会出现「同一品类两个名字」的口径分裂。

知识点数仓分层（ODS / DWD / DWS / ADS）model-layer · 数据的流水线

数仓分层（data warehouse layering）是把「从业务库到报表」的加工过程切成几段，每段只做一件事。最通用的四层是 ODS → DWD → DWS → ADS：ODS 贴源、DWD 清洗、DWS 汇总、ADS 应用。

分层的价值在于复用与口径统一：同一个「支付订单数」只在一处计算，所有报表都引用它；某一层出问题可以只重跑该层，不影响其它层；原始数据始终留档，随时可回溯重算。

  • ODS（Operational Data Store）：与业务库同构，只同步与分区，不做清洗，保留原样。
  • DWD（Data Warehouse Detail）：清洗（去重、剔无效单、统一单位）、换代理键、退化维度，粒度仍是最细。
  • DWS（Data Warehouse Summary）：按主题 + 粒度轻度汇总，是复用性最高的一层。
  • ADS（Application Data Store）：面向报表、看板、接口，只保留展示需要的列。
layer-pipeline.sql
-- ODS：原样落地，只加分区列 etl_date
CREATE TABLE ods_order_item (
  etl_date DATE NOT NULL,
  id INT, order_id INT, product_id INT, qty INT, unit_price DECIMAL(10,2)
) ENGINE=InnoDB;

-- DWD：清洗 + 业务键换代理键，粒度不变（一行一个订单商品）
INSERT INTO dwd_order_item
  (order_item_id, order_id, customer_sk, product_sk, date_sk, qty, amount, status)
SELECT oi.id, oi.order_id, dc.customer_sk, dp.product_sk,
       CAST(REPLACE(o.order_date, '-', '') AS UNSIGNED) AS date_sk,
       oi.qty, oi.qty * oi.unit_price AS amount, o.status
FROM ods_order_item oi
JOIN orders o        ON oi.order_id   = o.id
JOIN dim_customer dc ON o.customer_id = dc.customer_id
JOIN dim_product dp  ON oi.product_id = dp.product_id
WHERE o.status <> 'cancelled';        -- 剔除取消单，保留退款单（金额口径另行处理）

-- DWS：按「天 × 客户等级」轻度汇总
INSERT INTO dws_customer_level_day (stat_date, customer_level, order_cnt, item_cnt, gmv)
SELECT d.date_value, c.level,
       COUNT(DISTINCT f.order_id) AS order_cnt,
       SUM(f.qty)                 AS item_cnt,
       SUM(f.amount)              AS gmv
FROM dwd_order_item f
JOIN dim_date     d ON f.date_sk    = d.date_sk
JOIN dim_customer c ON f.customer_sk = c.customer_sk
GROUP BY d.date_value, c.level;

-- ADS：派生客单价，只留看板要的列
INSERT INTO ads_customer_level_report
  (stat_date, customer_level, gmv, order_cnt, aov)
SELECT stat_date, customer_level, gmv, order_cnt,
       ROUND(gmv / NULLIF(order_cnt, 0), 2) AS aov   -- NULLIF 防除零
FROM dws_customer_level_day;
层职责粒度典型表
ODS贴源同步，不做加工，可回溯与源表一致ods_order_item
DWD清洗、规范化、换代理键最细明细dwd_order_item
DWS按主题轻度汇总，供多方可复用天 × 维度dws_customer_level_day
ADS面向报表与接口，出宽表 / 指标表看板维度ads_customer_level_report
flowchart LR SRC["业务库

★

核心要点：每一层都要有明确的复用价值。判断要不要加一层，只看一个问题：这层的产出会不会被两个以上的下游引用。

◆

提醒：ODS 不是备份层，只同步真正需要的表；清洗规则必须集中在 DWD，若把业务规则散落到 DWS / ADS，口径就会随报表需求漂移，跨表对数永远对不上。

知识点缓慢变化维 SCDmodel-scd · 维度怎么变

缓慢变化维（slowly changing dimension, SCD）处理的是「维度属性随时间变化」这件事：客户从银卡升级为金卡、商品改了品类、员工换了部门。维度表不像事实表那样只追加，它的属性会变，因此必须提前决定：变了之后怎么记？

三种经典做法：Type 1 直接覆盖旧值（不保留历史）；Type 2 关闭旧行 + 新增一行，配合生效 / 失效时间与当前标志（完整保留历史，生产环境最常用）；Type 3 在原行上新增一列保存上一个值（只保留有限历史）。

  • Type 2 让「订单发生时的客户等级」可以被还原，是分析类需求的刚需。
  • Type 1 最省事，适合「改错了要纠正」这类不需要留痕的属性（如拼写纠错）。
  • Type 3 只能记住一版，属性频繁变化时会丢历史，一般只用于「对比上一版」的简单场景。
scd-type2.sql
-- 场景：客户 5「陈晨」在 2024-06-01 由银卡升级为金卡

-- 第 1 步：关闭旧版本（失效时间 = 变更日前一天，当前标志置 0）
UPDATE dim_customer
SET end_date   = DATE_SUB('2024-06-01', INTERVAL 1 DAY),
    is_current = 0
WHERE customer_id = 5 AND is_current = 1;

-- 第 2 步：插入新版本
INSERT INTO dim_customer
  (customer_id, name, city, level, start_date, end_date, is_current)
VALUES
  (5, '陈晨', '杭州', '金卡', '2024-06-01', '9999-12-31', 1);

-- 事实表按「订单时间落在维度版本区间」关联，才能还原历史真相
SELECT o.id, o.order_date, c.level AS 下单时等级
FROM orders o
JOIN dim_customer c
  ON c.customer_id = o.customer_id
 AND o.order_date >= c.start_date
 AND o.order_date <  c.end_date
ORDER BY o.order_date;
类型改动方式是否保留历史行数 / 列数适用场景
Type 1直接覆盖旧值不保留行数不变、列数不变纠正错误、无需留痕的属性
Type 2关闭旧行 + 新增一行完整保留行数增加、列数不变分析类需求，需要还原历史
Type 3原行新增一列存旧值只保留上一版行数不变、列数 +1只做「与上一版对比」
!

易错：Type 2 的维度表如果只用 is_current = 1 关联事实表，所有历史订单都会被算成「当前等级」，去年同期报表会随时间悄悄变化。必须用订单时间落在 [start_date, end_date) 区间关联。

◆

提醒：区间关联请用左闭右开（>= start_date AND < end_date），否则变更当天会被两个版本同时命中，行数翻倍。MySQL 8.0 本身不提供 SCD 组件，实际由 ETL 任务或 Hive / Spark 作业实现。

知识点指标口径与宽表设计model-metrics · 说清一个数

指标口径（metric definition）是把一个业务名词翻译成唯一可执行的算法。标准写法是「原子指标 + 修饰词 + 时间周期」：原子指标是业务过程的最小度量（订单金额），修饰词限定范围（支付成功、不含退款），时间周期指明统计窗口（日 / 月）。

一致性维度（conformed dimension）指同一维度在多张事实表里含义、粒度、编码完全一致，这是跨业务过程对齐指标的前提。在一致性维度之上，把高频查询用到的维度冗余进一张大表，就得到宽表（wide table）——用空间和更新成本换查询端的零 JOIN。

  • 宽表适合放在 DWS / ADS 层，DWD 保持明细与规范；把宽表做在 DWD 会让上游一变就全量重刷。
  • 值得冗余的维度：查询频率高、基数低、变更不频繁（如客户等级、品类、城市）。
  • 不值得冗余的维度：高基数（用户 id）、变更频繁（实时库存）、只在个别报表用到。
metric-wide.sql
-- 指标表：口径写进表结构注释，一行 = 一天 × 一个客户等级
CREATE TABLE dws_customer_level_day (
  stat_date      DATE          NOT NULL,
  customer_level VARCHAR(20)   NOT NULL,
  order_cnt      BIGINT        NOT NULL COMMENT '支付成功订单数（去重到订单）',
  gmv            DECIMAL(18,2) NOT NULL COMMENT '支付成功订单金额，退款前口径',
  PRIMARY KEY (stat_date, customer_level)
) ENGINE=InnoDB;

-- 宽表：把常用维度一次性打平，查询端零 JOIN
CREATE TABLE ads_customer_wide (
  stat_date      DATE          NOT NULL,
  customer_level VARCHAR(20)   NOT NULL,
  city           VARCHAR(50),
  order_cnt      BIGINT        NOT NULL,
  gmv            DECIMAL(18,2) NOT NULL,
  aov            DECIMAL(18,2) NOT NULL COMMENT '客单价 = gmv / order_cnt',
  PRIMARY KEY (stat_date, customer_level, city)
) ENGINE=InnoDB;

-- 用内置示例数据验算口径：金卡 / 银卡 / 普通 的支付订单数与销售额
SELECT c.level AS 客户等级,
       COUNT(DISTINCT o.id)            AS 支付订单数,
       SUM(oi.qty * oi.unit_price)     AS 销售额
FROM order_items oi
JOIN orders    o ON oi.order_id   = o.id
JOIN customers c ON o.customer_id = c.id
WHERE o.status = 'paid'
GROUP BY c.level
ORDER BY 销售额 DESC;
指标原子指标修饰词时间周期口径说明
支付订单数订单数支付成功日status='paid'，COUNT(DISTINCT order_id)
GMV订单金额支付成功日SUM(qty * unit_price)，退款前
客单价 AOV—（派生）支付成功日GMV / 支付订单数
退款率—（派生）退款月退款订单数 / 支付订单数
验算结果（内置数据）支付订单数销售额

普通159.00
!

易错：「销售额」在运营、财务、技术三方往往不是同一个数——含不含退款、含不含运费、按下单时间还是支付时间，都会差出一截。建模时把口径写进字段注释与指标字典，并让所有报表引用同一个字段，否则跨表对数永远对不上。

★

核心要点：宽表不是越宽越好。只有「高频查询 + 低基数 + 变更不频繁」的维度才值得冗余；否则查询快了一点，重刷成本和口径风险却成倍上升。

知识点建模实战案例model-case · 从需求到表

需求：「分析各品类、各客户等级的销售表现，支持按天看趋势。」下面按固定四步走完：① 选业务过程（下单支付）→ ② 定粒度（一行 = 一个订单商品，最细，可上卷到订单 / 天 / 品类）→ ③ 选维度（客户、商品、日期、状态）→ ④ 定事实（数量、金额可加和；单价不可加和，只用于算均价）。

四步顺序不能颠倒。若先画维度再想粒度，几乎一定返工：粒度决定了哪些维度是合法的（例如「一行 = 一个订单」时，商品维度就不能直接放进来）。

  • 事实表落地后，绝大多数报表都是「事实表 + 若干维度表 + 聚合」，不再新建业务表。
  • 不可加和的度量（单价、折扣率）不要直接 SUM，要用「总金额 / 总数量」重算。
  • 状态类字段（paid / refunded / cancelled）作为退化维度（degenerate dimension）直接放进事实表，便于过滤与分组。
case-end2end.sql
-- ① 维度：日期（date_sk 用 YYYYMMDD 整数，便于分区裁剪）
CREATE TABLE dim_date (
  date_sk    INT      NOT NULL,
  date_value DATE     NOT NULL,
  year_no    SMALLINT NOT NULL,
  month_no   TINYINT  NOT NULL,
  day_no     TINYINT  NOT NULL,
  PRIMARY KEY (date_sk)
) ENGINE=InnoDB;

-- ② 事实：订单商品（粒度 = 一行一个订单商品）
CREATE TABLE fact_order_item (
  order_item_id BIGINT        NOT NULL AUTO_INCREMENT,
  order_id      INT           NOT NULL,
  customer_sk   BIGINT        NOT NULL,
  product_sk    BIGINT        NOT NULL,
  date_sk       INT           NOT NULL,
  qty           INT           NOT NULL,
  amount        DECIMAL(12,2) NOT NULL,
  status        VARCHAR(20)   NOT NULL,
  PRIMARY KEY (order_item_id),
  KEY idx_dim (date_sk, customer_sk, product_sk)
) ENGINE=InnoDB;

-- ③ 端到端查询：品类 × 客户等级的销售额与客单价
SELECT p.category  AS 品类,
       c.level     AS 客户等级,
       COUNT(DISTINCT f.order_id) AS 订单数,
       SUM(f.amount)              AS 销售额,
       ROUND(SUM(f.amount) / NULLIF(COUNT(DISTINCT f.order_id), 0), 2) AS 客单价
FROM fact_order_item f
JOIN dim_product  p ON f.product_sk  = p.product_sk
JOIN dim_customer c ON f.customer_sk = c.customer_sk
JOIN dim_date     d ON f.date_sk     = d.date_sk
WHERE d.year_no = 2024
  AND f.status = 'paid'
GROUP BY p.category, c.level
ORDER BY 销售额 DESC;
