01索引的结构与存储
B+ 树如何把「找一行」从翻遍全表变成走三层楼梯

知识点B+ 树索引结构B+ tree index · 一切索引优化的地基

B+ 树（B+ tree）是 InnoDB 默认的索引数据结构，一棵「多路平衡查找树（multi-way balanced search tree）」。它有两个关键特征：一是非叶子节点只存键值和子节点指针，不存数据行，所以一个节点能塞下几百个键；二是所有数据都在叶子节点，且叶子节点之间用双向链表相连，并按键值有序排列。

为什么长成这样？因为数据库的瓶颈是磁盘 I/O，一次读盘读的是「一页（page，InnoDB 默认 16KB）」。非叶子节点不存数据行，就能让每页存更多的键，树就变得更「矮胖」：一个三层 B+ 树通常能索引约两千万行数据，查任意一行最多 3 次磁盘 I/O。相比之下，B 树把数据散落在所有节点上，节点能存的键更少、树更高，而且范围查询要在不同层之间来回跳。

叶子节点的有序双向链表还免费送了两个能力：WHERE id BETWEEN 3 AND 6 这样的范围查询只需定位到起点，然后顺着链表向右扫；ORDER BY id 也可以直接沿索引顺序读出，省掉排序。这两点正是 B+ 树统治数据库索引的原因。

  • 根节点 → 中间节点 → 叶子节点，逐层比较键值，每层确定一个子节点（3 层树最多 3 次 I/O）。
  • 非叶子节点存「键 + 子节点指针」，叶子节点存「键 + 数据（聚簇索引）或主键（二级索引）」。
  • 所有叶子在同一层，天然平衡，不存在某条路径特别长的情况。
  • 叶子按序双向链表相连 → 范围查询、ORDER BY、GROUP BY 都能顺水推舟。

★

核心要点：B+ 树的优势可以一句话概括——矮、胖、叶子有序。矮胖降低了单点查找的 I/O 次数（O(log n)），叶子有序链表让范围查询和排序几乎免费。面试时把「非叶子不存数据」和「叶子双向链表」这两点讲出来，基本就到位了。

!

易错：不要以为「建了索引，查询就一定会变快」。B+ 树的定位是 O(log n)，但每一次比较、每一次回表都是真实开销；当查询要返回表中大部分行（例如 WHERE gender = '男' 命中 50% 数据）时，优化器会认为顺着叶子链表扫索引再回表还不如直接全表扫描，于是主动放弃索引。索引是「找少数行」的利器，不是万能加速器。

知识点聚簇索引与二级索引clustered / secondary index · 回表的根源

InnoDB 是「索引组织表（index-organized table）」：数据行本身存放在聚簇索引（clustered index）的叶子节点上，而聚簇索引就是主键索引。换句话说，表就是一棵按主键排序的 B+ 树——叶子节点里放的不是主键值，而是完整的一行数据。这也解释了为什么 InnoDB 必须有主键：没有显式主键时，它会选第一个非空唯一索引顶上；再没有，就生成一个 6 字节的隐藏列 row_id。

除聚簇索引外的所有索引都叫二级索引（secondary index，也叫辅助索引）。二级索引的叶子节点存的不是行地址，而是索引列的值 + 主键值。所以用二级索引查一个不包含在索引里的列时，必须走两步：先在二级索引里找到主键，再拿主键去聚簇索引里取出整行——这一步就叫回表（bookmark lookup）。

回表是随机 I/O，代价远高于顺序读，而且可能触发大量页访问。理解「回表」是后面覆盖索引、最左前缀、索引失效所有优化的共同前提：能少回一次表，就少一次随机 I/O。

  • 聚簇索引叶子 = 完整行数据；一张表只有一个聚簇索引（就是主键）。
  • 二级索引叶子 = 索引列值 + 主键值；每多一个二级索引，写入时就要多维护一棵树。
  • 通过二级索引取非索引列 → 必须回表；取「索引列 + 主键」→ 不需要回表。
  • 主键越小越好：所有二级索引都要复制一份主键，主键膨胀会让每个二级索引一起膨胀。
clustered.sql
-- 建表：主键即聚簇索引，idx_city 是二级索引
CREATE TABLE customers (
  id          INT PRIMARY KEY AUTO_INCREMENT,   -- 聚簇索引
  name        VARCHAR(50) NOT NULL,
  city        VARCHAR(20) DEFAULT NULL,
  gender      CHAR(1)     DEFAULT NULL,
  signup_date DATE        NOT NULL,
  level       TINYINT     NOT NULL,
  KEY idx_city (city)                           -- 二级索引：叶子存 city + id
) ENGINE=InnoDB;

-- 走聚簇索引：叶子节点直接就是整行，不需要回表
SELECT * FROM customers WHERE id = 3;

-- 走二级索引 idx_city：先拿到 id，再回聚簇索引取整行（回表 1 次/行）
SELECT * FROM customers WHERE city = '北京';

-- 只取 city 与 id：二级索引叶子已包含这两列，无需回表
SELECT id, city FROM customers WHERE city = '北京';

-- 看主键与二级索引的定义
SHOW INDEX FROM customers;

★

核心要点：「二级索引的叶子节点存的是主键，不是行地址」——这句话是 InnoDB 索引优化的总纲。它决定了：主键要短、回表要少、覆盖索引有效、UPDATE 主键代价极高（要把所有二级索引里的主键副本都改掉）。

!

易错：主键用 UUID() 或随机字符串是常见坑。随机主键会让插入位置在整棵树里乱跳，引发页分裂（page split）与碎片；同时 36 字节的 UUID 会被复制进每一个二级索引，索引体积成倍增长。InnoDB 更推荐自增 BIGINT 这类单调、紧凑的主键。

02从索引到查询计划
联合索引怎么排、覆盖索引为什么能省掉回表

知识点联合索引与最左前缀原则composite index / leftmost prefix · 索引列顺序决定成败

联合索引（composite index，多列索引）是把多个列按定义顺序拼成一个键来排序的索引，例如 KEY idx_city_level_name (city, level, name)。它的排序规则是：先按 city 排，city 相同的再按 level 排，level 也相同的再按 name 排——就像电话簿先按城市、再按姓名排序一样。

由此推出最左前缀原则（leftmost prefix rule）：联合索引只能被「从最左列开始的连续前缀」利用。(city, level, name) 支持 city、city+level、city+level+name 三种定位方式；而 WHERE level = 'VIP' 或 WHERE name = '张三' 跳过了最左列，无法用于定位，只能退化成全表扫描（或全索引扫描后过滤）。

还有一条容易忽略的规则：范围查询之后的列失去定位能力。WHERE city = '北京' AND level > 2 AND name = '张三' 中，city 是等值、level 是范围，一旦 level 用了范围，name 就无法继续在 B+ 树里定位了（MySQL 5.6+ 可以用索引条件下推 ICP 在索引层做过滤，但仍不能用于缩小扫描区间）。所以设计联合索引的顺序口诀是：等值列在前，范围列放最后，区分度高的列优先。

  • 联合索引 = 按列顺序拼接的多列 B+ 树，列顺序一旦定下就不能「随便换用」。
  • 能用的前缀：city、city+level、city+level+name；不能用的：level、name、level+name。
  • 范围条件（> < BETWEEN LIKE 'x%'）之后的列只能被 ICP 过滤，不能用于索引定位。
  • 联合索引也能服务 ORDER BY city, level：只要排序方向与索引列顺序一致即可避免额外排序。
composite.sql
-- 建立联合索引：列顺序 = 等值查询列在前、范围列在后
ALTER TABLE customers ADD INDEX idx_city_level_name (city, level, name);

-- ✅ 命中 1 列：city
SELECT id FROM customers WHERE city = '北京';

-- ✅ 命中 2 列：city + level
SELECT id FROM customers WHERE city = '北京' AND level = 2;

-- ✅ 命中 3 列：city + level + name
SELECT id FROM customers WHERE city = '北京' AND level = 2 AND name = '张三';

-- ❌ 跳过最左列 level：无法定位，退化为全表扫描
SELECT id FROM customers WHERE level = 2;

-- ⚠️ city 等值 + level 范围：只有 city、level 能定位，name 只能 ICP 过滤
SELECT id FROM customers WHERE city = '北京' AND level > 2 AND name = '张三';

-- ✅ 前缀匹配仍可用于定位（'北%' 是有序前缀）
SELECT id FROM customers WHERE city LIKE '北%';

-- ❌ 前导通配符破坏有序性，索引失效
SELECT id FROM customers WHERE city LIKE '%北京%';

-- 顺序一致时，联合索引可直接消除排序
SELECT id, level, name FROM customers
WHERE city = '北京' ORDER BY level, name;

WHERE city = '北京' AND level = 2✅ 能city, level连续前缀 2 列

WHERE level = 2❌ 不能—跳过最左列，全表扫描
WHERE name = '张三'❌ 不能—同样跳过最左列

WHERE city = '北京' AND level > 2 AND name = '张三'⚠️ 部分city, level范围列之后的 name 不能定位
WHERE city LIKE '%北京%'❌ 不能—前导通配符破坏有序性
★

核心要点：判断能否用联合索引，只要问一句：「这个查询的等值条件，能不能凑出从最左列开始的连续前缀？」能凑几列，就能定位几列；范围条件出现后，后面的列一律只能过滤。所以联合索引的列顺序应当按「等值 → 范围 → 仅排序/覆盖」排列。

!

易错：不要以为「把区分度最高的列放第一位」永远正确。最左列必须是查询里经常出现的列，否则这个索引对大多数 SQL 都不可用；正确做法是先用「等值列」组成前缀，再在这个前缀内部按区分度从高到低排。另外 MySQL 8.0 支持索引跳跃扫描（Index Skip Scan），在特定条件下能部分弥补最左列缺失，但它依赖优化器判断、命中不稳定，不能当作设计依据。

知识点覆盖索引与回表covering index · 少一次随机 I/O 就是快一截

回表（bookmark lookup）指通过二级索引找到主键后，再回到聚簇索引取整行数据的过程。一次回表意味着一次额外的 B+ 树查找，而且这些查找的主键在物理上可能分散，属于随机 I/O。当命中行数很多时，回表会成为查询的主要成本。

覆盖索引（covering index）是指：查询需要的所有列都能从某个索引里拿到，因此完全不必回表。判断标准很简单——把 SELECT 的列、WHERE 的列、ORDER BY / GROUP BY 的列放在一起，看它们是否都是某个索引的列（记得二级索引自带主键）。命中覆盖索引时，EXPLAIN 的 Extra 会显示 Using index。

它的价值在于把「N 次随机回表」变成「一次顺序扫索引」。代价则体现在写入侧：索引越宽，占的空间越大，INSERT / UPDATE / DELETE 维护的代价越高。所以覆盖索引是典型的读写权衡——读多写少的表很划算，写密集的表要谨慎。

  • 二级索引叶子 = 索引列 + 主键 → 只查这些列时天然不回表。
  • Extra: Using index = 覆盖索引；Using index condition = ICP，不等于覆盖索引。
  • SELECT * 几乎永远无法被覆盖（除非索引包含了全部列）。
  • 覆盖索引能省 I/O，但会加宽索引、拖慢写入，需要按读写比权衡。
covering.sql
-- 建一个「刚好覆盖常见查询」的联合索引
ALTER TABLE customers ADD INDEX idx_city_level (city, level);

-- ❌ 需要回表：SELECT * 要取 name、signup_date 等索引里没有的列
SELECT * FROM customers WHERE city = '北京' AND level = 2;

-- ✅ 覆盖索引：city、level 都在索引里，id 是二级索引自带的主键
SELECT id, city, level FROM customers WHERE city = '北京' AND level = 2;

-- ✅ 用 EXPLAIN 确认：Extra 出现 Using index 即为覆盖索引
EXPLAIN SELECT id, city, level FROM customers WHERE city = '北京' AND level = 2;

-- ⚠️ 常见误解：Using index condition 是 ICP（索引条件下推），仍会回表
EXPLAIN SELECT * FROM customers WHERE city = '北京' AND level > 2;

-- 只取主键：二级索引即可满足，最省
SELECT id FROM customers WHERE city = '北京';

-- 计数也可以被覆盖索引加速（扫索引比扫表小得多）
SELECT COUNT(*) FROM customers WHERE city = '北京';

核心要点：把常用查询的返回列精简到「索引列 + 主键」，就能把它变成覆盖索引，Extra 里出现 Using index 即证明不再回表。实战中最有效的一招是把 SELECT * 改成明确列名——很多慢查询因此直接省掉了成千上万次回表。

!

易错：别把 Using index condition 当成覆盖索引。前者是索引条件下推 ICP，意思是「部分过滤条件被下推到存储引擎层在索引上完成」，但被选中的列仍需回表；后者才是「完全不需要回表」。看 EXPLAIN 时一定要盯准 Using index 这五个字，多一个 condition 含义就完全不同。

03读懂执行计划与索引设计
用 EXPLAIN 诊断、用设计原则收尾

知识点EXPLAIN 执行计划解读EXPLAIN / execution plan · 优化器的自白书

EXPLAIN 会打印 MySQL 优化器为这条 SQL 选定的执行计划（execution plan）：用哪个索引、按什么顺序连接表、预估扫描多少行、有没有额外的排序或临时表。它不会真正执行语句（EXPLAIN ANALYZE 才会执行并给出实际耗时），因此可以放心地拿它做诊断。

看执行计划时优先级最高的四个字段是：type（访问类型，反映定位精度）、key（实际用到的索引，NULL 表示没用索引）、rows（预估扫描行数，越小越好）、Extra（额外信息，Using filesort / Using temporary 是典型的坏信号）。type 的优劣顺序是：system > const > eq_ref > ref > range > index > ALL，其中 ALL 就是全表扫描。

还要注意：rows 和 filtered 都是统计信息估算值，不是精确值。它们来自 InnoDB 的采样统计（可用 ANALYZE TABLE 刷新），因此偶尔会与真实情况偏差很大；当你怀疑优化器选错索引时，可以用 EXPLAIN FORMAT=JSON 或 EXPLAIN ANALYZE 看到更细的代价估算与实际行数。

  • id：查询序号，同一 id 表示同一个 SELECT；id 越大越先执行。
  • select_type：SIMPLE、PRIMARY、SUBQUERY、DERIVED 等。
  • type：定位精度，最差是 ALL；index 是「扫整个索引」，也不算好。
  • key_len：实际使用的索引字节数，可用于反推联合索引用了几列。
  • Extra：Using index 好；Using filesort、Using temporary 差。

-- 1) 最基本的用法：看计划而不执行
EXPLAIN SELECT * FROM customers WHERE id = 3;

-- 2) 看连接顺序与被驱动表的访问方式（多行输出，自上而下）
EXPLAIN
SELECT o.id, o.amount, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE c.city = '北京';

-- 3) MySQL 8.0.18+：真正执行并给出实际耗时与实际行数

system表中只有一行最好系统常量表
const通过主键/唯一索引等值定位到一行很好WHERE id = 3

range索引范围扫描较好BETWEEN、>、IN
index扫整棵索引树（比全表略好）一般覆盖索引但无过滤条件

★

核心要点：读 EXPLAIN 的口诀是「先看 type，再看 key，然后 rows，最后 Extra」。type = ALL 或 key = NULL 说明这条 SQL 在裸奔；rows 很大而 filtered 很低说明扫了很多又丢了很多；Extra 里出现 Using filesort 或 Using temporary 说明还有排序/临时表的额外成本。

!

易错：①rows 是估算值，别把它当成真实扫描行数，需要精确值时用 EXPLAIN ANALYZE。②type = index 名字里有「index」，但它其实是全索引扫描，数据量大时依然很慢，不要误以为「用了索引就一定快」。③possible_keys 有值而 key 为 NULL，说明有索引但优化器没用——通常是索引区分度太低或统计信息过期。

知识点索引失效的常见场景index invalidation · 明明建了索引，为什么还是全表扫

索引失效的本质是：查询条件破坏了索引的有序性，或者优化器算出来「用索引反而更贵」。前者是写法问题（改 SQL 就能解决），后者是代价问题（索引区分度太低、命中行数太多），两者要分开判断。

最常见的写法问题有六类：对索引列做函数或运算（YEAR(signup_date) = 2023、id + 1 = 4）——B+ 树按 signup_date 原值排序，按年份比较就无法定位；隐式类型转换（WHERE name = 123，而 name 是 varchar）——MySQL 会把列转成数字再比较，等价于对列做函数；前导模糊匹配（LIKE '%伟'）——字符串前缀未知，有序性失效；违反最左前缀；OR 连接了没有索引的列；负向条件（!=、NOT IN、NOT LIKE）——它们通常需要扫描大部分行，优化器直接放弃索引。

注意：OR 并非一定失效——如果 OR 两侧的列都有索引，MySQL 可以使用索引合并（index merge）；同理 IS NULL 也能走索引。判断的唯一可靠方式仍然是看 EXPLAIN 的 key 与 type。

  • 索引列上出现函数/运算/类型转换 → 失效。改写：把列单独放在等号左边，用范围表达。
  • LIKE 'x%' 可用；LIKE '%x' 与 LIKE '%x%' 失效（考虑全文索引或反向列）。
  • 跳过最左列、范围列之后再接等值列 → 部分失效。
  • OR 两侧只要有一侧没索引就可能退化为全表扫描。
  • 区分度极低的列（如 gender）即使建了索引，优化器也可能选择全表扫描。
index-fail.sql
-- ❌ 索引列上做函数 → 失效
SELECT * FROM customers WHERE YEAR(signup_date) = 2023;
-- ✅ 改写为范围条件 → 走 range 扫描
SELECT * FROM customers WHERE signup_date >= '2023-01-01' AND signup_date < '2024-01-01';

-- ❌ 索引列参与运算 → 失效
SELECT * FROM customers WHERE id + 1 = 4;
-- ✅ 把运算移到等号右边
SELECT * FROM customers WHERE id = 3;

-- ❌ 隐式类型转换（name 是 varchar，右边是数字）→ 失效
SELECT * FROM customers WHERE name = 123;
-- ✅ 用字符串字面量比较
SELECT * FROM customers WHERE name = '123';

-- ❌ 前导通配符 → 失效
SELECT * FROM customers WHERE name LIKE '%伟';
-- ✅ 前缀匹配 → 走 range
SELECT * FROM customers WHERE name LIKE '张%';

-- ❌ OR 一侧无索引 → 可能全表扫描
SELECT * FROM customers WHERE city = '北京' OR gender = 'M';
-- ✅ 两侧都有索引时可考虑索引合并；否则拆成两条 UNION ALL
SELECT * FROM customers WHERE city = '北京'
UNION ALL
SELECT * FROM customers WHERE gender = 'M' AND city <> '北京';

-- ❌ 负向条件通常扫大部分数据
SELECT * FROM customers WHERE city <> '北京';
-- ✅ 若能穷举取值，改成 IN
SELECT * FROM customers WHERE city IN ('上海','广州','深圳');

-- 验证：看 key 是否为 NULL、type 是否为 ALL
EXPLAIN SELECT * FROM customers WHERE YEAR(signup_date) = 2023;

★

核心要点：记住一条铁律——索引列必须「单独」出现在比较符的一侧。WHERE 索引列 = 常量 是最理想的形式；任何函数、运算、类型转换、前导通配符都会让 B+ 树失去有序性。判断是否失效，永远以 EXPLAIN 的 key 是否为空为准，不要凭感觉。

!

易错：①LIKE '张%' 能走索引，但 LIKE '%张%' 不行，这个差别在代码 review 里经常被放过。②UNION ALL 拆分 OR 时一定要处理重复行（第二条加 AND city <> '北京'），否则结果会多出重复记录；需要去重时用 UNION（但要付出排序代价）。③PostgreSQL 有 ILIKE 等 MySQL 不支持的写法，跨库迁移时索引行为会变。

知识点索引设计原则与代价index design & cost · 索引不是越多越好

索引不是免费的：每个二级索引都是一棵独立的 B+ 树，要占磁盘空间、占 buffer pool，并且每次 INSERT / UPDATE / DELETE 都要同步维护。索引越多，写入越慢——一张表挂 8 个索引，写一行就要改 9 棵树（含聚簇索引）。所以索引设计的本质是用写入成本换读取速度。

设计时先看查询：为 WHERE 的等值列、JOIN ... ON 的关联列、ORDER BY / GROUP BY 的列建索引，并尽量用一个联合索引覆盖多条 SQL 的公共前缀。然后看区分度（selectivity）：区分度 = COUNT(DISTINCT col) / COUNT(*)，越接近 1 越适合建索引；gender 这种只有两三个取值的列单独建索引意义很小，更适合作为联合索引的一部分。

最后要清理：避免冗余索引（已有 (city, level) 时，再建 (city) 就是浪费），长字符串用前缀索引KEY idx_name (name(6)) 节省空间，定期用 sys.schema_unused_indexes 找出从未被使用过的索引并删除。线上变更索引要走 ALTER TABLE，大表上建议用 ALGORITHM=INPLACE, LOCK=NONE 或工具（如 gh-ost / pt-online-schema-change）避免长时间锁表。

  • 建索引的四个目标位置：WHERE 等值列、JOIN ON 关联列、ORDER BY、GROUP BY。
  • 优先建联合索引并复用最左前缀；单表索引数量一般控制在 5～6 个以内。
  • 区分度低的列不要单独建索引；长字符串用前缀索引。
  • 及时删除冗余与未使用索引，减少写入负担与空间占用。
index-design.sql
-- 1) 先量区分度：越接近 1 越适合建索引
SELECT COUNT(DISTINCT city)   / COUNT(*) AS sel_city,
       COUNT(DISTINCT gender) / COUNT(*) AS sel_gender,
       COUNT(DISTINCT name)   / COUNT(*) AS sel_name
FROM customers;
-- 结论：city、name 区分度高；gender 只有 2 个取值，不适合单独建索引

-- 2) 为「按城市 + 等级查客户」设计一个联合索引（等值列在前）
ALTER TABLE customers ADD INDEX idx_city_level (city, level);

-- 3) 覆盖索引：把常用返回列也放进索引，避免回表
ALTER TABLE customers ADD INDEX idx_city_level_name (city, level, name);

-- 4) 长字符串用前缀索引，省空间（注意：前缀索引不能用于覆盖索引）
ALTER TABLE customers ADD INDEX idx_name_prefix (name(6));

-- 5) 大表在线加索引：InnoDB 支持不锁表的在线 DDL
ALTER TABLE customers ADD INDEX idx_signup (signup_date),
      ALGORITHM=INPLACE, LOCK=NONE;

-- 6) 找出从未被使用过的索引（MySQL 8.0 自带 sys 库）
SELECT object_schema, object_name, index_name
FROM sys.schema_unused_indexes
WHERE object_schema = 'shop';

-- 7) 删除冗余索引，减少写入负担
ALTER TABLE customers DROP INDEX idx_city;
决策点应该建索引不该建 / 要谨慎
列的使用频率高频出现在 WHERE、JOIN ON 中几乎不出现在查询条件里
区分度COUNT(DISTINCT col)/COUNT(*) 高（如 name、id）只有 2～3 个取值（如 gender）
表读写比读多写少（报表、订单查询）写极密集（日志、埋点），索引要克制
列宽度窄列（INT、DATE）超长字符串，考虑前缀索引
与已有索引的关系能作为新联合索引的前缀或补足是已有索引的冗余前缀
更新频率很少更新的列频繁更新的列（维护代价高）
★

核心要点：索引设计的三步法——① 列出高频查询的过滤/排序列；② 用联合索引合并公共前缀，等值在前、范围在后；③ 删除冗余与未使用索引。判断一个索引是否值得，先算区分度，再看它能不能顺带变成覆盖索引，最后别忘了写入代价。

!

易错：①COUNT(DISTINCT col)/COUNT(*) 时 COUNT(*) 不计 NULL 行，而 COUNT(col) 会跳过 NULL——计算区分度时用 COUNT(*) 做分母更符合直觉。②前缀索引无法用于覆盖索引，因为索引里只有前缀，无法确认完整值。③不要为了「看起来很全」给每个列都建索引，索引膨胀会让写入和空间双双恶化，收益是负的。
