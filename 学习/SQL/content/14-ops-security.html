（把数据库当成「会出故障的系统」来管）

知识点备份与恢复backup & recovery · 数据丢了能救回来，才叫有备份

备份（backup）是把数据库在某一时刻的状态复制成一份可以独立还原的副本；恢复（recovery）是把它重新装载回数据库的过程。运维里衡量备份价值的两个指标是 RPO（Recovery Point Objective，能容忍丢多少数据）与 RTO（Recovery Time Objective，能容忍停多久）。只有「全量备份 + 增量日志」配合，才能做到秒级 RPO 的时间点恢复（PITR，Point-In-Time Recovery）。

MySQL 里最常用的两条路线：逻辑备份用 mysqldump 导出 SQL 文本，跨版本、跨平台、能挑表，但慢、恢复也慢；物理备份用 XtraBackup 直接复制 InnoDB 数据文件，大库首选，能热备不停机。两者都只是「某个时刻的快照」，快照之后发生的写入必须靠 binlog 补齐，这就是 PITR 的核心思路。

  • 备份不是目的，能恢复才是；没演练过的备份等于没有备份。
  • RPO 由「全量备份频率 + binlog 是否完整」决定，RTO 由「备份体积 + 恢复方式」决定。
  • binlog 必须与备份文件分开存放，并定期校验；生产库建议开启 binlog_format = ROW。
backup.sh
# 1) 逻辑全量备份：--single-transaction 让 InnoDB 在一个一致性快照里导出，不长时间锁表
mysqldump -uroot -p --single-transaction --source-data=2 \
  --routines --triggers --events --set-gtid-purged=ON \
  --databases shop > /backup/shop_full_$(date +%F).sql

# 2) 切一个新的 binlog，并把它复制到异地（PITR 的原料）
mysqladmin -uroot -p flush-logs
cp /var/lib/mysql/binlog.* /backup/binlog/

# 3) 时间点恢复：先还原全量，再用 binlog 回放到误操作之前
mysql -uroot -p < /backup/shop_full_2024-05-01.sql
mysqlbinlog --stop-datetime="2024-05-01 12:29:59" /backup/binlog/binlog.000012 | mysql -uroot -p

# 4) 物理热备：大库首选，备份期间不阻塞写入
xtrabackup --backup --target-dir=/backup/xtra_20240501 -u root -p
xtrabackup --prepare --target-dir=/backup/xtra_20240501

mysqldumpSQL 文本（结构 + 数据）跨版本、可单表、体积小易传输慢、恢复更慢；适合中小库、逻辑迁移

★

核心要点：恢复公式 = 最近一次全量备份 + 之后的全部 binlog。所以「binlog 有没有丢」比「备份文件有多大」更致命，两者必须异地分开保存。

!

易错：① mysqldump 不加 --single-transaction 会锁表，线上高峰直接阻塞写入；② 该参数只对 InnoDB 有效，MyISAM 表仍会锁；③ 从库不能当备份用——主库误删 DELETE FROM customers，从库会照样删掉。

知识点用户、权限与最小授权users & privileges · 只给够用的，绝不多给

MySQL 的账号由「用户名 + 来源主机」共同确定，例如 'app_rw'@'10.0.1.%' 和 'app_rw'@'%' 是两个完全不同的账号。权限（privilege）按粒度分层：全局 *.* → 库 shop.* → 表 shop.orders → 列 SELECT (name, city)。最小授权原则（principle of least privilege）要求：账号只拿到完成它职责所必需的最小权限、最小范围、最小来源。

MySQL 8.0 引入了角色（role）：把一组权限打包成一个角色，再把角色授予多个账号，权限变更时只改角色一处即可。这对「读账号、应用账号、运维账号」这类固定职责特别有用，也避免 GRANT ALL 满天飞。

  • 应用账号禁止使用 root；每个应用一套独立账号，便于审计与单独回收。
  • 写账号不要带 DELETE 与 DROP；删除业务上用软删（status = 'cancelled'）代替物理删。
  • 限制来源主机（'10.0.1.%' 而不是 '%'），并强制 TLS：REQUIRE SSL。
grants.sql
-- 1) 应用写账号：只给业务必需的表与动作，并限制来源主机 + 强制加密连接
CREATE USER 'app_rw'@'10.0.1.%' IDENTIFIED BY 'S3cure#Pass' REQUIRE SSL;
GRANT SELECT, INSERT, UPDATE ON shop.orders    TO 'app_rw'@'10.0.1.%';
GRANT SELECT, INSERT, UPDATE ON shop.customers TO 'app_rw'@'10.0.1.%';
GRANT SELECT                 ON shop.products  TO 'app_rw'@'10.0.1.%';
-- 注意：没有 DELETE、没有 DROP、没有 GRANT OPTION

-- 2) 只读账号给报表 / BI：全库只读，绝不能写
CREATE USER 'bi_ro'@'10.0.2.%' IDENTIFIED BY 'R0Pass#2024' REQUIRE SSL;
GRANT SELECT ON shop.* TO 'bi_ro'@'10.0.2.%';

-- 3) 列级授权：HR 只能看员工的工号、姓名、部门，看不到工资
CREATE USER 'hr_ro'@'10.0.3.%' IDENTIFIED BY 'Hr#Pass2024';
GRANT SELECT (id, name, dept, hire_date) ON shop.employees TO 'hr_ro'@'10.0.3.%';

-- 4) 角色：把权限打包，批量授予、统一回收
CREATE ROLE 'role_readonly';
GRANT SELECT ON shop.* TO 'role_readonly';
GRANT 'role_readonly' TO 'bi_ro'@'10.0.2.%';
SET DEFAULT ROLE ALL TO 'bi_ro'@'10.0.2.%';

-- 5) 审计与回收：先看清楚，再收紧
SHOW GRANTS FOR 'app_rw'@'10.0.1.%';
REVOKE UPDATE ON shop.customers FROM 'app_rw'@'10.0.1.%';
DROP USER 'temp_test'@'%';
账号类型典型权限红线（绝对不能给）
只读 / 报表SELECT（可到表或列级）任何写权限、PROCESS 之外的元数据权限
应用写账号SELECT / INSERT / UPDATE，按表授予DELETE、DROP、ALTER、GRANT OPTION
运维 / DBADDL、用户管理、REPLICATION、备份恢复用个人账号直连生产；应走跳板机 + 双人复核
!

易错：GRANT ALL PRIVILEGES ON *.* TO 'app'@'%' 是最常见的生产事故来源；WITH GRANT OPTION 会让被授权者自己再授权，等于把权限彻底交出去。另外 MySQL 8.0 默认认证插件是 caching_sha2_password，旧版客户端连不上时需要升级客户端而不是降级插件。

★

核心要点：最小授权 = 最小动作（只 SELECT） + 最小对象（只某张表/某几列） + 最小来源（只内网网段）。三个维度都要收，只收一个不算。

知识点主从复制与读写分离replication · 一台写、多台读，但要小心延迟

主从复制（replication）让从库自动重放主库的数据变更：主库把变更写进 binlog，从库的 IO 线程把 binlog 拉到本地变成 relay log，再由 SQL 线程重放。有了这份实时副本，就能做读写分离（写走主库、读走从库）来分摊读压力，也能在故障时快速切换。

代价是主从延迟（replication lag）：从库永远比主库慢一点。延迟来自大事务、大表 DDL、从库单线程/并行度不足、无主键表在 ROW 格式下的全表扫描、以及网络带宽。于是「刚写入的数据立刻去从库读」就可能读到旧值——这就是读写分离最典型的坑。

  • 写请求只能走主库；读请求默认走从库，但关键业务的「写后读」要强制走主库。
  • Seconds_Behind_Source 是估算值，不能作为唯一判据；更可靠的是对比 GTID 位点。
  • MySQL 8.0.23 起复制命令改为 CHANGE REPLICATION SOURCE TO / START REPLICA，旧写法是 CHANGE MASTER TO / START SLAVE。
flowchart LR App["应用 / 连接池"] -->|"写请求"| M[("主库 primary
binlog")] App -->|"读请求"| R[("从库 replica
relay log")] M -->|"binlog dump 线程"| R R -->|"Seconds_Behind_Source"| App
replication.sql
-- 主库：建复制专用账号（只要 REPLICATION SLAVE，不要业务权限）
CREATE USER 'repl'@'10.0.1.%' IDENTIFIED BY 'Repl#2024';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.0.1.%';

-- 主库：确认 binlog 与 GTID 已开启
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'gtid_mode';

-- 从库（MySQL 8.0.23+ 语法）：指向主库，GTID 模式自动定位位点
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST     = '10.0.1.10',
  SOURCE_PORT     = 3306,
  SOURCE_USER     = 'repl',
  SOURCE_PASSWORD = 'Repl#2024',
  SOURCE_AUTO_POSITION = 1;
START REPLICA;

-- 从库：观察复制健康度
SHOW REPLICA STATUS\G
--   Replica_IO_Running  = Yes   ← 能否拉到 binlog
--   Replica_SQL_Running = Yes   ← 能否重放 relay log
--   Seconds_Behind_Source       ← 延迟估算（秒）
--   Retrieved_Gtid_Set / Executed_Gtid_Set  ← 位点差异才是硬证据
延迟原因表现常见对策
主库大事务 / 批量 DML从库突然落后几十秒后追平拆小批量提交、控制单事务行数
从库单线程重放写并发高时延迟持续累积开启并行复制（replica_parallel_workers）
大表 DDLDDL 期间从库长时间阻塞用 gh-ost / pt-online-schema-change
无主键表ROW 格式下逐行全表扫描补主键或唯一键
!

易错：「用户下单成功后跳到订单详情页」这类写后立刻读的请求如果被路由到从库，用户会看到「订单不存在」。解决办法：关键读强制走主库、写后 1–2 秒内会话粘住主库、或把订单详情直接从写事务返回的数据渲染。

★

核心要点：读写分离提升的是读吞吐，不解决写瓶颈；一致性问题的本质是「延迟不可预测」，所以要用路由策略兜住，而不是等延迟变小。

🖥 演示：读写分离路由器切请求类型 + 拖复制延迟

Part B · 拆分与安全

02拆得开、守得住
（数据量上去了要拆，数据敏感了要防）

知识点分库分表与水平拆分sharding · 最后手段，不是第一选择

当单表数据量到千万甚至亿级，索引再优化也救不了写入与维护成本时，就要考虑分库分表。它有三种常见形态：垂直分库（按业务把不同表拆到不同库，如订单库、用户库）、垂直分表（把大字段或低频字段拆到附表，让主表更窄）、水平分表（按某个分片键 sharding key 把同一张表的数据行分散到多张表/多个库）。

水平拆分的核心是分片键选择与路由规则。规则通常是哈希取模（customer_id % 4）或范围（按时间/ID 区间）。分片键要满足两点：一是高频查询条件里带它，二是同一业务主体的数据落在同一片，否则跨片事务、跨片 JOIN、跨片聚合会迅速把复杂度拉满。

  • 拆分前先做完这些：SQL 与索引优化、读写分离、缓存、归档冷数据。分库分表是最后一步。
  • 主键不能再依赖单表自增，要用全局唯一 ID（雪花算法、号段模式、Redis 自增）。
  • 扩容时哈希取模要重分布数据，所以生产上常用「预分片 + 一致性哈希 / 双倍扩容」降低迁移量。
flowchart TD Q["订单写入 / 查询"] --> RT{"路由：customer_id % 4"} RT -->|"余 0"| T0["orders_0"] RT -->|"余 1"| T1["orders_1"] RT -->|"余 2"| T2["orders_2"] RT -->|"余 3"| T3["orders_3"]
sharding.sql
-- 分片表结构：每片结构完全一致，只是表名后缀不同
CREATE TABLE orders_1 (
  id          BIGINT       NOT NULL COMMENT '全局唯一 ID，由号段/雪花算法生成',
  customer_id BIGINT       NOT NULL,
  order_date  DATE         NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  status      VARCHAR(16)  NOT NULL DEFAULT 'paid',
  PRIMARY KEY (id),
  KEY idx_customer_date (customer_id, order_date)
) ENGINE=InnoDB;

-- 带分片键的查询：中间件改写后只落到 1 片，等价于单表查询
SELECT customer_id, COUNT(*) AS n, SUM(amount) AS total
FROM orders_1
WHERE customer_id = 5 AND order_date >= '2024-01-01'
GROUP BY customer_id;

-- 不带分片键的查询：只能广播到 4 片再归并，代价是单表查询的 4 倍以上
SELECT COUNT(*) FROM orders_0 WHERE status = 'refunded';
SELECT COUNT(*) FROM orders_1 WHERE status = 'refunded';
SELECT COUNT(*) FROM orders_2 WHERE status = 'refunded';
SELECT COUNT(*) FROM orders_3 WHERE status = 'refunded';
拆分方式怎么拆解决的问题代价
垂直分库按业务域分到不同库单实例连接数 / IO 瓶颈跨库 JOIN 消失，需服务层组装
垂直分表宽表按冷热字段拆成主表 + 附表单行过大、缓存命中率低多一次关联查询
水平分表按分片键哈希/范围分散行单表数据量与写入压力跨片查询、全局 ID、扩容重分布
!

易错：分片键选错等于白拆。例如按 order_date 分片，用户查自己的订单就要扫全部分片；按 status 分片会让数据倾斜。另外跨分片 JOIN、跨分片 ORDER BY … LIMIT 深分页、跨片聚合都是性能陷阱，必须在设计阶段就想清楚。

★

核心要点：分片键的验收标准是「80% 以上的核心查询都带它」。带上它 → 单分片路由；不带 → 广播 + 归并，代价随分片数线性上升。

知识点SQL 注入原理与防护SQL injection · 数据被当成代码执行

SQL 注入（SQL injection）的本质是：程序把用户输入拼进 SQL 文本，于是输入里的引号、OR、UNION 被数据库当成语法而不是数据来解释，攻击者就能改写查询逻辑。经典例子：登录查询写成 WHERE name = '用户输入'，攻击者输入 ' OR '1'='1，条件恒真，返回全部用户。

防护的第一原则是参数化查询（parameterized query，即预编译 prepared statement）：SQL 语句结构先发送给数据库编译，参数随后以「值」的身份单独传输，无论内容是什么都不会改变语法。其次是白名单（表名、列名、ORDER BY 方向这类无法参数化的部分）、最小权限（应用账号没有 DROP，注入也删不掉库）和输入校验。

  • 参数化不是「转义」，而是让数据和代码在协议层就分离，所以它不怕新的绕过技巧。
  • 转义函数（addslashes）依赖字符集与驱动实现，属于「补救」而非「根治」。
  • 错误信息不要回显给前端：--param 类的报错会泄露库表结构。
injection.sql
-- ✗ 危险：字符串拼接。当输入是 ' OR '1'='1 时，WHERE 变成恒真条件
SELECT id, name, city FROM customers WHERE name = '' OR '1'='1';
-- 结果：返回全部 8 位客户（本意只是查一个人）

-- ✗ 危险：拼接还能用 UNION 直接读别的表
SELECT id, name FROM customers WHERE name = '' UNION SELECT id, salary FROM employees;
-- 结果：员工工资被当作客户姓名一起返回

-- ✓ 安全：参数化查询。SQL 结构先编译，问号参数只当值使用
PREPARE stmt FROM 'SELECT id, name, city FROM customers WHERE name = ?';
SET @n = ''' OR ''1''=''1';
EXECUTE stmt USING @n;
-- 结果：0 行 —— 数据库在找「名字真的叫 ' OR '1'='1 的客户」
DEALLOCATE PREPARE stmt;

-- ✓ 安全：无法参数化的部分（排序方向、表名）用白名单映射
-- 前端传 sort=amount，后端映射为固定字符串，绝不直接拼接
SELECT id, amount FROM orders ORDER BY amount DESC LIMIT 10;
攻击手法典型输入后果防护
联合查询注入' UNION SELECT …直接读出其它表数据参数化 + 最小权限
布尔盲注' AND 1=1 --逐位猜出数据参数化 + 关闭错误回显
时间盲注' AND SLEEP(5) --靠响应时间推断参数化 + 请求超时告警
堆叠注入'; DROP TABLE …执行第二条语句参数化 + 禁用多语句
★

核心要点：防注入的优先级是参数化 > 白名单 > 最小权限 > 输入校验 > WAF。前三条是根治与兜底，最后两条只是加固。

!

易错：表名、列名、ORDER BY 的列和方向、LIMIT 的偏移量不能用参数标记（它们属于语法结构），必须用白名单枚举映射；很多「我们用了参数化」的漏洞都出在这里。

知识点审计、脱敏与合规audit & masking · 谁能看到什么，都要说得清

审计（audit）记录「谁在什么时候对哪些数据做了什么」，用于事后追责与异常发现；脱敏（data masking）让敏感字段在被查看时变成不可还原或不可识别的形式；合规（compliance）则要求数据「最小必要、用途明确、可追溯、可删除」。三者是一套组合拳：权限控制决定「能不能看」，脱敏决定「看到什么」，审计决定「看完留不留痕」。

落地手段上，最轻量的是脱敏视图——把真实表锁死，只把掩码后的视图授权给 BI、客服等外部角色；再配合列级授权、动态脱敏插件（MySQL 企业版 Data Masking）和传输加密（TLS）、静态加密（TDE）。审计方面，MySQL 企业版有 audit_log 插件，社区版可用 general_log、代理层审计或云数据库自带审计。

  • 脱敏要区分「掩码」（如 张*）、「泛化」（年龄 → 年龄段）与「哈希」，选择取决于业务是否需要还原。
  • 审计日志本身也是敏感数据：里面可能有明文 SQL，要加密存储、限制访问、定期轮转。
  • 「可删除」意味着设计时就要能按主体定位数据（例如全部用 customer_id 关联），否则注销请求无从执行。
audit_mask.sql
-- 1) 审计：社区版可用 general_log 应急排障，写入表方便查询
SET GLOBAL log_output = 'TABLE';       -- 记录到 mysql.general_log
SET GLOBAL general_log  = ON;          -- 排障完务必关闭，它会显著影响性能
SELECT event_time, user_host, argument
FROM mysql.general_log
WHERE argument LIKE '%customers%'
ORDER BY event_time DESC LIMIT 20;

-- 2) 脱敏视图：真实表不给外部角色，只授权视图
CREATE OR REPLACE VIEW v_customers_masked AS
SELECT id,
       CONCAT(LEFT(name,1), REPEAT('*', CHAR_LENGTH(name)-1)) AS name_masked,
       city,
       CASE WHEN gender IS NULL THEN NULL ELSE 'X' END AS gender_code,
       level
FROM customers;

CREATE USER 'bi_ro'@'10.0.2.%' IDENTIFIED BY 'R0Pass#2024' REQUIRE SSL;
GRANT SELECT ON shop.v_customers_masked TO 'bi_ro'@'10.0.2.%';
-- 注意：绝不 GRANT SELECT ON shop.customers

-- 3) 验证脱敏效果
SELECT * FROM v_customers_masked WHERE id = 1;
-- id | name_masked | city | gender_code | level
--  1 | 张**        | 北京 | X           | 金卡
手段作用适用层注意事项
脱敏视图 / 列级授权让外部角色只看到掩码数据数据库视图要 SQL SECURITY DEFINER，避免绕过
动态脱敏插件按账号规则实时改写返回值数据库 / 代理企业版或中间件能力
TLS + TDE传输与静态加密网络 / 存储解决「被截获 / 磁盘被拿走」
审计日志操作留痕、异常追溯数据库 / 代理有性能开销，需轮转与权限隔离
★

核心要点：合规三问——能不能看（最小授权）、看到什么（脱敏 / 泛化）、看过留痕吗（审计）。三问都答得出来，才叫数据治理到位。

!

易错：长期开着 general_log 会记录包含明文密码的全量 SQL，既拖慢性能又制造新的泄露面；把脱敏视图建好了却忘了回收原表的 SELECT 权限，等于没脱敏。
