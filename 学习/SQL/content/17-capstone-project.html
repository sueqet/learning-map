Learning Points · 知识点

01从需求到表结构
把「想看销售情况」变成能跑的分析

知识点需求分析与表设计cap-design · 先定义问题，再定义表

项目的第一步不是写 SELECT，而是把业务语言翻译成**可量化的问题**。例如「想看看销售情况」这句话里至少藏着五个问题：总销售额是多少？哪些客户贡献最多？哪类商品卖得好？销售趋势是涨还是跌？退款和取消影响了多少收入？每一个问题都对应一个**指标口径**（metric definition）——比如「销售额」到底算不算退款订单？只有口径先定下来，后面写 SQL 才不会出现「两个人算出两个数」的尴尬。

第二步才是**表设计**（schema design）。设计的核心是回答三个问题：实体有哪些（客户、订单、订单明细、商品、员工）、实体之间是什么关系（一对多 / 多对多）、每个字段用什么类型和约束。本项目直接复用内置示例数据的 5 张表，你需要做的是把它们的**关系画清楚**：customers 与 orders 是一对多，orders 与 order_items 是一对多，products 与 order_items 是一对多，employees 通过 manager_id 自关联形成汇报树。

为什么不能跳过设计直接写查询？因为**冗余的表结构会让每条查询都变得复杂且易错**。比如把客户名直接冗余进 orders，客户改名时历史订单就会前后不一致；把订单金额只存在 orders 而不存明细，就无法回答「哪个商品贡献了这笔钱」。规范化的表设计让你写查询时只需关注连接关系，而不是在数据里做考古。

schema.sql
-- 项目核心表设计（MySQL 8.0；DDL 在练习台不支持，请在真实数据库执行）
CREATE TABLE customers (
  id          INT           PRIMARY KEY,
  name        VARCHAR(32)   NOT NULL,
  city        VARCHAR(32)   NULL COMMENT '来源缺失时为空',
  gender      CHAR(1)       NULL,
  signup_date DATE          NOT NULL,
  level       VARCHAR(8)    NOT NULL DEFAULT '普通'   -- 普通 / 银卡 / 金卡
);

CREATE TABLE orders (
  id          INT           PRIMARY KEY,
  customer_id INT           NOT NULL,
  order_date  DATE          NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  status      ENUM('paid','refunded','cancelled') NOT NULL DEFAULT 'paid',
  KEY idx_orders_customer (customer_id),
  KEY idx_orders_date (order_date),
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers(id)
);

CREATE TABLE order_items (
  id         INT           PRIMARY KEY,
  order_id   INT           NOT NULL,
  product_id INT           NOT NULL,
  qty        INT           NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL COMMENT '下单时价格快照',
  KEY idx_items_order (order_id),
  KEY idx_items_product (product_id)
);
实体角色关键字段关系
customers客户维度id、name、city、level、signup_date1 : N → orders
orders订单事实（头）id、customer_id、order_date、amount、statusN : 1 → customers；1 : N → order_items
order_items订单明细事实order_id、product_id、qty、unit_priceN : 1 → orders；N : 1 → products
products商品维度id、name、category、price、stock1 : N → order_items
employees运营团队id、dept、manager_id、salary、hire_date自关联（manager_id → id）
erDiagram customers ||--o{ orders : "下单" orders ||--|{ order_items : "包含" products ||--o{ order_items : "被购买" employees ||--o{ employees : "管理" customers { int id PK varchar name varchar city varchar level date signup_date } orders { int id PK int customer_id FK date order_date decimal amount varchar status } order_items { int id PK int order_id FK int product_id FK int qty decimal unit_price } products { int id PK varchar name varchar category decimal price int stock }
★

核心要点：先写「问题清单 + 指标口径」，再写建表语句。本项目的统一口径是：销售额默认只统计 status = 'paid' 的订单；订单明细金额 = qty * unit_price（下单时价格快照，不取 products.price，因为商品可能调价）。口径写在脚本注释里，结果才可复现。

!

易错：把 orders.amount 与 SUM(order_items.qty * unit_price) 当成同一口径混用——示例数据里两者恰好都能汇总到 8658.00，但真实业务中订单可能有运费、优惠、部分退款，两者会分叉。另外 orders.customer_id = 8 不存在（id=8 的周涛从未下单），外键设计要考虑「新客户」而不是无脑报错。

知识点数据导入与清洗cap-etl · 让数据可信，分析才有意义

ETL 是 Extract-Transform-Load（抽取—转换—加载）的缩写。在小型项目里它常常被压缩成一句 LOAD DATA，但**真正花时间的永远是「清洗」那一步**：字段类型对不对、NULL 有没有语义、枚举值有没有拼写变体、日期格式统不统一、有没有重复行。示例数据里已经埋好了三类典型问题：customers.id = 8 的 city 与 gender 为 NULL；orders.status 有三种取值（paid / refunded / cancelled）；order_items.unit_price 是历史快照，可能与 products.price 不同。

清洗的原则是**先观察、再决策、后落地**。先跑几条「体检查询」看行数、NULL 分布、枚举分布、重复情况；再决定每种问题的处理规则（丢弃 / 归入「未知」/ 用默认值补齐）；最后把规则写成可重复执行的脚本。切忌边导边改——一旦规则没记录下来，第二次导入就会得到不同的结果。

导入完成必须做**行数与关键值校验**：customers 8 行、orders 12 行、products 6 行、order_items 15 行、employees 9 行。校验通过才进入分析阶段；不通过就先回到清洗步骤，而不是硬着头皮写查询——脏数据上的分析结论毫无价值。

check_clean.sql
-- 体检 1：NULL 分布（id=8 的 city、gender 为 NULL）
SELECT SUM(city IS NULL) AS 缺城市, SUM(gender IS NULL) AS 缺性别, COUNT(*) AS 总客户
FROM customers;

-- 体检 2：状态枚举分布（paid 10 / refunded 1 / cancelled 1）
SELECT status, COUNT(*) AS 订单数, SUM(amount) AS 金额
FROM orders GROUP BY status ORDER BY 订单数 DESC;

-- 体检 3：明细金额与订单金额是否对得上（示例数据两者都等于 8658.00）
SELECT SUM(o.amount) AS 订单汇总,
       (SELECT SUM(qty * unit_price) FROM order_items) AS 明细汇总
FROM orders o;

-- 清洗：把缺失城市归入「未知」，而不是丢弃客户
SELECT COALESCE(city, '未知') AS 城市, COUNT(*) AS 客户数
FROM customers GROUP BY COALESCE(city, '未知') ORDER BY 客户数 DESC;
脏数据问题示例推荐处理不推荐做法
维度字段缺失id=8 的 city 为 NULLCOALESCE 归入「未知」并在口径中说明直接改成一个真实城市
枚举取值多样paid / refunded / cancelled明确主口径只算 paid，其余单列指标不过滤就 SUM(amount)
重复导入同一次 LOAD 跑两遍主键 + REPLACE / 先 TRUNCATE 再导靠肉眼检查
价格不一致unit_price 与 products.price 不同分析用 unit_price 快照用 products.price 反推历史
★

核心要点：导入顺序遵循外键依赖：customers → products → orders → order_items。清洗规则必须写进脚本注释，做到「同一份 CSV + 同一份脚本 = 同一个结果」。练习台不支持 LOAD DATA 等 DML / DDL，这类语句请到真实 MySQL 中验证。

!

易错：COUNT(city) 会跳过 NULL，而 COUNT(*) 不会——体检 NULL 分布时要写 SUM(city IS NULL) 或 COUNT(*) - COUNT(city)。另外 LOAD DATA LOCAL INFILE 需要客户端与服务端同时开启 local_infile，否则报 3948 错误，这与 SQL 写法无关。

02写出并调优核心查询
从「能跑」到「跑得快、看得懂」

知识点核心分析查询实现cap-query · 8 条查询撑起一份分析报告

核心查询实现就是把前面定下的问题清单逐条翻译成 SQL。一个能撑起分析报告的最小查询集通常包含 5 类：**总览指标**（一行汇总）、**维度排行**（分组 + 排序 + LIMIT）、**趋势**（按月份分组）、**结构占比**（多表连接 + 分组）、**异常检测**（LEFT JOIN 找缺口、CASE WHEN 算比率）。本项目把这五类展开成 8 条查询，全部基于内置示例数据，每条都能在下方练习台真跑。

写查询时建议遵循固定套路：先写 FROM … JOIN … 把数据「拼」出来，再加 WHERE 过滤口径，然后 GROUP BY 聚合，最后 ORDER BY / LIMIT 排序取前几名。这个顺序与逻辑执行顺序（FROM → ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT）基本一致，按它写能避免「在 WHERE 里引用聚合别名」这类错误。

每条查询写完后要立刻**核对结果行数与关键值**：例如「未下单客户」必须返回 1 行（周涛）；「客户消费排行」必须返回 6 行（12 笔订单中只有 10 笔 paid，涉及 6 位客户）；「品类销售结构」返回 3 行（数码 / 图书 / 家居）。核对不上就说明口径或连接条件写错了，不要带着错误的数往下分析。

analysis_queries.sql
-- Q1 总览：有效订单数 / 有效销售额 / 客单价  → 1 行
SELECT COUNT(*) AS 有效订单数,
       SUM(amount) AS 有效销售额,
       ROUND(AVG(amount), 2) AS 客单价
FROM orders
WHERE status = 'paid';

-- Q2 客户消费排行（只算有效订单）→ 6 行
SELECT c.name AS 客户, c.level AS 等级,
       COUNT(o.id) AS 订单数, SUM(o.amount) AS 消费额
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.name, c.level
ORDER BY 消费额 DESC;

-- Q3 品类销售结构（明细口径）→ 3 行
SELECT p.category AS 品类,
       SUM(oi.qty) AS 销量,
       SUM(oi.qty * oi.unit_price) AS 销售额
FROM order_items oi
JOIN products p ON oi.product_id = p.id
GROUP BY p.category
ORDER BY 销售额 DESC;

-- Q4 月度销售趋势 → 4 行（2024-01 ~ 2024-04）
SELECT DATE_FORMAT(order_date, '%Y-%m') AS 月份,
       COUNT(*) AS 订单数, SUM(amount) AS 销售额
FROM orders
GROUP BY DATE_FORMAT(order_date, '%Y-%m')
ORDER BY 月份;

-- Q5 从未下单的客户（LEFT JOIN 找缺口）→ 1 行（周涛）
SELECT c.id, c.name, c.city
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL;

-- Q6 退款 / 取消占比（CASE WHEN 条件聚合）→ 1 行
SELECT COUNT(*) AS 订单总数,
       SUM(CASE WHEN status = 'refunded'  THEN 1 ELSE 0 END) AS 退款数,
       SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS 取消数,
       ROUND(SUM(CASE WHEN status <> 'paid' THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS 异常率
FROM orders;

-- Q7 商品销量 TOP3（分组 + LIMIT）
SELECT p.name AS 商品, SUM(oi.qty) AS 销量
FROM order_items oi
JOIN products p ON oi.product_id = p.id
GROUP BY p.name
ORDER BY 销量 DESC
LIMIT 3;

-- Q8 主管管理幅度（employees 自连接）→ 4 行
SELECT m.name AS 主管, COUNT(e.id) AS 下属数
FROM employees e
JOIN employees m ON e.manager_id = m.id
GROUP BY m.name
ORDER BY 下属数 DESC, 主管;
#查询目的核心技术预期行数 / 关键值
Q1总览指标聚合 + WHERE 口径1 行：有效销售额 8211.00，客单价 821.10
Q2客户消费排行INNER JOIN + GROUP BY + ORDER BY6 行：王强 2297 > 孙悦 1636 > 李娜 1586
Q3品类销售结构两表 JOIN + 表达式聚合3 行：数码 7648 > 家居 833 > 图书 177
Q4月度趋势DATE_FORMAT 分组4 行：4 月 3133 最高
Q5未下单客户LEFT JOIN + IS NULL1 行：周涛
Q6退款 / 取消占比CASE WHEN 条件聚合1 行：异常率 16.67%
Q7商品销量 TOP3GROUP BY + LIMIT3 行：机械键盘 7 件居首
Q8主管管理幅度自连接（self join）4 行：张伟、刘敏各带 2 人
★

核心要点：「行数对不对」是验证查询最快的手段。先估算期望行数（分组数、客户数、月数），再跑 SQL 对比；数量不符通常是连接方式选错（INNER 丢行）或分组粒度写错（多带/少带一列）。

!

易错：Q2 若把 WHERE o.status='paid' 写成 LEFT JOIN + 条件，未下单客户会以「0 元」混进排行；Q3 若用 products.price 而不是 order_items.unit_price，历史订单金额会被当前价覆盖；Q6 的百分比要用 * 100 并注意整数除法（MySQL 中 1/12*100 会自动转 DECIMAL，但用整除列时要小心）。

知识点性能优化与索引落地cap-optimize · 先测量，再优化

示例数据只有几十行，任何写法都「很快」，这正是最容易忽略优化的阶段。优化的正确姿势是**先测量、再动手**：用 EXPLAIN 看访问类型（type）、扫描行数（rows）、是否用到索引（key）、是否出现文件排序（Extra 中的 Using filesort）或临时表（Using temporary）。没有测量就加索引，等于蒙着眼睛调参。

索引落地的判断依据是**查询里的「入口条件」和「连接条件」**。WHERE 用到的列、JOIN 的关联列、ORDER BY / GROUP BY 的排序列，都是候选。本项目最值得加索引的三处是：orders.customer_id（客户维度连接、找未下单客户）、orders.order_date（月度趋势范围扫描）、order_items.order_id 与 order_items.product_id（明细连接）。复合索引要遵守最左前缀原则，例如 (status, order_date) 能服务「先按状态过滤再按日期排序」的查询。

索引不是越多越好：每个索引都会拖慢写入、占用空间，而且**当过滤条件对列做了函数运算时索引会失效**（如 DATE_FORMAT(order_date,'%Y-%m') = '2024-03'）。正确写法是把函数挪到常量一侧：order_date >= '2024-03-01' AND order_date < '2024-04-01'，这样范围扫描才能用上索引。

optimize.sql
-- ① 优化前：对列做函数运算，索引失效（type=ALL，全表扫描）
EXPLAIN
SELECT COUNT(*), SUM(amount)
FROM orders
WHERE DATE_FORMAT(order_date, '%Y-%m') = '2024-03';

-- ② 改写成范围条件，可用 idx_orders_date（type=range）
EXPLAIN
SELECT COUNT(*), SUM(amount)
FROM orders
WHERE order_date >= '2024-03-01' AND order_date < '2024-04-01';

-- ③ 给连接列补索引（父表已由主键提供索引）
ALTER TABLE orders      ADD INDEX idx_orders_customer (customer_id);
ALTER TABLE orders      ADD INDEX idx_orders_date (order_date);
ALTER TABLE order_items ADD INDEX idx_items_order (order_id);
ALTER TABLE order_items ADD INDEX idx_items_product (product_id);

-- ④ 复合索引：最左前缀 (status, order_date) 服务「先过滤状态再排序日期」
ALTER TABLE orders ADD INDEX idx_status_date (status, order_date);

-- ⑤ 覆盖索引：Q2 只需 name/level/amount，若把 level 并入索引可避免回表
ALTER TABLE orders ADD INDEX idx_customer_amount (customer_id, amount);

WHERE order_date BETWEEN '2024-01-01' AND '2024-04-30'range✅ 用 idx_orders_date范围条件保持列「裸露」
WHERE DATE_FORMAT(order_date,'%Y-%m') = '2024-03'ALL❌ 索引失效改写成范围条件
WHERE status = 'paid' ORDER BY order_dateref✅ 用 (status, order_date)复合索引 + 最左前缀
GROUP BY p.categoryALL❌ 小表可接受品类基数低，不值得建索引
★

核心要点：优化顺序永远是「先 EXPLAIN 看代价 → 再改写法（避免函数包裹、避免隐式类型转换）→ 最后才加索引」。小表上索引收益有限，但养成「关联列必须有索引」的习惯，数据量涨到百万级时不用返工。

!

易错：① 在 orders.status 这种只有 3 个取值、区分度极低的列上单独建索引，优化器多半直接忽略；② 索引建了但查询里出现隐式转换（customer_id = '3'）同样会失效；③ 练习台不支持 ALTER TABLE 与 EXPLAIN，请到真实 MySQL 验证，本页用下方面板模拟代价对比。

03交付与继续深入
让结果可复现、让别人能接手

知识点代码规范与交付cap-review · 分析师的工程素养

一份分析结果的价值，很大程度上取决于**别人能不能复跑**。规范的交付物通常包含四件东西：可执行的建表脚本、可重复的导入脚本、按编号组织的分析查询脚本、以及一份说明口径与结论的 README。缺了任何一件，你的分析就变成了一次性的「截图汇报」——下次老板追问「这个数怎么算的」，你只能重新推一遍。

SQL 代码规范的核心是**可读性优先**：关键字大写、每个子句换行、表用简短别名（c / o / oi）、聚合列起有意义的中文别名、复杂查询在头部写清目的与口径。不要用 a、b、c 这种无意义别名，也不要把 8 条查询压成一行——省下的字符换不来任何收益。

交付时还要**主动暴露假设与局限**：示例数据只有 12 笔订单，结论不能当作业务事实；退款率 16.67% 的样本量太小；时间范围只有 4 个月，看不出季节性。把「数据局限」写在 README 里，比给出一个看起来漂亮但站不住的结论更专业。

Q2_top_customers.sql
/* ============================================================
   Q2 · 客户消费排行
   目的：找出有效销售额贡献最高的客户，用于会员运营分层
   口径：仅统计 status = 'paid' 的订单；金额取 orders.amount
   输入：customers, orders        输出：6 行
   维护：2024-05-01 初版 / 2024-05-08 增加 level 列
   ============================================================ */
SELECT
    c.name                AS 客户,
    c.level               AS 会员等级,
    COUNT(o.id)           AS 订单数,
    SUM(o.amount)         AS 消费额,
    ROUND(AVG(o.amount), 2) AS 客单价
FROM customers AS c
INNER JOIN orders AS o
        ON c.id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.name, c.level
ORDER BY 消费额 DESC;

核心要点：命名规范让代码自解释：表名单数、字段名 snake_case、索引 idx_表_列、外键 fk_表_引用表。查询脚本头部四行（目的 / 口径 / 输入输出 / 维护记录）是团队协作的最低成本投入，收益极高。

!

易错：把 SELECT * 留在交付脚本里（表结构一变结果就变）；用中文别名却不加引号导致某些客户端乱码；只提交结果截图不提交脚本。另外脚本里不要写死本机绝对路径，用相对路径或环境变量。

知识点下一步学习路线cap-next · 从这里走向真实业务

完成这个项目意味着你已经打通了「需求 → 设计 → 导入 → 查询 → 优化 → 交付」的完整链路。但示例数据是干净的、小规模的，真实业务会立刻给你三个新挑战：**数据量**（千万行级别，需要理解执行计划与分区）、**分析深度**（窗口函数、CTE、同比环比）、**工程化**（把查询变成可调度的数据管道）。这三条就是接下来的主攻方向。

优先级建议：先把**窗口函数**补齐，它能把「累计销售额、环比增长、分组内排名」这类问题一行解决，是分析师与普通 SQL 使用者的分水岭；再学 **CTE（WITH）** 把复杂查询拆成可读的步骤；然后深入**执行计划与索引原理**（B+ 树、回表、覆盖索引、优化器成本模型）；最后接触**数据仓库建模**（星型 / 雪花、缓慢变化维度）与调度工具。本项目练习台不支持窗口函数与 WITH，请在真实 MySQL 8.0 中练习。

持续提升的关键是**换更大的数据集**。示例数据的 12 笔订单练的是语法，练不出直觉；把公开数据集（电商订单、公开票务、天气日志）导入 MySQL，跑一遍本项目同样的 8 条查询，再对比 EXPLAIN 的差异，你对性能的理解会立刻上一个台阶。

next_step.sql
-- 下一步练习方向 1：窗口函数（MySQL 8.0；练习台不支持 OVER()，请到真实数据库验证）
-- 客户消费排行 + 组内排名 + 累计占比
SELECT c.name AS 客户,
       SUM(o.amount) AS 消费额,
       RANK() OVER (ORDER BY SUM(o.amount) DESC) AS 排名,
       ROUND(SUM(o.amount) / SUM(SUM(o.amount)) OVER () * 100, 2) AS 占比
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.name
ORDER BY 消费额 DESC;

-- 下一步练习方向 2：CTE 把复杂查询拆成可读步骤（练习台不支持 WITH）
WITH paid_orders AS (
  SELECT customer_id, amount FROM orders WHERE status = 'paid'
)
SELECT c.name, SUM(p.amount) AS 消费额
FROM customers c JOIN paid_orders p ON c.id = p.customer_id
GROUP BY c.name ORDER BY 消费额 DESC;

-- 下一步练习方向 3：在真实数据上观察执行计划
EXPLAIN ANALYZE
SELECT p.category, SUM(oi.qty * oi.unit_price)
FROM order_items oi JOIN products p ON oi.product_id = p.id
GROUP BY p.category;

★

核心要点：学习路线的核心不是「再学一遍语法」，而是「换更大的数据、解更复杂的问题」。每学一个新特性（窗口函数、CTE、分区），都回到本项目的订单数据上重写一遍，对照结果是否一致——这是最高效的验证方式。

!

易错：把窗口函数当成 GROUP BY 的替代品——两者语义不同，GROUP BY 会压缩行数，窗口函数保留明细行；WITH 在 MySQL 8.0 中才支持，5.7 及更早版本会报错；不同数据库窗口函数语法有差异（如 PostgreSQL 支持 FILTER，MySQL 不支持），迁移时要逐一验证。
